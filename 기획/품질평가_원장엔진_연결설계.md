# 품질평가 원장과 관측 엔진 연결 설계

기준: 2026-09-27. B의 합성 비용 원장 다음 C1 구현 범위다. C1의 내부 합성 runner와 원문 관측 훅은 구현했다. 이 문서는 실행 승인이나 운영 가격 설정이 아니며 실제 공급자를 호출하지 않는다. 최종 시험 범위는 `3단계_기획반영_개발현황.md`와 `web/VALIDATION.md`에 기록한다.

## 1. 먼저 연결할 범위

등록 후보 한 개를 시작하고 생성 → 독립 검토 → 최종 원고 보관까지 기존 `generateObservedPlan()`으로 실행한다. 전송은 반드시 주입한 합성 어댑터만 사용한다. 기존 `runQualityMockExecution()`과 8개 테이블의 모의 이력은 보존한다. B의 `actual-ledger-simulation`, `synthetic-test`, `actualAiCalls:0`도 그대로 유지한다.

새 runner는 내부 전용이며 제품 HTTP의 실제 시작·승인·예산 설정 경로를 열지 않는다. 기존 A는 production 가격·토큰·예산 null과 세 권한 false를 유지한다. B의 GET 조회와 원문 다운로드에서 C1 기록을 볼 수 있다. 기본 메뉴 3개는 바꾸지 않는다.

## 2. 엔진에 필요한 관측 지점

관측 엔진의 기존 `onDispatch(request)`, `onResponse(metadata)`, `onValidated(output)`을 보존하고 아래 두 선택적 훅을 추가했다. 기존 요청 계약 digest와 생성·검토 JSON 바이트는 바꾸지 않았다.

- `onRequestPrepared({request, body})`: 정확한 system/user/schema·모델·토큰 상한을 확인하고 요청 BLOB과 준비 이벤트를 저장한다. 이 await가 성공하기 전 dispatch가 없다.
- `onResponseCaptured({metadata, capturedResponse})`: 허용된 SDK JSON 필드만 전달한다. 요청 ID·모델·status·usage·output을 보존하며 키·헤더·SDK client·원시 오류 객체는 전달하지 않는다. 원문과 metadata/사용량 이벤트 저장 후에만 출력 구조·근거 검증으로 이동한다.
- 기존 `onValidated`는 검증된 최초 생성 원고와 검토 의견을 저장한다. 검토는 저장한 최초 생성 원고와 validation event에서만 파생한다.

전달 객체는 복사·동결한다. 수신 원문 복사 실패나 크기 초과도 성공으로 표시하지 않는다. 훅의 예외를 공급자 오류로 바꾸거나 삼키지 않는다. 응답 저장 실패 뒤 두 번째 호출은 0회다. 기존 metadata 훅과 새 원문 훅이 같은 이벤트를 중복 기록하지 않도록 runner별 소유권을 명시한다.

## 3. 시작과 전송 권한

runner는 단순 snapshot이나 외부에서 받은 `newlyCommitted:true`를 실행 권한으로 사용하지 않는다. 자신이 시작 트랜잭션을 호출하고 최초 commit 결과를 받은 경로만 진행한다. 동일 시작 nonce의 replay는 저장 결과만 반환하며 엔진을 호출하지 않는다.

각 단계는 현재 예산 head와 run revision을 다시 읽고 요청을 고정한 다음 `actualRecordDispatch()`를 호출한다. **이번 호출이 직접 최초 commit을 완료한 경우만** transport를 한 번 호출한다. replay나 조회 결과라면 즉시 중단한다. 최초 작업이 commit 후 전송 전에 종료되어도 다른 작업이 대신 전송하지 않는다.

생성 요청은 start에서 저장한 바이트와 정확히 같아야 한다. 검토 요청은 고정 템플릿·같은 입력·같은 실행의 검증된 최초 원고에서 파생한 바이트와 같아야 한다. 검토 입력 토큰은 합성 토큰 어댑터로 별도 검사하며 문자 수를 토큰 수로 대체하지 않는다. 주입한 어댑터와 상한이 준비안의 증빙 범위를 벗어나면 호출하지 않는다.

## 4. 중단 처리

dispatch 전 실패는 아직 전송하지 않은 단계의 예약만 명시 해제할 수 있다. dispatch 후 응답 없음이나 원문 저장 실패는 미확인 예약을 유지한다. 사용량을 확인한 응답의 비용은 출력 검증 실패와 별개로 보관한다.

실패 이벤트 저장도 실패하면 마지막 확정 원장 상태를 남기고 종료한다. 메모리에만 있는 결과로 저장 완료를 응답하지 않는다. 사용자·공급자 오류 원문을 로그에 출력하지 않는다. 이미 보관한 response의 재전송, 자동 재시도, 수정 생성은 지원하지 않는다. 최대 호출은 생성 1회와 검토 1회다.

늦은 응답 기록은 원래 dispatch에 맞는 관측만 받으며 새 전송 권한을 만들지 않는다. B에서 아직 지원하지 않는 청구 대조·누락 usage의 사후 수정·예산 정책 변경을 구현한 것으로 표시하지 않는다.

구현에서는 전송을 기다리는 동안 정확한 기존 event prefix 뒤에 `result-unobserved` 종료 기록 하나만 추가된 경우에 한해 원래 응답 원문·사용량을 보관한다. 종료 기록은 유지하며 `LATE_RESPONSE_RECORDED`와 마지막 확정 상태를 반환한다. 검증·검토 호출을 재개하거나 미확정 원고를 완료 처리하지 않는다. 수신 중 현재 엔진 계약이 바뀌어도 이미 보낸 요청의 비용 관측은 보관하고 다음 검증·전송은 차단한다.

시작·dispatch 권한은 동일 함수 호출이 직접 받은 최초 commit 반환값으로만 만든다. transport 직전에도 정확한 요청·예산 초과 여부·증빙 유효기간을 다시 검사한다. dispatch commit 직후 실제 별도 Node 프로세스를 종료하는 시험에서도 재오픈한 runner는 재전송하지 않는다. 기존 B 시험의 합성 카운터와 달리 C1 시험은 관측 엔진의 실제 주입 transport 호출 횟수를 센다. 외부 공급자 호출은 여전히 0이다.

## 5. 필요한 시험

1. 정확한 등록 후보·생성 요청·검토 파생 본문으로 두 번 호출하고 최초/최종 원고·응답·비용을 보존한다. 사람 평가와 실제 AI 품질 상태는 미완료다.
2. 시작·원문·예약·준비·dispatch 기록 실패 지점에서는 해당 transport 호출이 없다. 응답·검증·종료 기록 실패 때 마지막 확정 원문과 비용을 재오픈해 확인한다.
3. 동일 nonce 시작 재현과 동시 runner는 중복 생성·검토를 하지 않는다. dispatch commit 후 전달 전 중단도 재실행하지 않는다.
4. 생성 후 검토 사용량 부족·모델/원문/엔진 변경·상한 초과·가격 만료·전역 초과 비용은 다음 호출을 막는다.
5. 응답 원문·metadata 불일치, usage 누락/합계 오류, 잘못된 모델, 잘못된 인용·검토 대상은 각각 원장 상태를 정확히 남긴다.
6. 기존 관측 엔진·모의 API/UI·A 준비 조회·B 원장/백업/과거 JSON은 회귀를 통과한다. 실제 키·회사 DB·외부 네트워크 접근은 0이다.

## 6. 실제 실행 연결은 다음 별도 계약

C1 통과가 실제 실행 준비 완료는 아니다. 실제 모델의 제공 여부·공식 요율·전체 요청 토큰의 보수적 계산 근거·운영 누적 예산·보관 조건을 먼저 확정해야 한다. synthetic-only B v1을 실제 기록으로 재해석하지 않는다. actual 출처가 필요한 새 버전 계약과 백업 검증을 정의하고 기존 v1 바이트를 유지한다.

그 다음 정확한 후보 1개·등록 버전·모델·요청 원문·검토 파생 범위·2회 호출·재시도 0·최대 예약액을 한 검토안으로 제시한다. 사용자 승인 이후에만 해당 범위의 실제 공급자 전송을 연다. 승인 없이 12건 전체·고객 회사 자료로 확대하지 않는다.
