# 독립 품질검증세트 준비안

작성 기준: 2026-09-26

## 1. 준비 상태

v3 서비스 기획 §13.1의 업종·신청 유형 편향을 줄이기 위해 **평가용 합성 후보 12개**를 별도 파일에 준비했다. 현재 50개 개발 회귀 사례, 평가 core, 실행기, UI에는 연결하지 않았다.

**이 자료는 AI가 작성한 검증용 후보이며, 사람이 승인한 정답표나 최종 독립 held-out 검증세트가 아니다. 실제 AI 작성·수정·품질평가를 호출하지 않았고 실제 원고 품질은 검증하지 않았다.**

회사·고객·기술 시험·금액·계약·일정은 모두 비실제 합성 내용이다. 실제 기업자료, 고객 개인정보, 원본 파일, 기관 인증서, 실제 법령·기준 원문은 포함하지 않는다. 재확인 유형은 신청 상황의 구성일 뿐 과거 확인을 받았거나 갱신 요건을 충족했다는 판정이 아니다.

| 항목           | 현재 상태                                                            |
| -------------- | -------------------------------------------------------------------- |
| 작성물         | 합성 회사·사업 주제·기술/고객/재무/조직/권리/일정 자료와 작성자 메모 |
| 후보 수        | 12개. v3의 독립 고정 세트 최소 50건을 충족하지 않음                  |
| 업종·신청 유형 | 제조·소프트웨어·서비스 각각 신규 2개, 재확인 2개                     |
| 자료 구성      | 연결형 6개, 의도된 자료 부족 3개, 의도된 충돌 3개                    |
| 작성자         | AI. 사람의 사실·쟁점 정답표 작성과 승인 전                           |
| 독립성         | 기존 50개 파일과 분리했지만 최종 독립성은 미확정                     |

파일 위치는 저장소 기준 다음과 같다.

- `web/src/lib/studio-plan-quality-validation-candidates.ts`
- `web/src/lib/studio-plan-quality-validation-candidates.test.ts`

기존 `studio-plan-quality-fixtures.ts` 및 `studio-plan-quality-evaluation.ts`는 수정하지 않는다. 기존 평가 core는 현재 50개 manifest만 허용하므로 새 후보 ID를 넣으면 `unknown-fixture`가 된다. 기존 ID를 재사용하거나 digest를 덮어써 등록을 우회하지 않는다.

## 3. 원자료 구성과 의도된 충돌

각 후보는 다음 다섯 자료 묶음을 기본으로 가진다. 필요한 경우 전사문·타사 소개·폐기된 안내·적대적 작성 요청을 별도 자료로 추가한다.

1. 개발 구성·시험 기록: 고객 문제, 기술 구성·처리 흐름, 시험 조건·표본·한계, 비교 범위
2. 고객 상담·사업화 기록: 실제로 수행한 것으로 설정한 일과 미래 의향·계약의 구분, 가격·직접비·과금 계획
3. 예산·기존 거래 기록: 기간·단위·금액, 개발비 세부 항목, 조달재원과 미확정 항목
4. 담당 역할·권리 범위 기록: 회사·외주·고객의 역할, 자체 개발물과 외부 구매품·협력사 권리 구분
5. 개발 경과·향후 실행 일정: 이전 사업·신규 개발 경과, 다음 단계 산출물·조건, 중기 계획

연결형 후보에는 기술→해결할 고객 문제→시험 범위→고객 검증→가격/비용→담당자→일정/자금의 관계를 설명할 수 있도록 원문을 제공했다. 이를 `sufficientForCompleteDraft: true`라는 사람 정답으로 확정하지 않는다. 시험 결과·제품명·일정이 있다는 사실만으로 문서 충분성이나 현실적 타당성이 증명되는 것은 아니다.

의도된 자료 부족은 빈 곳을 일반론으로 메우지 않고 구체적으로 미확정 상태를 기록했다. 프로필과 자료 사이의 모순은 `authoringNotes`에 위치와 구성 의도를 명시했다.

| 후보           | 명시한 프로필·자료 충돌                                                |
| -------------- | ---------------------------------------------------------------------- |
| 슬러리 회수    | 프로필의 특허 보유·계약 체결 주장과 권리자료의 협력사 소유·계약 부재   |
| 회전기기 감시  | 프로필의 매출 단위와 재무 원장의 금액 불일치                           |
| 권한 로그 대조 | 프로필의 독점 기술 소개와 권리자료의 타사 엔진 소유·계약 협의 상태     |
| 냉장배송 기록  | 프로필의 타사 배송 건수·매출과 재무자료의 자사 일정표 용역 기록 불일치 |

`authoringNotes`, `challengeTags`, `materialDesign`은 작성자 메타데이터다. 향후 성능 평가 시 이를 정답처럼 생성 모델에 전달하면 입력 누설이 된다. 모델에 줄 자료 범위와 검토자용 구성 메모를 분리할 등록 계약이 필요하다. 후보 주제의 `gaps: []`는 문제 없음을 뜻하지 않으며 사람 검토 결과도 아니다.

OCR 관련 후보는 문자·숫자가 혼동된 합성 전사문이다. 원본 이미지가 없으므로 OCR 엔진 인식 정확도를 평가할 수 없다. 오래된 기준 관련 후보도 폐기된 **가상 작성 안내**를 사용한다. 실제 현행 기관 기준이나 법률 해석의 정확성을 평가한 것으로 표시하면 안 된다.

자료 속 허위 실적 작성 요청은 적대적 입력 데이터다. 실행기·개발자·검토자에게 내려진 업무 지시가 아니다. 이 요청을 실행하거나 원고에 반영하는 코드 경로는 이 후보 작성 작업에서 추가하지 않았다.

## 4. 코드 계약

`createPlanQualityValidationCandidates()`는 매번 독립 사본의 `PlanQualityValidationCandidate[]`를 반환한다. 외부 파일을 읽거나 고객자료·AI API를 호출하지 않는다. 생성 엔진과 평가 엔진을 import하지 않는다.

후보의 핵심 상태는 고정되어 있다.

```ts
{
  synthetic: true,
  status: "validation-candidate",
  authoredBy: "ai",
  humanAnswerKey: null,
  independentHoldoutConfirmed: false,
  performanceEvaluation: "not-performed",
  catalogRegistration: "not-registered"
}
```

구조는 `planQualityValidationCandidateSchema`로 검증한다. `company`는 기존 `StudioCase`, `candidate`는 기존 `Candidate` 형태다. 회사 기록에는 생성 원고·분석 결과·선택 완료·심사 결과를 만들지 않았다. 사업자번호는 비어 있고 자료 원본 경로·MIME도 `null`이다.

`materialDesign`의 값은 `connected-narrative`, `intentional-gap`, `intentional-conflict`다. 이 필드는 AI의 자료 구성 목적을 나타내며 예상 합격 여부·문서 완결성 확정값이 아니다.

`challengeTags`에는 연결된 자료, 자료 부족, 상충 수치, OCR 전사, 권리 주체, 타사 자료, 오래된 안내, 허위 실적 유도라는 구성 조건을 표시한다. `deterministicExpectation`, `expectedPass`, `semanticReviewResult` 같은 모델 성능 기대·결과 필드는 없다.

## 5. 독립 검증으로 확정하기 전 필요한 절차

현재 파일이 기존 50개 파일과 분리되어 있다는 이유만으로 독립 검증세트가 되지 않는다. 이 후보는 개발 작업 중 AI가 작성했고 현재 개발자에게 내용이 공개되어 있다. 사람이 적절성을 검토하고 사용·접근·동결 범위를 정해야 한다.

1. 검토 담당자가 합성 사실의 내부 일관성, 의도된 충돌, 업종·신청 유형의 대표성을 확인한다. 의도되지 않은 모순은 평가 전에 정리한다.
2. 담당자가 각 사례의 사실·쟁점·자료 충분성·기대 동작·중대 차단 조건의 정답표를 작성한다. AI 작성자 메모를 승인 없이 정답표로 복사하지 않는다.
3. v3 최소 50건과 필요한 분포를 충족할 별도 후보를 추가한다. 기존 50개와 12개를 단순 합산해 “독립 62개 확보”라고 표시하지 않는다.
4. 개발 튜닝용 세트와 평가용 세트의 사용 경계를 정하고 평가 세트를 동결한다. 이 12개에 맞춰 생성·검토 판정 규칙을 수정했다면 그 사례를 독립 성능 증거로 재사용하지 않는다.
5. catalog 등록을 승인한 뒤 새 세트 ID·버전·원문/주제 digest·정답표 digest·접근 이력을 관리한다. 현재 평가 core의 50개 고정 manifest에 자동 병합하지 않는다.
6. 별도로 허용·구성된 실제 AI 실행과 독립된 두 사람의 평가를 수행한다. 충분한 자료의 완결 원고, 중대 허위, 차단 동작, 질문 적합성, 수정 효과를 기록한다.
7. 실제 고객 시범은 합성 평가와 다른 범위로 계획한다. 필요한 자료 사용·외부 처리·평가 허용을 갖춘 뒤 별도 결과로 기록한다.

최종 독립성 승인·사람 정답표·실제 AI 실행·두 사람 평가·출시 기준 판정은 모두 아직 남아 있다. 이 준비안은 그 절차를 시작하기 위한 후보 정리다.

## 6. 검증 범위와 실행

테스트는 schema 유효성, 업종×신규/재확인 분포, 회사·기술·자료 ID의 고유성, 구성 조건 태그, 입력 재현성과 사본 독립성만 확인한다. 생성·수정·검토 엔진을 호출하지 않고 예상 품질 통과·오류 검출률을 검사하지 않는다. 형식 테스트 통과를 원고 품질 통과로 표시하지 않는다.

`venturepass/web/`에서 다음과 같이 2 workers로 자체 검증한다.

```powershell
& '..\..\.venturepass-tools\pnpm.cmd' exec vitest run src/lib/studio-plan-quality-validation-candidates.test.ts --maxWorkers=2
```

이 작업은 위 두 코드 파일과 이 준비안 문서만 추가한다. 기존 고정 50개·평가 core·실행기·스토리지·화면을 변경하지 않는다.
