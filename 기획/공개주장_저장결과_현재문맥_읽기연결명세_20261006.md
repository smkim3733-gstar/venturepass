## 2. 다음 4I32의 입력과 포트

기존 createIsolatedPublicComparisonService 내부에 다음 두 명시 읽기 포트를 연결한다. 이름은 다음 구현의 예정 이름이며 현재 API가 아니다. 서비스 생성은 같은 session/회사 guard/합성 driver를 고정하고 새 환경·시계·SDK·owner를 준비하지 않는다.

| 포트 | 입력 | 의미 |
|---|---|---|
| readStoredComparison | strict data-only selection: runId, dispatchCommandDigest, comparisonEventDigest, responseArtifactSha256, validatedArtifactSha256 | 정확히 저장된 비교 결과 한 건과 원래 선택 근거를 읽는다. 현재 회사 행을 읽지 않으며 current는 not-checked다. |
| inspectStoredComparisonContext | 위와 동일한 selection | 같은 결과를 감사한 뒤 같은 회사 guard의 현재 snapshot에 원래 요청을 대조한다. 결과 본문을 현재 자료로 재생성하거나 저장하지 않는다. |

UUID/hash의 기존 schema를 재사용하고 추가 키/임의 body/회사 객체/경로/권한 boolean은 거절한다. 입력 UTF-8 JSON은 기존 selection 8KiB 이내다. selection은 기존 previewPostcapture의 run/dispatch·comparisonEventDigest·responseArtifactSha256·expectedValidatedArtifactSha256에서 정확히 취한다. comparisonEventDigest:null인 계산 미리보기로 이 포트를 호출할 수 없다. 결과를 찾기 위해 최신 run을 임의 선택하거나 자동 execute/write/recover하지 않는다.

원래 실행 또는 첫 후속 선택으로 고정된 run/dispatch digest를 그대로 사용한다. 저장 결과의 event/hash는 읽기 신원이며 새 쓰기/전송 권한이 아니다. 나중에 같은 run의 close8행이 추가되어도 원래 result event/hash가 그대로이고 전체 감사가 통과하면 같은 과거 결과를 읽을 수 있다. 읽기 입력에 최신 run head를 억지로 요구해 과거 결과를 바꾸지 않는다. 다른 run/회사/dispatch/result/response의 교차 결합은 거절한다.

## 3. 좁은 출력과 현재 문맥의 의미

읽기 사본의 겉 source는 synthetic-comparison-stored-review, owner:null, runtimeObserved:false, authority는 기존 comparisonPlanAuthority의 모든 false다. DB 행/전체 archive/canonical response/SDK 도우미/키·경로/SQL handle/capability를 노출하지 않는다.

| 출력 영역 | 허용 내용과 한계 |

| resultIdentity | 위의 다섯 선택 값, 원래 requestIdentity, preparation digest, 원래 회사 revision·주장 record/version/input digest·원고 id/version/content hash·section key. |
| historical | 감사된 원래 주장·항목 전체 문맥, 선택 발췌 전체와 수동 메타데이터/인용/메모, 제외 source IDs, 저장 비교 state 및 검증된 comparison 또는 null. 기존 경계 false를 그대로 유지한다. |
| database | comparisonRecorded/costSettled/finalized, 기존 run 저장 hold와 같은 scope 금액 hold/recognition의 읽기 사본. 읽기가 비용을 인정하거나 hold를 해제하지 않는다. |

합성 읽기 출력 전체 JSON UTF-8은 4MiB 이내로 제한하고 초과하면 거절한다. 긴 항목/발췌/의견을 자르거나 빈 내용으로 성공시키지 않는다. 이는 새 읽기 투영의 상한으로, canonical response4MiB·HTTP 성공 body4MiB/오류64KiB·AI 입력24만자와 다른 측정이다. 기존 context/validated artifact별2MiB, capture/final별4MiB·run32MiB·원장256MiB 검사는 그대로다. 자료1~10개/원래 인용1500자/전체 응답24만자 제한도 유지한다.

현재 검사는 inspectPublicClaimComparisonRequest(currentCompany, originalRun.command, originalRun.identity)를 재사용한다. original command의 selection.companyRevision이나 자료/모델을 새 값으로 바꾸지 않는다. 현재 snapshot은 같은 guard가 읽고 projectStoredCompany가 투영한 값만 사용한다.

- not-checked: 과거 결과만 명시 읽었다. 현재 일치/불일치 어느 쪽도 추정하지 않는다.
- exact-original-request: 원래 revision 및 request identity 재구성이 정확히 일치했다. 의미는 읽은 snapshot에서 원래 선택 근거가 같은 요청을 만든다는 것이다. 최신 원고 선택·회사 해당성·내용의 진실·현재 원본 파일 검사·채택 권한은 아니다.
- changed: 유효한 같은 회사 snapshot과 원래 요청의 대조에서 revision/선택 신원/원고 또는 선택 발췌 불일치가 확인됐다. revision만 달라도 보수적으로 재검토 필요다. 자료가 같다는 이유로 원래 command를 고치지 않는다.
- unavailable: 현재 회사 행을 안전하게 확인하지 못했거나 지원 형식/한도/감사에서 일치를 확정할 수 없다. 사유는 allowlist로 좁히며 예기치 않은 오류·손상을 단순 changed로 삼지 않는다. 정리 실패는 이 정상 출력으로 감추지 않고 전체 호출을 거절한다.

원래 planId/version은 명시 선택한 저장 원고이지 최신 원고가 아니다. exact-original-request라도 원래 버전만 가리키며 현재 화면의 다른 버전에 자동 이동·적용하지 않는다. 이후 UI가 연결될 때 관측한 회사 revision과 화면 snapshot을 다시 대조하고 변경되면 현재성 표시를 철회해야 한다. 이번과 다음 단계에는 UI/route 변경이 없다.

claimReviewContext의 current/judgementCurrent는 별도 수동 기록 표시다. 이를 위의 request identity 검사나 사실 확인 권한으로 사용하지 않는다. 새 judgement가 등록돼 회사 revision이 바뀌면 현재 요청은 changed가 될 수 있지만 원래 저장 비교 의견은 그대로 남는다.

## 4. 같은 session의 읽기·정리 수명

requireHandoff 및 엔진의 비공개 canRelease를 먼저 사용한다. public phase/캡처0/활성0/DB finalized만으로 진행 중 I/O·lease나 불명 COMMIT/정리 책임이 끝났다고 추정하지 않는다. retained postcapture 명령이 있으면 읽기에서 ack를 대신 수행하지 않고 원래 recoverPostcapture 명령을 요구한다.

같은 모듈의 기존 withStorage/read/select/inspectTransaction/checkpoint·SQL13 전체 감사·checkComparisonWitnessCompany/checkComparisonWitness(version3)를 재사용한다. 감사한 원래 run/context/request/capture/result를 projected DTO로만 반환한다. pending witness/부분행/복원 불명은 조용히 수선하지 않는다. result artifact만 독립 JSON.parse해서 신뢰하지 않는다.

현재 검사는 quality session/lease와 SELECT snapshot을 먼저 확보한 뒤 studio SELECT guard를 연다. 필요한 동일 읽기 구간은 기존 private inspectTransaction을 이용해 quality→studio 순서로 묶고 종료 때 역순으로 정리한다. 기존 inspectVersionedDatabase는 자기 BEGIN/COMMIT 범위를 닫으므로 그 반환만으로 두 DB가 동시에 잠겼다고 주장하지 않는다. 두 DB의 일반 원자적 거래를 새로 만들지 않는다.

회사 guard의 성공적인 획득과 그 호출의 정리 책임을 같은 guard 내부에서 식별해야 한다. beginComparisonCompanyRead가 내부 BEGIN 후 실패하고 ROLLBACK도 실패하면 반환된 회사 값이 없더라도 책임이 남는다. 필요한 획득/정리 표시는 기존 guard 내부의 호출 수명으로 제공하며 외부 boolean이나 새 전송 owner/별도 lease 프로토콜을 만들지 않는다. COMPANY_TRANSACTION_ACTIVE 등 획득 전 거절로 다른 호출의 거래를 종료해서는 안 된다.

자기 회사 read/quality SQL/lease의 종료가 모두 확인된 뒤만 읽기 응답과 closed를 확정한다. 자기 cleanup 실패는 원래 서비스와 정리 책임을 보관하며 교체/폐기를 거절한다. 명시 재조회는 자기 실패한 읽기의 정리만 재시도할 수 있다. 경쟁 호출·원래 실행의 lease를 정리하지 않는다. 복구 명령이 필요한 쓰기 실패를 읽기 재시도로 해결하지 않는다.

읽기에서 DML/증인 intent·ack·새 result/close 행·금액/원고/judgement 변경은0이다. SELECT 거래 종료와 기존 일시 lease 파일의 획득/반납은 발생할 수 있으므로 전체 파일 byte 무변화를 주장하지 않는다. 기존 증인 내용과 DB 논리 행·회사 body/revision·원래 nonce/bytes가 불변인지 검증한다. storage-only 재개방도 원래 result 전체 감사만 수행하고 새 driver/전송 owner0이다.
