# 복수파일 접수와 추출 재개 설계

작성일: 2026-09-25. 제품 23번, 잔여 범위 R02 일부와 R03의 로컬 처리 부분은 구현·전체 검사·격리 API/UI·실제 재시작 검증을 마쳤다. 아래 설계 중 외부 AI 처리 재개는 후속 범위이며 아직 활성화하지 않았다.

## 2026-09-25 23:12 구현 결과와 경계

- 복수 예약→원본 저장 checkpoint→원본 보관→로컬 문서/Windows OCR→미검토 결과→교정·명시 채택을 구현했다. 파일별 순차 접수는 확정 거절 뒤 저장 상태를 확인하고 다음 파일을 진행하며 불확실 응답을 자동 재전송하지 않는다.
- 결과 본문 50만 자 한도는 채택 뒤 보관한 판독 초안도 포함한다. 명시 초안 비우기는 채택 본문을 유지한다. 원본 없는 미접수 예약만 취소할 수 있고 기록은 보존한다.
- 원본 저장 중 중단은 파일 없음 또는 정확한 SHA/메타데이터 일치 파일만 복구한다. 일부만 기록됐거나 다른 바이트인 파일은 덮어쓰거나 삭제하지 않고 중단한다. 해당 checkpoint가 남으면 백업 완료를 차단한다.
- PDF/OCR 페이지와 XLSX/자막 본문은 로컬 보관한다. 실제 XLSX 셀·자막 시간 구간의 구조화 위치와 자료/기업정보 제안은 24에서 별도로 구현·검증한다.
- 고정 앱 2,990개·운영 CLI 34개 검사 통과. API와 브라우저의 부분 실패·재시작 보존·확인 초기화·교정 본문만 채택을 검증했다. 외부 AI/실제 회사 전송/공식 신청은 실행하지 않았다.

## 3. 추천 데이터 경계

첫 구현은 현재 SQLite 회사 레코드의 `sourceIntakes: []` 기본값을 추가하는 편이 작다. 새 테이블·스토리지 서비스가 필요하지 않다. 단, 본문 크기는 별도 합계 제한을 둔다. 기존 백업 검증기는 새 스키마 기본값/본문 한도에 맞춘 합성 호환 회귀를 추가한다.

- 한 묶음은 최대 10개 파일, 합계 24MiB, 파일마다 기존 12MiB 제한을 제안한다. 전송은 파일별 요청으로 순차 처리하여 서버가 묶음 전체를 메모리에 올리지 않는다.
- 회사 자료 40개 제한은 접수 중 예약한 source ID까지 포함한다. 동시 접수가 제한을 넘어가지 못하게 저장 트랜잭션 안에서 계산한다.
- 회사별 작업 항목 100개, 파일별 시도 10개, 요청 영수증 20개, 미검토 추출 본문 합계 500,000자를 제안한다. 잘라 저장하거나 오래된 기록을 몰래 삭제하지 않는다. 용량을 확보하지 못하면 원본을 유지하고 `awaiting_capacity`로 멈춘다.
- 원본 저장 경로·계정·키·환경 설정은 작업 DTO에 넣지 않는다. 결과 본문은 해당 회사 내부에만 보관하며 로그·Git·승인 토큰에 복제하지 않는다.
- 채택 후에는 원본 추출 결과와 교정된 채택 본문을 구분한다. 미검토 결과 본문을 보관하는 동안 합계 제한을 계속 적용한다. 한도에 도달하면 명시적인 미검토 결과 폐기 기능이 필요하며, 원본·작업 ID·결과 해시·채택 영수증은 보존한다. 이 폐기 동작 없이 자동 GC로 한도를 해결하지 않는다.

후보 타입은 다음과 같다. 명칭·숫자 제한은 구현 착수 전에 확정한다.

```ts
type IntakeEngine =
  "local-document" | "windows-ko" | "ai-document" | "ai-transcription";
type IntakePhase =
  | "awaiting_original"
  | "storing_original"
  | "original_stored"
  | "extracting_local"
  | "requesting_external"
  | "awaiting_method"
  | "awaiting_review"
  | "awaiting_capacity"
  | "retryable_failure"
  | "external_result_unknown"
  | "adopted"
  | "result_discarded"
  | "cancelled";

type SourceIntakeItem = {
  id: string;
  batchId: string;
  sourceId: string;
  version: number;
  original: null | {
    originalName: string;
    mimeType: string | null;
    sizeBytes: number;
    sha256: string;
    sourceUpdatedAt: string;
  };
  declared: { originalName: string; sizeBytes: number; kind: SourceKind };
  phase: IntakePhase;
  attempts: Array<{
    id: string;
    engine: IntakeEngine;
    startedAt: string;
    finishedAt: string | null;
    originalSha256: string;
    externalRequestStarted: boolean;
    status: "running" | "completed" | "failed" | "unknown";
    code: string | null;
    resultId: string | null;
  }>;
  result: null | {
    id: string;
    attemptId: string;
    engine: IntakeEngine;
    generatedAt: string;
    originalSha256: string;
    sourceUpdatedAt: string;
    textSha256: string;
    content:
      | { kind: "plain"; text: string }
      | { kind: "pages"; pages: Array<{ pageNumber: number; text: string }> };
    warnings: string[];
    reviewStatus: "unreviewed";
  };
  adoption: null | {
    id: string;
    clientRequestId: string;
    inputDigest: string;
    resultId: string;
    resultTextSha256: string;
    adoptedTextSha256: string;

    adoptedAt: string;
  };
  requests: Array<{
    clientRequestId: string;

  }>;
};
```

페이지 배열과 단일 본문 중 하나만 저장하고, 표시용 본문은 결정적인 조합으로 반환한다. 해시는 그 조합에 대해 계산한다. PDF가 아닌 형식에는 존재하지 않는 페이지 번호를 부여하지 않는다. 계획된 날짜·실적·사업자 정보 추론은 하지 않는다.

## 4. 원본 접수의 복구 경계

1. 묶음 생성 시 파일별 ID와 미래 source ID를 서버가 발급하고 예약한다. 이 단계에는 파일 본문이 없다.
2. 파일 요청을 제한 내에서 읽어 실제 형식·이름·MIME·SHA를 서버가 검증한다. 클라이언트가 보낸 해시는 신뢰하지 않는다. 업무 잠금과 회사 CAS도 확인한다.
3. `storing_original` checkpoint에 서버 계산 SHA·바이트 수·미래 source ID·요청 nonce를 먼저 저장한다. 파일을 기록하기 전에 해당 파일의 소유 근거가 남는다.
4. 서버가 계산한 고정 경로에 독점 생성한다. 같은 요청 재개 때 이미 존재하는 파일은 안전 reader로 현재 job의 SHA·크기·경로 동일성을 확인한 경우에만 재사용한다. 다른 파일을 덮어쓰지 않는다.
5. 다시 원본을 대조한 뒤 source의 `text:''`, `extraction:'pending'`, 원본 경고와 작업 `original_stored`를 같은 SQLite 트랜잭션에 저장한다. 원본 접수 실패가 다른 파일의 source나 결과를 롤백하지 않는다.
6. 서버 종료 후 `storing_original`은 같은 소유 기록으로만 조정한다. 파일 없음이면 재전송 대기, 정확한 파일이면 등록 단계만 완료, 링크·변조·소유 불명확 파일이면 고정 오류로 중단한다. 업로드 bytes가 없는 브라우저 새로고침 후에는 사용자가 같은 파일을 다시 선택해야 한다. 로컬 경로를 저장해 파일을 몰래 다시 읽지 않는다.

기존 `addUpload`를 그대로 여러 번 호출하는 방식은 응답 유실과 파일 생성 직후 종료를 구분하지 못하므로 충분하지 않다. 접수/파일 저장의 소유 checkpoint를 추가한 내부 메서드가 필요하다. source가 아직 없는 동안에는 클라이언트 경로를 받지 않는 전용 내부 안전 읽기를 사용한다.

## 5. 추출·재개·외부 요청 규칙

로컬 처리는 기본값이다. 엔진은 파일 종류와 사용자가 허용한 방법으로 명시한다. 로컬 PDF에서 본문을 못 읽으면 `awaiting_method`로 두고 Windows OCR 또는 별도 AI 전송을 선택하게 한다. `extractSource` 안의 자동 외부 분기를 새 작업 서비스가 그대로 호출하지 않는다.

장시간 파서·OCR·AI 실행 중에는 SQLite 쓰기 트랜잭션을 열어두지 않는다. 시작 checkpoint와 결과 checkpoint를 짧은 개별 트랜잭션으로 저장한다. HMR 공유 잠금은 중복 요청을 막고, DB의 시도 ID·개정·phase는 재시작 후 늦게 돌아온 작업을 차단한다. 종료 시간만 지났다고 아직 실행 중인 동일 작업의 두 번째 worker를 시작하지 않는다.

| 현재 상태                    | 다시 요청할 때                                                                                                           |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `original_stored`            | 서버에 있는 원본을 안전하게 재읽고 아직 완료하지 않은 판독만 시작한다.                                                   |
| `awaiting_review`            | 저장된 정확한 result ID를 반환한다. 파서·OCR·AI를 다시 부르지 않는다.                                                    |
| `adopted`                    | 채택 영수증과 현재 source 연결을 확인한다. 본문을 다시 덮어쓰지 않는다.                                                  |
| 종료된 `extracting_local`    | 활성 worker가 없고 원본·회사 연결이 같으면 명시 재개로 새 시도를 남길 수 있다. 원본 읽기 이외의 외부 효과는 없어야 한다. |
| 종료된 `requesting_external` | 결과가 DB에 없는 경우 `external_result_unknown`으로 표시한다. 자동 재전송하지 않는다.                                    |
| `retryable_failure`          | 같은 원본으로 로컬 실패 단계만 명시 재개한다. 완료된 다른 파일은 반복하지 않는다.                                        |
| 원본 SHA/회사/source 변경    | 이전 시도를 완료 처리하지 않는다. 현재 자료를 다시 확인해야 한다.                                                        |

AI 전송은 방법·정확한 원본 SHA·파일 목록·명시 확인·서버 기록 시각을 포함한 별도 승인 범위가 필요하다. API 키 존재나 이전 파일의 허용으로 새 파일의 전송을 허용하지 않는다. 외부 호출 직전에 `externalRequestStarted:true`를 먼저 durable 저장한다. 요청 결과 불명확 상태에서는 새 승인과 중복 비용 가능성 안내 없이는 다시 보내지 않는다. 현재 공급자 API가 완료 결과를 복원한다고 가정하지 않는다. `maxRetries:0`을 유지한다.

첫 UI 구현은 한 번의 ‘접수한 로컬 자료 처리’ 범위 안에서 파일별 `run-next`를 순차 호출할 수 있다. 한 요청은 파일 하나의 제한된 판독만 처리한다. 탭 종료 뒤 무인 작업을 계속한다는 보장은 하지 않으며, 새로 열면 저장 상태를 먼저 읽고 명시적으로 이어간다. 자동 재시도와 사용자가 허용한 다음 파일 처리는 구분한다. 외부 결과 불명확한 파일은 대기시키고 다른 로컬 파일 결과는 보존한다.

## 6. API 후보와 응답 확인

새 `GET/POST /api/studio/cases/{caseId}/source-intakes`와 파일별 원본 경로를 제안한다. 모든 변경 요청은 strict body, no query, UUID, 용량·회사 잠금·CAS를 적용한다.

```ts
type IntakeCommand =
  | {
      action: "create";
      revision: number;
      clientRequestId: string;
      files: Array<{
        clientFileId: string;
        originalName: string;
        sizeBytes: number;
        kind: SourceKind;
      }>;
    }
  | {
      action: "run-next";
      revision: number;
      clientRequestId: string;
      batchId: string;
      itemId: string;
      expectedItemVersion: number;
      engine: "local-document" | "windows-ko";
    }
  | {
      action: "approve-external";
      revision: number;
      clientRequestId: string;
      itemId: string;
      expectedItemVersion: number;
      originalSha256: string;
      engine: "ai-document" | "ai-transcription";
      approved: true;
    }
  | {
      action: "resume";
      revision: number;
      clientRequestId: string;
      itemId: string;
      expectedItemVersion: number;
    }
  | {
      action: "adopt";
      revision: number;
      clientRequestId: string;
      itemId: string;
      expectedItemVersion: number;
      resultId: string;
      originalSha256: string;
      sourceUpdatedAt: string;
      text: string;
      reviewed: true;
    }
  | {
      action: "discard-result";
      revision: number;
      clientRequestId: string;
      itemId: string;
      expectedItemVersion: number;
      resultId: string;
      confirmed: true;
    };

// PUT /source-intakes/{itemId}/original : multipart, file 하나 + revision/nonce/itemVersion
// GET /source-intakes : 회사 내 저장 checkpoint. 실행 동작 없음.
type IntakeResponse = {
  company: StudioCase;
  batchId: string;
  item: SourceIntakeItem | null;
};
type IntakeFailure = { error: string; code: string; accepted: boolean };
```

같은 nonce와 같은 정규 입력은 이미 저장된 checkpoint를 반환한다. 다른 입력은 409다. 새 nonce의 오래된 revision도 409다. 파일 전송 replay는 파일 내용까지 서버 SHA로 대조한다. 같은 SHA라는 이유로 사용자가 별도로 접수한 두 자료를 자동 병합하지 않는다.

응답 유실 시 UI는 GET에서 회사·item ID·요청 nonce를 먼저 확인한다. `accepted:false`이며 저장된 요청과 활성 worker가 모두 없다고 확인한 경우만 새 요청을 허용한다. `accepted:true` 또는 네트워크 결과 불명확이면 원래 nonce를 보존한다. 클라이언트 상태만 보고 완료·실패를 확정하지 않는다.

본문 채택은 별도 명시 동작이다. 미검토 결과를 교정하고 확인 체크를 한 뒤, 정확한 결과 ID·원본 SHA·현재 sourceUpdatedAt에 묶어 저장한다. 기존 OCR 검토와 같은 회사 잠금, 원본 재읽기, 단조 증가 sourceUpdatedAt, 경고 보존, `invalidateEvidence`를 재사용한다. 성공 시 source는 `manual`, 작업은 `adopted`가 된다. 계획서 확정이나 기관 상태는 바꾸지 않는다. 이미 본문이 있는 자료에는 덮어쓰지 않는다.

## 7. 합성 검증과 완료 기준

- 서로 다른 3개 파일 중 1개 접수 실패, 1개 판독 실패, 1개 성공 시 각각의 원본·결과·오류가 남고 다른 파일의 성공을 지우지 않는다.
- 파일 기록 직전/직후, DB commit 직후, 로컬 판독 직후, 결과 저장 직후 종료와 응답 유실을 주입한다. 같은 nonce 재개에서 완료된 파서·파일 생성·본문 채택을 반복하지 않는다.
- 같은 nonce 다른 bytes/메타/엔진, stale 회사 개정, 다른 회사 item/source/result, 중복·누락 ID, 예상 phase/version 불일치를 거부한다.
- 원본의 같은 크기 변조, reparse/symlink/hardlink, 원본 읽는 동안 교체, source timestamp·metadata 변경을 전후 검사한다. 원본 경로·본문·키·오류 원문이 로그나 실패 DTO에 나오지 않는다.
- 판독 결과는 source.text에 자동 저장하지 않고 분석·진단·원고 생성 입력에 들어가지 않는다. 검토 확인 없는 채택, 오래된 결과 채택, 이미 작성된 source 덮어쓰기는 거부한다.
- worker 동시 요청, HMR, 프로세스 재시작, 늦게 돌아온 이전 시도 결과, 외부 결과 불명확을 검증한다. 외부 SDK는 mock으로만 호출 횟수를 확인한다. 실제 자료·실제 외부 AI는 사용하지 않는다.
- 개별/묶음/회사 원본 수·본문·결과·시도·영수증 한도와 전체 rollback을 확인한다. 원본은 유지하고 결과만 한도 때문에 사라진 경우 완료로 표시하지 않는다.
- 기존 단일 업로드/OCR/수동 자료/준비 pipeline/사전진단/백업-새경로복원 회귀를 보존한다. legacy `sourceIntakes` 없음은 빈 배열로 읽고 기존 레코드를 재작성하지 않는다.

이번 기능의 완료는 여러 파일의 원본 접수부터 미검토 결과 보관, 중단 뒤 재개, 명시 본문 채택까지 합성 환경에서 이어지는 것이다. 실제 음성 인식 품질·외부 전송 동의 운영정책·공유 사용자 권한·보관기간 결정은 별도 운영 검증이다.

## 8. 구현 전에 확정할 선택

추천 기본안은 **로컬 문서·Windows OCR durable 흐름을 먼저 완결**하고, 외부 전사/판독은 같은 원본·시도 모델에 명시 승인과 결과 불명확 대기를 추가하는 순서다. 두 경우 모두 UI는 실패 상태를 단순히 ‘다시 시도’ 버튼 하나로 합치지 않는다.

최소 확정 항목은 묶음/작업/결과 보관 한도, 채택 후 원시 판독 결과 보관 또는 명시 폐기, 새 접수에서 허용할 형식, 외부 재전송 승인 범위다. 문서·표·음성의 기존 지원 형식을 근거 없이 확대하지 않는다. 원본만 보관 경로의 현 PDF·이미지 제한을 그대로 둔 채, 새 접수 경로에서 DOCX/XLSX/텍스트/음성의 바이트 검증을 별도로 구현해야 한다.

자동 분류·기업정보 제안·정형 위치 모델은 접수 재개와 별개의 다음 계약이다. 이 문서의 API에 해당 기능을 암묵적으로 끼워 넣지 않는다.
