## 3. 상위 수명과 명시 시작

상위 호출자가 retainer와 화면 연결을 먼저 보관한다. 빈 연결 생성에는 invocation/Request/타이머가 없다. remount 때 슬롯을 새로 만들어 BUSY/cleanupFailed/unavailable을 우회하지 않는다. 향후 실제 부모 설치에서는 회사/revision·탭과 독립적인 한 수명을 확보해야 한다. 다음 격리 구현은 이 책임을 주입한 합성 호출자가 맡는다.

화면의 post-commit 연결은 새 view token을 얻고, cleanup은 그 setup이 받은 token만 detach한다. 옛 cleanup이 최신 ref의 token을 읽어 새 화면을 분리하면 안 된다. subscribe cleanup은 해당 등록 객체만 해제한다. 일반 effect cleanup을 retainer.close로 연결하지 않는다. close는 영구 admission 종료이며 개발 effect 재연결과 의미가 다르다. 실제 root가 종료될 때의 강한 참조/영속 보관은 미구현으로 남긴다.

명시 사용자 동작은 원래 snapshot/선택과 신뢰한 startRequest·signal을 첫 await 전에 고정한다. prepare 성공 후 원래 handle/ticket과 관측을 먼저 보관하고 현재 frame으로 start한다. 생성 중 닫힘/교체는 원래 객체를 보관한 후 취소하고 전송하지 않는다. 이미 시작한 호출의 재사용/자동 재시도는 없다. render·effect setup·subscribe·frame 갱신·통지에서 prepare/start를 실행하지 않는다.

실제 service/원래 선택 주입이 없으면 기존 supported:false/명시 미지원이다. 최신 run, preview/쓰기 receipt로 신원을 추정하거나 endpoint를 임의로 만들지 않는다.

## 4. 최소 통지 경로와 숨은 보관 경로

화면에 반환한 handle만 관측하는 별도 wrapper로는 충분하지 않다. retainer.prepare가 생성된 호출을 보관한 뒤 STALE_VIEW/CLOSED/관측 실패를 반환하면 화면에는 handle이 없기 때문이다. 추가 구현은 기존 retainer 내부에서 원래 호출을 보관한 직후 delivery/requestCompletion/responseCompletion/aggregate completion의 관측을 한 번씩 등록한다. 성공/실패 반환 여부나 화면 구독 유무와 독립적으로 유지한다. 실제 원래 Promise를 대체하거나 raw 결과를 통지 이벤트에 싣지 않는다.

기존 aggregate completion 관측·동일 entry/fresh canForget/observerFailed 동작을 유지한다. delivery의 빠른 오류, 각 I/O 완료, 불명/정리 실패, detached entry 해제, attach/prepare/start/cancel/release/close 같은 실제 상태 변화가 통지 대상이다. 각 원래 Promise/entry에 관측1회이며 새 화면 구독마다 then을 추가하지 않는다. 늦은 옛 entry의 통지가 새 슬롯을 해제하거나 옛 결과를 게시하지 않는다.

통지는 임계 구간과 fresh inspect/정리 의무가 끝난 뒤 전달한다. 원래 작업 도중 UI listener를 호출하지 않는다. 한 개의 예약된 microtask로 합칠 수 있으나 I/O 재조회 timer·retry queue가 아니며 최종 상태 변화를 잃지 않아야 한다. 같은 값의 inspect/display/구독/read에는 새 변경 통지를 만들지 않는다. inspect→notify→inspect의 무한 microtask 순환을 금지한다.

한 retainer에는 이 내부 통지를 맡는 화면 연결1개만 허용한다. 두 번째 연결이 기존 내부 구독을 빼앗거나 보관 수명을 나눌 수 없도록 명시 거절한다. 실제 UI의 구독 해제와 달리 내부 관측은 pending/실패/불명이 남는 동안 계속 보관하며, 닫힌 상위 연결의 참조도 fresh canForget 없이 버리지 않는다.

화면 연결은 이 내부 통지의 단일 구독자다. 실제 변화 후 렌더 밖에서 상태를 관측하고 snapshot을 게시한다. 임계 구간 도중의 일시적인 canPrepare:false/io:null을 최종 상태로 게시하지 않는다. retainer.inspect의 반환 뒤 finally 정리가 수행될 수 있으므로 해제 이전 사본을 해제 이후의 현재 상태로 확정하지 않는다. 같은 entry/revision을 대조해 안정된 관측만 게시하도록 다음 구현에서 순서를 검증한다. 필요하면 retainer 내부에 작은 변화 revision/안정된 상태 관측을 보완하되 원래 호출·SQL·wire 검증은 복제하지 않는다.

생성 실패 뒤 handle 없는 내부 entry, 이미 완료한 호출, 구독자가 없는 동안의 완료도 통지/현재 상태에 반영돼야 한다. 통지가 합쳐져도 빠른 delivery 실패를 I/O 완료로 바꾸거나 cleanupFailed/unavailable을 생략하지 않는다. notification failure는 원래 I/O observerCleanupFailed와 별도다. 화면 listener가 throw해도 원래 completion/정리 관측을 중단하지 않는다.

## 5. 순수 snapshot·현재 표시·구독

가칭 화면 연결은 같은 retainer의 고정 함수 참조를 보관하며 상위 호출자가 그 수명을 소유한다. 실제 화면 구독은 현재 view에1개다. 새 등록은 이전 등록을 대체하고 불투명 등록 객체로 비교한다. 옛 unsubscribe는 새 등록에 영향0이다. unsubscribe 자체는 화면 detach/호출 cancel/retainer close/새 요청을 수행하지 않는다. 재구독은 이미 갱신된 현재 snapshot을 읽으며 추가 Request0이다. subscribe 뒤 snapshot을 읽는 순서로 등록 사이 변화도 확인한다.

getSnapshot은 미리 게시한 불변 값의 참조만 반환한다. 내부 함수 호출·Promise 등록·새 객체/clone·타이머·cancel/reap가 없다. 변화가 없으면 같은 참조이며 SSR용 값이 필요하면 고정된 빈/미지원 snapshot을 제공한다. React나 window를 runtime import하지 않는다. 실제 useSyncExternalStore/hook 설치는 다음 범위가 아니다.

새 표시 후보는 렌더 밖의 명시 동작/frame 갱신/실제 완료 통지 때 기존 retainer.display와 ticket으로 확인한다. 정상 결과는 기존 양쪽 I/O 종료·정리 성공 후에만 후보가 된다. 빠른 오류에도 현재 ticket/frame을 적용한다. 원래 DTO를 다시 해독하거나 새 사실 확인 필드를 만들지 않는다. 게시한 결과 사본은 중첩 값까지 외부에서 바꿀 수 없게 유지하고 현재 view용1개만 보관한다. 과거 회사/결과 이력 cache는 없다.

순수 snapshot은 “마지막 관측”이다. 그 자체로 fresh canForget이나 새 호출 admission을 허가하지 않는다. prepare/release는 매번 기존 retainer의 신선한 검사를 통과한다. 외부 변화가 없는 상태에서 arbitrary 주입 포트의 미래 상태 변화까지 실시간 보장하지 않는다.

현재 render의 props가 post-commit frame보다 먼저 바뀔 수 있다. 화면 소비자는 캐시한 후보와 현재 token/ticket·snapshot/선택·열림/편집/차단 상태를 기존 순수 ticket.isCurrent로 대조한 경우에만 표시한다. 이 순수 선택 함수도 Request.inspect/display를 호출하지 않는다. mismatch는 공유된 빈 표시를 반환하고 effect 이전에도 이전 exact/오류를 숨긴다. commitFrame은 snapshot 참조를 보존하되 비교할 scalar/선택을 고정하며, 틀린 입력/닫힘/편집은 후보를 폐기하고 자기 호출을 취소한다. 이미 폐기한 후보를 원래 값으로 되돌렸다는 이유만으로 부활시키지 않는다.

통지 중 재진입한 prepare/start는 고정 BUSY로 거절하며 자동 재실행하지 않는다. detach/cancel/close 의도는 현재 표시를 즉시 무효화하고 안전한 시점에 기존 retainer에 반영한다. listener 교체/해제는 등록 동일성으로 적용한다. UI listener throw는 그 등록을 해제하고 고정 통지 실패 상태만 남기며 raw 오류/stack을 표시하지 않는다. 원래 보관자는 계속 살아 있고 다른 화면이 명시적으로 다시 연결할 수 있다. 새 연결은 미종료 슬롯을 지우지 않는다.

## 7. 정리 책임·권한·검증 범위

구독 해제는 UI listener 수명, detach는 해당 화면의 표시/취소 수명, canForget은 원래 요청/응답 I/O 보관 조건, SQL/guard/lease·pending command/cleanupRequired는 같은 service 수명이다. 네 가지를 합치지 않는다. snapshot의 closed/empty는 서버 retire/ack/hold 해제를 뜻하지 않는다. 새 화면 연결에는 해당 서버 명령 포트를 주입하지 않는다.
