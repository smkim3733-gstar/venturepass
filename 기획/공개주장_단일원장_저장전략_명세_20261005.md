금액은 기존 provider scope의 revision/head·cap·recognized/held를 이어받는다. scope 이름에 candidate가 있어도 새 목적을 별도 scope로 만들어 가용액을 늘리지 않는다. 전환은 기존 전체 원장/coverage 감사와 모든 과거 비용 실행의 종료·정산이 선행돼야 한다. 잠정 v10은 과거 prefix를 동결하고 비교 목적의 suffix만 쓰는 제한 확장이다. 전환 후 기존 generation/review 비용 실행의 새 쓰기는 명시 미지원이며, 현재 v9 기능을 이 문서로 바꾸지는 않았다. 과거 원장 행을 필터링하거나 해시/순번을 고쳐 기존 파서에 맞추지 않는다. 기존 완료 기록 읽기와 일반 품질 평가 데이터는 보존한다.

전송 직전에는 단일 실행 owner가 기존 quality writer 잠금과 회사 DB의 BEGIN IMMEDIATE를 정해진 순서로 짧게 잡고 양쪽 상태를 다시 확인한다. 영속 승인/예약/dispatch 기록은 quality DB에만 쓰고 회사 DB에서는 SELECT만 수행한다. 새 dispatch COMMIT을 관측한 호출만 owner를 받으며 실제 fetch hook 안에서 원래 request/회사 hash·승인 만료/예산 head·설정을 동기 대조한다. await 전에 잠금을 풀고, 이미 시작된 요청은 후속 COMMIT 오류로 재전송하지 않는다. DB 둘의 원자적 COMMIT이나 HTTP 전송의 원자성을 가정하지 않는다. SQLite 공식 거래/WAL 문서의 writer 잠금·복수 DB 원자성 범위도 확인했으나 현재 앱 실행 검증은 아니다.

원래 nonce 재호출은 현재 회사/키/설정 검사보다 먼저 원장을 감사해 원래 기록만 반환한다. 다른 명령이면 거절하고 replay에서 owner를 다시 만들지 않는다. 전송 이후 불명/usage 누락·모델 불일치·회사 변경에도 응답 캡처를 먼저 보존하며 비용을0으로 놓거나 예약을 자동 해제하지 않는다. 공급자 비용 정산과 비교 의견의 현재 유효성은 분리한다. 냉시작에서 dispatch 기록만 남으면 새 전송 없이 미확인 보류로 유지한다.

백업은 구조/원문 증거이며 실행 권한이 아니다. v10 coverage는 전환 전 전체 prefix·DB 인스턴스·예산 head를 고정하고, 기존 외부 제어 기록/lease 방식은 DB 복원·교체를 감지하는 증인으로만 확장한다. 승인/금액을 외부 파일에서 다시 계산하거나 DB 누락 행을 재생성하지 않는다. 복원/이동 후에는 조회·캡처 복구만 허용하고 새 전송은 운영 대조 전 차단한다. 기존 운영 검증의 고정 DB/control/lock과 소모된 두 실행은 건드리지 않는다. 서로 다른 data root의 비용을 자동 합치거나 새 DB의 빈 예산을 기존 사용량0으로 해석하지 않는다.

## 확정한 구현 방향과 제한

이 문서는 구현할 저장 계약을 정한다. 현재 제품의 SQL 형식은9이며 아래 v10/새 행/guard는 아직 구현하거나 운영 적용하지 않았다. 비교용 별도 DB나 금액 원장을 만드는 방안, studio와 quality의 양쪽 쓰기를 하나의 COMMIT으로 취급하는 방안은 채택하지 않는다.

기존 provider 금액 scope는 이름을 그대로 보존한다. 비교는 새 목적일 뿐 기존 실행 승인으로 전송할 수 없다. 이 설계에서 “단일 권한”은 quality DB의 감사된 run/승인/예약/dispatch만 전송 owner를 만들 수 있다는 뜻이다. 회사 잠금과 외부 제어 증인은 전송을 거절할 수 있지만 독립 실행 권한은 만들지 않는다.

초기 v10 전환은 모든 기존 actual/provider 실행이 terminal이고 미정산/held가0인 경우만 허용한다. 중단/미확인 실행을 v10으로 옮겨 정산하거나 강제 완료하지 않는다. v10에서는 과거 비용 prefix의 새 generation/review 실행·정책 변경/추가 예산 초기화를 지원하지 않는다. 기존 완료 이력/nonce 읽기와 일반 수동 품질 평가는 유지한다. 이 제한은 과거 해시/프롬프트를 동결하고 새 비교를 같은 금액 체인에 넣기 위한 초기 지원 범위다. 나중에 두 목적의 쓰기를 함께 지원하려면 별도 계약 검증이 필요하다. 현재 v9 writer를 이번 문서로 비활성화한 것은 아니다.

## 같은 예산 체인의 연속성

대상 data root의 기존 quality.sqlite 안에서 production은 candidate-quality-provider-v2-live, synthetic은 candidate-quality-provider-v2-synthetic을 유지한다. 통화/정수 단위/상한을 변환하거나 configure를 다시 넣지 않는다. 데이터 경로가 다르면 같은 scope 문자열만으로 같은 돈 원장이 아니다. 고정 operational-validation DB의 USD0.402573/held0/cap15는 그 경로의 과거 사실이고 고객 data root에 자동 복사할 잔액이 아니다. 실제 목적별 활성화 전에 원래 경로/인스턴스와 누적 비용의 운영 대조가 필요하며 이번에는 경로를 설정하지 않는다.

전환 coverage의 prefix는 기존 전체 archive validator로 그대로 감사하고 getProviderExecutionBudgetSnapshot의 cap/recognized/held/reservations/head를 재사용한다. 최초 비교 event는 그 head 다음 revision에 연결된다. 새 schemaVersion3 event는 다음3종만 필요하다.

|release-comparison|아직 dispatch commit이 없고 같은 거래에서 취소를 확정한 경우만 전액 해제. reason not-dispatched|
|recognize-comparison-usage|정확한 dispatch/capture/usage assessment digest를 연결. 기존 정수 단위 계산과 consumed/released/boundExcess를 사용. 1회만 정산|

비교 단계의 token 측정/금액 평가 자체는4I7에서 만들지 않는다. 보고 usage를 금액 근거로 cast하지 않는다. typed 비용 근거가 없는 응답은 그대로 보류다. 모델 별칭/누락 usage=0/보고 등급=요청 등급을 추정하지 않는다. 비용 초과는 음수 잔액으로 숨기지 않고 boundBreached/deficit로 표시해 후속 예약을 차단한다.

prefix에서 빠진 행/중복 nonce·budget revision/head/전체순서 변경, prefix 이후 schemaVersion2 비용 쓰기, 다른 scope나purpose 혼입은 거절한다. prefix만 감사하거나 suffix만 감사한 결과를 전체 원장으로 반환하지 않는다. 중간 비교 이벤트를 지운 뒤 old validator용 순번/hash를 재작성하는 방식은 금지다.

## 회사/예산 상태와 실제 fetch 시작의 경계

회사 파일은 잠금 대조 대상이고 유일한 영속 실행 writer는 quality DB다. DB 단위 writer 잠금이므로 한 회사만 잠근다고 표현하지 않는다. 두 DB 동시 쓰기/ATTACH를 사용하지 않는다.

1. 원래 nonce를 전체 원장/coverage와 대조한다. 재호출은 원래 영수증만 돌려주고 새 owner/키 확인/회사 guard를 시작하지 않는다.
2. 새 명령은 현재 회사의4I2 요청 대조와 선택된 범위/모델/예산·보관 조건을 검토한다. 명시 동의 이후 원래 snapshot/manifest, 예약/run/영수증을 quality DB의 한 거래에 저장한다. 회사가 그 뒤 바뀌어도 자동 갱신하지 않는다.
3. dispatch 명령은 원래 승인/예약/현재 head·남은 슬롯을 다시 감사하고 dispatch event를 먼저 durable COMMIT한다. 이 COMMIT 성공을 관측한 현재 호출만 메모리 owner를 받는다. 응답 유실/replay/cold read는 owner 없음.
4. SDK 준비 후 실제 fetch hook에서 잠금 순서를 quality BEGIN IMMEDIATE → studio BEGIN IMMEDIATE로 고정한다. 반대 순서로 두 DB를 잡는 경로 금지. quality만 쓰는 기존 경로와 studio만 쓰는 경로는 다른 DB를 잡지 않는다.
5. 양쪽 잠금 안에서 DB 파일/루트 신원, 외부 lease와 witness, 원래 run/dispatch/승인 만료/금액 hold/currenthead, 회사 revision/claim history·실제 원고/선택 자료 hash, 설정/취소/시계를 다시 대조한다. StudioStore guard는 SELECT만 하며 run예약을 회사revision+1로 보정하지 않는다.
6. 정확한 SDK wire와 원래 rawBody가 같을 때 한 번만 fetch를 동기로 호출한다. 이 콜백/guard에 await·사용자 공급 함수·writer 재진입 금지. promise/rejection handler와 capture 소유권을 잡은 뒤 studio → quality 순서로 거래를 끝내고 잠금 밖에서 await한다.
7. 잠금 종료/COMMIT 실패가 start 뒤에 나면 이미 시작한 요청을 취소됐다고 단정하지 않는다. promise와 최초 동기 capture를 보존하고 기록만 복구한다. start 전 실패면 전송0이지만 dispatch 영속기록은 남으므로 냉시작에서 미전송을 추정하지 않는다.

SQLite 공식 문서는 한 DB에 동시 writer1개, BEGIN IMMEDIATE의 즉시 writer 거래/SQLITE_BUSY와 WAL의 복수 DB 전체 원자성 한계를 명시한다. 이 사실을 바탕으로 위 guard를 설계했으며 동시 writer 배제는 파일을 제멋대로 교체하는 행위나 전원 차단 후 HTTP 상태까지 보장하지 않는다. 경로 신원/복원 marker·multi-process 합성 검증이 별도로 필요하다. 참고: [Transaction](https://www.sqlite.org/lang_transaction.html), [Write-Ahead Logging](https://www.sqlite.org/wal.html), 확인2026-10-05. 이번은 공식 문서 읽기이며 앱 HTTP/운영 검증이 아니다.

회사 guard의 새 함수는 호출자가 이미 연 거래 안에서 다시 BEGIN하지 않도록 전용 진입을 둔다. timeout/busy/취소는 재시도 없이 종료한다. guard의 BEGIN IMMEDIATE 자체는 쓰기 거래 잠금이며 “DB를 readOnly로 열었다”는 뜻이 아니다. 회사 row/DDL 변경0을 검증 대상으로 한다.

## 실패·재시작·늦은 응답

|상황|보존/후속|
|---|---|
|예약 COMMIT 결과 미관측|원래 nonce만 조회. 미확인을 새 run으로 대체하지 않음|
|dispatch COMMIT 이전 확정 취소|동일 quality 거래에서 cancel+정확한 hold 해제. 전송0|
|dispatch COMMIT 오류/응답 유실|새 owner0, 원래 영수증 감사. 기록 존재 시 재전송0/hold 유지|
|dispatch 기록 후 프로세스 종료|실제 send 여부 미확인. 자동 재시도/나이·PID로 해제0|
|start 이전 guard 거절|현 owner의 not-started 증거는 retain 가능. 냉시작에서 이를 추정하지 않음. 초기 지원은 hold 유지; 자동 release 구현 없음|
|start 이후 오류/timeout/응답 소실|미확인 비용 보류. 클라이언트 취소는 무청구/미전송 증거 아님|
|응답은 왔으나 현재 회사가 변경됨|capture 우선 영속화, 비교 의견은 stale/null. 원래 요청에 대한 usage 정산 가능 여부는 독립 판정|
|capture persist COMMIT 오류|원래 capture digest/nonce로 GET·동일 기록 persist만 복구. 원문을 재생성하지 않음|
|응답 refusal/불완전/모델 불일치|capture·보고 usage 보존, 비교 null. 비용 규칙의 증거가 부족하면 hold 유지|
|정산 뒤 비교 JSON/인용 실패|정산을 취소하거나 비용을0으로 돌리지 않음. 의견 실패와 비용 상태 분리|
|같은 nonce에 다른 입력/capture|변경 거절. 원래 승인/결과를 교체하지 않음|

공급된4I5 JSON은 실제 실행 증거가 아니다. 외부 호출 route에 raw supplied capture를 받아 사용량/비용을 기록하는 기능은 만들지 않는다. 실제 owner가 최초로 관측한 response와 supplied 어댑터의 출처 표시를 별도로 유지한다. 기존4I5 adapter/false authority를 true로 바꾸는 방식으로 전송 이력을 만들지 않는다.

결과 저장은 수동 claim judgement/원고/source 자동 수정이 아니다. 현재 회사가 삭제/변경돼도 원래 run의 캡처·비용 감사는 가능해야 한다. 조회 시 현재 적용 가능성은 별도로 표시한다.

## 마이그레이션·백업·복원의 완료 조건

v10은 현재 생성자에서 자동 승격하지 않는다. 검증된 새 migration을 명시 호출하는 단계까지는 pure contract만 만든다.

1. 중단된 lease/미확인 실행/hold 또는 unknown schema가 있으면 전환 거절. 회사/quality DB와 기존 운영 서버를 자동 종료하거나 복구하지 않는다.
2. 같은 quality write transaction 안에서 v9 전체 schema/모든 row/coverage를 감사하고, 삽입 순서·원문 body/blob/hash 및 각 budget prefix의 revision/head/잔액을 고정한 purpose coverage를 생성한다.
3. 새 coverage 테이블·immutable trigger·quality-v10 writer gate만 추가/교체한다. old body/blob/hash·nonce·approval·artifact·budget events는 단1byte도 재직렬화하지 않는다. 완료 prefix의 원래 logical digest 검증은 계속 가능해야 한다.
4. 새 inspection이 같은 transaction에서 전체 v10을 감사한 후COMMIT. 실패/디스크full/busy/미관측COMMIT은 원래 상태 또는 완전한 v10 중 하나로만 관측돼야 한다. 부분표/coverage 소실 때 자동 생성 금지.
5. 백업 manifest version10은 원래 행 수/hash·prefix coverage/전체 logical digest를 포함하고 기존 v1~v9 reader/manifest 해석은 보존한다. v10에 v9 writer를 연결하면 SQL gate/검사에서 거절해야 한다.
6. 회사/quality 백업은 각기 다른 시점이다. 회사 원문 hash가 다르면 새 전송을 막고 과거 의견을 현재 결과로 적용하지 않는다. 두 파일의 백업 완료만으로 결합 snapshot이라 하지 않는다.
7. 복원본의 marker 해제는 구조 검증 완료일 뿐 send 활성화가 아니다. 기존 제어 기록의 DB 신원/현재 head와 다르면 새 전송 불가. old backup에 존재하지 않는 최신 dispatch/비용을 witness로 재생성하거나 cap을 새로 configure하지 않는다.

외부 제어 기록은 기존 journal의 배타lease/양쪽 사본/DB신원/command-intent→DBreceipt-ack 패턴을 목적별 버전으로 확장한다. 새 독립 승인/돈 원장이 아니다. intent가 DB에 없거나 ack가 손실됐으면 원래 DB 영수증을 대조할 뿐 전송을 재개하지 않는다. 제어 파일은 run/command/receipt/head digest와 신원만 보관하며 선택 본문·키는 보관하지 않는다. 새 profile 설정/마이그레이션도 후속 구현이고 현재 고정 operational-validation 파일을 재사용해 비교를 승인하지 않는다.

DB복원/이동 후 runtime authority는 기본 폐쇄다. 현재 DB와 제어 증인의 일치·소모 내역·미확인 상태를 운영 대조하기 전 fresh nonce라도 새 전송을 허용하지 않는다. 모든 DB/control 사본이 함께 과거로 되돌아간 악의적 복제까지 로컬해시가 막는다고 보장하지 않는다.

## 다음4I7 — 순수 저장 계약/예산 전환 감사

한 구현 단위는 다음을 함께 마감한다. 새로운 화면/파서/실행기를 복제하지 않는다.

- 입력: 이미 읽은 v9 원장의 정확한 행 벡터(key/body/body_hash 및 artifact bytes/hash/순서), 해독된 도메인 원장/기존 coverage, 명시 환경/기존 scope, DB인스턴스 식별자, schemaVersion3 비교 event/receipt 사본. 파일 경로/DB핸들/키/SDK/현재시간 자동 읽기 없음. 행 벡터와 해독 사본의 일치를 검사한다. 제공된 DB인스턴스/schema 식별자는 실제 파일 신원/DDL 감사 증거가 아니다.
- create/inspect purpose coverage: 기존 frozen 도메인 원장/예약·전송 coverage validator를 재사용해 전환 전 terminal/settled·prefix 원문/순서/nonce/용량을 고정한다. SQL DDL/integrity/path의 실제 감사는 후속 migration 거래 안의 기존 DB inspector가 담당한다. 순수 계약만으로 전체 DB 감사 완료라 하지 않는다. 출력은 pure proposal이며 migration committed/approval/dispatch는false.
- 동일 budget scope의 원래 head에서 비교 suffix를 fold한다. 기존 prefix 계산은 frozen 함수, suffix의 금액은 BigInt이며 reserve/release/recognized 증거·CAS/상한/중복/정산1회/미확인 hold를 확인한다.
- 전체 nonce는 과거 평가/candidate/execution/policy/native receipts까지 대조한다. 원래 명령 digest가 같을 때만 과거 결과 재현, 다른 입력은 거절. 비교가 아닌 prefix 이후 돈 이벤트는 명시 미지원.
- 새 합성 시험: 비어 있지 않은 비용 prefix 보존, 신규·기존 schema 혼합 경계, 불명/held 차단, 순번/해시/nonce/coverage 변조, 중복예약/정산·초과·용량·반환사본, old pure 함수 결과 동등성. 과거 corpus 의미 품질이나 실제 SDK로 집계하지 않는다.
- DB/DDL/constructor/writer/backup 실행·route/UI·실제 비용 설정은 미실행. 준비된 순수 계약/시험을 검토한 다음 DB integration과 실패 주입을 진행한다.

그다음 저장 구현 완료에는 v1~v9 bytes golden·v10 migration 실패 주입/재열기·명시 old writer 거절·동일nonce 경쟁·회사/금액 writer 경쟁·capture 늦은 저장·복원된 오래된 dispatch 재전송0이 필요하다. 이번 문서로 이 시험을 통과했다고 세지 않는다. 실제 전송 활성화는 모델/조건/가격·보관/예산·목적별 사용자 동의가 준비된 뒤 별도로 다룬다.
