# 벤처인 인증 화면 읽기 점검 — 2026-10-05

## 범위와 수치

사용자가 기존 처리 회사 한 곳을 선택해 공식 창에서 직접 로그인했고, 이 회사가 혁신성장유형으로 확인받았다고 알렸다. 사전에 승인한 읽기 점검을 이어갔다. 암호·인증번호 입력/수집은 하지 않았다. Codex 내장 브라우저의 공식 MY벤처현황을 읽었으며 VenturePass 앱의 별도 Edge runner를 실행하거나 계정/고객 DB를 연결하지 않았다.

1/5는 사용자 직접 로그인 후의 실환경 접근 증거다. 제품의 credential runner 자동 로그인이나 지정 로컬 회사와 사업자번호를 비교하는 기능을 검증한 수치가 아니다. 진행/결과를 화면에서 읽었더라도 원래 로컬 신청 회차와의 정확한 연결·자동 수집을 검증하지 않았으므로 나머지 단계는 완료 처리하지 않는다.

## 실제로 확인한 구조

열람 목적지는 공식 홈과 MY벤처현황이다. 기록 URL은 [공식 MY벤처현황](https://www.smes.go.kr/venturein/myVntr/viewMyVntr)처럼 origin/path만 남긴다. 고객명, 사업자번호, 계정, 담당자 연락처, 신청/확인서 번호 값, 실제 날짜, 쿠키, URL query, 화면 원문 캡처는 이 문서/시험 fixture에 남기지 않는다.

### 1. 인증 표시

상단에는 '로그인'이 남아 있는 동안 모바일 주 메뉴에는 '마이페이지'와 '로그아웃'이 있었다. 마이페이지에서 기업정보·실제 신청 이력이 표시됐다. 따라서 상단 문구 하나만으로 로그아웃/로그인 성공을 추론해서는 안 된다. 기존 runner의 모바일 메뉴·로그아웃 검사 경로를 먼저 재사용하고 약화하지 않는다.

기업정보 표의 표제는 개인사업자 회원정보이며 기업명, 사업자등록번호, 설립일, 업종 등의 라벨을 제공한다. 해당 표에는 연락처/담당자 개인정보도 있으므로 표 전체 본문 수집은 하지 않는다. 기존 companyLabels/verifyVentureCompany의 최소 회사 식별 비교를 재사용할 수 있으나 이번 점검에서는 고객 값을 로컬 회사 DB와 대조하지 않았다.

### 2. 진행 상태

'2. 벤처확인 진행상태'의 다음 board_write_box 안에 process_flow 순서 목록이 있으며 최상위 진행 항목은 다음 5개다.

1. 서류검토 및 보완완료 — 신청완료일 표기.
2. 접수완료(수수료 결제) 및 유형별 전문평가기관 배정 — 결제요청일/접수일 표기.
3. 전문평가기관의 서류평가 및 현장 실제 조사 — 평가기관, 최초/연장 예상기간, 평가완료일 표기.
4. 벤처기업확인위원회 사전검토 및 최종심의 — 사전검토기간/심의예정일 표기.
5. 공시 — 공시일 표기.

진행 항목의 class on과 날짜/내용 표시를 관측했다. 날짜가 빈 항목도 있다. on을 곧바로 완료/접수 성공으로 해석하거나 빈 날짜를 미실행으로 판단하지 않는다. 중첩 li는 날짜 설명이므로 모든 li를 진행 단계로 세지 않는다. 이 진행 영역이 어느 신청번호를 가리키는지 명시적으로 연결하지 못한 상태에서 특정 회차에 귀속하면 안 된다.

### 3. 신청 심의결과

계정의 신청 이력에는 2개 행과 서로 다른 '확인'/'탈락' 표시가 있었다. 고객의 전체 이력을 하나의 성공/실패로 합치거나 배열 첫 행·날짜 하나만으로 목표 회차를 고르지 않는다.

요약 화면의 머리글은 9개: No, 신청번호, 신청일자, 통지완료일자, 이의신청가능기간, 결과, 결과확인, 이의신청, 결제정보.
확인서 상세 이력을 펼친 화면의 머리글은 8개이며 이의신청가능기간 열이 없다. 결과 열의 위치가 달라진다. caption의 오래된 설명과 현재 th 목록도 동일하지 않다. 현재 표시된 머리글·행의 일치부터 확인해야 한다.

'결제영수증', '탈락사유 보기', '이의신청' 버튼이 있으나 이번에 열거나 실행하지 않았다. 결제영수증이 존재한다는 사실을 기관 접수증 수집이나 이번 결제 완료로 기록하지 않는다.

### 4. 확인서 이력

'벤처기업 확인 이력 및 확인서 출력·재발급·취소·상세내용' 링크로 같은 MY벤처현황의 확장 표시를 열었다. 확인 이력에서 혁신성장유형 1건을 확인했다. 발급일/유효기간/벤처확인발급번호/최초확인일/변경사항/신청내역보기/취소일/출력 열이 있다. 값은 보관하지 않는다.

이 표는 머리글 table과 board_list_scroll의 내용 table이 분리돼 있으며 양쪽 caption이 같다. 머리글은 끝의 빈 칸까지 11개, 내용 행은 10칸이었다. 단순 table별 조회, caption만으로 중복 행 처리, 모든 표의 같은 위치 결합은 오독 위험이 있다. 같은 의미 영역의 명시적인 표 쌍만 연결하고, 확인한 끝의 빈 머리글 차이 외 불일치는 미확인으로 남겨야 한다.

재발급, 영/중문 발급, 정보변경, 취소 대상 이력도 별도 영역이다. 일부 표의 단일 안내 행은 실제 이력 1건을 의미하지 않는다. 이번에 각 빈 상태의 상세 문구/rowspan·colspan 계약을 모두 확인한 것은 아니므로 해당 영역을 지원 완료로 선언하지 않는다.

## 미확인 상세와 수행하지 않은 동작

확인 이력의 '신청내역보기' 열에 있는 '보기'를 한 번 눌렀다. 연결된 브라우저에서는 새 화면·탭·dialog가 관측되지 않았다. 수집 가능한 error 로그에도 오류 항목은 없었다. 이 사실만으로 팝업 차단/사이트 오류/권한 부족 중 하나를 원인으로 확정하지 않는다. 사용자에게 같은 '보기'를 직접 열 수 있는지 요청했다. 열리지 않은 신청내역의 본문/파일 제한·입력 양식/최종 제출 방식을 추정하지 않는다.

출력·재발급·취소·이의신청·결제영수증 버튼은 실행하지 않았다. 신청을 새로 시작하거나 기존 자료/필드/첨부를 변경하지 않았다. 고객 서버/DB·원장·키 변경0, 실제 신청·납부·서명·유료 AI 0, 새 채팅/하위 에이전트0이다. 공식 웹 탐색은 읽기 화면을 표시하는 요청이며 로그인 자체는 사용자가 수행했다. 사이트 내부의 접근 로그까지 불변이라고 주장하지 않는다.

## 기존 구현과 다음 독립 개발

- 기존 venturein-inspection-collector는 필드 메타데이터와 제한된 회사 식별 근거를 읽는다. 이번 진행/결과 표는 일반 입력 필드가 아니므로 현재 수집기가 자동으로 지원한다고 주장하지 않는다.
- 기존 venturein-workflow 관측 POST는 DB snapshot을 쓴다. 이번 무쓰기 점검에서 호출하지 않았다.
- 기존 수동 application/agency 기록의 officialVerification:unverified와 lastCheckedAt:null을 이번 브라우저 읽기로 수정하지 않는다.
- 원래 회사/계정·현재 document/revision·원래 요청 대조와 늦은 응답 처리 경계를 재사용한다. 새 읽기 결과는 전송 동의나 신청 성공 영수증이 아니다.

다음 4G5b는 이번에 확인한 MY벤처현황의 읽기 결과를 위한 제한된 어댑터부터 구현한다. 회사 식별 검사와 현재 화면 신원 검사를 재사용하고, 8/9열 신청결과와 분리된 확인서 표를 정확히 구분한다. 신청번호/확인서 번호를 별도 신원으로 보존하며, 예상 신청번호가 없거나 중복/열 불일치/회사 변경/진행 영역 귀속 불명인 경우 자동 연결하지 않는다. '확인'을 새 제출 성공이나 현재 유효한 확인서라고 단정하지 않는다.

첫 검증은 새로 만든 합성 값만 사용한다. 실제 고객 원문/번호/날짜를 복사하거나 치환한 fixture를 만들지 않는다. 공급 원문을 공식 관측 증거로 승격하지 않으며 처음부터 결과 DB writer/자동 polling/제출 core를 만들지 않는다. 이 독립 개발에는 추가 실제 인증·고객 전송·유료 호출이 필요하지 않으므로 자동후속 ACTIVE로 재개할 수 있다. 실제 상세가 열리면 읽기 근거를 보완하되 그 응답을 기다리느라 다른 독립 작업을 멈추지 않는다.

최종 제출과 공식 접수증의 실제 동작, 첨부 반영과 회차 귀속의 종단 검증은 여전히 남는다. 공식 지원/API·자동화 허용 여부도 이번 UI 읽기로 확정하지 않는다.
