# 공개 주장 — 실행 보관과 SQL13 후속 인계 계약 (4I29)

고정20개 기능 기준15/20=75%, 미완료5/20=25%, 직전 대비+0%p. 이번4I29는 비활성 실행 보관과 SQL13 판정·정산·종료 인계 계약 점검1건이며 제품 소스 변경0개다. 신규 제품 시험0/0(미실행), 기존 회귀 재실행0·새 앱 HTTP/브라우저/lint/typecheck/빌드0회다. 과거4I28 신규22+기존8=30/30·YnPUPZ와4I26 92/92·PtzDZJ는 별도이며 재실행/합산하지 않는다. 백업27개 DESTINATION_REPOSITORY 제한은 미해결·이번 미실행이다. 실환경1/5=20%는 과거 사용자 직접 인증/접근이며 앱 자동실행 성공0단계·KOSIS 실제0/1이다. 필수 결정0개, 다음4I30 postcapture 미리보기·명시 저장·복구의 비활성 서비스 연결3~6시간(잠정), 전체 완료시간 미정, 자동후속 ACTIVE.

기준 커밋은 4I28의 17b712c다. 이 문서는 제품 코드 실행 없이 기존 소스에 대조한 연결 계약이다. 아래 제안 포트와 후속 저장 수명은 다음4I30 구현 대상이며 이번에 구현하거나 시험하지 않았다.

## 2. 원래 응답에서 계산하는 검토안

원래 session의 SQL13 전체 snapshot을 기존 reader/inspector로 감사한다. 선택한 run과 전송 binding의 원래 dispatch 명령 digest를 대조한다. response-captured event와 comparison-response/context artifact의 canonical bytes·hash·size, 원래 request/identity, 예약/금액 scope, binding3/4 및 모든 영수증을 함께 감사하며 선택한 한 행만 읽어 성공으로 표시하지 않는다.

createComparisonPostcapturePreview의 현재 반환은 responseArtifactSha256/ByteLength, expectedValidatedArtifactSha256, comparisonState, usage(status/reasons/assessment/usagePolicyDigest), expectedAssessmentDigest다. source는 supplied-postcapture-plan, owner:null과 authority:false다. preview 자체에는 run/budget head나 comparison event를 모두 담고 있지 않으므로 후속 서비스가 같은 감사 snapshot의 기존 필드로 좁은 선택 검토안을 구성한다. raw response/context·전체 원장·DB 경로·내부 해제 값은 반환하지 않는다.

비교 결과는 inspectArchivedPublicClaimRequest → derivePublicComparisonCapturedResult → 기존 decodePublicClaimCapturedOutput/validatePreparedPublicClaimComparison으로 재계산한다. 저장 validated 본문은 supplied-response/manual-unverified·currentContextVerified:false다. comparison-ready는 원래 선택/인용과의 구조 대조 결과이며 현재 회사 적용성·AI 의미 품질·공식 사실 검증이 아니다. refusal/불완전/모델·인용 불일치의 기존 상태를 그대로 보관한다.

사용량은 binding4.approvedReview의 고정 usagePolicy와 원래 예약 financialBasis를 assessComparisonUsage에 넘긴다. 현재 시각/새 가격으로 바꾸지 않고 binding.recordedAt의 전송 시점 유효성을 재검사한다. 정책의 requestedTier:null, 요청v1의 네 옵션 생략, 모델/등급 mapping·캐시/구간·출처 digest/기한을 그대로 대조한다. 숫자 정규화/BigInt category별 올림은 기존 assessProviderUsageScalars를 재사용한다. 이미 dispatch된 binding3에는 정책을 소급 부착하지 않는다.

## 3. 명시 저장 입력과 정확한 행

두 명령 모두 commandVersion1/purpose compare-public-claim, clientRequestId/runId/transmissionBindingDigest/dispatchEventDigest/responseArtifactSha256/expectedRunHead를 갖고 strict parser와 8KiB 명령 한도를 유지한다.

| 명령 | 추가 필드와 신규 기록 입력 | 쓰기 결과 |
|---|---|---|
| record-public-comparison-result | responseArtifactByteLength, expectedValidatedArtifactSha256. current는 at/eventId만 | 기존 비교 decoder가 생성한 validated artifact + comparison-recorded event/receipt의 3행 |
| settle-finalize-public-comparison | comparisonEventDigest, usagePolicyDigest, expectedAssessmentDigest, expectedBudgetHead. current는 at/usageEventId/usageNonce/costEventId/budgetEventId/finalEventId/finalizationNonce만 | usage event/receipt2 + 같은 scope budget event/cost event/receipt3 + final artifact/event/receipt3, 한 거래의 8행 |

result와 close는 별도 명시 호출이다. preview나 record-result 성공이 close를 자동 호출하지 않는다. 사용자 nonce는 result에서는 비교 영수증, close에서는 cost 영수증을 소유한다. usage/final 내부 nonce와 새 ID는 기존 전역 충돌 검사로 대조한다. 원래 명령뿐 아니라 최초 시도에 고정한 current/내부 nonce/시각/행 bytes도 복구 책임에 보관하고 새 시도 값으로 교체하지 않는다.

planner는 전체 감사 → strict 명령 → 원래 nonce/전체 값 대조를 current 검사보다 먼저 한다. 정확한 replay는 원래 recordedRows/명령·영수증을 반환하고 rows:null·새 행0이다. 같은 nonce의 다른 목적/hash/head/정책 또는 내부/legacy nonce 사용은 충돌이다. 새로운 result는 원래 run head와 응답 크기/예상 validated hash를, 새로운 close는 원래 comparison event와 usage 직전 run head/금액 이전 head·정책/assessment를 검사한다. preview가 stale해지면 자동 최신 head 대입 없이 거절한다.

result3행과 close8행은 기존 exact table/SQL value/BLOB/순서/행 수 gate·전체 사후 감사 아래 저장한다. close의 usage→cost→final은 같은 run의 연속 revision/previousDigest와 같은 recordedAt이어야 한다. final 공간이 부족하면 정산만 따로 저장하지 않는다. SQL/파일 증인의 원자성을 주장하지 않는다.

## 4. 다음 비활성 서비스 포트와 수명

아래 이름은 제안이며 현재 API에는 없다. 기존 createIsolatedPublicComparisonService를 같은 모듈에서 확장하는 하나의 격리 단위로 구현한다. 새로운 전송 owner·별도 lease 프로토콜·전역 registry·생산 server import는 만들지 않는다.

| 제안 포트 | 입력/동작/반환 계약 |
|---|---|
| previewPostcapture(selection) | strict runId/dispatchCommandDigest만 받는다. 같은 session의 감사된 원래 binding/명령과 대조하고 해당 run의 좁은 검토안/DB 상태·head/hash·사용량을 반환. nonce/새 event ID 생성, SQL INSERT/증인 append0 |
| writePostcapture(operation, command, current) | operation은 record-result/settle-finalize만. 기존 strict 명령과 planner/private writer를 사용. 동일 원래 run 선택만 허용. 입력으로 결과 JSON/가격/정책/회사/금액/SDK/경로를 받지 않음 |
| recoverPostcapture(operation, originalCommand) | 정확한 원래 전체 명령을 먼저 감사. 기존 저장행 replay와 증인 ack 복구만 허용. current/새 ID/시계/driver 준비0, 새 INSERT0. 행이 없거나 다른 명령이면 재실행하지 않고 책임 보존 |
| inspect/retire | 기존 실행 상태를 보존하며 별도 postcapture 상태(미시도/검토/보관/blocked/recovery-required)를 좁게 표시. retire는 새 전송만 닫고 명시 저장·복구를 자동 실행하지 않음 |

진행 execution의 private canRelease가 false인 동안 postcapture의 snapshot/새 쓰기 인계를 닫는다. public phase나 caller의 boolean을 증거로 받지 않는다. 첫 응답이 SQL에 있어도 원래 I/O/driver/lease가 살아 있으면 기존 실행의 recover/finish를 먼저 마쳐야 한다. retire 후 execution 참조를 해제했을 때는 모듈 내부에서 확인한 종료 상태만 보존한다. 여기에 pending postcapture 명령/SQL·lease 정리 책임이 남아 있으면 서비스 전체 폐기를 완료로 표시하지 않는다.

초기 미사용 canRelease=true나 새 서비스의 ready만으로 저장 가능한 run이라고 추정하지 않는다. storage-only 재개방은 같은 경로 신원의 정상 session/기존 lease 획득·전체 SQL13/witness3 감사와 원래 dispatch digest/capture를 필요로 한다. 이후 명시 선택을 원래 run에 고정한다. 원래 execution 명령이 이미 있으면 그 run/digest에만 연결한다. 이미 고정한 선택을 다른 run으로 바꾸지 않는다. 다른 객체/프로세스가 원래 lease를 잡고 있으면 기존 beginComparisonStorageSession이 거절한다. 재개방은 runtime owner/driver를 복원하거나 execute를 호출하는 과정이 아니다.

실행 lease가 끝난 뒤 후속 저장이 사용하는 것은 기존 guardedWrite의 짧은 begin/end 저장 lease다. 같은 파일의 두 lease를 겹치거나 새 owner를 발급하지 않는다. preview의 읽기 session/거래와 checkpoint 검사는 같은 기존 private reader/helper를 사용하고 SQL rows/증인 기록은 바꾸지 않는다. 저장은 매번 transaction 안에서 다시 전체 감사하므로 미리보기 snapshot을 쓰기 허가로 재사용하지 않는다.

현재 공개 guardedWrite는 finally의 lease 정리 실패를 PUBLIC_COMPARISON_LEASE_CLEANUP_REQUIRED로 던진다. 후속 서비스는 예외/commitObserved만 보고 원래 객체를 버릴 수 없다. 같은 모듈의 기존 begin/end/write/reconcile 본문을 재사용해 자기 호출의 획득 여부·SQL 종료 여부·미종료 lease를 비공개로 추적한다. 이전 실행이나 경쟁 호출의 lease를 소유한 것처럼 정리하지 않는다. 필요한 내부 공통화만 하고 외부 transaction/callback/boolean 권한 인수를 추가하지 않는다.

## 5. 복구 순서와 보관 책임

1. 전체 감사에서 원래 nonce가 신규임을 확인한 뒤 명령의 전체 값과 원래 current/내부 nonce를 최초 저장 전에 한 번 고정한다. 원래 nonce replay는 current를 읽기 전에 반환한다. 성공/blocked/error와 SQL COMMIT 관측, witnessMatched, lease 정리를 독립적으로 보존한다.
2. COMMIT 반환 유실/ack 실패는 원래 명령을 prepareComparisonV4StorageCommand의 전체 감사/replay 경로로 먼저 확인한다. 원래 기록이 없는 상태에서 writeGuardedPublicComparisonV13을 복구 명목으로 다시 호출해 신규 행을 만들지 않는다.
3. 정확한 replay라도 witnessMatched:false이면 구조 조회만 성공한 것이다. 기존 reconcilePublicComparisonStorageWitnessV3의 same-session 재대조로 정확한 행/inventory를 확인하고 ack 파일만 복구한다. 다시 원래 명령/증인 일치를 확인한 뒤 저장 관측을 표시한다.
4. intent-only·부분 사본·부분3/8행·원문/정책 충돌·DB 되돌림·원래 lease 미종료는 복구 필요를 유지한다. 새 nonce/행 재삽입/금액 재생성·hold 임의 해제·자동 재전송은 없다.
5. 자기 후속 저장의 읽기/SQL/lease 종료 실패도 원래 명령과 정리 책임을 보존한다. 정상 SQL 종료를 확인한 자기 lease만 기존 end helper로 명시 정리할 수 있다. 실패가 계속되면 새 호출/참조 폐기를 막는다. 시간/PID·단순 abort/retire로 파일을 지우지 않는다.
6. 프로세스 재시작에서는 메모리 원문/owner를 복원하지 않는다. 명시 원래 전체 명령과 저장된 행·증인만 감사한다. 남은 lease나 intent-only를 자동 해제하지 않으며 이 격리 재열기를 일반 백업/전원차단 복구 성공으로 보고하지 않는다.

replay의 commitObserved:false는 과거 쓰기가 없었다는 뜻이 아니다. 현재 호출이 새 쓰기 COMMIT을 관측하지 않았다는 뜻이다. 반대로 write의 commitObserved:true는 해당 SQL 관측이며 사람 동의·공식 가격·실제 전송/청구·AI 의미 품질 인증이 아니다. 서비스 safe view에는 raw artifact/오류 cause·키/헤더/경로/내부 capability를 노출하지 않는다.
