# 기존 공개 근거 비교 예약의 실행 입력 준비

기존 SQL13 예약 한 건과 검토된 전송·사용량 정책을 대조해 실행 입력 JSON을 내보내는 운영 준비 명령이다. 명령 실행에 API 키가 필요하지 않다. 회사/원장/증인 기록을 읽고 잠금을 해제한 뒤 새 출력 파일만 만든다. 예약·예산·정책·승인·DB 스키마·환경 설정은 생성하거나 수정하지 않는다.

## 필요한 기존 자료

- 자료 디렉터리의 `studio.sqlite`, `quality.sqlite`와 대응하는 증인 제어 디렉터리. 두 디렉터리는 같은 상위 폴더에 있어야 한다.
- 기록된 production/live DB UUID, 정확한 회사 UUID와 현재 revision. 기존 비교 예약 run UUID는 아래 회사별 조회에서 확인한다.
- 공식 근거를 검토한 정책 JSON 한 개. 최상위에는 `basis`, `usagePolicy` 두 필드만 허용한다. 각각 기존 `comparisonTransmissionBasisSchema`, `comparisonUsagePolicySchema`의 전체 내용이어야 한다. 이 도구가 가격·근거·모델 대응·해시를 만들어 주거나 supplied `official-reviewed` 표기만으로 검토 완료를 인정하지 않는다. 기존 예약의 금액 근거/요청 identity·출처/기한과 기존 감사 로직으로 대조한다.

실제 운영 자료가 준비되지 않았다면 합성 시험 데이터를 운영 정책으로 옮기지 않는다. 최신 가격·요금 조건·계정 사용 범위의 채택은 구체적 검토가 선행되어야 한다. 정책 파일과 출력에는 공개 발췌 및 내부 식별값이 들어갈 수 있으므로 Git에 넣지 않는다.

## 앱에서 실행 입력 파일 준비

기존 예약/취소/실행 연결의 정리 완료를 먼저 확인한다. **예약한 공개 근거 비교 실행 → 회사별 기존 예약 확인 → 기존 예약 목록 불러오기 → 살펴볼 기존 예약**에서 정확한 한 건을 고른다. 현재 회사 버전과 일치하고 조회 당시 기한 내이며 마지막 기록이 reserved인 경우 **선택한 예약의 입력 파일 준비**가 활성화된다. 이 표시는 실행 가능 판정이 아니며 서버가 현재 원장·회사·정책을 다시 감사한다.

운영자는 기존 DB 설정 3개(`VENTURE_DATA_DIR`, `VENTUREPASS_COMPARISON_EXECUTION_CONTROL_DIR`, `VENTUREPASS_COMPARISON_EXECUTION_DATABASE_ID`)와 함께 검토된 정책 파일의 절대 경로를 `VENTUREPASS_COMPARISON_INPUT_POLICY_FILE`로 명시한다. 정책은 위 `basis`·`usagePolicy` 형식이다. 새 예약용 `VENTUREPASS_COMPARISON_RESERVATION_POLICY_FILE`의 금융 근거 형식과 다르다. 파일은 128KiB 이하의 안정된 일반 파일이어야 하며 링크·하드링크·읽는 중 교체를 거절한다. 실제 정책 작성·검토·설정 활성화는 이번 개발에서 수행하지 않았다.

POST `/api/studio/cases/[caseId]/public-claim-comparison/input-preparation`은 loopback/동일 origin, 정확한 URL·JSON 8KiB/UTF-8·본문 종료를 확인하고 회사 UUID/revision/run UUID만 받는다. 브라우저가 정책·경로·금액·원고를 지정할 수 없다. 기존 `createComparisonInputPreparation`을 재사용하여 감사하고 원래 읽기 연결이 닫힌 뒤 구성/정책 SHA·기한을 다시 확인한다. 원고·발췌 본문 없이 기존 실행 입력 스키마의 JSON과 제한된 준비 메타데이터만 반환한다. 서버 파일·환경 설정·예산·승인·원장은 쓰지 않는다.

실패한 원래 정리 객체는 회사와 origin별로 보존한다(최대8). **준비 연결 정리**의 빈 DELETE는 설정이 철회돼도 같은 객체만 다시 닫는다. 미완료 자원을 새 객체로 교체하거나 잠금/증인을 복구하지 않는다. 정리 실패 시 파일은 제공하지 않는다. 응답 유실 시 자동 재시도하지 않으며 명시 정리 후 다시 준비할 수 있다. 준비는 예약/전송 쓰기가 아니다.

브라우저는 응답 크기·정확한 회사/revision/run·기한·UTF-8 SHA-256을 확인한 뒤 **입력 JSON 내려받기**를 제공한다. 클릭할 때 다시 기한을 확인하며 선택/회사/편집 상태 변경·화면 닫기·새로고침에는 준비 결과를 보관하지 않는다. 내려받은 파일에는 정책과 내부 식별값이 있으므로 Git에 넣지 않는다. 다운로드 완료는 운영 입력 활성화나 전송 승인이 아니다.

운영 담당자가 내려받은 파일을 검토하고, 기존 제어 디렉터리와 같은 상위 폴더의 **새 JSON 경로**에 별도로 배치한 후 `VENTUREPASS_COMPARISON_EXECUTION_INPUT_FILE`로 활성화한다. 기존 파일을 자동 교체하지 않는다. 이후 목록을 다시 불러 정확한 실행 입력 일치를 확인하고 기존 실행 화면에서 새 검토와 개별 동의를 진행한다. 준비 검토 기한이 지나거나 회사/정책이 바뀌면 다시 준비한다. 파일 자체는 실행 승인·키·nonce가 아니며 실행 시점 감사도 그대로 적용된다.

## CLI 실행

현재 PC의 `web`에서 먼저 도움말만 확인할 수 있다. 이 호출은 DB/SDK를 로드하지 않는다.

```powershell
node ../../.venturepass-local/toolchain/node_modules/pnpm/bin/pnpm.cjs comparison:prepare-input --help
```

다음은 자리표시자를 실제 검토된 경로/식별값으로 교체하는 명령 형식이다. 이 문서에 운영값이나 가상의 요금 정책을 제공하지 않는다.

먼저 해당 회사의 기존 예약을 조회한다. 이 단계에는 정책 파일·출력 파일·API 키가 필요하지 않다.

```powershell
node ../../.venturepass-local/toolchain/node_modules/pnpm/bin/pnpm.cjs comparison:prepare-input list `
  --data-root "<기존 자료 절대 경로>" `
  --control-dir "<기존 증인 제어 절대 경로>" `
  --database-id "<기존 DB UUID>" `
  --company-id "<회사 UUID>" `
  --company-revision "<현재 정수 revision>"
```

목록의 `reservations`에서 작성 항목(`sectionTitle`/`sectionKey`), 모델, 예약 당시 비용(`costs`), 생성/만료 시각과 마지막 기록(`latestEventKind`)을 확인한다. `reserved`는 예약 기록, `dispatch-recorded`/`dispatch-unknown`은 전송 기록/결과 미확인, `response-captured`/`comparison-recorded`는 응답/의견 보관, `finalized`는 기록 종결을 뜻한다. 비용은 예약 당시 산식이며 실제 청구·정산 확인이 아니다.

`companyRevisionMatches:false`는 현재 회사 버전과 다른 과거 예약이고, `reservationExpired:true`는 예약 기한이 지난 상태다. `reserved`이고 두 표시가 적절해도 현재 원고·근거·정책 유효성이나 실행 가능성은 아직 확인되지 않았다(`currentContextVerified:false`, `policiesVerified:false`, `transmissionAllowed:false`). 다른 회사의 예약·원고/발췌·정책 본문은 목록에 포함하지 않는다. 현재 회사 버전 인자가 오래되었거나 전체 기록/증인이 손상되면 목록을 반환하지 않는다. 예약이 없으면 빈 배열이며 자동 생성하지 않는다.

확인한 **정확한 `runId` 한 개를 직접 선택**해 아래 `--run-id`에 넣는다. 번호 순서나 가장 최근 예약을 자동 선택하지 않는다. 목록 확인 후에도 준비 명령이 선택한 예약·현재 회사·정책·기한을 새로 감사하므로, 사이에 변경되었으면 다른 예약으로 대체하지 않고 거절한다.

```powershell
node ../../.venturepass-local/toolchain/node_modules/pnpm/bin/pnpm.cjs comparison:prepare-input prepare `
  --data-root "<기존 자료 절대 경로>" `
  --control-dir "<기존 증인 제어 절대 경로>" `
  --database-id "<기존 DB UUID>" `
  --company-id "<회사 UUID>" `
  --company-revision "<현재 정수 revision>" `
  --run-id "<기존 예약 UUID>" `
  --policy-file "<검토된 정책 JSON 절대 경로>" `
  --output "<제어 디렉터리와 같은 상위 폴더의 새 JSON 절대 경로>"
```

명령은 현재 회사·원래 요청/예약·전체 원장·증인·정책 결합을 기존 전송 검토와 동일하게 검사한다. SQLite의 조회/롤백 잠금을 사용하므로 다른 작업이 진행 중이면 기다리거나 거절될 수 있다. 활성 서버를 종료하거나 기존 잠금 파일을 수동 삭제하지 않는다.

성공 출력에는 회사/revision/run, 검토 시각과 만료, 모델·예약 비용, 출력 바이트 SHA256과 `transmissionAllowed:false`, `consentRecorded:false`가 포함된다. 출력 파일은 실행 입력 형식 `{inputVersion:1,databaseInstanceId,settings:{companyId,companyRevision,runId,basis,usagePolicy}}`이다. 기존 출력은 동일한 내용이어도 덮어쓰지 않는다. 자료/정책/증인 검사나 자기 연결 정리가 실패하면 내보내지 않으며 원래 비용 보류를 해제하지 않는다. 파일 쓰기 중 OS 오류가 발생해 부분 출력이 남으면 검증 완료로 취급하지 않는다.

## 준비 이후

출력은 그 시점의 검토 결과이며 전송 승인이나 비용 청구 인증이 아니다. 운영 활성화를 결정한 뒤에만 기존 실행 설정과 이 파일 경로를 연결한다. 이 도구는 `.env`를 수정하거나 서버를 재시작하지 않는다.

앱의 `예약한 공개 근거 비교 실행`에서 등록→최신 비용/원문 확인→7개 직접 동의→1회 실행으로 이어진다. 회사·원고·정책·예약·만료·파일 내용이 바뀌면 기존 실행 경계에서 다시 대조한다. 응답 유실 시 원래 연결 상태를 조회하고 새 실행으로 대체하지 않는다. 실제 유료 AI 호출, 기관 입력/최종 제출, 배포, Git push에는 해당 범위의 별도 구체적 승인이 필요하다.

새 예약 생성/공식 근거의 자동 검토/운영 활성화는 이 명령의 범위가 아니다. 아직 예약이 없거나 필요한 정책이 준비되지 않았으면 원래 준비 단계에서 이어가며 임의로 생성하지 않는다.

## 앱에서 예약과 실행 입력 확인

`사업계획서 → 주장·근거 검토 → 예약한 공개 근거 비교 실행 → 회사별 기존 예약 확인`에서 **기존 예약 목록 불러오기**를 누른다. 화면을 열거나 회사를 바꾸는 것만으로 조회하지 않는다. 기존 실행 저장소의 명시 설정(`VENTURE_DATA_DIR`, `VENTUREPASS_COMPARISON_EXECUTION_CONTROL_DIR`, `VENTUREPASS_COMPARISON_EXECUTION_DATABASE_ID`)이 필요하며, 이 목록 조회 자체에는 API 키가 필요하지 않다. 이 문서는 실제 운영 설정을 변경하는 승인이 아니다.

현재 실행 입력이 미지정/확인 불가/다른 회사/다른 버전/예약 없음/일치 중 어느 상태인지 보여준다. 입력 파일의 경로·정책 본문·다른 회사의 예약 번호는 반환하지 않는다. **살펴볼 기존 예약**에서 항목을 선택하면 예약 당시 상한·만료·마지막 기록과 서버 입력 일치 여부를 볼 수 있다. 이 선택은 조회 표시만 바꾸며, 아래 실행 등록은 계속 서버에 준비된 원래 예약을 사용한다. 실행 입력을 바꾸려면 정확한 예약 번호로 위 운영 준비 절차를 거쳐야 한다. 일치 표시는 원고/정책 검토·전송 승인·실제 청구 확인을 뜻하지 않는다.

회사/원고 변경·편집 중 전환·화면 닫기에는 목록과 선택을 지운다. 실패/미확인 조회 뒤 **예약 조회 연결 정리**로 원래 연결 종료를 재시도한 다음 다시 불러온다. HTTP 연결이 끊겨도 미정리 서버 객체는 같은 프로세스에서 보관하며, 설정을 철회한 뒤에도 같은 회사·로컬 origin의 정리 요청은 가능하다. 프로세스 재시작 뒤 복구는 별도다. 정리 요청은 예약 취소·비용 보류 해제가 아니다.

`PREPARATION_CLEANUP_REQUIRED`는 자기 연결 정리를 확인하지 못한 상태다. 출력 파일을 만들지 않으며 잠금 파일을 자동 삭제하지 않는다. 내부 준비 객체는 같은 객체에서 `close()` 재시도를 지원하지만 CLI 프로세스가 종료된 뒤 미정리 잠금을 자동 복구하는 기능은 없다. 해당 오류는 원인을 확인한 뒤 별도 복구해야 하며, 새 예약/승인으로 우회하지 않는다.

## 예약이 없는 경우의 서버 연결 — 개발 범위

`createComparisonReservationBooking`은 기존 SQL13·증인·회사 자료와 검토된 `comparisonFinancialEvidenceSchema`의 근거, 정확한 원고/주장/공개 자료 선택으로 새 예약을 준비하는 서버 내부 소유자다. 생성에는 키나 환경변수 조회가 없고 실제 연결은 명시 `review()`에서 취득한다. 아래 새 예약 HTTP·앱 화면에 연결했으며, 위 `comparison:prepare-input` CLI는 계속 기존 예약만 다룬다.

| 단계 | 동작과 경계 |
| --- | --- |
| `review()` | 같은 SQL13 전체 기록·증인과 현재 회사 잠금 아래 원고/자료·금융 근거·기존 예산·보관 조건을 대조한다. 검토 자체는 예약/예산/정책을 쓰지 않는다. |
| `reserve(consent)` | 검토 digest와 목적·선택 내용 보관·현재 예산 예약·금액 근거의 한계·자동 재시도 없음에 대한 5개 개별 동의가 모두 있어야 한다. 서버가 명령/nonce·run/event UUID·시각을 만들고 원래 명령을 보관한 뒤 한 번만 예약 저장을 시도한다. 전송 동의는 별도다. |
| 반복 `reserve` / `recover()` | 원래 명령의 저장 여부를 전체 감사와 증인 대조로 읽기만 한다. 미관측·응답 유실·실패를 새 nonce나 재저장으로 바꾸지 않는다. `recorded`는 예약 확인이며 AI 실행/응답/청구 확인이 아니다. |
| `revoke()` | 새 검토/예약을 차단한다. 원래 기록 조회·연결 정리는 유지한다. |
| `close()` | 자기 원래 읽기 범위·트랜잭션·lease·연결을 순서대로 정리한다. 실패 시 `draining` 상태와 원래 객체를 보존하고 같은 객체에서 재시도한다. 예약 취소·예산 해제·증인 복구는 수행하지 않는다. |

실제 운영 정책/예산/스키마를 초기화하거나 예제를 운영값으로 채우지 않는다. `official-reviewed` 표기와 구조 검사는 공식 근거의 실제 검토를 대신하지 않는다. HTTP는 검토 전체/DB 경로/명령을 공개하지 않고 선택 식별값·금액·보관 안내·출처와 기록 확인만 제한해서 반환한다. 프로세스 재시작 뒤 원래 예약 소유자 재구성, 미확인 증인의 자동 복구, 실행 입력 파일의 자동 교체는 아직 지원하지 않는다. 미전송 예약 취소는 아래 별도 검토·동의 절차를 따른다.

## 앱에서 새 비교 예약 검토·기록

운영자가 검토한 금융 근거 파일을 `VENTUREPASS_COMPARISON_RESERVATION_POLICY_FILE`로 명시한다. UTF-8 JSON 최상위는 `{policyVersion:1,databaseInstanceId,evidence}`이며 evidence는 `comparisonFinancialEvidenceSchema`의 전체 금융/모델/가격/보관/출처 근거다. 기존 전송/사용량 정책 파일과 형식이 다르다. 파일은 기존 제어 디렉터리와 같은 상위 폴더의 절대 경로여야 한다. 링크·하드링크·읽는 도중 교체·128KiB 초과는 거절한다. DB UUID와 official-reviewed 표기를 검사하되 실제 근거 검토나 운영 승인을 대신하지 않는다. 실제 정책 파일은 이번 개발에서 생성하거나 활성화하지 않았다.

`공개 근거 비교 새 예약`에서 저장 주장 버전과 수동 공개 발췌 1~10개를 선택하고 **예약 내용·비용 검토**를 누른다. 서버 지정 모델, 전체 선택 입력, 현재 예산/예약 상한, 만료, 보관 안내와 근거를 확인한다. 회사/편집·선택 변경이나 접기는 검토 표시와 동의를 지운다. 각각 비선택 상태의 목적·보관·예산 예약·금액 근거 한계·자동 재시도 없음 5항목에 동의한 뒤 **동의한 내용으로 예약 기록**을 누른다. 현재 회사·정책/기한·예산을 서버가 다시 대조하며 원래 명령으로 한 번만 기록한다. 예약에 포함된 전체 작성 항목 문맥도 화면에서 확인해야 한다.

POST `/api/studio/cases/[caseId]/public-claim-comparison/booking`은 loopback/동일 origin, JSON 8KiB/UTF-8·종료·취소/시간 제한과 strict action을 검사한다. `x-venturepass-comparison-booking`에는 브라우저 등록 UUID를 넣으며, 예약 nonce와 다르다. `open`의 선택 ID 이외에 모델·정책·원고 본문·금액·명령을 받지 않는다. 등록은 수동적이고 같은 회사/선택/origin/UUID의 원래 소유자를 보존한다. 동시에 최대 8개의 연결, 종료 확인 기록 64개만 유지하며 활성 연결은 자동 삭제하지 않는다. 요청 본문 정리가 실패하면 원래 본문 객체를 보존하고 추가 작업을 차단한다.

브라우저 sessionStorage에는 등록 UUID·선택 식별값/해시·시도 여부만 저장하며 본문·정책·동의를 저장하지 않는다. 새로고침만으로 호출하지 않는다. 응답 유실 후 **원래 예약 상태 조회 → 원래 예약 기록 확인**으로 원래 서버 객체를 확인한다. 기록이 없거나 상태가 불명확해도 재예약하지 않는다. 설정 철회 뒤에도 같은 프로세스의 원래 기록 조회와 **예약 연결 정리**는 가능하다. 정리 실패 시 같은 버튼으로 원래 객체만 재시도하며 예약/예산 보유를 취소하지 않는다. 프로세스 재시작으로 원래 객체가 없으면 새 UUID로 우회하지 말고 별도 복구 판단이 필요하다.

예약 기록 확인 뒤 **예약 연결 정리**의 정리 완료를 먼저 확인한다. 원래 연결이 보유한 잠금을 해제한 다음 앱 목록에서 정확한 예약을 선택해 입력 파일을 준비하거나, 확인된 `runId`를 위 CLI 명령에 직접 지정한다. 담당자의 파일 검토·별도 활성화 후 기존 실행 화면의 별도 검토/7개 동의 절차를 따른다. 신규 예약 UI는 유료 호출·비용 청구·사실 확인·업무 완료를 자동 수행하지 않는다.

## 앱에서 미전송 예약 취소

실행을 중단할 때는 기존 예약/실행 연결의 정리를 먼저 확인한다. **회사별 기존 예약 확인 → 기존 예약 목록 불러오기 → 살펴볼 기존 예약**에서 정확한 예약을 고르고 **선택 예약 취소 검토**를 누른다. 현재 회사 버전과 예약 당시 버전, 예약 번호·작성 항목·모델, 해제할 예산 보유액과 기록 보존 안내를 확인한다. 검토는 10분 동안 유효하다. 원래 예약이 만료되거나 회사 버전이 달라도 미전송 상태라면 검토할 수 있으며, 회사 버전이 검토 뒤 다시 바뀌면 쓰기를 거절한다.

비선택 상태의 **정확한 예약 취소·예산 해제**와 **증거 보존·환불 아님** 두 항목에 각각 동의한 뒤 **동의한 예약 취소 기록**을 누른다. 서버는 현재 회사와 SQL13 전체 감사/증인·원래 원장 head를 다시 대조하고 기존 취소 계획으로 한 번 기록한다. 전송/정산/종결 기록이 있거나 전송 바인딩이 있으면 새 취소 검토를 거절한다. 취소는 cancelled/finalized 이벤트, 예산 보유 해제, 영수증과 종결 산출물의 기존 6행을 추가하며 원래 예약·선택 문맥·증거를 삭제하지 않는다. 실제 청구 환불 처리가 아니다.

POST `/api/studio/cases/[caseId]/public-claim-comparison/cancellation`은 loopback/동일 origin·정확 URL·8KiB UTF-8 JSON·종료/취소/시간 제한과 strict action을 검사한다. `x-venturepass-comparison-cancellation`의 등록 UUID는 서버가 만드는 원래 취소 nonce와 구분한다. 브라우저는 회사/revision/run 선택과 검토 digest·두 동의만 전달하며 명령·금액·시각·원장 head를 만들지 않는다. 취소에는 기존 자료/제어 경로·DB UUID 세 설정만 필요하며 정책/키·실행 입력 파일을 새로 요구하지 않는다. 설정 변경/철회 뒤 새 검토와 취소는 막고 원래 조회·정리는 허용한다. 활성 연결 최대 8개/종료 기록 64개, 본문 정리 실패 시 원래 IO 보존은 새 예약 경계와 같다.

응답 유실·새로고침 뒤에는 **원래 취소 상태 조회 → 원래 취소 기록 확인**을 명시 실행한다. 원래 명령과 취소 원장을 대조해 기록된 해제만 표시하며 미관측을 재취소/새 nonce로 우회하지 않는다. sessionStorage에는 등록 UUID·선택·시도 여부만 남고 검토/동의/원문은 저장하지 않는다. 회사/선택/편집 상태 변경·화면 접기는 검토와 동의를 비우며 자동 요청이 없다. 취소 기록을 확인하면 **취소 연결 정리**가 완료된 뒤 목록을 다시 불러온다. 정리 실패에는 원래 객체를 보존하고 같은 정리 버튼을 재시도한다. 연결 정리 자체는 취소가 아니며 프로세스 재시작으로 원래 소유자가 사라진 경우의 복구는 지원하지 않는다. 기존 실행 입력 JSON은 취소 뒤에도 남지만 원래 예약 감사에서 실행을 허용하지 않는다.

이번 개발은 임시 SQL/합성 화면 검증이다. 실제 운영 예약·예산·승인·키·고객 자료는 변경하지 않았으며 운영 취소 실행에 대한 승인으로 이 문서를 사용하지 않는다.

## 서버 재시작 뒤 저장된 예약·취소 기록 확인

원래 예약/취소 상태 조회에서 **현재 서버에서 원래 연결을 찾지 못했습니다**가 표시되면, 같은 회사의 **기존 예약 목록 불러오기 → 살펴볼 기존 예약 → 저장된 예약·취소 기록**으로 확인한다. 자동으로 가장 최근 예약을 고르지 않는다. 작성 항목·모델·회사 버전·예약 번호와 함께 예약 요청 번호/기록 시각을 대조한다. 감사된 취소가 있으면 취소 요청 번호/시각·취소와 동시에 종결된 시각·해제된 예산 보유액을 표시한다. 취소가 없는 종결은 다른 절차의 종결이며 예산 취소나 환불이라고 표시하지 않는다. 현재 실행 입력 일치 표시는 계속 별도다.

기존 GET/CLI list가 원래 예약 바인딩과 전체 SQL13 취소·예산·종결 영수증을 대조한 뒤 제한된 `history`를 반환한다. 전체 명령/선택 원문/정책/키를 반환하지 않는다. 현재 회사 확인·증인·원래 읽기 연결 정리를 모두 통과해야 기록을 표시하며, 목록의 시각/해제 금액/종결 관계가 맞지 않으면 클라이언트도 표시하지 않는다. 새 가격 검토·전송/취소 동의·쓰기 없이 새로운 조회 프로세스에서 읽을 수 있다. 실제 비정상 종료로 남은 잠금이나 부분 증인은 자동 제거/복구하지 않으므로 그런 상태에서는 별도 원인 확인이 필요하다.

새 예약·취소는 검토에 성공한 서버 소유자가 요청 nonce(예약은 runId도)를 먼저 발급한다. 검토 갱신에도 같은 번호를 유지하며 이때 승인 명령·동의 시각·원장 쓰기는 만들지 않는다. 사용자가 개별 동의 후 쓰기 버튼을 누르면 브라우저가 등록 UUID·선택·서버 요청 번호/예약 번호·시도 표시를 sessionStorage에 저장하고 재읽기 대조를 마친 뒤 요청한다. 저장이 실패하거나 서버 번호가 없으면 쓰기를 보내지 않는다. 원장 쓰기는 사전 발급한 번호를 그대로 사용하며, 예약 승인 시각은 실제 동의 요청을 처리할 때 정한다.

서버 재시작 후 **기존 예약 목록 불러오기 → 미확인 요청 기록 대조**를 누르면 현재 회사 목록의 원래 runId와 해당 종류(예약/취소)의 서버 nonce가 모두 일치해야 기록 확인을 표시한다. 예약은 예약 당시 회사 revision도 일치해야 하며 현재 회사 revision으로 바꿔 맞추지 않는다. 취소는 과거 버전 예약을 취소할 수 있다. 대조는 조회 시점의 목록 기준이며 목록 재조회·회사 변경·원래 연결 변경에는 결과 표시를 무효화한다.

사전 식별자가 없는 구형 sessionStorage, 다른 회사·run·nonce, 취소 없는 종결, 목록에서 못 찾은 경우에는 완료로 처리하지 않는다. 미관측은 미실행이나 실패의 확정이 아니며 자동 재예약·재취소·새 nonce 발급·원래 연결 초기화를 하지 않는다. 브라우저의 원래 연결과 시도 표시를 보존한다. 저장 기록의 정확한 대조는 실행 소유자/동의의 재구성이나 잠금/부분 증인 복구가 아니다. 브라우저 저장 자체가 지워진 경우의 귀속과 운영 복구는 미완료이며 이번 확인으로 전송/사실 검증·실제 청구 환불이 승인되지 않는다.


## 서버 연결 없는 확정 요청 보관 후 다음 작업

목록에서 원래 요청을 대조한 뒤 **확인된 예약 요청 보관 / 확인된 취소 요청 보관**을 누른다. 이전 표시만 믿고 해제하지 않는다. 원래 등록의 inspect가 정확한 OWNER_UNAVAILABLE 404인지 확인하고, 현재 회사 revision의 새 목록을 GET으로 읽어 원장 감사/조회 연결 정리를 통과한 기록을 대조한다. 마지막 inspect에서도 원래 연결이 없어야 한다. 살아 있는 연결이 돌아오면 원래 기록 확인·연결 정리를 사용하도록 안내한다. 네트워크 실패를 연결 부재로 취급하지 않는다.

원래 등록 UUID·선택·서버 nonce/runId·시도 여부와 조회 시각/회사 revision/예약·취소 history/금액 단위를 함께 보관한다. 활성 요청 해제와 보관을 **같은 sessionStorage 값(version2 envelope)** 한 번의 쓰기 및 재읽기 확인으로 처리한다. 구형 version1 활성 요청도 읽으며, 보관 없는 기존 동작은 유지한다. 중간 저장 실패에는 자동 재전송하지 않고 저장 상태를 재확인한다. 회사/화면 변경·원래 요청 교체·미관측/불일치 기록·구형 사전 식별자 없음은 보관하지 않는다. 원래 등록과 확인 기록은 보관 배열에 남고 새 등록으로 덮어쓰지 않는다.

보관 후 새 예약 또는 다른 미전송 예약의 취소를 직접 검토할 수 있다. 이전 동의를 복원하거나 바로 쓰지 않는다. 새 작업의 정상 연결 정리·설정 미구성 처리에서도 과거 보관은 유지한다. **이 탭에 보관한 요청 → 보관 기록 불러오기**는 브라우저 저장만 읽고 네트워크를 호출하지 않는다. 회사별로 해당 기록만 표시하며 이는 당시 조회 내역이지 현재 서버 상태가 아니다. 예약/취소 각각 최대20건, 전체 저장값256KiB까지이며 자동 삭제/덮어쓰기로 한도를 우회하지 않는다. 탭을 닫거나 브라우저 저장을 지우면 이 보관 사본이 사라질 수 있으나 운영 원장 기록에는 영향이 없다.

이 작업은 브라우저의 확정 요청 보관이다. 서버 자원을 닫았다는 증명·원장/승인/예산 변경·새 nonce 재전송·잠금/부분 증인 복구·실제 청구 환불은 수행하지 않는다. 원래 서버 연결이 있을 때는 기존 close 경로를 따른다.
