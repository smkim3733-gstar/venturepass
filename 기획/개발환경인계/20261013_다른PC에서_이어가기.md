# 다른 PC에서 개발 이어가기 — 2026-10-13

이번 인계는 사용자의 GitHub 업로드 요청에 따른 소스·기획·개발 기록 이전이다. 최신 개발 브랜치는 `codex/continue-development`다. `main`에는 이번 누적 개발을 합치지 않았으므로 반드시 이 브랜치를 받아야 한다.

## 새 PC에서 시작

Node.js 24.x와 pnpm 11.19.0을 준비한다. OneDrive 같은 동기화 폴더 밖에 새 작업 폴더를 정한 뒤 실행한다.

```powershell
git clone --branch codex/continue-development https://github.com/smkim3733-gstar/venturepass.git
cd venturepass
git status --short --branch
pnpm --dir web install --frozen-lockfile
pnpm --dir web dev --webpack
```

브라우저에서 <http://127.0.0.1:3000/studio>를 연다. 새 PC 설치/실행은 이번 업로드 작업에서 실제로 실행하지 않았다. 기존 작업 사본이 있다면 먼저 미커밋 변경을 보존하고 원격 브랜치를 확인하며, 위 clone 명령으로 별도 폴더를 만드는 편이 명확하다.

AI 키 없이 소스 개발과 합성 자료 기반 작업을 시작할 수 있다. API 키는 필요한 경우에만 [환경변수 예시](../../web/.env.example)를 참고해 새 PC의 `web/.env.local`에 별도로 설정한다. 이전 PC 전용 `.venturepass-tools/pnpm.cmd`와 시작 배치 파일에는 절대 경로가 있으므로 복사해 실행하지 않는다.

## 이번 업로드에 포함한 작업

- 기존 원격 개발 브랜치 `114791a` 이후의 로컬 개발 커밋 272개. 마지막 완료 기능 커밋은 `39f689d`다.
- 그동안 별도로 보존한 원고 편집기 소스/검증기 3개의 미커밋 변경. 동급 패널의 React key에 역할 이름을 구분하는 변경과 합성 검증 항목이다. 이번 이전에서는 내용을 수정하지 않고 저장한다.
- 보존 문서 4개: VALIDATION 충돌 사본, 개발현황/작업대장 충돌 사본, 품질평가 운영 승인 후속 설계.
- 루트 README 충돌 사본과 상위 폴더의 개발 인계 원본, 이 안내, 새 PC용 저장소 작업 지침.
- 앱 소스, 기존 합성 fixture/검증기, lockfile, 공개 명단·통계 JSON, 기존 기획/개발 이력.

충돌 사본은 삭제하거나 최신 문서에 합치지 않았다. 원래 편집기 변경의 독립적인 기능 완료/인수를 이번 업로드로 선언하지 않는다. [이관 파일 목록](이관파일목록_20261013.json)에 보존 파일의 SHA-256과 출처를 기록했다. Git의 텍스트 줄끝 정규화는 별도이며, 목록에는 커밋 전 로컬 바이트의 해시가 담겨 있다.

## GitHub에 포함하지 않는 항목

실제 `.env`/API 키, 고객 DB·업로드 원본·계정 정보, 운영 실행 원장/예산·승인 기록, `node_modules`/패키지 캐시, `.next`/임시 빌드·실행 로그·검증 화면은 기존 PC에 남는다. 상위의 원본 PDF·Excel·고객 서류·분석 산출물도 포함하지 않는다. 소스와 문서의 GitHub 이전은 고객 데이터 백업 또는 운영 환경 복원이 아니다.

기존 고객 데이터를 이어서 써야 한다면 별도 안전한 이전이 필요하다. 이번 작업에서는 고객 자료를 열거나 옮기지 않았다. 과거 품질평가 승인·nonce·해시·본문·비용 hold/원장을 재생성하거나 빈 DB를 기존 사용량 0으로 간주하지 않는다. 소진된 유료 AI/KOSIS/기관 실행 승인은 새 PC에서도 재사용하지 않는다. 저장된 Windows DPAPI 계정 정보는 이전 PC의 사용자/환경에 묶이므로 새 PC에서 그대로 해독된다고 가정하지 않는다. [기존 이전·복원 안내](../../web/DEVELOPMENT_HANDOFF.md)는 당시 기록과 현재 지시를 구분해 참고한다.

## 검증을 이어갈 때

이번 업로드에서는 제품 코드를 새로 고치거나 완료 검사를 반복하지 않았다. 마지막 기능 작업의 기존 관련 시험 40/40, 개발·프로덕션 합성 앱 1개 흐름, lint/typegen/tsc/격리 빌드 결과는 위 상세 문서에 있다. 전체 lint에는 기존 미사용 함수 경고 1개가 남는다. `pnpm lint`는 `--max-warnings=0`이므로 그 경고 때문에 실패할 수 있으며, 과거 직접 ESLint 종료 0과 구분한다.

새 제품 변경 때는 정적 의존 전이 확인 → 정확한 파일/이름의 영향 시험(maxWorkers 1) → 격리 합성 앱 → lint 종료 확인 → typecheck 종료 확인 → 격리 build 종료 확인 순서다. 운영 API/SQLite·SDK·외부 fetch 차단을 유지한다. 시험/기존 합성 검증기의 필요한 브라우저 및 환경 조건은 실행할 스크립트를 먼저 읽어 확인한다.

새 PC의 격리 빌드 예시(저장소 루트에서 시작):

```powershell
New-Item -ItemType Directory -Force .\.venturepass-local\build-temp | Out-Null
$env:TEMP = (Resolve-Path .\.venturepass-local\build-temp).Path
$env:TMP = $env:TEMP
Set-Location web
node scripts/build-local.mjs
```

이 명령은 앱 밖이면서 같은 드라이브인 임시 폴더를 쓰고, 허용된 소스와 기존 의존성 연결로 별도 빌드를 만든다. 실제 환경 파일/고객 자료는 복사하지 않는다. 출력된 임시 빌드와 원래 개발 서버의 `.next`를 혼동하지 않는다. 설치·검증·서버 실행은 새 PC에서 별도로 수행해야 한다.
