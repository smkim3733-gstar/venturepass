## 이번에 구현한 범위

- v2 읽기 전용 검토안·이력 화면을 기존 후보 도구에 연결했다. 현재 운영 모델·금액·공식 근거·예산·보관·권한은 미완료로 표시하고 실제 실행은 제공하지 않는다. 선택한 후보/등록 버전의 실행과 정확한 과거 revision·당시 원문만 조회·다운로드한다. 기존 A의 미설정 계약과 합성 원장/백업을 보존한다.
- 조회 실패는 마지막 기록과 원문을 보존하고 자동 재전송하지 않는다. 전송 의도·응답·원고 검증·종료·미확인 예약을 구분하며, 늦은 응답이 도착해도 중단을 유지한다. 후보 변경·지연·기존 편집과의 교차 잠금과 닫기를 연결했다. 코드 검토에서 발견한 runner 근거 만료/엔진 변경의 오류 분류를 INTERRUPTED로 바로잡았고 실제 잘못된 원고의 OUTPUT_INVALID는 유지한다.
- 이번 최종 관련13파일346개(207.80초/1worker)·실패/건너뜀0, 전체 lint·독립 tsc·격리 build 통과. src/scripts516파일 SHA 일치. 합성 화면의502보존/명시재조회·320/375px·실제 다운로드 SHA·재시작 archive11개 동일을 확인했다. 전체 앱/백업/회사 CLI는 반복하지 않았고 기존3000과 원자료를 보존했다.
- 다음은 `품질평가_운영근거_검토안_후속설계.md`의 서버 고정 공식 근거·정확한 한 건 요청/예약액 검토안이다. 운영 예산이 없을 때 가짜 준비안·run·승인 manifest를 만들지 않는다. 실제 전송·품질평가·서비스 전체 완료는 아직 아니다.

- v2 예약 뒤 별도 전송 승인·요청·dispatch·응답·usage 정산·검증·종료를 연결했다. 내부 runner는 승인과 dispatch를 직접 최초 commit한 호출자만 합성 transport를 호출한다. replay·조회·재오픈은0회이며 기존 예약 동의·시작0회·r0/취소 r1 bytes를 전송 권한으로 소급하지 않는다. production 쓰기·실제 AI 전송 HTTP는 닫혀 있다.
- v2 관측 어댑터는 기존 builder·도메인 검증을 재사용하고 응답 model/service tier/usage를 출력 검증 전에 보관한다. 명시 요율 정책으로 계산하며 누락·불명확은 held 유지/후속0, 초과 비용은 전액 recognized로 보관해 부족액과 새 dispatch 차단을 유지한다. 수신 중 기한/엔진 변경과 늦은 원래 응답도 비용을 보관하지만 중단을 철회하지 않는다.
- generation은 저장한 원래 요청, review는 같은 실행의 저장·검증된 최초 원고에서만 파생한다. 원문/단계 기록 실패 호출0·응답 저장 실패 뒤 후속0·자동재시도0을 검증했다. 최종 쓰기 실패에도 생성/검토 원고를 보존한다. 요청2MiB·응답4MiB·검증2MiB·최종4MiB와 artifact 합계20MiB를 기존32MiB 예약 안에서 관리한다.
- 현재 quality 백업은13테이블39트리거의 v6이며 v1~v5와 과거 bytes를 지원한다. frozen v5 검사기로 새 전송 행 혼입을 이행 전 거절한다. format2 예약/취소와 format3 전송 prefix를 구분한다. v2 최종 원문2~4MiB의 decoder 불일치를 수정했으며 v1 개별 상한은 유지한다. 이후 항목은 앞서 구현한 기반의 기록이다.

- C2 v2 예약 전용 준비안·동의·고정 요청·예산 원장·취소·조회·과거 JSON을 내부 저장소에 연결했다. 기존13테이블에서 v1/v2 행을 엄격히 구분하고 v1·v2합성·v2운영의 금액과 head를 분리한다. 전체 nonce·총20건·32MiB 예약 공간·슬롯·256MiB/물리264MiB 한도는 통합한다. 기본 저장소의 실제 운영 mutation과 HTTP 전송 경로는 계속 닫혀 있다.
- 새 예약은 현재 builder·후보·금융 근거·보관 조건·승인·예산을 대조한다. 과거 조회·동일 nonce 재현과 전송 전 취소는 당시 고정 근거로 검증하므로 가격/준비안 만료 뒤에도 보존한다. `acknowledgedReservationOnly:true`를 전송 승인으로 승격하지 않는다. 예약만 구현했던 시점의 응답/usage 미구현 상태는 위 후속 합성 경로로 확장했으며 시작 행과 snapshot의 dispatch/resume false는 그대로 유지한다.
- quality 백업 v5는13테이블39트리거다. 정확한 v4 형식에 v2 정책/실행이 섞이면 DDL 변경 전에 거절하고, 구버전 writer를 모든13테이블에서 차단한다. 정상 v1~v4 복원과 혼합 v5 복원, v1/v2 각 과거 JSON 바이트를 보존한다. 기존 회사 백업 경로는 변경하지 않았다.

- 이어 C2의 별도 순수 금융 예약 계약을 구현했다. 공식 문맥 C 전체와 출력 O를 각각 예약하고 짧은/긴 문맥·캐시 읽기/쓰기의 최고 총요율을 BigInt로 계산한다. 이는 토큰 실측이나 문맥 적합성 검증이 아니다. 모델 기본값·운영 요율 등록·실제 예산·승인·전송 권한을 만들지 않으며 증빙 부족·만료·조건 불일치는 금액 null로 남긴다. A/B v1에 연결하거나 합성 근거를 운영 근거로 바꾸지 않았다.
- C2 조건은 텍스트 생성·검토 2회, 자동 재시도0, standard/global/default·store:false·truncation:disabled·stateless·도구/별도 token counting 없음으로 고정했다. 캐시 쓰기 값은 할증만의 금액이 아니라 기본 비용을 포함한 총 대체 요율이어야 한다. 공식 정보는 공개 문서 조사만 했으며 계정 권한·가격의 운영 채택·모든 실패의 청구 상한을 확인한 것으로 표시하지 않는다.

- 합성 비용 원장과 관측 엔진을 C1 내부 runner로 연결했다. 정확한 요청 보관 → 최초 dispatch commit → 합성 transport → SDK 허용 응답 원문·usage 보관 → 출력 검증 → 검토 → 최종 원고 순서를 지킨다. 선택적 await 훅을 추가하고 기존 계약 digest·요청 JSON·모의 8테이블 이력은 보존한다. 실제 시작·승인 HTTP 경로는 아직 없다.
- 시작·dispatch를 직접 최초 commit한 호출자만 전송하며 조회·replay·다른 프로세스에는 권한이 없다. 원문/예약/단계 기록 실패와 모델·토큰·가격 범위 변경을 검사한다. 전송 직전에도 유효기간과 예산을 대조한다. 늦은 원래 응답은 정확한 종료 이력과 결합해 비용만 보존하고 중단을 유지한다. 실제 AI 호출은 0이다.
- 별도 Node 프로세스 두 개의 동일 요청은 실제 주입 transport 총 2회(생성·검토 각 1회)다. dispatch commit 직후 프로세스를 종료해도 재오픈한 runner가 재전송하지 않는다. 완료·usage 누락·응답 저장 실패의 원문/과거 JSON과 v4 백업·복원도 확인했다. B의 13테이블34트리거는 바꾸지 않았다.

- 생성·검토 요청, SDK 응답 JSON의 허용된 필드, 최초/최종 원고를 raw SHA와 정확한 파생 연결로 보관한다. event의 예산 head와 영수증을 고정하여 과거 revision JSON이 뒤의 관측에 따라 바뀌지 않는다. 로컬 GET 6경로로 원장·현재/과거 실행·원문·정확한 nonce 조회를 제공한다. 실제 시작·승인·예산 설정 HTTP 경로는 제공하지 않고 기본 저장소의 합성 쓰기도 차단한다.
- quality 백업 v4는 13테이블·34트리거와 원문/예산/이력 결합을 검사·복원한다. 기존 v1/v2/v3와 회사 백업 경로를 보존한다. 구버전 writer의 기존 테이블 쓰기를 차단하고 문자열 리터럴까지 정확히 검사한다. 모든 v4 이력과 표식을 삭제하고 정상 legacy로 재구성한 위조까지 외부 신뢰 근거 없이 식별한다고 주장하지 않는다.

- 실제 AI를 실행하지 않는 준비 조회를 추가했다. 등록 후보 한 개와 명시 입력한 모델 ID의 정확한 생성 요청 원문(system·user·출력 schema) 및 미완성 검토 템플릿을 확인·내려받는다. 모델 제공 여부와 사용 권한을 확인한 것으로 표시하지 않으며 키·환경파일·회사 저장소·외부 공급자를 읽거나 호출하지 않는다.
- 엔진 요청 조립을 순수 함수로 분리하고 기존 관측 실행도 동일 함수를 사용한다. 기존 계약 digest와 생성/검토 JSON 바이트를 고정 회귀로 보존했다. 검토 템플릿에는 같은 실행의 검증된 최초 생성 원고만 결합한다는 규칙을 명시하며 존재하지 않는 검토 본문을 승인된 것으로 표시하지 않는다.
- 가격 출처·적용 범위·유효기간, 전체 요청/검토 원고/공급자 부가분을 포함한 토큰 상한, 통화·정수 단위·올림·미확인 비용의 순수 계약을 검증했다. 실제 가격·토크나이저·예산 어댑터는 미설정이다. 제품 API는 이를 모두 null로 고정하고 실행/승인/예약을 false로 유지한다. 합성 계산 근거를 운영 준비에 사용하지 않는다.
- 준비 조회본은 서버에 저장한 승인이나 영속 실행 준비안이 아니다. 화면에 대조된 동일 조회 시각·본문·SHA만 JSON으로 내려받는다. 선택 변경 시 이전 조회본을 해제하고 기존 평가 초안/모의 준비와 교차 잠금한다. A에서는 품질 DB와 백업 스키마를 확대하지 않았다.

- 등록 후보 한 개의 입력·등록 버전·엔진 프롬프트/schema·모델·최대 2회 범위를 고정하는 모의 실행 준비안과 이력 API·화면을 연결했다. 실제 회사 DB·키·외부 AI를 사용하지 않는다. 모의 비용은 0이고 실제 가격·금액 상한·전송 승인이 없으므로 유료 실행은 제공하지 않는다.

- 실행·이벤트·영수증을 불변 저장하고 20실행·실행당7단계·단계당1MiB·기존 기록 합산256MiB 한도를 적용했다. nonce/CAS·정확한 후보/계약/요청·단계 연결을 대조하며 기존 승인·회귀·후보 등록 nonce와도 충돌을 검사한다. 기록이 있는 요청은 다시 실행하지 않으며 결과 미확정인 후보는 새 nonce로 우회하지 않는다.

- quality 백업은 기존3/v1·후보5/v2·실행8/v3 테이블 형식을 함께 지원한다. 모의 출처·0원·요청·후보·단계·최종 출력 연결과 과거 바이트를 검사한다. 회사 자료 백업 범위는 변경하지 않았다.

- 합성 후보 12개를 별도 불변 버전으로 등록·조회·다운로드하고 기존 50개 개발 회귀와 구분한다. 서버에 포함된 원문만 등록하며 입력·신청 주제와 작성자 메모를 분리한다. 원문/manifest/버전 SHA, 이전 버전 연결, 동일 nonce 재현·충돌, CAS와 중복 원문 차단을 적용했다. 후보는 20버전·버전당 8MiB, 기존 평가와 합산 본문 256MiB 한도를 사용한다.
- 등록 결과는 요청 영수증과 정확한 버전·원문을 모두 대조한다. 응답 유실·미관측은 확인 필요로 유지하고 자동 재전송하지 않는다. 기존 평가 초안·진행 요청과 교차 잠금을 적용했다. 실제 화면에서 발견한 미확인 중 미등록 단정 문구를 수정하여 목록은 마지막 조회 기준으로 표시한다.
- 품질 전용 백업은 기존 3테이블/6트리거의 v1 형식과 새 5테이블/10트리거의 v2 형식을 함께 검사·복원한다. 빈 저장소·후보만·기존 평가 혼합을 지원하며 과거 JSON/DB 바이트와 회사 자료 DB를 보존한다. 후보 등록은 사람 정답표·독립 세트·실제 AI 평가 완료가 아니다.

- 기본 신청·진행 화면에 정확한 최신 보완 요청·통보·확인서·기한·사용자 기록 시각을 연결했다. 공식 확인 시각이 없는 현재 기록을 공식 조회 결과로 승격하지 않는다. 기한과 필요한 조치를 기준으로 주 실행 하나를 제공하며 실제 대기와 미래 확인서 준비일에는 주 실행을 만들지 않는다.
- 기본 화면에서 현재 요청 root/version에 맞는 기존 답변 편집·비교, 정확한 확인서 준비일 입력, 해당 업무 편집 또는 통보 원문으로 바로 이동한다. 이전 요청의 원고만 있으면 비교부터 열고, 여러 준비안 중 하나를 임의 선택하지 않는다. 기록 중복·고아 정정·끊어진 이전 버전 연결은 확인 필요로 남기며 안전한 대기로 오판하지 않는다.
- 대상 상세 화면의 상위 revision 재생성을 제거하고 편집기의 실제 저장 확인 후에만 초안 보호를 해제한다. 성공 저장 뒤 불필요한 오래된 이동 경고와 이전 준비안 안내도 갱신했다. 정확한 현재 통보·회차·절차에 실사 완료 수기 기록이 있으면 반복 안내만 해제하며 공식 완료로 표시하지 않는다.

- 준비본 대조를 기존 execution API·승인 화면·영속 실행 기록에 연결했다. 서버가 실제 ZIP과 현재 전체 원고·선택 문자열·원본을 검증하고, 명시한 준비본은 v2 승인과 최초 쓰기 전 running 기록에 고정한다. 실행 직전·중·결과 확인에서 같은 연결을 대조한다. 준비본 ID를 보낸 요청의 실패를 v1으로 우회하지 않는다.
- 일반 승인 화면은 준비본 선택→로컬 대조→정확한 검토안→전송 승인 순서다. 준비본 변경과 문맥 변경 시 이전 대조·승인 표시를 폐기하고 확인 필요 상태는 유지한다. v2 부분 복구는 원래 전체 선택과 준비본을 보존한 채 미시도 빈 텍스트만 새 승인에 포함한다. v1 기록·승인과 ID 없는 API의 기존 호환 경로는 준비본 미연결로 남기며 자동 승격하지 않는다. 첨부 실행의 자동 복구는 계속 제한한다.
- 응답 유실 복구에서 최신 실행 ID만으로 성공을 판단하던 문제를 수정했다. 전송 직전 회사·계정·세션·화면·revision·준비본·입력/보호 범위와 이전 실행 근거를 고정하고 POST/GET 모두 대조한다. 다른 최신 기록·진행 중·결과 미확인은 이번 요청의 확인으로 취급하지 않는다. 내부 검토 사유는 한국어로 표시한다.
- 회사 백업 도구가 새 준비본 테이블이 있는 DB를 거부하던 호환성 문제를 수정했다. 기존 3테이블과 정확한 준비본 4테이블 구조를 지원하고 메타데이터·원고·요청·ZIP 해시와 회사 관계·버전을 검사한다. 현재 원고·원본 삭제 뒤에도 과거 준비본을 보존·복원한다. 회사 백업 DB 64MiB 한도에는 ZIP도 포함되며 초과 시 자동 삭제 없이 명시 중단한다. 별도 품질평가 백업은 그대로 유지한다.


- 합성 품질 평가에 별도 SQLite 회차·불변 버전 이력·고정 입력 조회·결과 입력·집계·과거 JSON 다운로드를 연결했다. 기본 설정의 개발·검토 도구에서만 열며 일반 3단계 메뉴는 유지한다. 회차를 만들어도 정답표·AI 실행·사람 검토를 완료 처리하지 않는다.
- 같은 요청 번호 재현, 저장 충돌 시 초안 보존, 조회를 통한 응답 유실 복구, 명시적인 동일 요청 재확인을 구현했다. 회차·기록·용량 한도와 SHA/형식 검사를 적용하고 회사 자료 DB와 분리한다. PC 시계가 뒤로 보정되거나 현재 평가 규칙이 바뀌어도 정상 과거 기록과 내보내기를 보존한다.
- `quality-backup / quality-verify / quality-restore` 전용 관리 명령으로 고정 원문·전체 회차·버전·요청 이력을 보존·복원한다. 기존 평가 저장소 덮어쓰기를 거부하고 복원 중인 DB 접근을 차단한다. 기존 회사 백업 형식·지원 스키마 범위는 확대하지 않는다. 화면의 선택 버전 JSON은 복원 파일과 구분한다.
- 제조·소프트웨어·서비스 × 신규·재확인 후보 12개를 별도로 준비했다. AI 작성 후보이고 사람 정답표·독립 검증 세트 확정·정식 평가 등록·실제 AI 품질평가는 미완료다. 기존 개발 회귀 50개에 합쳐 62개 독립 검증을 완료했다고 표시하지 않는다.


- 일반 원고 읽기 화면의 `기준·근거 보기`에 기존 인용 대조·작성 가이드·신청별 기준 기록을 연결했다. 인용 일치, 기업 자체 설명, 미확인·누락·변경 상태를 구분하며 공식 심사 완료로 표시하지 않는다.
- 기존 ZIP 선택·다운로드 기능을 기본 화면에서도 열 수 있다. 선택한 원고·원본·검토 상태·SHA와 실제 ZIP을 별도 준비본으로 원자 저장하고, 자료 변경·원본 삭제 뒤에도 과거 파일을 그대로 내려받는다. 기업별 20개 한도, 같은 요청 재현, 저장 전후 버전·원본 재검사와 회사 삭제 시 함께 삭제를 적용했다. 이는 공식 제출 기록이 아니다.
- 저장된 AI 의미 의견과 현재 규칙 검토를 모두 보관한다. 미해결 의견이 있으면 ZIP·보관 기록·화면에 검토 필요 상태를 유지한다. 저장 결과가 불명확하면 같은 요청을 조회하고, 확정 거절·동시 작업·늦은 응답·복구 뒤 오류 문구를 구분한다.
- 합성 50사례의 입력/출력 해시, 사람 정답표, 두 독립 검토자와 의견 조정, 미평가·모의·실제 AI 결과를 분리하는 평가 기록 core를 구현했다. 이후 별도 로컬 영속 이력·평가 UI·전용 백업/복원을 연결했다. 실제 AI 실행기는 아직 없다. 사용 규격은 `AI_품질평가_기록규격.md`에 기록했다. 기존 사례는 소프트웨어·신규 중심이며 독립 검증 세트가 아니다.

- 기본 화면을 **자료 올리기 / AI 계획서 / 신청·진행**으로 변경했다. 밝은 바탕, 남색 주 버튼, 금색 표시를 적용했고 기존 일곱 상세 도구는 별도로 열 수 있다.
- 회사 설명만으로 시작하거나 여러 자료를 한 번에 올릴 수 있다. 본문을 읽지 못한 스캔 PDF·이미지는 미확인 원본으로 보관한다. 구형 XLS는 기본 업로드 대상에 포함하지 않는다.
- 등록 후 AI가 사용할 회사정보·문서 본문·작성 초안·제공자·모델 범위를 확인한다. 허용 뒤 AI 분석, 실제 사업에 맞는 신청 주제 선택, 계획서 작성과 독립 AI 검토를 연결한다. 기존 자료 기반 정리본은 AI 작성과 구분한다.
- 요약·전체 원고·근거·미확인 항목을 단계적으로 열고 필요한 부분만 수정한다. 수정본과 이전 원고를 모두 보관한다. 사실 확인과 내부 검토 완료는 사용자 확인 없이 처리하지 않는다.
- 자료·회사 버전·전송 범위·신청 주제와 실행 요청을 대조한다. 중복 클릭, 오래된 승인, 자료 변경 뒤 전송, 늦게 도착한 결과의 저장을 차단한다. 공급자 목적지는 OpenAI 공식 API로 고정한다.
- 중단·응답 유실 시 저장 상태를 먼저 조회한다. 재작성은 최신 실행에 대한 별도 확인과 새 승인을 받고 이전 실행을 보존한다. 같은 자료는 최초 포함 최대 세 번이며 자동 재전송하지 않는다.
- 입력 중인 회사 설명과 원고 초안을 보호한다. 새 작성본이 생기면 이전 편집 내용을 새 원고에 잘못 적용하지 않는다.
- 신청·진행 화면에서 현재 필요한 행동을 안내하고 기존 공식 연결·기관 기록 도구로 이동한다. 실제 기관 결과가 없는 상태를 접수 완료로 표시하지 않는다.
- 새 AI 준비 승인에는 같은 자료로 최대 한 번 자동 수정하고 독립 재검토하는 범위를 포함한다. 과거 승인에는 권한을 추가하지 않는다. 최초 작성·검토 원고와 수정 시도 기록을 먼저 저장하고, 수정 실패·근거 불일치·검토 악화 시 최초 원고를 유지한다. 본문이 같아도 검토 의견이 달라지면 별도 버전으로 보관한다. 수정 이력과 남은 사실 확인을 기본 화면에서 볼 수 있다.
- 자료 본문을 기본 화면에서 확인·교정할 수 있다. 스캔 PDF·이미지는 명시 동작으로 로컬 글자 읽기를 호출하고 원본 대조 후에만 채택한다. 자료 변경·실패 시 편집문을 유지하며 원본과 기존 원고를 보존한다.
- 분석 질문과 원고 작성 후 질문을 합쳐 필요한 질문만 보여 준다. 처음 세 개 이후 질문도 펼쳐 답할 수 있으며, 질문이 없는 충분한 자료에는 고정 질문을 만들지 않는다. 나중에 답하기와 자료 변경 뒤에도 입력 내용을 보존하고 오래된 버전으로 저장하지 않는다.
- 서로 다른 합성 품질 사례 50개와 사례별 기대 동작을 준비했다. 규칙 검사가 놓치는 의미 오류 30개와 정상 단위 변환을 잘못 경고하는 경우도 기록했다. 이는 실제 AI 의미 검토 통과 결과가 아니다.

## 실제 실행 전에 필요한 사항

실제 AI 품질 검증에는 사용할 자료·제공자·목적·비용 범위가 명확한 승인이 필요하다. 공식 사이트에는 현재 계정·회사·화면·정확한 입력 및 첨부·법적 동의·최종 제출·납부를 구분하여 기존 승인 범위부터 확인한다. 가상 자료를 공식 기관에 제출하지 않는다. 공식 미관측 동작을 추측해서 구현 완료로 표시하지 않는다.

기존 개발 서버와 사용자 자료·원본·미커밋 작업은 보존했다. Git push·공개 배포·실제 기관 실행은 수행하지 않았다. 이번 후속 범위는 v2 별도 전송 승인·합성 관측/정산·중단 복구·v6 백업이다. 다음 검토 화면 연결을 위한 자동 연속 개발 예약은 활성 상태다.
