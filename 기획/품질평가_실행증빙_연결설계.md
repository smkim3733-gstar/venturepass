# 품질평가 실행 증빙 연결 설계

기준: 2026-09-27. 후보 버전 등록 다음 구현을 위한 설계다. 실제 AI 호출·비용 승인·품질 검증을 완료했다는 기록이 아니다.

후속 구현 현황: 아래 설계 중 로컬 모의 준비안·관측 엔진·불변 실행 이력·조회 복구·화면·백업은 구현했다. 실제 가격·토큰 상한·비용 예약 및 유료 실행은 아직 연결하지 않았다. 다음 개발은 [실제 AI 승인 준비 설계](품질평가_실제AI_승인준비_개발설계.md)를 따른다. 아래 ‘현재 확인한 차이’는 이 문서 최초 작성 시점의 문제 기록이다.

## 현재 확인한 차이

기존 개발 회귀 50개의 평가 도구는 사용자가 입력한 실행·정답표·검토 기록의 형식과 연결을 검사한다. `mode: actual-ai`, 제공자, 모델 이름을 입력하는 것만으로 실제 호출을 증명하지 않는다. 새 12개 후보는 고정 등록할 수 있지만 기준 원고와 사람 정답표가 없으므로 기존 50개의 `inputPlanDigest`나 rubric을 임의로 만들어 넣지 않는다.

현재 `studio-engine.ts`의 `requestStructured()`는 공급자 응답의 ID·요청 ID·usage를 보관하지 않고 검증된 결과만 반환한다. 기존 `beforeRequest`는 실제 전송 외에도 상태 검사·복구·실패 처리에서 호출된다. 이 훅의 호출 횟수를 외부 AI 요청 횟수로 세면 부정확하다.

## 다음 최소 구현

등록된 후보 한 개의 생성과 독립 AI 검토부터 연결한다. 일반 고객 회사자료를 임시 회사로 복사하지 않는다. 기존 엔진의 작성·근거 검사·검토 규칙은 재사용하되 실행 기록은 후보 등록 영역과 별도 타입으로 관리한다.

1. 서버가 정확한 등록 버전과 후보 ID를 조회하고 입력만 추출한다. `candidateRegistryModelInput()`의 `profile / sources / candidate` 허용 목록을 사용한다. 작성자 메모·의도·challengeTags·향후 사람 정답표는 모델 요청에 넣지 않는다.
2. 실행 준비안에 등록 버전·versionDigest·candidateId·modelInputDigest, 제공자·고정 전송 목적지·모델, 엔진·시스템 프롬프트·요청 schema 버전의 digest, 생성/검토 단계와 최대 요청 수, 입력·출력 토큰 한도, 목적·비용 범위를 고정한다. 모델 또는 입력·프롬프트·schema·단계·한도가 바뀌면 이전 승인으로 실행하지 않는다.
3. 시작 요청을 nonce와 함께 영속 보관한 뒤 최초 전송을 허용한다. 동일 요청은 새 호출 없이 기존 기록을 반환한다. 동시 실행과 미확인 시도를 먼저 대조한다.
4. `requestStructured()`의 실제 SDK 호출 직전에 새 `onDispatch` 훅을 둔다. 단계·정확한 요청 digest·모델·호출 순서를 먼저 기록한다. 영속 기록 실패 시 전송하지 않는다. 기존 `beforeRequest`의 승인 범위 검사와 역할을 구분한다.
5. 실제 응답 수신 → 메타데이터 영속 보관 → 별도 출력 검증 순서로 분리한다. 현재 `responses.parse()`는 SDK 내부 구조화 검증 중 예외가 날 수 있으므로 그 반환 뒤에만 훅을 두면 수신 기록이 빠진다. `onResponse`로 response ID, request ID, 공급자가 보고한 모델·usage·status를 먼저 보관하고, 이후 검증한 출력 digest를 연결한다. 응답 기록 실패 시 다음 검토 호출을 금지한다. 설정 모델과 응답 모델은 각각 보관하며 같다고 추측하지 않는다. 응답 바디 전체·키·원시 오류를 로그에 남기지 않는다.
6. 모의 공급자는 같은 기록 계약을 사용하지만 `mock` 출처를 고정한다. 실제 증빙으로 승격하지 않는다. 실행 증빙은 앱 서버의 관측 기록이며 공급자 서명·청구서·사람 검토 또는 성능 합격을 뜻하지 않는다.

최초 범위는 생성 1회와 독립 검토 1회, 최대 2회다. 자동 수정까지 허용할 때만 수정·재검토를 포함한 별도 최대 4회 범위를 검토한다. SDK 자동 재시도는 0이며 실패한 실행을 단순 자료 정리 결과로 바꾸지 않는다.

## 비용과 승인

개발·모의시험에 실제 키나 유료 호출을 사용하지 않는다. 실제 실행 전 사용할 후보·모델·제공자·정확한 전송 내용·목적·최대 호출 수와 비용 상한을 구체적으로 보여 준다. 이전 회사의 작성 승인이나 후보 원문 등록 확인을 평가 실행 승인으로 재사용하지 않는다.

토큰 한도와 호출 횟수만으로 금액 상한을 충족했다고 표시하지 않는다. 실행 시점의 확인된 가격 근거·통화·단위·최대 입력/출력 및 추가 과금 조건으로 실행 전 예약 금액을 계산한다. 가격 또는 계산 근거가 없으면 실제 실행은 준비 미완료다. 승인된 한도 안에서 요청별 최대액을 먼저 예약하고, 공급자 usage를 받은 경우에만 사용량을 정산한다. 응답이 없으면 예약액을 자동 해제하지 않는다. 금액·사용량·공급자 청구 확인은 각각 구분한다.

## 중단과 결과 미확인

`prepared → authorized → dispatch-recorded → response-observed → output-validated`를 구분하고 실패·결과 미확인도 보존한다. `dispatch-recorded`는 전송 직전 기록이므로 공급자 수신 완료를 뜻하지 않는다. 네트워크 단절·응답 유실·재시작 뒤에는 자동 재전송하지 않는다. nonce 조회와 저장된 증빙만으로 복구하고, 새 호출이 필요하면 이전 미확인 시도와 예약액을 포함한 새 실행안을 명시한다.

늦게 도착한 응답을 다른 실행에 붙이지 않는다. 응답 ID가 없거나 usage가 제공되지 않은 경우는 `null/unknown`으로 남긴다. 원고 검증에 실패해도 수신과 과금 가능성이 사라지는 것은 아니므로 응답 메타데이터와 실패 코드는 보존한다. 기존 원고와 성공 출력은 덮어쓰지 않는다.

## 저장·백업과 후속 평가

후보 실행 이력은 append-only로 준비본·승인·시도·응답의 관계를 검증한다. 후보 원문·기존 50개 회차·회사 DB를 변경하지 않는다. 테이블을 늘릴 때는 전용 quality 백업의 정확한 스키마 허용 목록과 구버전 복원을 함께 보완한다. 기존 등록 JSON과 평가 JSON 바이트는 보존한다.

생성 원고가 생겨도 사람 정답표·독립 검토·독립 검증 세트로 승격하지 않는다. 검토자는 특정 실행 출력과 별도로 동결한 정답표를 읽고 판단한다. 후보 12개는 개발자가 이미 본 AI 작성 후보이므로 등록 여부와 관계없이 독립 holdout의 증거가 아니다. 정식 독립 세트 최소 50건 및 두 검토자의 실제 평가가 별도로 필요하다.

## 필요한 합성 시험

- 허용한 후보 입력만 전송, 메모·힌트 미포함, 실제 요청 digest와 승인된 입력 연결.
- 전송 전 영속 기록 실패 시 공급자 호출 0회; 동시 요청·동일 nonce는 최대 1회 실행.
- 기존 `beforeRequest`가 여러 번 불려도 실제 전송 수는 SDK 호출 수와 일치.
- 미승인 모델·단계·토큰·가격/금액 변경 거절, 예약 한도 초과 호출 0회.
- 저장 뒤 응답 유실·전송 뒤 재시작·출력 검증 실패를 구분하고 자동 재호출 0회.
- 모의 기록을 actual-ai로 변경 불가, 늦은 응답·다른 실행 출력·오래된 승인 대조 실패.
- 서버 관측 증빙·사용자 입력 평가·사람 검토 상태 분리, 과거 출력·다운로드·백업 복원.

이 설계의 로컬 구현과 모의 검증은 독립적으로 계속할 수 있다. 실제 제공자 호출과 사람 평가는 구체적인 승인·검토 담당자가 확정된 뒤 진행한다.
