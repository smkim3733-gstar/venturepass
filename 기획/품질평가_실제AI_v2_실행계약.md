# 품질평가 실제 AI v2 실행 계약

기준: 2026-09-27. C1의 합성 원장·엔진 연결 뒤에 이어가는 최소 실제 실행 경로다. 운영 예산 설정이나 실행 승인이 아니다. C2의 순수 예약 계산과 v2 예약 전용 준비안·동의 기록·영속 보관·취소·조회·v5 백업까지 구현했다. 현재 쓰기는 명시한 합성 시험 환경에서만 가능하며 실제 운영·전송 승인 API·dispatch·공급자 응답 정산은 아직 없다. 기존 A 조회 화면, B 합성 원장, C1 runner를 다시 만들지 않는다.

## 현재 구현 경계 — 예약만 지원

- v2 준비안은 고정 후보·요청·금융 근거·보관 조건·예산 head를 묶는다. 생성 본문은 기존 builder를 재사용하고 별도 계약 digest와 `service_tier:default`, `truncation:disabled`, `background:false`, `stream:false`를 고정한다. 검토 템플릿은 아직 생성되지 않은 검토 원문을 대신 승인하지 않는다.
- v2의 `acknowledgedReservationOnly:true`는 예약 전용 동의다. 이 동의나 `newlyCommitted`를 전송 권한으로 재해석하지 않는다. 모든 현재 snapshot은 `dispatchAllowed:false`, `canResume:false`, `actualAiCalls:0`이다. 현재 원장에는 전송 event가 없으므로 취소는 전송 전 예약만 해제한다. v1에서 미확인된 호출의 예약 해제 기능으로 사용하지 않는다.
- v1, v2 합성, v2 운영의 금액·revision·head는 고정된 서로 다른 scope다. nonce·총20건·공간·기록 슬롯은 통합 검사한다. 새 예약만 현재 builder·유효기간을 대조하고, 과거 조회·동일 요청 재현·전송 전 취소는 만료 후에도 가능하다.
- 13테이블을 재사용하며 writer gate는 13개로 확대해 총39트리거다. v4 envelope에 v2 행이 섞여 있으면 DDL 변경 전에 거절한다. 정상 v1~v4 백업은 그대로 검사·복원하고 v5는 혼합 이력의 실제 삽입 순서도 검증한다. v1 과거 JSON에는 v2 예산을 섞지 않는다.
- 기존 예약을 전송 가능 상태로 자동 승격하지 않는 후속 연결은 `품질평가_v2_전송승인_후속설계.md`에서 구체화한다. 실제 공급자 usage/service tier/cache 정산·전송 runner·한 건 검토 UI·운영 근거 등록은 다음 구현이다.

## 1. 이번에 해소할 문제

기존 A/B는 전체 system/user/schema와 공급자 부가분을 포함한 토큰 상한을 요구한다. 로컬 문자 수를 토큰 수로 바꾸거나 생성 전 검토 원고의 정확한 입력 수를 만들어 넣을 수 없다. 공식 input_tokens API는 완성된 요청의 정확한 수를 주지만 별도 외부 전송이며 요금·보관 조건도 확인해야 한다. 최초 1건 시험에 추가 원격 계산 절차를 넣지 않는다.

대신 새 계약에서 `provider-context-limit`을 금융 예약 근거로 분리한다. 공식 문맥 한도 C 전체를 입력 금액 상한으로 잡고, 명시한 출력 상한 O를 별도로 더한다. 생성·검토 각각 같은 방식으로 두 번 예약한다. 이는 보수적인 예약 계산이지 실제 토큰 수, 실제 예상 비용, 요청 적합성 검사 또는 모든 실패 청구에 대한 보증이 아니다. 기존 A의 `inputUpperBound + output <= context`를 억지로 통과시키거나 `model-tokenizer-reviewed`로 표시하지 않는다.

공식 문서는 문맥에 입력·출력·추론이 포함되고, `truncation:disabled` 요청이 문맥을 넘으면 400으로 거절한다고 설명한다. 이 근거에서 정상 처리되는 단일 요청의 입력을 C 이하로 예약할 수 있다고 판단했다. 모든 오류의 청구가 없거나 반드시 이 상한 이하라는 계약적 보장은 확인하지 못했다. 응답·사용량이 불명확하면 예약을 유지하고 다음 호출을 막는다. [문맥 설명](https://developers.openai.com/api/docs/guides/conversation-state), [Responses 요청](https://developers.openai.com/api/reference/cli/resources/responses/methods/create)

## 2. 고정할 호출 범위

- 서버에 이미 등록한 합성 후보 한 개의 정확한 버전·후보·입력 SHA만 허용한다. 고객 회사 DB·파일·작성자 정답 힌트는 읽지 않는다.
- 동일한 명시 모델 ID로 생성 1회와 독립 검토 1회, 자동 재시도 0회다. 수정·재검토·token counting·계정 조회는 이 2회 권한에 포함하지 않는다.
- 공식 공용 `https://api.openai.com/v1`의 Responses 텍스트 요청만 사용한다. `service_tier:default`, `store:false`, `truncation:disabled`, 출력 상한을 원문에 고정한다. 도구·이미지·파일·오디오·이전 response/conversation·자동 compaction·지역 처리·Fast/Batch/Flex·background/stream은 허용하지 않는다.
- 생성 원문을 승인 시 고정한다. 검토 원문은 같은 실행의 저장·검증된 최초 생성 원고와 고정 프롬프트/schema에서만 파생한다. 생성 전에 검토 원문까지 정확하게 완성됐다고 표현하지 않는다.
- 기존 v1 엔진 계약·JSON 바이트를 보존하고 새 공급자 옵션이 들어간 v2 요청 계약 digest를 따로 만든다. 프롬프트·schema의 조립 코드는 재사용한다.

`store:false`는 응답 조회용 저장 옵션이며 모든 공급자 보관이 없다는 뜻이 아니다. 검토안에는 공급자의 별도 로그·캐시 보관 조건을 함께 표시한다. [공식 데이터 정책](https://developers.openai.com/api/docs/guides/your-data)

## 3. 가격과 예약 계산

2026-09-27 공식 문서 조사에서는 모델마다 입력·캐시 읽기·캐시 쓰기와 짧은/긴 문맥 요율이 다름을 확인했다. 기본 입력 요율만 사용하지 않는다. 각 요율은 할증만 따로 적은 값이 아니라 해당 토큰의 총 대체 요율이어야 한다. 적용 가능한 입력 요율들의 최댓값과 출력 요율들의 최댓값을 각각 선택하고, 정수 단위 BigInt와 항목별 올림을 적용한다. 할인은 예약액을 줄이는 근거로 쓰지 않는다. 현재 순수 계약은 고정 조건에서 부가 요금이 없다는 명시 근거만 지원한다. 별도 부가 금액이 필요하면 근거·금액·정산 규칙을 먼저 확장해야 한다. [공식 가격](https://developers.openai.com/api/docs/pricing), [캐시 정책](https://developers.openai.com/api/docs/guides/prompt-caching)

모델은 아직 채택하지 않았다. 비교용 공개 문서에는 GPT-4.1의 날짜 고정 모델 `gpt-4.1-2025-04-14`, 문맥 1,047,576·최대 출력 32,768, Standard 입력 $2·출력 $8/100만 토큰이 명시돼 있다. O=16,000을 쓰는 두 번의 보수적 예약 산술 예시는 $4.446304다. 실제 견적·운영 예산·사용자 승인 금액이 아니며 계정 접근권한도 확인하지 않았다. [모델 문서](https://developers.openai.com/api/docs/models/gpt-4.1)

품질 우선 후보인 GPT-6 Sol/Astra는 문맥 1,050,000·최대 출력 128,000이며, 문맥 상한 전체를 예약하면 272K 초과 요율도 포함해야 한다. Sol의 최대 입력 요율 $5·출력 $15, Astra의 $25·$75/100만 토큰을 적용할 때 같은 O=16,000의 두 번 예약 예시는 각각 $10.98·$54.90다. 이것도 비교 계산일 뿐 모델 추천 확정이나 실질 청구액 예측이 아니다. [Sol](https://developers.openai.com/api/docs/models/gpt-6-sol), [Astra](https://developers.openai.com/api/docs/models/gpt-6-astra)

공식 공개 정보의 조회일과 내부 재확인 기한을 분리한다. `validUntil`은 앱의 재확인 정책이며 공급자의 가격 보장일이 아니다. 실제 전송 직전 재확인해야 한다. 계정별 모델 접근권한·응답 모델 식별과 실제 청구 항목은 별도 관측 사항이다.

## 4. 순수 계약부터 연결

`studio-plan-quality-provider-reservation.ts`는 C2의 별도 순수 예약 근거를 계산한다. 서버에서 고정한 모델·문맥·요율·출처·유효기간·호출 조건이 일치할 때만 금액을 반환한다. 합성 증빙과 공개 문서 기반 증빙을 구분하고, caller가 붙인 출처 문자열 자체를 독립 검증으로 취급하지 않는다. 입력 부족·조건 불일치·만료 시 금액을 null로 남긴다. 토큰 실측·요청 적합성·계정 권한·운영 예산·사용자 승인·전송 권한은 이 함수가 만들지 않는다.

이후 기존 A 화면의 선택 후보와 원문 펼침을 재사용하여 v2 검토안을 만든다. 새로운 차단 전용 조회 화면을 하나 더 만드는 것이 다음 목표가 아니다. 아래 영속 원장·승인·실행과 연결한 다음에만 사용자에게 정확한 한 건 검토안을 제시한다.

## 5. 원장·백업 변경의 최소 범위

기존 B v1의 `actual-ledger-simulation/synthetic-test/actualAiCalls:0`과 원문·과거 JSON은 변경하지 않는다. 새 실제 실행은 별도 v2 출처·준비안·승인·event 검증기를 사용한다. 합성 정책의 예약을 실제 예산으로 소비하지 않도록 별도 budget scope를 둔다.

현재 구현은 JSON body와 원문 BLOB을 보관하는 13개 테이블을 재사용한다. v5 migration은 정확한 이전 구조와 v4의 행 버전을 대조한 트랜잭션에서 writer gate를 교체·확대하고 기존 행을 재작성하지 않는다. 기존 8테이블과 actual 5테이블에 v5 writer gate를 적용해 13테이블·39트리거이며 정확한 DDL·검사기·백업 count를 함께 검사한다. 과거 v1~v4 보관본과 새 v5 보관본을 모두 검사·복원하고 기존 회사 DB 백업 범위는 유지한다. 같은 테이블에서 뒤에 실행 event를 확장할 경우에도 기존 writer가 새 행을 오인해 쓰지 못하도록 writer 계약과 백업 판독 범위를 다시 검토해야 한다.

동일 BEGIN IMMEDIATE 안에서 승인된 준비안 SHA·예산 head/run CAS·전체 nonce·비용·공간·슬롯을 대조한다. 공유 저장 공간은 합성/실제 이력을 모두 포함한다. v2만 실제 예산 scope를 쓸 수 있고 v1은 기존 scope만 쓸 수 있다. 조회·replay·프로세스 재시작은 C1과 같이 전송 권한을 복원하지 않는다. 기본 production mutation은 승인 경로 연결 전까지 계속 닫는다.

독립 검토에서 기존 다운로드의 `revision <= ?` budget 조회가 현재 단일 scope를 전제로 한다는 점을 확인했다. 새 scope를 추가하기 전에 모든 budget 조회·검증·export를 **run의 불변 schemaVersion에서 정한 고정 scope**로 필터해야 한다. 클라이언트가 임의 scope를 선택하게 하지 않는다. 전역 nonce·저장 공간·총건수는 통합 검사하되 금액·reservation·head·revision은 scope별로 검증한다. 실제 v2 기록을 추가하기 전과 후의 기존 v1 archive bytes가 완전히 같아야 한다.

## 6. 승인과 관측

한 건 검토안에는 후보·버전·입력, 모델과 공식 목적지, 정확한 생성 본문, 검토 파생 규칙, 요청 2회·수정/재시도 0회, 보수적 예약액과 운영 누적 한도, 공급자 보관 조건, 자료 변경 시 승인 무효를 표시한다. 금융 예약과 실제 토큰 적합성이 다르다는 설명을 한 문장으로 포함한다. 사용자가 이 검토안에 명시적으로 동의한 기록을 원장 시작과 결합한다.

첫 실제 공급자 응답에서 요청 ID·response ID·실제 모델·service tier·usage/cache 세부·status를 원문 검증 전에 보관한다. 요율 구분이 불가능하거나 모델·가격 범위를 벗어나면 미확인 비용 예약을 유지하고 두 번째 호출을 막는다. 알려진 비용은 원고 검증 성공 여부와 별도로 보관한다. 보수적 예약액에서 바로 실제 비용을 추정해 빼지 않는다.

필수 회귀: 합성/실제 출처 혼용 거부, 모델·요율·조건·원문/준비안 변경, stale approval, 동일 nonce/다중 프로세스, 기록 실패, 입력 초과/공급자 오류, usage·캐시 구분 누락, 실제/모의 budget 분리, 재시작·과거 bytes·백업 왕복. 실제 API는 이 범위가 모의 공급자로 검증된 뒤 한 건의 명시 승인에서만 연다.

## 7. 완료로 간주하지 않는 것

이 경로의 한 건 호출은 공급자 연결과 실행 증빙 시험이다. 기존 개발 회귀 50개와 AI 작성 후보 12개의 독립 의미 품질 검증, 사람 정답표·holdout, 실제 기관 승인이나 서비스 전체 완료를 대신하지 않는다. 승인 대기에도 공식 연결의 미관측 항목 정리와 외부 고객 권한·보관·복구 등 독립 개발을 계속한다.
