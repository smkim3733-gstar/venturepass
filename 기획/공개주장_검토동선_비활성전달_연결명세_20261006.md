## 2. 원래 run에서 정확한 저장 결과까지

입력 출발점은 기존 실행에서 보관한 원래 runId/dispatchCommandDigest 또는 storage-only 재개방의 명시 원래 두 값이다. 이를 회사ID·claimID·최근 시각·목록 첫 항목으로 찾아 채우지 않는다. 현재 production UI에는 이 두 값을 취득하는 지원 경로가 없다. 다음 격리 시험은 기존 합성 실행/후속 저장에서 이미 알고 있는 원래 값을 사용하며 실제 UI의 지원 완료로 세지 않는다.

다음 서비스 포트의 예정 이름은 readStoredReviewByRun(query)다. 아직 구현되지 않았다. 입력은 strict/data-only 객체 { runId, dispatchCommandDigest, mode }이며 mode는 historical 또는 inspect-current다. 기존 UUID/hash schema와 UTF-8 JSON8KiB를 재사용한다. 회사 객체·경로·원문·preview JSON·authority boolean·추가 키는 입력받지 않는다.

같은 factory의 closure 안에서만 다음 순서를 조합한다.

1. 기존 private 인계 검사 후 previewPostcapture의 같은 내부 구현으로 원래 run/dispatch를 감사한다. 외부 callback이나 caller가 보내 준 preview를 신뢰하지 않는다.
2. database.comparisonRecorded가 true이고 comparisonEventDigest가 유효한 hash일 때만 진행한다. 비교 state가 ready인지만 검사하지 않는다.
3. 위의 감사된 같은 반환에서 runId, dispatchCommandDigest, comparisonEventDigest, responseArtifactSha256, expectedValidatedArtifactSha256→validatedArtifactSha256를 취해 기존 strict 선택을 만든다.
4. mode에 맞춰 같은 storedRead를 호출한다. 여기서 SQL13/증인3·실제 event/hash·원래 context/capture를 다시 감사한다. 첫 감사의 preview를 결과로 반환하지 않는다.
5. 기존 StoredComparisonRead DTO만 제한된 사본으로 반환한다. resultIdentity 안에 다음 명시 재조회에 사용할 선택5개가 이미 들어 있다. 새 raw 응답/전체 archive/원장/경로/capability를 덧붙이지 않는다.

기존 previewPostcapture와 storedRead의 내부 구현을 재사용하도록 필요한 최소 private 함수 추출은 허용한다. writer/decoder/사용량 산술/증인 감사 복제는 금지한다. 필요 없는 별도 facade/factory/WeakMap·전역 registry를 추가하지 않는다. 원래 두 strict 읽기 포트도 유지한다.

두 번의 감사는 각자의 기존 SQL/lease 구간이다. 전체가 하나의 시점 또는 두 DB의 단일 거래라는 보장은 없다. 첫 단계 뒤 close가 저장되어도 원래 result identity가 같고 두 번째 전체 감사가 통과하면 의견은 같다. 비용/hold/종료 값은 마지막 읽기의 사본이다. 복원/손상·다른 결과·pending ack·정리 실패는 두 번째 읽기에서 거절하고 원래 책임을 남긴다. 후속 close가 생겼다는 이유로 새로운 선택을 자동 생성하거나 정산하지 않는다.

쓰기 영수증을 읽기 선택으로 cast하지 않는다. committed/replay·witnessMatched는 원래 기록/복구 관측이며 실제 전송 허가나 사람 동의가 아니다. ack 불명은 원래 recoverPostcapture 명령이 별도로 해결해야 한다. 이 포트가 자동 recover/ack/write/execute를 호출하는 경로는 없다.

## 3. 화면 수락과 표시 계약

다음에는 실제 React 컴포넌트/route를 연결하지 않고, 이미 감사한 서비스 DTO의 전달 사본을 수락할지 결정하는 순수 helper와 지연/순서 역전 합성 시험을 만든다. 실제 HTTP에서 온 임의 JSON을 타입 cast로 인증하는 decoder가 아니다. 향후 HTTP 연결에는 별도의 strict wire 형태/수신 byte 제한 검토가 필요하다.

호출자는 명시 읽기 시작 때 화면 ticket을 만든다. ticket은 같은 화면 수명 내 단조 증가 번호와 원래 snapshot 참조/회사ID·revision, 선택한 원래 run/dispatch 및 알고 있는 원래 claim/plan 신원을 고정한다. 모드도 함께 고정한다. snapshot이 같은 객체여도 revision/선택이 바뀌면 실패해야 하므로 시작 당시 scalar 값과 후속 값도 대조한다. 필요한 값은 첫 await 전에 사본으로 고정한다. ticket은 일시 메모리 표식이며 새 저장 nonce·승인 bytes·전송 owner가 아니다.

| 수락 조건 | 화면 의미 |
|---|---|
| 원래 run/dispatch·회사·claim record/version·원고id/version·선택한 mode 일치, 최신 ticket, 같은 snapshot/revision, mounted·열림·편집 차단 없음 | 동일한 명시 읽기의 과거 의견을 표시할 수 있음 |
| 현재 검사 exact-original-request이며 observedRevision=originalRevision=화면 revision | 그 시점의 원래 요청 일치만 별도 표시. historical.currentContextVerified는 false 유지 |
| changed이며 관측 revision=화면 revision | 원래 요청과 달라 재검토 필요. 과거 의견을 현재 원고 의견으로 바꾸지 않음 |
| unavailable, 관측 revision 없음 또는 화면과 일치 | 현재 일치 여부 미확인으로 표시. 안전하게 감사한 과거 본문과 구분 |
| 현재 검사에 관측 revision이 있는데 화면 revision과 다름 | 이 current 표시 수락 거절. 새 화면 snapshot 또는 명시 과거 읽기 필요 |
| historical mode | current:not-checked만 허용. 이전 exact/current 상태를 이어 붙이지 않음 |
| 닫힘/unmount/Abort·ticket 교체·회사/원고/주장/선택/snapshot/dirty 변경 | 이전 응답 전체 수락 거절. 기존 exact 표시도 숨김/해제 |

같은 회사 안에서도 새 원고 버전이 보인다는 이유로 원래 선택을 최신 버전으로 바꾸지 않는다. displayedPlan과 stored plan이 다르면 원래 연결 원고 표시를 분리한다. 모르는 claim/plan 기대값을 현재의 최신 항목으로 보충하지 않는다. 다음 helper의 입력은 테스트에서 원래 명령/기존 기록으로 명시 구성하며 실제 UI 취득 경로는 미완료다.

이미 읽은 과거 결과가 현재 unavailable 때문에 변조/삭제된 것으로 해석되지 않도록 한다. 다만 화면 변경 뒤 늦은 과거 응답을 다른 회사/선택에 표시하지 않는다. 필요하면 새 snapshot에서 historical 읽기를 명시 수행한다. 자동 polling/재요청·동시 여러 읽기를 만들지 않는다.

표시는 짧은 요약과 펼치는 원래 근거/의견으로 제한한다. 상태는 “저장 당시 비교 의견”, “원래 요청 일치/변경/확인 불가/미검사”, “사용량·비용/hold”, “저장 당시 담당자 판단”을 구분한다. raw relation/reason/checks는 일반 텍스트이며 HTML 실행/URL 자동 조회/수동 judgement 채우기0이다. comparison:null인 거절/불완전/해독 실패도 그대로 표시하고 새 의견을 만들지 않는다.

원래 원고/주장 이동은 기존 PlanReviewTarget 검사 계약을 따른다. 회사/revision·정확한 plan/section/record가 없어졌으면 이동을 강행하거나 최신 원고로 대신하지 않는다. 보호 plan-editor 수정은 이번/다음 범위에 포함하지 않는다. 수동 judgement와 원고 채택/confirmedAt은 기존 별도 명시 동작이다.

## 4. 수명·복구·미지원 경계

클라이언트의 취소나 화면 remount는 응답 표시를 끝내는 신호다. 서버 원래 service/session·owner/lease·unknown·retained 명령/읽기 cleanup의 종료 증거가 아니다. 신규 연결이 매 요청마다 service를 생성하거나 finally에서 retire/close를 호출해서는 안 된다. 기존 같은 service가 책임을 보관하며 private canRelease/자기 SQL·회사 읽기·lease 종료와 기존 명시 복구만 사용한다.

현재 공개 inspect().status와 activeCalls/캡처 개수로 새 서비스의 폐기를 결정하지 않는다. 외부에서 임의 cleanup을 호출하거나 다른 호출의 guard/lease를 정리하지 않는다. storage-only 재시작에는 보관 JSON에서 owner를 복원하거나 driver를 준비하지 않는다.

실제 서버 설치/소유 수명과 원래 run 선택 취득은 아직 구현되지 않았다. 기존 production-server는 generation/review용 registry이며 import에 부작용이 있다. getStudioStore도 constructor 실행 시 실제 환경/DB를 열므로 이번 계약 점검과 다음 합성 전달의 호출 대상이 아니다. 다음 테스트는 기존 격리 fixture의 session/guard와 기존 createIsolatedPublicComparisonService를 사용한다.

기존 loopback/origin/no-store·8KiB 요청 제한은 미래 route의 재사용 후보일 뿐 이번/다음 route 구현은 없다. studioFetch의 JSON 후 사본 제한을 네트워크 수신 제한이라고 보고하지 않는다. provider용 bounded body를 그대로 client bundle로 import하거나 120초 공급자 시계를 로컬 HTTP에 복제하지 않는다. 실제 HTTP를 열기 전 응답의 단일 bounded 수집·UTF-8 해독/JSON·오류 한도/중단 수명 계약을 따로 확인해야 한다.

## 6. 다음 4I34 전체 완료 조건

1. 같은 비활성 서비스에 strict 원래 run/dispatch+mode의 명시 전달 포트를 연결한다. 위 감사→실제 stored flag/event 확인→기존 strict 결과 읽기 순서와 원래 run 고정을 유지한다.
2. 외부 preview/callback/boolean 권한, 최신 run 검색, 별도 service/session/registry·owner/ledger·SQL14를 추가하지 않는다. 같은 private helper와 writer/decoder/산술/증인3를 재사용한다.
3. 계산 preview만 있을 때 거절, 정상/거절/불완전/인용 실패, 사용량 unknown/binding3/0/초과, close 전후 같은 identity, 교차 선택/손상·pending ack를 관련 합성으로 검증한다.
4. 첫/두 번째 감사 및 자기 cleanup 실패·원래 I/O 미종료·retire/restart를 검증한다. 기존 읽기/복구와 service 책임을 보존하고 read에서 INSERT/ack/자동 recover/execute/settle/hold 해제0을 단언한다.
5. 순수 화면 수락 helper를 구현한다. DTO를 다시 의미 판정/해독하지 않고 원래 선택과 ticket·snapshot/scalar·mode·observed revision의 일치를 대조한다. 실제 HTTP JSON 인증/수신 제한 완료로 세지 않는다.
6. 합성 지연/역순 응답, 취소/닫힘/차단/편집, 같은 객체 내부 변경, 다른 회사·claim/plan·run/dispatch, exact/changed/unavailable/not-checked, 반환 사본 변경을 검증한다. 오래된 성공뿐 아니라 오류도 새 화면을 덮어쓰지 않아야 한다.

8. 실제 route/UI/HTTP/브라우저·production-server import/설치·운영/고객 DB/control/lock·SDK import/생성/실행·global fetch·키/환경/공식 가격/외부0. 기존 보호 편집기와 수동 judgement/채택 writer를 수정하지 않는다.

## 7. 이번 완료와 남은 실제 활성화

이번은 위 계약 확정이며 다음 포트/helper 구현은 아직 없다. 정확한 새 구현에 필수 외부 결정0개다. 실제 제품 UI/production 연결을 위해서는 원래 run 선택의 사용자 동선·승인된 서버 소유 수명/DB 전환·SDK 호환/본문 제한·현재 공식 가격/정책·회사/자료/횟수/예산·사람 동의/인수와 실제 전송 허가의 별도 검토가 남는다.

기존 고정 운영 검증의 완료 run/비용/승인 횟수는 재사용 권한이 아니다. 백업27개 및 실제 KOSIS/벤처인 최종제출·접수/영속 결과는 미해결 범위로 유지한다. 이번 보호7개 및 보존 대상 앱/설치SDK59개 SHA 불변을 확인하며 문서/인계만 변경한다.
