## 2. 최소 어댑터 입력·출력

## 3. 렌더·장착·구독·명시 시작의 순서

1. 합성 호출자가 React 장착 전에 retainer와 screen을 한 번 생성하고 참조를 보관한다. 반복 가능한 함수형 initializer가 필요하다면 이미 만들어진 참조를 그대로 반환하는 순수 초기화만 허용한다. 새 retainer로 두 번째 claim을 피하는 것도 금지한다.
2. render는 stable getSnapshot과 자기 token/원래 handle 및 **현재 props**로 만든 frame의 selectDisplay만 읽는다. frame 객체 자체가 새로 만들어져도 새 호출/외부 관측이 없어야 한다. render 중 ref.current 갱신, attach/detach/commitFrame/inspect·Promise 관측/타이머/취소를 하지 않는다. 폐기된 concurrent render가 원래 현재 호출을 무효화해서도 안 된다.
3. post-commit layout setup이 attachView로 자기 token을 얻고 setup 등록 객체를 보관한다. 반환null은 고정 연결 실패이며 재시도/새 연결을 만들지 않는다. token이 없는 최초 render는 표시null·동작 불가다. 새 token을 React 상태에 반영해 다음 render/구독이 원래 setup을 가리키게 한다.
4. useSyncExternalStore의 subscribe는 해당 setup token으로 screen.subscribe를 연결한다. getSnapshot 함수는 고정 순수 getter이고 subscribe 함수는 같은 token 동안 안정돼야 한다. 구독 등록 전후 최신 snapshot을 순수하게 대조하며 React의 post-subscribe 재대조와 함께 누락을 막는다. 구독은 attach/commitFrame/prepare/start를 실행하지 않는다.
5. layout frame 반영은 현재 commit의 props와 보관된 원래 handle로만 commitFrame을 수행한다. handle이 없으면 조회를 만들지 않는다. 같은 값의 반영은 snapshot 참조/통지 반복 루프를 만들지 않아야 한다. 렌더에서 새 props와 맞지 않는 성공/오류는 layout 반영 전에도 숨긴다.
6. 명시 사용자 동작에서 자기 setup이 아직 current인지 확인하고 원래 입력을 고정한다. prepare 성공 직후 같은 setup의 handle/ticket을 ref에 먼저 보관하고 현재 commit frame에 latest=원래 ticket을 넣어 start≤1을 호출한다. 첫 await보다 앞선 순서다. 입력 getter/prepare 중 화면 교체가 발생하면 돌아온 결과와 token/등록/handle을 재대조하며 옛 callback이 새 화면을 시작하지 않는다. render/effect/구독/완료 통지는 이 동작을 대신 실행하지 않는다.
7. 구독 cleanup은 **그 구독의 반환 unsubscribe**만 실행한다. layout setup cleanup은 캡처한 자기 token만 detach하고 자기 setup ref일 때만 비운다. 최신 ref에서 token을 새로 읽어 분리하지 않는다. late notification은 캡처한 등록이 아직 active인지 확인한다. handle의 delivery/completion을 React마다 다시 then으로 구독하지 않는다.
8. StrictMode의 layout/passive disconnect→reconnect는 detach/새 token·자기 등록 교체로 처리한다. screen.close를 호출하거나 retainer/screen을 다시 생성하지 않는다. 의도적 부모 종료의 close는 외부 호출자가 별도 명시한다. 일반 unmount cleanup만으로 의도적 종료와 개발 probe를 구분했다고 가정하지 않는다.

SSR/hydration은 후속 합성 검증의 지원 완료 범위가 아니다. hook이 getServerSnapshot을 제공한다면 module의 안정된 빈 sentinel만 반환하고 원래 회사/보관자의 실행·조회/claim은0이어야 한다. 서버에서 screen factory를 만들거나 render 결과에 원래 I/O/개인 데이터를 직렬화하지 않는다. 실제 RSC 경계와 hydration 지원은 별도다.
