# 19. 후보 상태의 명시적 추천 분류

상태: 구현과 관련 회귀·독립 검토 완료, 전체 통합·배포 검증 대기. 제품완성 잔여 범위 R04 중 후보 상태 3종을 다룬다. 17번의 선택 이유·변경 이력은 재사용하고, 추천 분류를 사실 확인이나 사람의 승인으로 취급하지 않는다.

## 직접 요구와 현재 차이

`기획/아이템도출_사업계획서자동작성_상세기획.md` 4.1의 L66~74는 ‘현재 신청 후보’, ‘근거 확인 후 후보’, ‘향후 개발 제안’을 구분하고 미래 제안을 이미 달성한 성과로 사용하지 않도록 요구한다.

현재 후보의 `stage`는 개발 단계에 관한 자유 문장이고 `recommendation`은 추천 설명이다. 둘 중 하나의 키워드를 보고 분류를 자동 확정하지 않는다. AI 분석 프롬프트의 ‘새 제안은 제안이라고 표시’ 요구는 이미 있지만, 후보마다 같은 의미로 저장·표시할 명시 필드는 없다.

## 최소 계약

새 pure 모듈 `web/src/lib/studio-candidate-classification.ts`에 다음을 둔다. Node 암호화 모듈이나 전체 회사 schema를 런타임으로 가져오지 않는다.

| 값                | 표시              | 의미와 한계                                                                                      |
| ----------------- | ----------------- | ------------------------------------------------------------------------------------------------ |
| `unknown`         | 후보 구분 미확인  | 구형 데이터 또는 현재 자료로 분류하지 않은 상태                                                  |
| `current`         | 현재 신청 후보    | 현재 보유·개발 내용에 연결된 후보라는 추천 분류. 기술 보유·권리·사실을 검증 완료했다는 뜻이 아님 |
| `evidence-needed` | 근거 확인 후 후보 | 기업 설명에 연결되지만 관련 활동·권한·근거 확인이 더 필요한 추천 후보                            |
| `future-proposal` | 향후 개발 제안    | 아직 수행하지 않은 확장 방향을 미래 계획으로 검토하는 후보. 과거 성과로 표현하지 않음            |

모듈은 enum schema·타입·한국어 labels/help와 `getCandidateClassification({ classification? })`를 export한다. `Candidate`와 17번의 선택 당시 후보 스냅샷에는 `classification`을 선택 속성으로 추가한다. 사유는 기존 `recommendation`을 사용하며 같은 설명을 별도 필드에 중복 보관하지 않는다.

카드와 선택 이력에는 ‘추천 분류이며 사실·기관 적합성·사용자 검토 완료를 뜻하지 않음’을 표시한다. 분류 값으로 점수·순위·합격 가능성을 만들지 않는다.

## 구형 데이터와 해시 보존

저장 schema에 `.default('unknown')`을 넣어 구형 객체에 실제 키를 삽입하지 않는다. 구형 분석·선택 스냅샷에는 속성이 없는 상태를 유지하고 표시 accessor만 `unknown`을 반환한다.

이 경계는 중요하다. 분석과 선택 후보의 전체 내용을 17번의 `analysisDigest`/`candidateDigest`, 로컬 준비 체크포인트가 참조한다. 읽기만으로 새 기본 필드를 끼우면 기존의 유효한 선택과 준비 기록을 변경된 자료로 오판할 수 있다. 기존 DB body·선택 이유·분석 해시·준비 해시는 마이그레이션 없이 그대로 유지해야 한다.

신규 후보에는 분류를 명시한다. 새 분석의 분류가 달라지면 후보 내용 변경에 포함되며, 이전 선택을 새 분석의 선택으로 이어 붙이지 않는다. 선택 이력은 당시 분류를 보존하고 현재 분류로 덮어쓰지 않는다.

## 자료 정리 모드와 AI 모드

- 자료 정리 모드는 현재처럼 원문 발췌와 질문을 만든다. 문서 존재·문자 수·‘개발’ 같은 키워드만으로 상태를 추정하지 않고 신규 후보에 `unknown`을 명시한다.
- 새 AI 분석 응답은 전용 structured-output schema에서 `classification` enum을 필수로 받는다. 저장 데이터의 optional 계약과 AI 출력의 필수 계약을 구분한다. 알 수 없는 값이나 ‘확정/합격’ 같은 값을 조용히 허용하지 않는다.
- AI는 후보의 출처·현재/미래 설명을 보고 분류를 제안할 수 있다. 인용이 있다는 사실만으로 검증 완료를 주장하지 않고 분류가 불명확하면 `unknown`으로 반환한다.
- 원고 생성 입력에는 선택한 후보의 분류를 전달한다. `future-proposal`은 미래 계획·가정·필요한 수행 조건으로만 다루고 과거 활동으로 바꾸지 않도록 지시한다. `current`도 사실 검증 완료를 뜻하지 않는다고 명시한다.
- 기존 정확 인용 검사, 심사 보장 표현 차단, `needsConfirmation`, 원고 검토·확정 제한을 유지한다. 새 분류가 선택 이유·명시 선택·근거 확인을 대신하지 않는다.

분류만을 이유로 기존 원고를 자동 수정하거나 새 원고를 만들지 않는다. 미래 제안의 선택 자체를 일률적으로 금지하는 새 규칙도 추가하지 않는다. 실제 AI 문장의 의미·품질 검증은 기존 품질 검증 범위에서 별도 수행하며, 프롬프트 시험만으로 미래/성과 혼동이 완전히 해결됐다고 표시하지 않는다.

## 화면 범위

분석 후보 카드와 선택 당시 이력에 분류와 짧은 설명을 표시한다. 구형 후보는 미확인, 과거 선택 기록은 당시 값으로 표시한다. 분석 모드와 추천 분류를 구분한다.

이번 최소 범위에서는 사용자 분류 정정 mutation, 추가 승인 체크박스, 별도 분류 변경 이력을 만들지 않는다. 후보 재분석과 기존 명시 선택·이유 저장 경로를 사용한다. 원문과 사람이 확인한 주장의 장기 이력은 R05에서 별도로 다룬다.

## 소유 범위와 회귀 검사

구현 범위는 새 pure 분류 모듈, `studio-schema.ts`의 후보 구간, AI 분석 전용 응답 schema와 분석·작성 프롬프트, 자료 정리 후보 생성, `studio-candidate-selection-types.ts`의 후보 스냅샷, 분석 카드/선택 이력의 작은 표시다. 18번 연락처의 공용 schema/storage 편집과 시작 시점을 조율한다. 연락처·기관 실행·회사 실제 자료는 다루지 않는다.

필수 회귀는 다음과 같다.

1. 구형 분석/선택 스냅샷에 속성을 삽입하지 않고 직렬화 결과와 서버 digest를 보존한다. 현재 유효한 선택과 준비 체크포인트도 유지한다.
2. 신규 자료 정리 후보는 `unknown`, 신규 AI 후보는 3종과 `unknown`을 정확히 저장·표시한다. invalid enum은 고정 오류로 거부한다.
3. 같은 후보 ID에서 분류가 변경되면 전체 내용 digest가 달라져 이전 선택으로 새 분석을 승인하지 못한다. 과거 이력은 원래 분류를 보존한다.
4. 추천 분류가 기존 사실 상태·원고 확인/검토·기관 단계·업무 완료를 승격시키지 않는다.
5. 생성 요청에서 미래 제안/현재 후보의 의미를 구분하고, 정확 인용·확인 필요·보장 표현 방어를 보존한다. 시험은 모의 AI와 합성 자료만 사용한다.
6. 구형 후보 표시, 3종 표시, HTML escaping, 기존 선택/dirty/생성 잠금의 UI 회귀를 확인한다.

17번과 이 항목의 구현·회귀가 모두 끝나면 R04의 선택 이유/이력과 명시적 후보 상태 차이를 닫을 수 있다. 추천 분류의 실제 적합성과 생성 품질은 G06의 검증 결과로 별도 기록한다.

## 구현 검증 기록

2026-09-25, 분류 전용 11개 및 AI/자료 정리 엔진의 신규 9개를 포함해 관련 5개 파일 102개 검사가 통과했다. 구형 DB body·선택 snapshot·digest·준비 현재성 보존, 분류 변경 후 과거 이력 보존과 stale, 새 AI enum 필수·미지원 값 거부, 자료 정리 unknown 및 UI 표시를 합성 자료로 확인했다. 전체 TypeScript·소유 파일 lint·형식·diff 검사와 독립 읽기 검토를 통과했으며 추가 P2 지적은 없다. 실제 회사 자료·외부 AI·기관 동작은 실행하지 않았다. 이 결과는 실제 생성 문장의 의미·품질 검증이나 전체 제품의 완료를 뜻하지 않는다.
