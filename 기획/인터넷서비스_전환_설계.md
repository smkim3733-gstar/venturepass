# 인터넷 서비스 전환 설계

작성일: 2026-10-25. 상태: 1단계(저장 경계)·2단계(Postgres 저장소) 구현, 3단계부터 진행 예정. 외부 계정 생성·비밀 등록·배포는 하지 않았다.

구현 메모: 저장소 전체를 비동기로 다시 쓰지 않고, 요청마다 회사 한 건을 메모리 SQLite에 올려 기존 `StudioStore` 코드를 실행한 뒤 revision 조건부 쓰기로 저장하는 세션 방식(`studio-case-session.ts`)을 택했다. 변경 규칙 중복이 없고 기존 시험이 서버 동작도 보증한다.

## 1. 확정한 결정 (2026-10-25 사용자)

| 항목 | 결정 |
|---|---|
| 이용자 | 한기평 내부 담당자만. 초대·승인제, 고객 로그인·공개 가입 없음 |
| 사이트 | 벤처패스 별도 사이트(Partner-hub와 분리) |
| 인프라 | Vercel(웹) + Supabase(Postgres DB·비공개 Storage) — Partner-hub와 같은 구성 |
| 벤처인 자동 입력 | 이 PC 로컬 앱에 유지. 웹 서비스는 자료·계획서·진행 관리 담당 |

`공유서비스_전환검토안.md`의 권장안(초대형 내부 협업 서버 + 공식 실행은 기존 PC)을 채택한 것이다.

## 2. 핵심 기술 과제

1. **저장소 비동기화.** `StudioStore`는 `node:sqlite`의 동기 API로 회사 문서(JSON) 한 행을 revision CAS로 갱신한다. Vercel 함수에는 영구 디스크가 없으므로 Supabase Postgres를 네트워크로 사용해야 하며 저장소 공개 메서드가 비동기가 된다.
   - 결정: 변경 규칙(레코드에 적용하는 순수 함수)은 그대로 두고, 읽기·CAS 쓰기만 `CaseRepository` 인터페이스로 분리한다. 구현은 기존 SQLite(로컬)와 Postgres(서버) 두 가지다.
   - Postgres 표: `studio_cases(id, organization_id, revision, evidence_revision, body jsonb)` + `UPDATE … WHERE id=$1 AND revision=$2` CAS. 문서 구조와 기존 시험의 의미를 유지한다.
2. **조직·사용자 권한.** 모든 회사는 조직에 속한다. 모든 읽기·쓰기·다운로드에서 서버가 로그인 사용자의 멤버십으로 회사 접근을 검사한다. 요청의 조직·사용자 ID는 신뢰하지 않는다.
3. **원본 파일.** Supabase 비공개 Storage에 `org/case/source` 경로로 불변 저장하고 서버가 계산한 SHA256·크기를 DB와 대조한다. Vercel 요청 본문 한도(약 4.5MB) 때문에 12MB 업로드는 서버가 발급한 짧은 수명의 서명 업로드 권한으로 브라우저가 Storage에 직접 올린 뒤, 서버가 크기·SHA·형식을 확인하고 본문을 추출한다.
4. **로컬 전용 기능 분리.** 서버 모드에서 끄는 기능: 벤처인 계정 보관·Edge 실행·입력·첨부(DPAPI·Playwright), Windows OCR, 품질평가 개발 도구, 로컬 백업 CLI. 화면에서 숨기고 API는 서버 모드에서 404/403으로 거절한다.
5. **로컬 안전장치 유지.** 로컬 모드의 127.0.0.1 바인딩·Host/Origin 검사는 그대로 둔다. 서버 모드는 환경변수 하나로 켜지지 않고, 인증·권한·저장소 구성이 모두 있을 때만 동작한다(빠진 설정이 있으면 업무 API 503).
6. **동시 작업.** `globalThis` 잠금(로컬 준비·OCR 등)은 여러 서버 인스턴스에서 공유되지 않는다. 서버 모드의 로컬 준비는 DB의 작업 기록(clientRequestId·revision CAS)으로 중복을 막는다. 현재 준비 기록·요청 번호 구조를 그대로 사용한다.

## 3. 인증

- 로그인: 이메일 + 사이트 전용 비밀번호. 관리자(대표)가 담당자를 초대하거나 가입 신청을 승인해야 이용 가능(Partner-hub 방식).
- 구현 후보: Supabase Auth(이메일·비밀번호, 초대 메일)를 사용하고 앱 DB에 `organizations`, `memberships(role)`을 둔다. 직접 비밀번호를 저장하지 않아 위험이 줄어든다.
- 역할: 관리자(초대·권한·삭제), 담당자(작성·편집), 조회자(읽기). 원본 다운로드는 담당자 이상.
- 세션 쿠키는 HttpOnly·Secure·SameSite=Lax, 변경 요청은 Origin 검사 유지.

## 4. 단계

| 단계 | 내용 | 외부 행동 필요 여부 |
|---|---|---|
| 1 | `CaseRepository` 분리(SQLite 구현), 저장소 메서드 비동기 전환, 기존 시험 통과 | 없음 |
| 2 | Postgres 구현 + 스키마/마이그레이션, 로컬 Postgres 대체(PGlite)로 같은 시험 실행 | 없음 |
| 3 | 조직·멤버십·권한 검사 계층과 서버 모드 스위치, 로컬 전용 기능 차단, 교차 조직 거부 시험 | 없음 |
| 4 | 인증 연결(Supabase Auth 어댑터 + 가상 인증 시험), 로그인·초대 화면 | 없음(실제 연결은 6단계) |
| 5 | Storage 어댑터와 서명 업로드·다운로드, 원본 SHA 대조 | 없음(가상 Storage로 시험) |
| 6 | 운영 구성: Supabase 프로젝트·Vercel 프로젝트 생성, 환경변수·비밀 등록, 관리자 계정 | **대표님 필요** |
| 7 | 비공개 미리보기 배포·합성 자료 수용 시험 → 실제 담당자 초대 | **대표님 승인 필요** |
| 8 | (선택) 기존 PC 자료 이전 도구 — 구현(`pnpm data:to-web`, 2026-10-26). 회사 기록·원본만, 미리 보기 기본·덮어쓰기 없음·중복 회사 건너뜀 | 실제 이전은 대표님 설정 후 |

1~5단계는 이 PC에서 혼자 개발·시험할 수 있다. 6단계부터는 대표님 계정 작업과 승인이 필요하다.

## 5. 대표님이 6단계에서 하실 일 (미리 안내)

1. Supabase에서 새 프로젝트 생성(서울 지역 권장) → Project URL, anon key, service role key 확인.
2. Vercel에서 새 프로젝트 생성 후 이 GitHub 저장소(`web` 폴더) 연결.
3. Vercel 환경변수에 Supabase 값과 `OPENAI_API_KEY` 등록(채팅에 붙여 넣지 않음).
4. 관리자 계정으로 쓸 이메일 지정.

## 6. 비용·위험

- Supabase·Vercel 무료 한도를 넘으면 월 비용이 생길 수 있다. 사용량은 담당자 수·자료 용량에 비례한다.
- OpenAI 사용은 호출마다 비용이 든다. 서버 모드에서도 앱의 전송 확인·동의 절차를 유지한다.
- 실제 고객사 자료가 외부 서버에 저장된다. 보관·삭제 정책과 접근 담당자를 운영 전에 정한다.
- 저장소 비동기 전환은 범위가 커서 단계 1에서 기존 5,444개 시험을 기준으로 동작 동일성을 확인한다.
