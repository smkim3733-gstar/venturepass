## 기존 실행 경계의 의미

보완 실행은 원래 clientRequestId와 전체 명령 해시가 같으면 과거 기록부터 반환한다. 이 경로에서 현재 키/모델로 새 owner를 만들거나 재전송하지 않는다. 신규 예약을 COMMIT하고 관측한 호출만 owner를 가지며, 실제 fetch 직전 동기 writer에서 원래 명령/현재 회사와 설정을 다시 대조한다. withCurrentWriter 안에 await를 넣어 확인과 실제 시작 사이에 간격을 만들지 않는다.

네트워크가 시작된 뒤 DB COMMIT이 실패해도 그 요청은 취소된 것으로 간주할 수 없다. 기존 SDK가 시작한 promise를 보존하고 원래 capture를 retain한 뒤 persist하도록 한 원리를 유지해야 한다. 응답 유실/미관측 상태를 자동 재실행하거나 새 nonce로 바꾸지 않는다. 재시작 후 복구는 원래 저장된 capture/기록을 읽으며 새로운 owner를 발급하지 않는다.

현재 보완 결과의 revision 보정은 자기 예약·capture 저장 증가분에만 한정된다. 비교 입력을 최신 회사로 자동 재기준화하거나 승인 뒤 바뀐 원고/근거를 섞는 근거가 아니다. 실제 비교 writer가 생기기 전4I5는 어떤 revision 보정도 하지 않는다.

## 저장소·금액 예산은 별도 설계가 필요하다

- StudioStore는 studio.sqlite를 열고 회사/보완 실행 상태를 쓴다. 보완 실행 계약에는 호출1회/무재시도 한도가 있지만 금액 예약/정산 계약은 없다.
- 품질 저장소는 quality-evaluation/quality.sqlite를 사용하고 studio.sqlite/회사 원본을 열지 않도록 분리돼 있다. 후보 registry/runtime authority·고정 두 단계와 예산 revision/head를 검사한다.
- 양쪽 BEGIN IMMEDIATE는 각 연결의 트랜잭션이다. 두 DB의 회사 revision/비용 예약이 동시에 COMMIT된다고 가정하지 않는다. 한쪽 승인이 다른쪽 쓰기/전송 권한을 만들지도 않는다.
- 실제 비교 실행 전에 기존 원장에 별도 목적을 어떻게 버전 확장할지, 회사 snapshot과 금액 예약을 어떤 단일 권한 경계로 결합할지 결정해야 한다. 실패/재시작/다중 프로세스의 원래 nonce·중복 예약·미확인 비용 보류까지 포함한 저장 전략과 마이그레이션/복구 검증이 필요하다.
- 이번 감사는 그 구현/원자성 증명이 아니다. 새 병렬 원장·복제 승인·새 예산으로 완료된 사용량을 초기화하지 않는다. SQL형식9/DDL·과거 v1/v2 bytes·완료 실행/nonce/승인/예산을 변경하지 않았다.

## 다음4I5 — 내부 응답 캡처·비교 어댑터

### 입력과 처리 순서

새 server-only 내부 함수의 명칭은 구현 시 정하되 계약은 아래처럼 좁힌다.

1. 이미 읽은 회사 snapshot, 기존 strict public comparison request command/expected identity, 공급된 Responses 형태 객체만 받는다. 사용자 endpoint/키·설정·승인 boolean·DB 핸들·SDK client를 받지 않는다.
2. 첫 동작으로 기존 captureProviderResponse를 동기 호출해 허용된 필드를 복사한다. 어떤 await/현재 회사 검사/본문 파싱보다 먼저 캡처한다. 이후 원래 공급 객체를 다시 읽지 않는다.
3. 캡처할 수 없으면 부분 결과를 사용하지 않고 안전한 오류 코드/상태를 반환한다. 허용 필드/중첩 JSON의 getter·toJSON·순환·비정상 객체·크기 검사는 기존 함수를 재사용한다. 기존 helper가 읽지 않는 최상위 추가 필드를 모두 검사/보존했다고 주장하지 않는다.
4. 캡처된 응답에서 보고 메타데이터를 읽고 원래 명령/identity를 strict 검사한다. inspectPublicClaimComparisonRequest로 현재 snapshot에서 요청을 다시 만들고 원래 digest/크기/모델·회사/revision/claim/선택 본문 hash를 대조한다.
5. 현재 상태가 바뀌었거나 요청이 잘못되면 capture/보고 메타데이터는 메모리에 남기고 비교 의견은 null이다. 다른 모델/미완성/거절/잘못된 출력도 같은 원칙이다. 실패 결과가 DB에 보관됐다는 뜻은 아니다.
6. 아래 구조를 통과한 단일 text만 기존 parseProviderResponseOutput으로 JSON 추출하고 validatePublicClaimComparisonRequestResponse로 정확한 주장·공개 발췌 인용/선택·의견을 대조한다. 새 사실 파서나 새 의미 정답 판정을 만들지 않는다.

### 새 어댑터가 허용할 응답 부분집합

- 응답 status=completed, 비어 있지 않은 id(최대500자)/model(최대200자). 최초 지원은 model 문자열이 원래 명시 모델과 정확히 같아야 한다. 별칭/스냅샷 이름은 자동 연결하지 않는다.
- output은 최대50개이고 message 또는 reasoning만 허용한다. message는 정확히1개, role=assistant, status=completed, content는 output_text1개다. 도구 호출/알 수 없는 종류/중복 메시지·텍스트/refusal은 비교 의견을 만들지 않는다. reasoning은 내용/판단의 근거로 사용하지 않는다.
- text는 기존 responseCharacters=240000 UTF-16 단위 이하다. JSON fence/설명문을 제거하거나 고쳐서 받아들이지 않는다. capture의4MiB와 domain text24만자는 서로 다른 상한이다. 기존 JSON 추출의 바이트 상한도 유지한다.
- 이것은 이 앱의 제한된 합성 지원 계약이다. 현재 실제 제공자/모델의 응답 형식이나 지원을 확인한 것처럼 표시하지 않는다. 원래 응답 모델과 문자열이 일치해도 응답 진위를 보장하지 않는다.
- 누락된 id/model/usage/빈 값의 원래 capture는 그대로다. 누락 usage는 null이지0이 아니며 invalid output도 네트워크 미전송/비용0의 증거가 아니다.

### 메타데이터 공통화

현재 providerResponseMetadataSchema는 configuredModel과 requestedTier:default를 요구한다. 공개 비교 요청의 동결 body에는 service_tier가 없으므로 이 값을 자동 추가하거나 default를 사용했다고 보고하면 안 된다.

기존 helper에서 응답의 responseId/requestId/responseModel/responseTier/status와 nullable usage 필드를 읽는 부분만 공통 보고 함수로 추출한다. 기존 providerResponseMetadata는 새 함수와 기존 configuredModel/requestedTier를 결합해 동일한 strict schema/반환 계약을 유지한다. 기존 가격/정산 schema를 넓히지 않는다. 비교 어댑터는 보고 함수만 사용하며 요청 등급은 미지정(null 또는 명시 omitted)으로 표현한다. 실제 request body의 service_tier·system/schema/digest/golden bytes는 바꾸지 않는다.

현재 비용 평가 assessProviderUsage는 generation/review별 financialBasis와 공식 가격/모델·보관 정책에 결합돼 있다.4I5에서는 호출하지 않고 금액/예산 예약·정산·현재 단가를 계산하지 않는다. 보고된 토큰 수는 공급된 객체에 적힌 값일 뿐 실제 청구 증거가 아니다.

### 반환 의미와 권한

결과는 성공/현재 상태 변경/요청 불일치/캡처 실패/미지원 출력 등을 구분하며, 캡처 가능할 때 immutable 사본·보고 메타데이터와 비교 의견(null 또는 기존 검증 결과)을 구분한다. 원래 identity는 비교 입력과의 일관성을 나타내며 공급자 요청 영수증이 아니다. 캡처/오류에는 외부 SDK 예외 본문이나 자격증명을 붙이지 않는다.

source=supplied-response, evidenceOrigin=manual-unverified를 유지한다. 실제 전송 관측/실제 AI 실행·사실/공식 진위·회사 해당성·전체 원문/현재 유효성·의미 정답/사람 인수·전송/승인/예산/DB 권한은 false다. 원래 capture와 실패가 메모리에 남는 것은 영속 복구 원장 구현이 아니다.

### 새 검증 범위

- 공급 객체를 나중에 바꿔도 캡처/의견이 달라지지 않는지, 현재 회사 revision/본문·claim/선택/identity가 바뀌면 캡처를 남기고 의견을 거절하는지 확인한다.
- 정확한 domain 인용의 성공과 인용·선택/주장 변조의 실패가 기존4I1/4I2 검사에 연결되는지 확인한다.
- completed/assistant·허용 output 종류/모델 불일치·미완성/refusal/잘못된 JSON/중복·text 크기에서 의견이 없는지 확인한다.
- getter/toJSON/순환/초과 캡처 실패, nullable usage·미지정 요청 등급, 모든 권한 false와 반환 사본을 확인한다. 기존 capture 전체 corpus를 복제하지 않고 새 조합에서 필요한 경계를 확인한다.
- 기존 providerResponseMetadata의 반환과 품질 실행 계약을 변경하지 않았음을 관련 회귀로 확인한다.4I1/4I2 fixture와 기존 helper/검사를 재사용한다.
- import/호출 중 SDK 생성·fetch·키/설정·DB 열기/쓰기를 금지한 합성 검증으로 수행한다. 실제 AI 의미 품질/모델 지원/청구·사람 인수를 시험했다고 집계하지 않는다.
- 필요한 관련 회귀→lint→typecheck→격리 build:local을 종료코드 확인 뒤 순차 수행한다. 사용자 화면 변경이 없으면 새 HTTP/브라우저 검증을 만들지 않는다. 다음 구현의 시험 수는 실제 결과로만 보고한다.

## 이후 실제 실행에 필요한 조건 — 이번 미완료

공개 비교만의 명시 목적/전체 요청 identity·fresh nonce·모델/컨텍스트/가격/보관·금액 상한과 사용자 전송 동의를 기존 승인 체계에 별도 버전으로 연결해야 한다. 단일 권한 원장/트랜잭션 설계가 먼저이고, 그 다음 fresh COMMIT owner·fetch 직전 동일 wire 확인·capture 우선 보존·원래 nonce 재호출/미확인 복구를 연결한다. 현재 builder에 없는 실행 조건을 추가하려면 새 계약 버전/미리보기 동의가 필요하며 기존 bytes를 몰래 바꾸지 않는다.

이러한 소스/합성 구현은 사용자에게 실제 호출 승인을 요청하기 전에 구체화할 작업이다. 실제 유료 호출은 현재 승인 범위 밖이고 과거 완료 validation 실행/예산을 재사용하지 않는다. 현재4I5는 이 외부 결정 없이 가능하므로 필수 결정0개/ACTIVE다.
