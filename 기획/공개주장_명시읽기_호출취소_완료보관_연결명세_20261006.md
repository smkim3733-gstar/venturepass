# 4I39 명시 읽기 호출·취소·완료 보관 연결 명세

2026-10-06 — **4I39 명시 읽기 호출·취소·완료 보관의 연결 계약 점검 완료**

acad0c2의 handler/receiver/body/ticket과 기존 PublicClaimPreview·ClaimReviews·studioFetch·미리보기 route·원고 이동/같은 service 소스를 실행 없이 대조했다. 이번은 문서 변경이며 다음 호출 객체 구현이나 실제 화면 연결 시험은 아니다.

기존 PublicClaimPreview는 입력 미리보기만 요청한다. 첫 await 전에 command/snapshot/controller를 보관하고 clear·effect 정리에서 abort 후 현재 controller 참조를 지운다. ClaimReviews는 회사 id/revision 변경으로 remount하고 편집·저장 상태도 미리보기를 교체한다. 이 동작은 저장 결과 Request/Response completion 보관 구현이 아니다. studioFetch는 먼저 response.json()을 수행하므로 전용 제한 receiver를 대신할 수 없다.

handler/receiver/ticket 조합은 현재 시험에만 있고 실제 service 보관자·stored-review route/UI는 없다. 같은 service와 원래 선택을 신뢰 경로에서 받은 고정 주입 계약을 유지한다. 최신 run 검색·미리보기/쓰기 receipt로 신원 추정·새 registry/store/session/owner로 빈 취득 경로를 보충하지 않는다.

다음 최소 연결은 호출자가 보관할 단일 비활성 호출 객체다. 회사/snapshot/revision·원래 run/dispatch/mode·claim/plan/발췌/section과 ticket을 첫 await 전에 고정하고, 보관 뒤 명시 start를 한 번만 한다. 주입 startRequest는 handler의 원래 operation을 동기로 반환하며 연결은 그 response/completion/inspect 참조를 await 전에 보관한다. receiver가 제공한 자기 signal을 Request에 전달한다. 이미 시작한 Request의 response Promise만 넘기는 방식은 요청 취소/완료 보관을 보장하지 않는다.

빠른 실패 전달, 원래 Request completion, Response 수신 completion을 따로 보관한다. completion은 원래 I/O 관측 종료이며 cleanupFailed:false와 다르다. 정상 결과 표시는 양쪽 completion과 정상 정리를 확인한 뒤 기존 ticket.accept를 통과해야 한다. 오류에도 ticket.isCurrent를 적용한다. pending·cleanupFailed·잘못된 주입 영수증을 화면 닫힘이나 시간 경과로 정상 종료시키지 않는다.

화면의 회사/선택/snapshot/revision·편집/차단/닫힘·ticket 변경은 이미 표시한 exact와 늦은 성공/오류를 모두 버린다. 취소한 호출은 재사용하지 않는다. 호출자는 화면 참조를 지우더라도 원래 호출 객체와 미종료 completion·정리 실패 상태를 계속 보관해야 한다. 다음 합성 연결은 이 보관 계약을 검증하며 실제 React 부모/운영 보관자를 설치하지 않는다.

Request/Response 정리가 끝나도 원래 service의 SQL/회사 guard/lease·pending ack/불명 명령 복구는 별도다. 연결은 retire/session close/recover/ack/INSERT/정산/hold 해제를 호출하지 않는다. 기존 service의 명시 재조회/원래 명령 복구만 그 책임을 처리한다. 각 요청/수신의30초 단조 기한은 그대로이며 동기 SQL/JSON 선점이나 전체60초 SLA가 아니다.

historical은 과거 의견과 not-checked, inspect-current는 현재 관측 상태를 따로 표시한다. exact는 원래·관측·화면 revision의 대조를 계속 요구하고 changed/unavailable을 자동 재조회·저장/채택 권한으로 바꾸지 않는다. 원래 PlanReviewTarget과 수동 판단·원고 채택의 별도 nonce/CAS 동선은 유지한다. source synthetic·owner:null·runtimeObserved:false·authority:false 및 원래 nonce/bytes/requestedTier:null/hold는 그대로다.

## 2. 다음 최소 연결과 입력

다음4I40의 대상은 **명시 호출 하나의 비활성 객체**다. 임시 명칭은 createComparisonReviewInvocation이며 실제 모듈명/내부 타입은 구현 때 기존 명명에 맞춰 정할 수 있다. UI·HTTP·운영 설치를 함께 완료했다고 표시하지 않는다.

신뢰한 호출자는 이미 원래 service와 원래 run 선택을 알고 있어야 한다. 그 호출자가 고정 handler에 대한 동기 startRequest(query, signal) 포트를 제공한다. 연결 모듈은 service·handler·store를 직접 생성/import하지 않고 주입 포트의 참조를 고정한다. 합성 시험 어댑터만 기존 handler에 native Request를 만들어 전달한다. 실제 fetch 기본값은 없다.

| 입력 | 고정 시점과 규칙 |
| --- | --- |
| sequence | 안전 정수이며 명시 화면 호출/변경마다 증가. 같은 번호라도 다른 ticket 객체는 이전 응답을 수락하지 않는다. |
| snapshot | 현재 화면 객체 참조와 id/revision scalar를 첫 await 전에 고정. 단순 deep clone으로 참조 검사를 대체하지 않는다. |
| expected | 기존 ComparisonReviewDisplaySelection의 원래 run/dispatch/mode·selection·binding·section을 독립 사본으로 보관한다. 원래 selection.companyRevision과 화면 revision을 임의로 같게 덮어쓰지 않는다. |
| query | 별도 임의 객체를 받기보다 고정 expected의 runId/dispatchCommandDigest/mode만 기존 copyComparisonReviewQuery로 추출한다. query와 ticket이 다른 선택을 보지 않게 한다. |
| signal | 이 명시 화면 호출의 AbortSignal. 이를 서버 service/SQL/guard 포트로 넘기지 않는다. |
| startRequest 또는 미지원 | 신뢰한 로컬 동기 함수 참조. 반환은 원래 handler operation의 response Promise·completion Promise·inspect 함수다. 참조 교체·객체 변경으로 새 서비스를 취득하지 않는다. 미주입이면 명시 미지원이며 호출0이다. |

모든 입력 사본/검사를 먼저 끝낸 뒤 receiver를 생성한다. 잘못된 초기 입력에서 불필요한 timer/Request를 만들지 않는다. 객체를 호출자가 보관한 다음 명시 start를 호출하므로 보관 전에 Request가 시작되지 않는다. start에는 현재 frame을 주어 기존 ticket.isCurrent를 확인하고, 중복 start는 기존 결과를 반환하되 주입 함수를 다시 부르지 않는다. 처음부터 닫힘·blocked·dirty·stale·aborted이면 시작0이다.

이 객체의 query/ticket은 표시 대조용이며 DB 접근 capability나 사람 동의가 아니다. 사본을 외부에 노출할 때도 내부 보관본 변경이 불가능해야 한다. callback에 주는 query 역시 내부 보관본을 변경할 수 없는 사본이다. frame 입력은 현재 화면 상태를 알려 주는 신뢰한 같은 프로세스 값이며 악성 JavaScript 전체를 격리하는 인증 장치는 아니다.

## 3. 시작·표시·완료의 순서

1. 원래 선택·query·ticket·주입 함수 참조를 동기로 고정한다. 호출 객체를 반환하여 호출자가 보관한다. receiver의 생성부터30초 기한은 유지하며 start에서 재생성하거나 갱신하지 않는다.
2. 명시 start의 현재 frame을 대조한다. receiver.start에 넣는 함수는 receiver가 제공한 자기 signal을 startRequest에 전달한다. 주입 포트는 그 signal로 native Request를 생성해 같은 handler.handle을 부른다.
3. startRequest가 동기로 돌려준 원래 operation과 response/completion/inspect를 await 전에 보관한다. response의 성공/거절과 요청 completion의 관측을 즉시 연결한다. Request를 먼저 실행하고 response Promise만 나중에 넘기는 패턴은 채택하지 않는다.
4. response는 기존 receiver의 단일 reader·한도·fatal UTF-8·strict wire를 통과한다. 임의 ready DTO를 ticket에 직접 주입하는 별도 통로는 만들지 않는다.
5. 빠른 수신/요청 오류는 고정 코드로 전달할 수 있지만 원래 I/O 관측과 정리는 계속 보관한다. 성공 DTO는 양쪽 completion을 관측하고 cleanupFailed가 모두 false일 때만 표시 후보로 승격한다.
6. 표시 시점마다 최신 frame을 받아 같은 호출 객체에 보관된 성공 후보에 ticket.accept, 실패에는 ticket.isCurrent를 적용한다. 외부에서 다른 호출의 DTO/예외를 주입해 이 객체의 결과로 만들지 않는다. false/null이면 표시 폐기이며 완료/정리 상태는 유지한다.
7. 화면이 바뀌면 caller가 latest ticket을 교체하고 이미 표시한 결과/오류도 지운다. 취소한 호출은 새 프레임이 같아져도 재사용하지 않는다. 새 명시 클릭은 새 호출 객체이며 자동 재조회는 없다.

요청/응답 정상 completion을 기다리는 성공 경로에 별도 무제한 재시도나 추가 타이머를 붙이지 않는다. 성공 본문은 도착했으나 요청 정리가 아직 남아 있으면 표시 대기다. 취소/실패는 빠르게 끝내되 completion은 계속 pending일 수 있다. completion 두 개가 끝나도 그 자체를 서버 정리 완료로 보고하지 않는다.

## 4. 보관자와 종료 의미

| 수명/상태 | 보관자 | 종료/폐기 조건 |
| --- | --- | --- |
| 최신 화면 ticket·표시 | 화면 호출자 | 선택/회사/snapshot/revision/편집/차단/닫힘/unmount/취소 때 표시 무효화 |
| 요청 operation | 명시 호출 객체, 그 객체를 계속 보관한 호출자 | 원래 Request read/cancel/pump 관측을 completion/inspect로 확인. timeout/화면 finally로 대체 금지 |
| 응답 receiver | 같은 명시 호출 객체 | 원래 start/late Response/read/cancel 종료까지 보관. cancel/release 실패도 남김 |
| 호출 전체 관측 | 명시 호출 객체 | 요청이 실제 시작되지 않았음이 확정됐거나, 요청/응답 양쪽 원래 completion 관측이 끝남. cleanupFailed는 별도 sticky 실패다. |
| SQL/guard/lease·pending ack·원래 명령 | 기존 동일 service와 신뢰한 서버 보관자 | 기존 canRelease/자기 정리·명시 원래 명령 복구 계약만 사용 |

다음 객체는 각 completion·inspect를 노출하거나 그 동일 의미의 읽기 전용 집계 상태를 제공한다. 최소한 요청의 not-started/pending/settled/unavailable, 응답의 started/delivered/settled/cleanupFailed와 호출의 cancelled/표시 상태를 구분한다. 집계 settled는 **원래 I/O 관측 종료**이지 성공적인 자원 정리나 조회 성공이 아니다. 정상 폐기 가능 조건에는 양쪽 정리 실패 없음이 추가된다. cleanupFailed인 객체는 자동 성공 처리/잊기를 하지 않고 상태를 보관한다.

호출 객체는 전역 Map/registry나 서버 owner가 아니다. 다음 합성 caller는 화면 ticket 참조를 교체하거나 화면을 닫아도 이전 객체의 강한 참조를 유지하고, 원래 completion/실패 상태를 확인하는 동작을 검증한다. 실제 React remount 위에서 이 객체를 보관할 부모와 운영 보관자는 아직 설치하지 않는다. 브라우저 종료·프로세스 강제 종료·전원 차단 후 영속 보관을 보장하지 않는다.

주입 포트는 동기 operation 반환을 보장해야 한다. 호출 전에 미주입/미지원이면 시작0을 확정할 수 있다. 호출한 뒤 throw·Promise 대신 잘못된 영수증·누락된 completion을 받으면 요청 시작 여부/정리를 추정하지 않는다. 고정 실패를 전달하고 request unavailable/정리 확인 불가 상태를 보관하며 전체 completion을 정상 종료로 만들지 않는다. 이미 시작한 뒤 영수증 없이 예외를 던지는 어댑터는 계약 위반이다. 새 operation 생성·타이머 만료·반복 호출로 수선하지 않는다. 같은 프로세스의 임의 callback을 안전한 서버로 인증하는 범위는 아니다.

원래 요청/응답 Promise의 rejection observer는 표시 폐기 뒤에도 유지한다. completion 거절 또는 inspect throw/불일치는 정리 확인 실패다. unhandled rejection이나 임의 오류 message/stack·경로 노출을 만들지 않는다. 정상 handler completion은 resolve하지만 주입 포트 실패 시험에서도 실패를 숨기지 않는다.
