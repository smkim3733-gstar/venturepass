## 2. 신뢰한 입력과 고정된 같은 서비스

다음4I38은 운영 경로를 설치하지 않는 factory/handler 합성이다. 이름은 구현 시 조정할 수 있으나 다음 책임은 고정한다.

- 신뢰한 호출자는 기존에 소유한 같은 IsolatedPublicComparisonService 참조와 원래 companyId/runId/dispatchCommandDigest, 이 handler가 허용할 localOrigin을 제공한다. 회사/run/dispatch는 원래 서버 보관 명령에서 가져오는 값이다. HTTP body/URL로 이러한 서버 보관 근거를 새로 만들 수 없다.
- localOrigin은 경로·사용자 정보·query·fragment가 없는 정규 http/https loopback origin이다. 서비스 선택 정보가 아니고, 실제 포트/인증 설정을 자동으로 찾아서 만들지 않는다. 현재 합성 호출자만 제공하며 실제 설치는 미완료다.
- factory에서 scalar 사본을 고정하고 service 참조를 그대로 보관한다. 생성 자체로 inspect/DB읽기/새 session/driver/실행을 하지 않는다. 주입이 없으면 supported:false에 해당하는 내부 상태와 고정 RESULT_UNAVAILABLE을 사용하고 요청 중 자동 취득하지 않는다.
- handler의 원래 service 참조는 호출자에게 계속 귀속된다. handler의 close/retire/자동 TTL·새 registry는 없다. 요청 객체의 completion으로 service를 버리지 않는다.
- body는 runId/dispatchCommandDigest/mode만 받는다. run/dispatch는 고정 주입 값과 정확히 같아야 하며 mode만 historical 또는 inspect-current로 명시 선택한다. companyId·파일 경로·DB handle·session token·SDK 옵션·현재 회사 snapshot·result 객체·nonce를 입력받지 않는다.
- 클라이언트 query의 UUID/digest나 loopback 검사는 인증 capability가 아니다. 주입한 임의 객체의 타입을 authentic service라고 인증하는 장치도 아니다. 실제 서비스 진위와 수명 보관자는 추후 명시 설치 경계가 책임진다.

기존 encoder는 전체 service 중 readStoredReviewByRun만 호출한다. 다음 구현에서 매개변수 타입을 이 한 메서드의 Pick으로 좁혀도 기존 실제 service 호출은 그대로 호환한다. handler는 해당 메서드를 호출하는 사적 read 포트만 encoder에 넘길 수 있다. wrapper는 원래 query/run/dispatch를 먼저 확인하고, 반환된 resultIdentity의 회사/run/dispatch를 고정 scope와 대조한 뒤 같은 객체를 encoder에 넘긴다. 다른 회사 결과는 직렬화하지 않고 READ_FAILED다. 반환 형태/인용/false 권한 검사는 기존 encoder/wire가 수행한다. 전체 service로 cast하거나 DTO를 다시 만드는 별도 decoder는 추가하지 않는다.

이 사적 포트는 새 owner가 아니다. 기존 SQL13/증인3 감사·원래 archive/request/capture decoder·현재 guard 검사를 단축하거나 우회하지 않는다. service.readStoredReviewByRun은 요청별 최대1회이며 내부 preview→strict read 두 감사는 기존 그대로다. preview의 ready, 쓰기 receipt, claim ID, 최신 run 검색으로 선택을 대체하지 않는다.

| 정규 query | JSON.stringify(고정3필드 사본)와 원래 문자열 완전 일치; BOM·중복/추가key·공백/순서/trim/coercion 거절 | INVALID_QUERY400 |
| 원래 선택 | query run/dispatch가 주입 원래 값과 동일 | INVALID_QUERY400; service호출0 |
| 서비스 | 고정 주입 참조 존재, 입력 정상/중단 없음, body 정리 정상 완료 | 미주입 RESULT_UNAVAILABLE404 |
| 출력 scope | 원래 회사/run/dispatch와 DTO 일치, 기존 encoder 성공 | 실패 READ_FAILED500, 원문 표시0 |

Host가 없을 때는 기존 assertLocalRequest처럼 URL host를 쓰되 주입 localOrigin과 같아야 한다. Origin이 없거나 null인 요청은 새 handler에서 거절한다. 기존 공통 helper가 Origin 부재를 허용하는 동작은 바꾸지 않는다. Origin과 Host는 로컬 요청 경계일 뿐 OS 사용자 인증·인터넷 배포 보안 보장이 아니다.

native accessor로 얻은 URL/method/header/signal 사본을 첫 await 전에 고정한다. 이후 원래 Request header가 바뀌어도 검사값을 바꾸지 않는다. 공통 검사에 사용하는 URL/header는 이 사본과 같아야 하며 accessor/toJSON 또는 subtype의 가짜 값으로 기존 로컬 검사를 대체하지 않는다. 같은 프로세스의 악성 JavaScript 전체를 격리하는 보안 sandbox는 아니다.

Request/URL은 런타임이 이미 정규화한 값을 제공한다. 고정 pathname 대조는 노출된 값에 대한 약속이며 원시 HTTP request-target, 브라우저 이전 문자열, reverse-proxy 정규화를 검증했다고 주장하지 않는다. raw socket/헤더 전체 크기·전송 계층 request smuggling 검증도 이번 합성 범위가 아니다.

Content-Length는 조기 거절 보조값이다. 실제 노출 bytes를 EOF까지 반드시 누적한다. header만큼 읽고 성공시키거나 header 없이 무제한 읽지 않는다. native Request.json/text/arrayBuffer/clone을 먼저 호출하지 않는다. 큰 단일 청크는 사본에 넣기 전에 거절하며 잘린 JSON 접두사를 성공시키지 않는다.

## 4. byte 핵심 공유와 세 가지 수명

기존 readBoundedBody에 단순 Promise.race만 붙이면 빠른 timeout 뒤 원래 read/cancel이 남고 보관자가 사라질 수 있다. 이 helper의 모든 기존 호출자를 바꾸는 것도 다음 범위가 아니다.

다음 구현은 4I36 review-receive의 단일 reader·누적 cap·단조 deadline·취소 한 번·원래 promise observer·completion/cleanupFailed 핵심을 **비교 읽기 내부 공용 모듈 한 곳으로 추출**한다. Response 전용 header/status·wire 해독은 기존 수신 어댑터에 두고 Request 전용 header/body query는 새 handler 어댑터에 둔다. 일반 fetch client나 또 하나의 독립 receiver 알고리즘을 복제하지 않는다. 공급자 SDK용 comparison-body(120초/4MiB·64KiB)는 변경/import하지 않는다.

공유 핵심은 외부 네트워크/SDK/SQLite/React/production module 의존성이 없어야 한다. 정책은 내부 caller가 고정한 값만 사용한다. HTTP body/query가 한도·시계·resolver·정리 callback을 바꿀 수 없다. 기존4I36의30초/성공4MiB+8KiB/오류8KiB·start1/lateResponse·byte한도 의미를 유지하며 변경 영향 회귀를 실행한다.

| 수명 | 시작/끝 | 책임 보관자 |
|---|---|---|
| 서버 Request body operation | handler 진입 시점부터30초 단조 deadline1개; 자기 원래 read/cancel/release/observer 종료까지 | 해당 operation을 주입 호출자가 보관 |
| 클라이언트 Response 수신 operation | 기존 receiver 생성부터30초 단조 deadline1개; 원래 start/read/cancel 종료까지 | 기존 화면/합성 전달 호출자 |
| 같은 service/session·SQL/guard/lease·불명 저장 | 기존 private canRelease·명시 복구·자기 정리 규약 | 원래 service와 그 신뢰한 서버 보관자 |

두30초는 서로 다른 경계의 대기 정책이다. 한 HTTP 동작에60초를 보장한다는 뜻이 아니며 다음 실제 전송 단계에서 자동 연장/재시작하지 않는다. 요청 내부 deadline도 청크·UTF-8·JSON·service 호출 단계마다 갱신하지 않는다. 각 read 전후, 해독 뒤, service 호출 직전과 직후에 중단/기한을 검사한다.

이미 취소되었거나 기한이 지난 요청은 service를 부르지 않는다. body EOF와 자기 release가 실패하면 정상 query를 얻었어도 service0이다. 입력 오류/취소/timeout의 고정 Response는 빠르게 반환할 수 있지만 원래 read/cancel이 미종료이면 operation completion은 pending이다. cancel은 자기 body에 최대1회이며 reject/throw·release 실패는 sticky cleanupFailed다. 실패를 성공적인 정리로 바꾸지 않는다.

Request의 body는 handler에 넘긴 그 요청에 한해 소유한다. native 확인 뒤 unused/unlocked body를 자기 대상으로 확보한 경우에만 오류 시 cancel한다. 이미 used/locked이거나 획득 전 실패로 다른 reader가 보유한 경우 그 reader/stream을 취소·release하지 않는다. 선행 header 거절에서도 자기 것으로 확보 가능한 body의 취소와 completion 책임을 추적한다. Request/Response를 서로 cast하거나 clone해 원래 책임을 잃지 않는다.

service는 현재 동기 호출이다. 한번 진입하면 Request.signal을 service/guard/session으로 넘기지 않는다. 호출 뒤 abort/deadline이 확인되면 결과 Response 전달을 폐기하거나 고정 요청 오류를 반환할 뿐 이미 끝난 SQL을 미실행으로 보고하지 않는다. 동기 SQL/JSON은 타이머로 선점할 수 없으므로 CPU hard timeout/SLA라고 표현하지 않는다.

operation completion이 끝나도 service의 retained 원래 명령·불명 COMMIT/pending ack·실패한 회사/quality 정리는 남을 수 있다. handler가 inspect·recoverPostcapture·retire·session.close·ack/INSERT/정산/hold 해제를 호출해서 수선하지 않는다. 기존 service의 명시 재조회는 자기 읽기 정리만, 명시 recoverPostcapture는 원래 명령만 사용한다. 획득 전 busy로 남의 guard/lease를 종료하지 않는다.

## 5. Wire와 오류 계약

기존 wireVersion1과 성공/오류 shape, 성공200, 기존7개 code/status를 유지한다. 필요한 입력 경계만 다음 구현에서 아래3개 고정 code/status에 추가한다.

| 추가 code | status | 의미 |
|---|---|---|
| METHOD_NOT_ALLOWED |405| 이 handler는 POST만 받음; Allow: POST |
| REQUEST_CANCELLED |409| 요청 입력 또는 반환 전에 중단 관측; 서버 원래 실행 취소 증거 아님 |
| REQUEST_TIMEOUT |408| 요청 operation의 단조 기한 경과; SQLite 강제 중단 증거 아님 |

전용 wire schema/status/message 매핑을 함께 갱신하고 임의 서버 오류 body를 표시하지 않는다. 구버전 decoder가 모르는 code를 INVALID_RESPONSE로 닫는 동작은 유지한다. 기존 code의 뜻/상태를 바꾸거나 REST 오류를 성공 DTO로 wrap하지 않는다. timeout의 클라이언트 로컬 TIMEOUT과 서버 wire REQUEST_TIMEOUT은 관측 주체를 구분한다.

모든 Response는 기존 privateHeaders와 JSON UTF-8를 적용하며 CORS 허용/리디렉션을 추가하지 않는다. 기존 encoder가 내는 RESULT_UNAVAILABLE404/READ_BLOCKED409/TOO_LARGE413/READ_FAILED500을 그대로 전달한다. 스키마·origin·입력 오류를 studioRoute의 일반 envelope나 예외 message로 바꾸지 않는다. fixed error body8KiB, result4MiB, 성공 전체4MiB+8KiB 한도는 유지한다.

## 6. Import 경계와 검증 분리

이번4I37은 파일 텍스트와 SHA만 읽었다. 제품/SDK/SQLite module을 import하거나 시험을 실행하지 않았다. 기존 review-server는 database-v11의 type-only 참조와 data-only/studio-http/wire 의존성이다. 기존 production command-service는 production-server를 runtime import하므로 새 handler에서 재사용하지 않는다. 기존 preview route도 getStudioStore를 runtime import하므로 진입 함수 전체를 공유하지 않는다. 필요한 assertLocalRequest/privateHeaders만 직접 가져온다.

4I36의 초반 단위 시험2회는 openai mock이 없고 encoder의 이전 data-only 의존성이 SDK 진입 모듈까지 이어졌다. 실제 모듈 평가 횟수는 계측하지 않았다. 실제 SDK 생성/요청이 없었다는 관측을 전체 SDK import0으로 확장하지 않는다. 최종 추출 후 encoder 정적46개 로컬/zod와 SDK/SQLite loader-fail 시험 통과는 **과거4I36** 기록이다. 이번 재실행하지 않는다.

다음 첫 제품 시험 전에 새 handler·encoder·공유 core의 value import를 재귀 정적으로 확인한다. type-only와 runtime을 구분하고 SDK/SQLite/storage/production registry/env/key 경로가 있으면 먼저 제거한다. 독립 import 차단 시험은 openai/openai helpers/node:sqlite뿐 아니라 실제 production/store 모듈 로드가 발생하면 실패하도록 구성한다. 이 시험에서 진짜 service/store를 import해 fixture를 만들지 않는다.

실제 같은 SQL13 서비스 통합은 별도 시험 파일에서 기존 합성 fixture와 SDK mock을 재사용한다. 테스트가 합성 SQLite를 쓰는 것과 handler import가 SQLite를 자동 여는 것을 구분한다. 두 종류를 같은 no-import 수치로 혼합하지 않는다. 실제 SDK 호환성·공식 가격·동의·전송·의미 품질은 완료로 세지 않는다.
