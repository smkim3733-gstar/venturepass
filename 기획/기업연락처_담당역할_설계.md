# 18. 기업 연락처와 신청 담당 역할

상태: 설계안. 제품완성 잔여 범위 R01을 구현하기 위한 최소 계약이다. 실제 회사 연락처를 추정하거나 기존 서류에서 자동 복사하지 않는다.

## 직접 요구와 보관 경계

서비스 기획의 기업 소재지·대표/담당자 연락처·자료 제공·최종 확인·납부 담당자 요구를 충족한다. 기존 기업 설명과 요청별 자료/작성/검토 담당자는 유지한다. 새 기록은 기업 차원의 연락 메모이며 사용자 계정, 회사 접근권한, 알림 발송 동의 또는 실제 납부 승인을 뜻하지 않는다.

현행 `profile`은 분석·진단 입력에 사용된다. 연락처와 운영 담당자 이름을 여기에 바로 추가하면 불필요한 외부 AI 입력이 늘어난다. 따라서 별도의 `companyContacts` 추가 전용 이력으로 보관하고 기본 분석·원고·진단·제출 ZIP에는 자동 포함하지 않는다. 미래에 제출 기록에 이 정보를 포함하려면 정확한 버전과 항목을 명시 선택하는 별도 동작으로 연결한다.

## 최소 사용자 흐름

기업정보 화면의 ‘연락처·신청 담당 역할’ → 선택 정보 입력 → 미확인인 항목은 공란 유지 → 정확한 새 버전 저장 → 과거 버전 조회. 기존 기업은 기록 없음으로 표시한다. 원자료에 연락처가 있다는 사실만으로 현재 담당자나 연락 가능 여부를 확정하지 않는다.

필드는 소재지(500자), 대표 연락 메모(500자), 기업 담당 연락 메모(500자), 자료 제공 담당자(100자), 최종 내용 확인 담당자(100자), 납부 담당자(100자), 설명/수정 이유(2,000자)다. 전화·이메일·담당자 정보를 수동 메모로 받되 형식을 임의 교정하거나 유효한 수신처로 판단하지 않는다. 공백 정규화 후 빈 값 허용. 사용자가 기존 기록을 공란으로 정정할 수 있지만 이전 버전은 보존한다.

## 저장 계약

- strict PATCH `append-company-contacts`, 회사 revision, `clientRequestId`, 정확한 `previousVersionId`(최초 null), 필드 객체를 받는다.
- 서버 ID·version·recordedAt·origin(manual)·입력 digest를 생성한다. 최초 미기록 상태를 가짜 버전으로 만들지 않는다.
- 회사당 최대 100개 버전/20만 자, 요청 본문 16KiB. 한도 초과는 이전 이력 삭제나 잘라내기 없이 거부한다.
- 같은 nonce와 동일 입력은 기존 저장 결과를 반환하고 revision을 증가시키지 않는다. 같은 nonce의 변경 입력, 오래된 회사 revision·이전 버전은 충돌로 거부한다.
- 기존 profile/analysis/sourceRevision/원고 확인 표시/제출본/기관 기록은 바꾸지 않는다. 연락 메모 저장을 새로운 기업 사실 근거로 승격하지 않는다.

## 화면·검증

편집기는 회사 ID/revision에 묶고 기존 기업정보 편집과 dirty 보호를 공유한다. 저장 중 단일 요청, 같은 입력 재시도의 nonce 유지, 입력 변경 시 nonce 갱신, 정확한 회사/nonce/이전 버전/입력 ACK를 확인한다. 불확실한 응답을 성공으로 표시하지 않는다. 외부 링크·전화 걸기·메일 보내기 버튼은 이 범위에 추가하지 않는다.

검사는 구형 데이터 읽기, 최초/정정/공란 정정, append-only, nonce 재전송/충돌, CAS, 회사 격리, 한도/실패 원상복구, 사용자 입력 escaping, dirty 충돌을 포함한다. 분석·원고·진단·ZIP 입력과 과거 제출 스냅샷이 연락처 저장 전후 동일하게 보존되는 회귀가 핵심이다. 실제 사용자 연락처나 기관 데이터는 시험에 사용하지 않는다.
