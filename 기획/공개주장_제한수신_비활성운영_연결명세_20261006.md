2026-10-06. 기준 커밋4fc6780. 제품 변경 없는 로컬 소스 점검이다.

고정20개 기능 기준15/20=75%, 미완료5/20=25%, 직전 대비+0%p. 이번4I27은 제한 수신·원래 I/O 종료와 비활성 운영 연결 계약 점검1건이며 제품 소스 변경0개다. 신규 제품 시험0/0(미실행), 기존 회귀 재실행0·새 앱 HTTP/브라우저/lint/typecheck/빌드0회다. 과거4I26 신규53+기존39=92/92·PtzDZJ와4I24 75/75·5cMj79는 별도이며 재실행/합산하지 않는다. 백업27개 DESTINATION_REPOSITORY 제한은 미해결·이번 미실행이다. 실환경1/5=20%는 과거 사용자 직접 인증/접근이며 앱 자동실행 성공0단계·KOSIS 실제0/1이다. 필수 결정0개, 다음4I28 원래 실행 보관·폐기 경계의 비활성 연결 격리 합성 구현3~6시간(잠정), 전체 완료시간 미정, 자동후속 ACTIVE.

## 1. 확정한 연결 범위

4I26의 본문 제한과 원래 I/O 종료는 같은 private owner/lease 안에서 구현되어 있다. 설치 OpenAI SDK7.20.0의 TypeScript와 대응 JavaScript를 텍스트로 대조했다. SDK를 import/생성/실행하지 않았다. 설치 버전과 소스상 일치는 실제 SDK 호환·현재 API 지원·가격·계정 인증이 아니다.

기존 production-runtime은 generation/review2단계와 PlanQualityStore에 결합되어 있다. 비교 요청v1·requestedTier:null·한 번의 호출에 그대로 사용할 수 없다. 특히 운영 service의 active/retained capture 개수만 비교 실행의 폐기 조건으로 가져오면 안 된다. 비교는 캡처가0개이고 외부 호출 promise가 끝나도 dispatch-unknown·원래 lease·복구 책임이 남을 수 있다.

따라서 다음 비활성 연결은 원래 비교 실행 객체를 유지하는 얇은 격리 서비스로 한정한다. 전송 owner는 기존 엔진 하나만 발급하며 서비스는 그 객체의 보관 책임만 가진다. 실제 운영 모듈 import·설치나 SDK/키를 얻는 factory가 아니다.

## 4. 비활성 연결의 입력·출력 및 순서

‘비활성’은 실제 운영 설치·실제 전송 경로가 없다는 뜻이다. 합성 fixture를 넣은 격리 실행만 할 수 있으며 public authority는 계속false다. 명칭만 production으로 바꿔 권한을 얻는 API는 만들지 않는다.

| 경계 | 허용 입력 | 출력/보관 |
|---|---|---|
| 격리 서비스 구성 | 신뢰된 서버 시험 구성의 기존 session·회사 guard·합성 driver | 원래 비교 execution 한 객체를 private 참조로 고정. key/URL/options/DB경로/SDK client를 명령에서 받지 않음 |
| execute | 기존 approve-dispatch 명령과 기존 current 입력 | 원래 engine의 nonce/전체 명령 감사부터 시작. supplied current는 새 요청에서만 읽음. safe view와 원래 진행 promise를 별도 보관 |
| SDK 형태 준비 | 기존 비교 boundary.body와 별도 {signal} | dummy options/factory만. final fetch에서 원래 rawBody/headers/signal 재검사; nonce 재조회에는 준비0 |

| inspect/retire | 호출자 response/raw/key 없이 명시 호출 | 기존 안전한 view/단조 retire. lease·capture 참조 해제는 내부 책임 종료를 확인한 경우만 |
| 서비스 교체/종료 | 원래 engine의 비공개 release-safe 관측 | lease 없음·모든 등록/소유 promise/정리 책임 종료를 확인. public boolean 객체를 입력으로 받아 release시키지 않음 |

원래 nonce 우선→새 current 검사→SQL13 dispatch COMMIT/회사 SELECT 종료/재감사/양쪽 정확한 증인 ack→동일 private 호출의 일회용 owner→SDK형 준비→최종 quality→studio 검사/동기 시작→잠금 밖 대기→첫 capture/보관→모든 원래 I/O/SDK/driver/SQL/lease 종료 순서를 유지한다. fresh COMMIT/ack는 내부 일회용 소유권의 근거이며 실제 사람 동의·공식 가격·외부 전송 허가는 별도다.

원래 진행 중 execute의 반환을 기다리는 호출자가 없어져도 서비스 참조를 없애지 않는다. 활성 호출 수와 원래 실행 책임은 별도다. 서비스는 한 session에 한 원래 execution을 보관하며 recovery-required 슬롯을 지워 새 호출 공간을 만들지 않는다. 확정된 종료 뒤 새 업무를 만들려면 별도의 원래 명령/승인과 명시 구성이 필요하며 자동 재전송하지 않는다.

## 6. 실제 활성화에 남은 검토 항목
