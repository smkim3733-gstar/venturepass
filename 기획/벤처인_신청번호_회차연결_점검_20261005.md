# 벤처인 신청번호·원래 회차 연결 점검 — 2026-10-05

## 4G5d 결론과 범위

기능 구현15/20=75%, 미완료5/20=25%, 직전 대비+0%p. 이번은 기존 계약 점검과 다음 구현 범위 결정이며 새 제품 기능을 완료 처리하지 않는다. 실환경 증거1/5=20%는 이전 사용자 직접 인증/접근, 앱 실제 자동실행 성공0단계, KOSIS 실제0/1이다. 필수 추가 결정0개. 다음4G5e 수동 신청번호 연결·정정/해제 writer와 합성 검증은2~4시간(잠정), 전체 완료시간 미정이다.

공식 화면의 신청번호, 수동 기관 기록의 접수번호, 확인서 발급번호는 서로 다른 식별자다. 현재 로컬 신청 회차에 공식 신청번호를 전용으로 보관하는 계약이 없다. 기존 메모에 번호가 있을 가능성만으로 값을 추출하거나 같은 번호라고 추정하지 않는다. 첫 행·최신 날짜·최근 회차·확인서 번호로 연결하지 않는다.

다음 구현은 **담당자가 주장한 신청번호와 정확한 로컬 회차의 수동 연결 이력**으로 한정한다. 현재 UI가 받은 임시 관측 결과를 신뢰된 기관 원문으로 저장하는 방식은 사용하지 않는다. 수동 연결은 공식 귀속 증명·접수증·현재 결과 확인·전송 권한이 아니다. 실제 신청/최종 제출 양식과 확인서 상세는 이번에 새로 관측하지 않았다.

## 다음 구현 계약 — 아직 미구현

### 1. 별도 선택적 수동 연결 이력

회사 JSON에 새 선택적 이력을 둔다. 기존 회차/제출/기관 원문에 신청번호를 끼워 넣거나 기존 명령에 기본값을 추가하지 않는다. 이전 회사 읽기에 빈 배열을 새로 만들지 않고 과거 요청 bytes/해시를 보존한다.

이력은 회사 ID·서버가 읽은 사업자번호 신원, 원래 회차 ID/정보 버전, 원래 전체 명령, 담당자/사유, 서버 기록 시각, 이전 연결 버전, 연결/해제, 번호를 불변으로 보관한다. `origin:manual`과 `officialVerification:unverified`를 유지한다. 시각은 담당자 기록을 앱이 보관한 시각이며 기관 확인 시각이 아니다.

번호는 기존 `ventureMyIdentitySchema`의 최대200자·양끝 공백/마스킹·제어문자 거절을 재사용한다. 숫자만 남기거나 대소문자·하이픈·공백을 조용히 변환하지 않는다. 회사 안의 정확한 동일 문자열만 비교하며 회사 간 전역 유일성이나 기관 번호 문법을 입증하지 않는다.

### 2. 명시 명령과 기존 writer

기존 로컬 mutation 경로/Origin·본문 제한과 `StudioStore.update`를 재사용한다. 제안 명령은 action, 원래 revision/clientRequestId, applicationId/metadataVersionId, expectedPreviousBindingId, bind/release, applicationNumber 또는 null, recordedBy/reason, confirmed:true로 제한한다. 공식 관측 JSON·접수/확인서 번호·자격증명·AI 승인·임의 회사 신원은 받지 않는다. 이 명세는 아직 API 지원을 뜻하지 않는다.

새 명령의 신원은 회사 ID와 전체 명령(원래 revision 포함)에 결합한다. 기존 신청 writer의 revision 제외 해시를 바꾸거나 새 명령의 해시로 재사용하지 않는다. 저장된 전체 연결 이력을 먼저 감사한 뒤 원래 nonce를 CAS보다 먼저 찾는다. 동일한 원래 명령은 같은 기록을 찾고 추가 버전을 만들지 않는다. 같은 nonce의 다른 명령/다른 원래 revision은 거절한다. 기존 반환 회사 객체를 쓰더라도 UI는 원래 nonce/전체 명령의 정확한 기록을 찾고 최신 head와 구분해야 한다.

저장은 기존 회사 revision을 한 번 올리되 근거 revision·원고 본문/확인·자료·수동 기관 기록·lastCheckedAt·승인/실행 bytes를 변경하지 않는다. 기존 update가 수행하는 준비본/진단 stale 계산과 자동화 변경 수집의 부작용은 합성 시험에서 따로 확인한다. return false만으로 다른 필드 보존을 단정하지 않는다. 새 이력은 자체200개 상한과 기존 신청 이력 용량 합산을 적용해 기존8MiB/본문 한도를 늘리지 않는다. 기존30/200개 계약과 요청64KiB는 유지한다. 원문/사유를 자르지 않는다.

### 3. 정정·해제와 모호성

- 현재 한 회차에는 활성 번호1개, 같은 회사의 같은 번호에는 활성 회차1개만 허용한다. 중복 요청을 최근 날짜로 고르지 않는다.
- 정정/해제는 정확한 이전 head와 현재 회차 정보 버전에 결합한다. 다른 head/버전이면 거절하며 최신 값으로 바꿔 저장하지 않는다.
- 다른 회차로 옮기려면 기존 연결을 명시 해제하고 새 회차에 별도 명령으로 연결한다. 해제 후 새 연결 실패는 해제 상태로 남고 자동 이전/재전송하지 않는다.
- 회차 정보나 현재 사업자번호가 바뀌면 기존 연결은 과거 기록이며 현재 읽기 대상으로 바로 쓰지 않는다. 명시 정정/재확인 전까지 미확인으로 남긴다. 원래 회차/번호는 지우거나 새 회사 신원으로 덮지 않는다.
- 중복 ID/nonce, 끊긴 부모·분기, 다른 회사/없는 회차, 손상된 최신 이벤트는 이전 정상 head로 되돌아가 처리하지 않는다.
- 후속 정정 뒤 예전 명령을 재조회하면 원래 기록의 존재만 복구한다. 예전 번호를 현재 활성 연결로 복원하지 않는다.
- 보관 전 중단/조회 실패는 미확인이다. 저장 결과가 모호하면 새 nonce로 자동 재저장하지 않는다. 새 UI 단계에서 기존 엄격한 원래 요청 보관/GET 대조 패턴을 재사용할 범위를 별도로 연결한다.

### 4. 공식 화면 읽기와의 후속 연결

4G5e writer는 실제 MY 조회·로그인·화면 이동을 시작하지 않는다. 수동 번호 보관만으로 F20이나 실환경5단계 중 결과 확인을 완료 처리하지 않는다.

이후 읽기는 명시 선택한 **저장 연결 버전**을 서버가 재확인하고 기존 runner/session/documentRevision/operationInProgress/withVentureLock과 collector를 재사용한다. 현재 read-current-my-status 회사 화면 계약을 조용히 바꾸지 말고 원래 호출과 구분된 엄격한 명령/응답을 정의한다. await 전후 번호·회사/계정·회차·버전 변경 시 결과를 버린다.

정확한 신청번호가 새로 읽은 신청 결과 표의 단일 행에 있는 경우에만 그 행의 문자 대조 결과를 표시한다. 없음·중복·미지원은 미확인이다. 수동으로 연결한 번호와 실제 화면 한 행이 일치한다는 것과 담당자가 올바른 회차를 골랐다는 사실은 별도다. 신청 귀속 근거는 계속 담당자 진술로 표시한다. 진행 단계/확인서 이력은 현재 수집 구조에 해당 신청번호와의 연결 증거가 없어 별도 미귀속으로 남긴다.

영속 공식 관측/접수증 수집과 원래 요청에 결합한 서버 capture·정확한 결과 보관은 별도 미완료다. 새 수동 기록이 기존 owner/capture·전송/채택 영수증을 대신하지 않는다.

## 4G5e 합성 검증 범위

다음은 구현 후 확인할 요구이며 이번 통과 시험 숫자가 아니다.

1. 이전 회사 JSON 읽기·과거 명령/해시/승인 bytes 불변, 추가 필드/무동의/잘못된 번호 거절.
2. bind→정정→해제, 다른 회차 중복/이전·현재 head 충돌, 회차 메타데이터/회사번호 변경.
3. 전체 체인 감사, 중복/분기/소실·후속 손상, 오래된 명령을 최신 연결로 복원하지 않음.
4. 두 writer 경쟁, 원래 nonce 재호출, COMMIT 전 rollback/후 응답 유실·SQLite 재열기와 원래 기록 복구.
5. 원고/자료/수동 기관/lastCheckedAt/근거 revision·승인/원래 실행, 파생 준비 상태와 운영 예산 보존.
6. 한도와 DDL 불변, 키/계정 복호화·SDK·네트워크 금지. 고객 데이터 대신 새 격리 SQLite만 사용.
