# 원고 비교·보완 답변·실사 연습 구현 설계

작성일: 2026-09-25. 상태: **설계안. 아래 11~13번 제품 기능을 구현했다는 문서가 아니다.**

[서비스 기획 v1.5](./혁신성장유형_서비스기획_v1.md)의 직접 요구를 [제품 완성 로드맵](./제품완성_개발로드맵.md) 1~10번 다음 작업으로 구체화한다. 실제 기업자료·DB·계정·공식 화면을 조회하지 않았다. 제품 코드가 고정된 동안 이 설계 문서만 작성한다.

아래 기능은 기존 원고·요청·기관 기록을 보존하고 로컬에서 준비·대조하는 범위다. 비교 화면을 열거나 초안을 만드는 행위로 내부 검토, 기관 발송·수용, 신청 접수, 실사 통과를 표시하지 않는다. 외부 AI 전송·기관 작업의 기존 승인 범위도 확대하지 않는다.

## 11. 두 원고 버전의 정확한 비교

### 11.1 근거와 현재 구현

- 서비스 기획 11절은 사업계획서 화면에 **버전 비교**를 명시한다. 6절 작성 화면의 수정 이력·변경 영향, 8절 수정 전후 비교도 이 기능을 필요로 한다.
- 현재 [`plan-editor.tsx`](../web/src/components/studio/plan-editor.tsx)는 하나의 `planId`를 골라 편집한다. 버전 보관과 선택은 있으나 두 버전의 변경 부분을 비교하는 경로는 없다.
- [`studio-schema.ts`](../web/src/lib/studio-schema.ts)의 `BusinessPlan`에는 불변 원고 ID·버전·내용과 현재 저장된 검토 메타데이터가 있다. `save-plan`은 새 ID를 추가한다. 다만 `confirmedAt`과 `review`는 이후 근거 변경·검토로 바뀔 수 있다. 따라서 원고 비교의 검토 메타데이터를 과거 제출일의 상태로 설명하면 안 된다. 제출 기록 당시 값은 10번의 별도 스냅샷이다.

### 11.2 첫 구현의 사용자 흐름

1. 원고 화면에서 ‘저장된 원고 비교’를 연다. 편집 중이면 먼저 저장하거나 취소하도록 안내한다. 미저장 편집 내용을 비교 대상에 몰래 섞지 않는다.
2. 사용자가 같은 회사의 왼쪽·오른쪽 버전을 각각 직접 선택한다. 최신·직전 버전을 자동 확정하지 않는다. 선택 옵션은 `vN`, 원고 제목, 작성 시각으로 구분하고 실제 식별에는 ID를 쓴다.
3. 선택한 두 버전과 비교 방향을 화면 상단에 고정한다. 동일 ID를 양쪽에 골랐다면 ‘같은 버전’으로 알리고 비교 결과를 새 검토 기록으로 만들지 않는다.
4. 변경 항목 목록에서 한 항목을 골라 좌우 원문과 추가·삭제 표시를 읽는다. 항목·인용·확인 필요 상태·과제·실사 질문의 변화를 각각 표시한다.
5. 비교를 닫아도 원고 내용·선택 후보·`confirmedAt`·업무·기관 기록은 바뀌지 않는다. 기업 또는 `revision`이 바뀌면 비교 선택과 계산 결과를 초기화한다.

### 11.3 단일 컴포넌트와 순수 함수 계약

신규 파일 후보:

- `src/lib/studio-plan-diff.ts`: 브라우저에서도 쓰는 순수 함수·결과 타입. 파일·네트워크·시간·저장소 접근이 없다.
- `src/lib/studio-plan-diff.test.ts`: 정확성·상한·중복·문자 경계 검사.
- `src/components/studio/plan-comparison.tsx`: 비교 대상 선택과 결과 표시를 맡는 단일 컴포넌트.
- `src/components/studio/plan-comparison.test.ts`: 선택 미완료·과거 버전·생략·접근성·이스케이프 검사.
- `plan-editor.tsx`: 컴포넌트 한 곳 삽입. 기존 원고 상태·편집·저장 함수를 변경하지 않는다.

`ComparisonItem`은 경로·사람이 읽는 제목·상태·원문 양쪽 값·순서 정보·선택적 텍스트 변경 조각만 가진다. HTML 문자열을 생성하지 않는다. 순수 함수에는 현재 회사의 `plans`만 전달하며, 해당 ID가 그 배열에 정확히 한 번 존재해야 한다. 버전 숫자나 제목이 같다는 이유로 다른 ID를 대신 선택하지 않는다.

### 11.4 비교 범위와 대응 규칙

| 영역      | 비교 내용                                              | 대응 기준·표시                                                                                                                        |
| --------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| 원고 전체 | `content.title`, `content.summary`                     | 원문 문자열을 정확하게 비교한다. 공백·개행 변경도 변화다.                                                                             |
| 항목 구조 | `sections`의 존재·순서·`key`                           | 양쪽에서 유일한 key만 연결한다. 순서 변경은 본문 변경과 별도로 표시한다. key 이름이 바뀌면 삭제+추가다. 제목 유사도로 합치지 않는다.  |
| 항목 내용 | `title`, `content`                                     | 대응된 항목별 정확한 문자열 비교.                                                                                                     |
| 근거      | `evidence`의 `sourceId`, `quote`, `locator`            | 세 값의 튜플을 정확하게 비교한다. 중복 개수와 순서를 보존한다. source 이름은 현재 표시용 보조 정보이며 과거 자료명으로 꾸미지 않는다. |
| 확인 필요 | `needsConfirmation`                                    | 전후 boolean을 ‘확인 필요 표시’ 변화로 설명한다. false로 바뀌었다고 사실 검증·기관 승인으로 해석하지 않는다.                          |
| 과제      | `actionItems`                                          | 순서가 있는 문자열 목록. 중복 원문도 발생 순서대로 보존한다.                                                                          |
| 실사 질문 | `interviewQuestions`                                   | 순서가 있는 문자열 목록. 실제 기관 질문으로 표시하지 않는다.                                                                          |
| 작성 맥락 | `candidateId`, `sourceRevision`, `mode`, `generatedAt` | 본문 변경 개수와 분리하여 표시한다. 아이템이 다르면 비교는 허용하되 다른 아이템 간 비교임을 알린다.                                   |
| 검토 정보 | `confirmedAt`, `review`의 전체 필드                    | 현재 저장된 각 버전의 검토 메타데이터임을 명시한다. 제출 당시 스냅샷과 구분한다.                                                      |

어느 한쪽에서라도 같은 section key가 둘 이상이면 해당 key 묶음 전체를 `ambiguous`로 표시한다. 첫 항목을 임의로 연결하거나 나머지를 버리지 않는다. 중복된 양쪽 항목은 배열 순서와 제목을 붙여 원문을 읽게 하고 다른 유일한 key의 비교는 계속한다. 최상위 plan ID가 중복이면 전체 비교를 중단한다.

근거·과제·질문은 고유 식별자가 없는 배열이다. 동일 튜플/문장의 반복을 모두 같은 하나로 축약하지 않는다. 순서만 달라진 경우와 내용이 추가·삭제된 경우를 구분하되, 의미가 같다는 추론은 하지 않는다.

### 11.5 텍스트 알고리즘·긴 입력 상한

1. 문자열의 정확한 동등성을 먼저 검사한다. trim, 대소문자·숫자·유니코드 정규화, CRLF→LF 치환을 비교 전에 하지 않는다.
2. 개행 문자를 포함한 행 토큰으로 나눠 줄 끝 개행 유무를 보존한다. 행 수가 양쪽 각 400개 이하이고 LCS 표가 40,000칸 이하일 때만 행 단위 LCS를 계산한다.
3. 상한을 넘으면 전체 행 LCS를 실행하지 않는다. 공통 앞·뒤 부분을 선형 탐색하여 가운데 블록을 삭제/추가로 표시하는 `block` 모드로 전환한다. 블록 표시를 문장별 의미 비교로 설명하지 않는다.
4. 작은 변경 블록의 문자 표시에는 유니코드 코드포인트 경계를 쓴다. 한글·이모지의 surrogate pair를 잘라 서로 다른 색 조각으로 만들지 않는다. 입력·출력 문자열을 다시 결합했을 때 원문이 보존되어야 한다.
5. 상세 표시 조각은 비교 항목당 400개, 한 번 렌더링하는 좌우 텍스트 합계는 40,000자로 제한한다. 배열 상세는 항목당 200개, 한 비교의 상세 표시 문자열 합계는 400,000자를 한도로 둔다. 상한 값은 상수 한 곳에서 관리하고 검사에 고정한다.
6. 상한을 넘는 내용은 `limited`, `complete:false`와 생략 범위를 표시한다. 표시하지 않은 내용을 ‘동일’로 판단하거나 전체 비교 완료로 표시하지 않는다. 원래 버전을 원고 화면에서 읽는 경로를 제공한다. 근거·검토 배열은 현재 스키마상 개수 제한이 없는 곳도 있어 원고의 일반 길이 제한만 신뢰하면 안 된다.
7. 변경 목록은 작게 만들고 상세 원문은 사용자가 펼친 항목만 렌더링한다. 닫힌 모든 항목의 거대한 diff DOM을 미리 생성하지 않는다. 계산은 명시 선택/실행 시 하고 매 키 입력·타이머마다 다시 하지 않는다.

React 텍스트 노드로만 렌더링하며 `dangerouslySetInnerHTML`, raw HTML/Markdown 실행, 외부 링크 추출·요청은 없다. 추가·삭제 색상에 더해 글자 라벨·기호를 제공한다. 모바일에서는 좌우 비교가 위아래로 배치되어도 버전 이름을 반복 표시한다.

### 11.6 완료 검사

- 같은 원고, 제목/요약만 변경, 항목 추가·삭제·순서 변경, 근거만 변경, 확인 필요만 변경, 과제/질문 중복·순서 변경.
- 다른 아이템·원고 ID 중복·section key 중복·없는 회사/버전·같은 ID 두 번 선택.
- 공백·개행·마지막 개행·한글·이모지·HTML 모양 텍스트의 원문 보존. 변경 조각으로 좌우 입력을 각각 재구성할 수 있는지 검사.
- LCS 상한과 표시 상한 바로 아래/위, 매우 긴 한 줄·대량 근거 목록. 한도 초과가 동일/완료로 표시되지 않는지 검사.
- 변경 원고 저장·검토 확인·기관 상태 API 호출이 없고, dirty/회사 변경 시 비교 대상을 재확인하는지 SSR·격리 UI로 확인.

## 12. 요청별 보완 답변 준비 MVP

### 12.1 확정 범위

2026-09-25 구현 계약: 기존 기관 답변 입력의 canonical hash를 바꾸지 않고 별도 `responsePreparations` 추가 이력에 로컬 초안을 보관한다. 준비안에서 기존 기관 답변으로 가는 명시적 등록 버튼을 제공한다. 초안 작성·저장·등록은 외부 AI나 기관 발송을 실행하지 않으며 검토 완료·업무 완료·기관 수용을 만들지 않는다.

원기획의 AI 요청 요약·의미 기반 자료 탐색은 후속 범위다. 이번에는 사용자가 정확한 요청 문장과 원고·자료를 선택하고 고정 서식으로 미검토 답변을 준비한다. 담당자 요약은 자동 기관 요약으로 표시하지 않는다.

### 12.2 사용자 흐름

1. 현재 회사의 최신 요청/정정 버전을 직접 선택한다. 통보나 다른 회사의 요청은 사용할 수 없다.
2. 최대 10개 항목에 요청의 정확한 인용, 담당자 요약, 원고 인용 1개, 자료 인용 최대 6개, 부족 자료·확보 이유, 답변 초안을 작성한다.
3. `buildLocalResponseDraft(item)`으로 요청 원문·원고 기재·선택 자료·미확인을 구분한 서식을 만든다. 기존 편집 본문은 자동 덮어쓰지 않으며 사실 확인이 완료된 것으로 표시하지 않는다.
4. 준비안 버전을 저장한다. 기존 준비안·기관 답변·원고·업무는 보존한다. 정정은 최신 부모 버전에서 새 이력으로 추가한다.
5. 두 준비 버전 또는 기존 기관 답변과 현재 편집 초안을 plain text로 비교한다. 정확한 버전을 표시하고 비교 자체는 저장하지 않는다.
6. 등록 본문과 선택 원본 목록을 확인한 뒤 `기관답변 초안으로 등록`을 누른다. 서버는 최신 요청·준비 버전·원고·자료·원본 SHA를 재검증하고 기존 agency response에 `responseStatus:'draft'`로 추가한다.
7. 실제 발송 기록은 기존 별도 수동 기록 경로다. 이 기능에서 `reported-sent`, 발생일, 기관 접수·승인을 입력하거나 자동 생성하지 않는다.

### 12.3 실제 타입과 API

순수 타입은 `studio-response-preparation-types.ts`, 서버 helper는 `studio-response-preparation.ts`다. 기존 회사 PATCH와 공통 트랜잭션을 재사용한다.

```ts
type ResponsePreparationInput = {
  preparationId: string | null;
  previousVersionId: string | null;
  requestRecordId: string;
  requestVersionId: string;
  title: string;
  items: Array<{
    id: string;
    requestQuote: string;
    summary: string;
    planClaim: { planId: string; sectionKey: string; quote: string } | null;
    evidence: Array<{ sourceId: string; sourceUpdatedAt: string; quote: string; locator: string }>;
    gap: string;
    draft: string;
  }>;
};

// 준비 버전 저장
{ action: 'append-response-preparation', revision, clientRequestId, preparation }

// 저장한 최신 준비안을 기관 답변 draft로 등록
{
  action: 'register-prepared-response', revision, clientRequestId,
  preparationId, preparationVersionId, previousResponseId: string | null
}
```

두 요청은 strict schema, 회사 revision, UUID 단회 요청 ID를 요구한다. URL query, 서버 메타, 임의 등록 본문·발송 상태를 거부한다. 같은 nonce·입력의 응답 유실 재생은 기존 결과를 반환하고 다른 내용은 충돌한다. 새 nonce로 같은 준비 버전을 다시 등록할 수 없다.

등록 본문은 서버가 `preparedResponseBody(preparation)`로 항목 요약과 저장된 draft를 순서대로 조합한다. 빈 답변은 확인 필요로 표시한다. 담당자 문장을 임의 보강하거나 자동 자르지 않는다.

### 12.4 보관·검증 계약

`StudioCase.responsePreparations`는 누락 시 빈 배열이다. 서버는 ID·최신 부모·버전·보관 시각·inputDigest와 `origin:'manual'`, `mode:'assisted'`, `reviewStatus:'unreviewed'`를 고정한다. 요청 루트별 준비 체인 하나를 두고 요청이 정정되면 같은 체인의 새 버전으로 최신 요청을 채택한다.

원고 스냅샷은 plan ID·version·본문 SHA256이다. 자료 스냅샷은 source ID·이름·수정 시각·추출 상태·등록 본문 SHA256이며, 원본이 있으면 원본명·MIME·크기·SHA·시각도 고정한다. 같은 회사의 유일한 원고/항목과 정확한 인용을 검증한다. pending 원본은 빈 인용으로만 연결하며 원본 없는 자료의 빈 인용은 거부한다. 문자열 일치는 기재 확인이며 진위 증명이 아니다.

기관 답변에는 서버 전용 `preparedFrom:{preparationId,preparationVersionId}`를 추가한다. 기존 수동 response 입력에 이를 주입할 수 없다. 최신 response 부모를 요구하고 답변 본문은 기관 이력에 한 번 저장한다. 준비 이력·단계·업무·원고 확인 상태는 변경하지 않는다.

공통 `studio-evidence-history.ts`는 기관·소명·신청회차·답변 준비·실사 답변의 불변 원본/원고를 모은다. 같은 source ID의 과거 SHA·크기·원본명·MIME 또는 같은 원고 ID의 version·content SHA와 충돌하면 어느 저장 경로에서도 연결하지 못한다. 제품별 오류코드는 유지한다.

선택 원본은 공통 안전 reader로 처음과 마지막에 읽고 회사·메타·전체 SHA를 확인한다. 준비에 연결된 자료는 삭제를 막는다. 등록 시에도 저장된 자료/원고 스냅샷과 현재 값을 재대조한다. 현재 파일 훼손을 이유로 과거 SHA를 갱신하지 않는다.

### 12.5 한도와 화면 경계

- 회사당 준비 버전 50개, 모든 문자열 합계 200,000자. 과거 버전 자동 삭제 없음.
- 항목 1~10개, 전체 고유 자료 10개, 항목당 자료 6개·원고 인용 1개.
- 요청·원고·자료 인용 1,500자, 담당자 요약 200자, 부족 자료·이유 2,000자, locator 150자.
- 등록 조합 본문 전체 20,000자, 원본 개별 12MiB·합계 24MiB, 실제 요청 256KiB.
- UI `responsePreparationContext`는 등록 정보의 오래됨 안내이며 실제 원본 bytes 검증을 대신하지 않는다.
- dirty/busy는 부모와 합산한다. 회사·revision 변경 시 재확인하며 불확실한 응답에 자동 재전송·새 nonce 발급을 하지 않는다.
- 본문 미작성·부족 근거가 남은 버전도 미검토 초안으로 보관 가능하나 답변 완성·검토 완료로 표시하지 않는다.

### 12.6 검증과 후속 범위

합성 SQLite/API로 저장/등록 분리, 미발송 고정, legacy·재시작·nonce·CAS·회사 격리·요청 정정·자료 변경·pending 인용·원본 변조·최종 재검사·SQL rollback을 검사한다. 순수 검사는 원문 보존·미확인 표시·주입/중복 거부·공통 증거 교차 보호를 확인한다. UI는 정확한 전후 버전, 명시 등록, 응답 회사 바인딩, stale/dirty와 실패 재시도를 검증한다.

외부 AI 요약·자료 추천·실제 기관 발송·검토 완료 선언·기한 자동 추정은 후속 범위다. 구현·검사 완료 수치는 최종 검증 기록에서 관리한다.

## 13. 실사 모의 답변 기록과 원고·근거 대조

### 기존 구현과 누락

서비스기획 9절은 제출본 기반 질문, 역할별 설명, 원고 수치와 답변의 차이, 근거 확인을 요구한다. 현재 `evaluation-preparation.tsx`의 `VisitPreparation`은 선택 원고의 `interviewQuestions`를 보여주고 질문·답변 요점·원본 위치를 업무 메모에 채운다. 질문별 답변 버전이나 답변과 원고·근거의 정확한 연결, 변경 후 재대조 기록은 없다. `studio-engine.ts`는 이미 준비 질문을 만들고 기관 확정 질문이 아님을 표시하므로 질문 생성 엔진을 중복 구현하지 않는다.

### 가장 작은 완결 흐름

선택 원고의 준비 질문 1개 → 담당자·역할과 모의 답변 입력 → 답변의 특정 부분과 원고·자료 인용을 나란히 연결 → 로컬 대조 결과와 추가 확인 메모 → 새 버전 저장 → 과거 답변 조회·DRAFT 연습자료 내려받기. 실제 기관 질문, 발언 녹음·전사, 외부 AI, 점수·합격 전망, 공식 실사 완료나 진행 단계 변경은 이번 범위에 포함하지 않는다.

### 입력과 저장 계약 제안

`append-visit-answer`는 기존 case PATCH의 strict 요청으로 `revision`, `clientRequestId`, `answer`를 받는다. `answer`에는 `answerId/previousVersionId`(최초에는 모두 null), `planId`, `questionIndex`, `questionText`, 선택 `submissionRecordId`, `respondentRole`(대표/기술 담당/실무/기타), `respondentName`, `answerText`, `pairs[]`, `followUpNote`, `review:{reviewed,reviewer,note}`를 둔다. 역할과 이름은 사용자가 기입한 설명 담당자이며 계정 권한이나 실제 참석 증명이 아니다.

각 `pair`는 사용자가 고른 `answerQuote`, 선택 `planReference:{sectionKey,quote}`, `sources:[{sourceId,sourceUpdatedAt,quote,locator}]`, `contextNote`를 갖는다. 최소 하나의 원고 또는 자료 연결을 요구하고, 인용은 공백·숫자를 임의로 바꾸지 않은 exact substring으로 검사한다. 원고 인용은 지정 planId 내부의 유일한 sectionKey만 허용한다. 원본만 연결하려면 source quote를 비우되 실제 보관 원본이 있어야 하며, pending 원본은 본문 근거로 대조하지 않는다.

서버는 `id/rootId/previousVersionId/version/recordedAt/origin:'manual'/inputDigest`와 질문 스냅샷(`planId/planVersion/planContentSha256/questionIndex/questionText/questionSha256`), 답변 SHA, 자료 스냅샷(`sourceUpdatedAt/textSha256/선택 원본 SHA·이름·크기·MIME`), 검사 알고리즘 버전·당시 결과를 저장한다. 질문 배열에는 ID가 없으므로 인덱스만 저장하지 않는다. 선택한 제출 기록은 동일 회사의 정확한 submission event 및 동일 planId/contentSHA일 때만 연결하며 ‘담당자 제출 기록 기준’으로 표시한다. 미연결이면 참고 원고이며 실제 제출본으로 추정하지 않는다.

### 로컬 점검의 의미와 상태

점검 결과는 사실 판정과 분리한다. 답변 미작성, 원고·질문 불일치, 빈/끊긴 인용, sourceUpdatedAt 변경, pending 본문, 자료 누락을 고정 코드로 표시한다. 사용자가 연결한 인용 짝의 숫자 표기가 다르면 ‘수치 표기 차이: 기간·단위·대상 확인 필요’를 제안한다. 비교 대상·기준기간·단위를 추론하거나 금액을 자동 환산하지 않는다. 서로 다른 문장의 숫자 집합을 회사 전체에서 비교하지 않는다. 표기 차이는 모순 확정이 아니며 숫자·키워드가 같아도 의미·진위·정합성이 확인된 것이 아니다. 숫자가 없거나 비교 범위가 불명확하면 ‘대조 불가/담당자 확인 필요’를 유지한다.

저장된 답변의 내부 상태는 `draft/내부 검토 기록 있음` 정도로 제한하고, 별도로 현재 연결 상태 `current/stale/missing`과 미해결 점검 항목을 보여준다. 원고·질문·자료 변경 시 과거 답변은 보존하고 새 답변 버전에서 명시적으로 다시 연결한다. 새 버전·답변 편집은 검토 표시를 자동 승계하지 않는다. 검토자 입력과 명시 확인만 내부 검토시각을 만들며, 미해결 항목·원본 진위·기관 결과를 자동 확정하거나 숨기지 않는다.

### 안전·호환과 연결 지점

새 `visitAnswers:[]`를 legacy 기본값으로 두고 기존 StudioStore.update의 회사 잠금·CAS·동기 트랜잭션·nonce 재시도를 재사용한다. 같은 질문 답변 root의 최신 이전 버전만 append하고 다른 질문·원고로 root를 옮기지 않는다. 자료는 같은 회사 source ID에서만 조회하며 원본 연결은 safe reader, 저장 경계 해시 재검사, 기존 agency/application/appeal 증거와 같은 ID의 원본 불변 정책을 재사용한다. 참조 자료 삭제를 막되 원고·분석·업무 완료·stage·기관 기록은 변경하지 않는다. 모든 조회·저장·출력은 명시한 질문·답변·근거만 포함하고 경로·자격정보·무관 자료를 제외한다.

초기 한도는 기업별 답변 버전 100개, 저장 문자열 합계 20만 자, 답변 1만 자, 연결 짝 10개, 서로 다른 source 10개, 원본별 12MiB·합계 24MiB로 제안한다. 한도 초과 시 기존 이력 삭제 없이 거부한다. `VisitPreparation` 질문 카드에 연습 진입 버튼을 추가하고 현재 WorkflowPanel의 dirty/busy 보호를 합산한다. 정확한 plan.section 연결에는 `resolveTaskPlanReference`의 단일 항목 검사, 인용·해시 스냅샷에는 소명/신청 기록 패턴을 재사용한다.

### 검증 계획

합성 자료와 임시 SQLite로 질문 인덱스 교체·중복 질문·원고 ID/본문 변조, 다른 회사 원고·source·submission 연결, answerQuote 변조, sourceUpdatedAt 변경·pending 인용, 원본 같은 크기 변조, 이전 증거 해시 충돌을 검사한다. 숫자 표기 차이/동일 숫자지만 다른 기간·단위/계획과 실적 혼재를 모두 ‘진위 미확인’으로 유지하는 회귀를 둔다. nonce 재시도·내용 충돌·stale CAS·이전 버전 보존·상한 rollback·재시작·실행 잠금·참조 삭제 차단·legacy 빈 배열을 확인한다. UI는 답변 편집 후 검토 해제, 오래된 근거 자동 재연결 금지, 정확한 원고·질문·답변 버전 출력, DRAFT·준비 질문 표시, 외부 AI/공식 runner 호출 0, 다른 회사/탭 이동 중 작성 내용 보호를 검증한다.
