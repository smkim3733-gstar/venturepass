1. 목적별 증인 lease를 잡고 quality 경로/root·.restore-pending·DB binding과 현재 파일 증인을 대조한다. company row/가격/키는 아직 읽지 않는다. 이미 가진 lease의 owner 신원도 매번 대조한다.
2. quality BEGIN IMMEDIATE. 같은 snapshot에서 기존 v11 schema/prefix/coverage/native/binding/예산/용량·전체 nonce를 감사한다.
3. 원래 nonce와 전체 명령 일치면 DB의 원래 결과만 반환한다. 이 경로는 studio가 없거나 현재 회사가 바뀌어도 새 회사 guard를 호출하지 않는다. witness가 불명확하면 원래 DB 구조 조회로만 표시하며 새 쓰기/현재 잔액 인증을 하지 않는다. nonce가 다른 명령과 충돌하거나 원장이 손상되면 거절한다.
4. 신규인 경우 witness의 마지막 확정 DB head와 현재 raw rows/head를 대조한다. 미확인 intent·다른 file/root·partial copy면 새 쓰기 차단.
5. 서버의 실제 studio handle에 BEGIN IMMEDIATE를 잡고 SQL row를 읽는다. 기존 assertVentureCompanyWritable를 앞뒤로 확인한다. 이 프로세스 Set이 다중 프로세스 잠금을 대신하지 않는다. studio writer가 busy면 새 DB/재시도 없이 실패한다.
6. 정확한 current company를 기존 요청 검사/계획기에 전달한다. 원래 review/notice/모델/선택/hash·시각/예산/head가 바뀌면 실패. 예약 때문에 회사 revision을 조정하지 않는다.
7. 계획7행의 정확한 digest와 이전 quality raw/head에 결합한 witness intent를 두 사본에 확정한다. 사본 하나 실패하면 SQL INSERT 없이 rollback하고 partial witness를 보존한다.
8. 기존 private gate로7행 저장, 같은 transaction 사후 SQL/native/binding/예산/용량 전체 감사. company row/hash·양쪽 파일 신원과 lease를 COMMIT 직전에 재대조한다.
9. **studio writer 잠금을 유지한 채 quality COMMIT을 관측한다.** 그다음 studio의 SELECT-only transaction을 ROLLBACK으로 끝낸다. ROLLBACK은 회사 변경을 되돌린다는 뜻이 아니라 읽기 거래 종료다. 품질 DB만 영속 데이터가 변한다.
10. lease를 유지하고 새 quality 읽기 transaction에서 원래 영수증/정확한 저장 행·현재 raw/head를 다시 감사한 뒤 witness ack 두 사본을 기록한다. 원래7행을 재실행하지 않는다.
11. 사용 중 handle/lease·복구 필요 상태를 정리한다. 회사 잠금이 끝났으므로 반환 시점 이후 현재 회사 일치를 보장하지 않는다. 나중 dispatch 직전에는 새로 같은 요청을 검사해야 한다.

예약에서는 studio를 quality COMMIT 전에 해제하면 안 된다.4I6의 fetch-start 뒤 studio→quality 종료는 실제 dispatch 단계의 별도 계약이다. 어떤 경우에도 DB 둘/파일/HTTP 전체의 원자 COMMIT을 가정하지 않는다. 이번 구현 목표에는 dispatch 자체가 없다.

quality COMMIT 뒤 studio 종료·ack가 실패하면 quality 행이 이미 남을 수 있다. 오류는 고정 code와 qualityCommitObserved/cleanupRequired 범위로 구분하고 고객 본문/임의 예외 메시지를 노출하지 않는다. 미확인 상태를 rollback 성공/예약 미실행으로 보고하지 않는다. 원래 nonce 조회가 복구 기준이며 새로운 nonce로 자동 대체하지 않는다. 정리 실패가 있는 handle은 폐기/격리하고 자동 강제 종료·lease 삭제를 하지 않는다.

## 복원 증인의 정확한 역할과 저장 계약

기존 operational journal의 저수준 안전한 파일 읽기/새 쓰기·사본/lease 구현을 공통화하고, 목적별 decoder/프로토콜을 분리한다. 기존 운영 profile/schema/00~기록/승인·완료 bytes는 그대로다. 같은 고정 control 또는 추가 승인 프로토콜에 비교를 끼우지 않는다.

비교 측 kind는 public-comparison-storage-witness, recordVersion1이다. 이 버전은 SQL11/binding3/native4 숫자와 독립적이다. 운영 profile/실제 경로를 이번에 설정하지 않는다. 후속 격리 fixture에서만 이미 승인된 새 루트 하위 data/control 형제 경로를 명시한다.

|기록|허용 내용|금지 내용|
|---|---|---|
|binding|purpose/version, 선택한 canonical data/studio/quality/control 경로와 root·주DB dev/ino/birthtimeNs, 기존 coverage DBinstance/cutoverDigest/coverageDigest, scope/environment|신규 예산·가격·승인·사람 동의, 회사 본문, 새 DB 자동 생성|
|anchor|단일 감사된 native-empty v11의 정확한 rawRowsDigest/archiveDigest/budget revision/head|운영 DB 잔액 자동 복사, 과거 nonce 변경|
|intent|sequence/previous digest, reserve 또는 cancel, 원래 nonce/전체 command digest, 원래 run/expected binding 참조, 이전 raw/head, 예정 행 집합 digest|새 nonce 소유권/영수증, 금액 계산, 명령 본문·review/자료 복제|
|ack|정확한 원래 DB receipt/binding 또는 cancel/finalize 참조, 실제 삽입 행 digest, 사후 rawRowsDigest/archiveDigest/budget head|DB행 생성/보정, missing usage=0, 현재 회사/승인 권한 승격|

rawRowsDigest는 같은 감사된 SQLite snapshot의 기존 표/coverage 원문 문자열·SQL 키/순서/body_hash 및 artifact 정확한 bytes/hash/크기에 결합한다. 전체 raw vectors를 witness에 저장하지 않는다. archiveDigest만 사용해 SQL 공백/encoding 변화까지 확인했다고 말하지 않는다. frozen prefix bytes는 기존 coverage 감사 그대로 유지한다.

주 DB dev/ino/birthtimeNs와 canonical root 신원은 프로세스/복원 전후를 비교한다. size/mtime/ctime은 정상 SQL 쓰기로 변하므로 영구 identity로 고정하지 않는다. WAL/SHM/journal은 정상 수명 동안 생성/삭제될 수 있어 inode 영구 pin을 하지 않는다. 존재 시 경로/nlink/reparse·용량 안전 검사를 수행하고 실제 내용은 SQLite snapshot으로 읽는다.

파일 인코딩은 정확한 JSON+newline, O_EXCL·fsync·열린 FD/경로 신원 대조와 외부 control 먼저→DB측 metadata 사본 순서다. 복구 때 partial 파일/누락 사본을 조용히 덮어쓰지 않는다. 레코드당32KiB·최대128개·사본당4MiB의 제한된 최초 프로토콜을 제안한다.20 native run의 reserve/cancel 각 intent+ack와 binding/anchor를 수용한다. 그 이상이면 삭제/회전·다른 control로 이동하지 않고 명시 미지원이다. dispatch/capture/정산 단계는 이 recordVersion1에서 미지원이다.

처음 witness 결합은 명시된 v11/native suffix0이며 기존 whole ledger/coverage/원래 비용이 감사된 상태에서만 허용한다. 양쪽 파일이 모두 없는 것을 기존 비용0/초기화 가능으로 해석하지 않는다. 현재 파일/coverage와 원래 선택의 운영 대조가 필요하다. 한번 기록한 binding/anchor는 immutable하며 실패/부분 초기화/DB 소실 시 새로 초기화하지 않는다.

새 승인/예산 표·병렬 DB·회사 본문 실행 이력을 만들지 않는다. witness nonce/digest는 DB 명령을 가리키는 교차 참조이며 성공 영수증/재실행 권한을 발급하지 않는다. DB에 없는 행을 파일로 복원하지 않고 파일의 amount/cap으로 회계하지 않는다.

## 재조회·취소·복원 실패 판정

|관측|허용|거절/보류|
|---|---|---|
|원래 DB nonce/전체 명령 일치, 회사 삭제/근거 만료|원래 기록 구조 조회, 아직 미전송이고 증인 정상일 때 취소|새 회사 snapshot을 대체하거나 replay owner 생성|
|새 reserve intent 두 사본, DB행 없음|불명 상태/원래 DB 진단 조회|같은 또는 새 nonce의 자동 예약, intent 삭제·DB행 재생성|

|단일 사본/partial·lease 잔존|격리·진단, 명시 운영 대조 후 후속 복구 설계|PID/시간으로 해제·사본 자동 보정|

최초 구현은 intent 이후 DB행이 없으면 자동 abort/예약 재개를 지원하지 않는 보수적 범위다. 제품 거래가 rollback됐다는 메모리 사실만으로 냉시작의 같은 상태를 자동 해제하지 않는다. 이런 현상이 실제 운영에서 발생하면 원래 기록을 보존한 별도 운영 대조가 필요하다. 다음 합성 개발 자체에는 사용자 결정이 필요하지 않다.

경로 신원이 같아도 파일 내용을 제자리에서 과거로 덮어쓰는 경우 최신 외부 ack/head와 교차 감사해야 한다. 모든 DB/양쪽 증인 사본까지 함께 과거로 돌린 악의적 복제나 전체 전원 차단의 모든 filesystem 지속성까지 로컬해시가 보장하지 않는다. studio가 제자리 복원됐어도 원래 요청과 같은 선택 bytes만 남은 경우, 회사 전체 과거 행 손실을 guard가 인증하지 않는다. 현재 선택 요청과 DB writer 잠금/확인한 신원 범위만 보고한다.

## 4I14 한 구현 단위의 완료 조건

다음은 계획이며 이번 시험 결과가 아니다.

1. private 거래/nonce 조회 로직을 재사용해 lazy 실제 studio 읽기를 연결한다. SELECT id/revision/body/파생 의미·32MiB와 기존 작은 한도, same revision 다른본문 거절. 회사4표/원고/원본 불변.
2. 원래 nonce replay에 회사 getter/시계/가격을 금지한 시험, 회사 삭제·근거 만료 뒤 원래 조회/취소, 다른 명령 nonce 충돌. 취소는 studio handle이 없어도 quality/증인으로 대조.
3. quality→studio 획득·quality COMMIT까지 studio잠금 유지. 경쟁 연결/프로세스가 회사 변경을 시도할 때 배제됨을 확인하고 잠금 밖에서는 정상 기존 변경이 가능한지 확인. 반대 순서·caller transaction·재진입/thenable 거절.
4. 경로/root/주DB 교체·restore marker/unsafe sidecar 거절, 정상 WAL 수명/쓰기 후 mtime 변화 오인 방지. 기존 생성자/설정/키를 열지 않고 격리 already-open DB만 사용.
5. 목적별 witness binding/anchor·reserve/cancel intent/ack와 v11 저장을 한 흐름으로 검증한다. 기존 journal의 v1/v2 golden/고정 profile·원래 기록은 불변. 실제 운영 control/lock은 열지 않는다.
6. intent 두 사본 각 쓰기/SQL 행/COMMIT/회사 종료/ack 각 실패, 재열기·DB-only COMMIT과 ack-only 소실/과거 복원 대조. witness를 DB 복구에 사용하거나 새 owner를 만들지 않음.
7. 원래 nonce/사용량·동일 scope/head·coverage/raw bytes/순서 보존,7/6행 외 SQL 쓰기0. 자체 COMMIT 관측과 회사 guard 범위만 새 transient 상태로 표현하고 가격/사람동의/dispatch false 유지.
8. 기존 실제 SDK/fetch/운영 DB·환경 설정 읽기 금지. 알려진 backup27개와 파일 내2개는 제외하고 영향 회귀→lint→typecheck→격리 build:local의 종료코드를 순서대로 확인한다.

첫 운영 연결/가격 근거/사람 동의/dispatch와 v10/v11 백업·복원 출시는 별도 조건이다. 이를 이번 명세나 다음 격리 합성 시험으로 완료 처리하지 않는다.
