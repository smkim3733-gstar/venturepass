# 품질평가 실제 AI 승인 준비 개발 설계

기준: 2026-09-27. 등록한 합성 후보의 실제 AI 실행을 준비하기 위한 후속 설계다. 현재 구현은 로컬 모의 공급자 실행이며, 이 문서는 실제 전송·유료 호출·가격 채택·품질 합격을 승인하거나 완료 처리하지 않는다. 실제 키·환경 파일·회사 자료를 읽지 않았고 공급자 가격도 조회하거나 채택하지 않았다.

구현 갱신: 같은 날 A의 순수 요청/가격/토큰/금액 계약과 로컬 준비 조회·화면·정확한 현재 조회본 JSON 다운로드를 구현했다. 생성 본문은 확정하고 검토 템플릿은 미완성으로 남긴다. 제품 API의 가격·토큰·예산은 null이며 실행·승인·예약은 false다. 이 조회본은 서버에 영속 저장된 준비안이 아니다. 아래 B/C는 여전히 미구현이며 상세 다음 연결은 [비용 원장 설계](품질평가_실제AI_비용원장_연결설계.md)를 따른다. A 검증은 관련14파일319개와 lint·타입·격리 빌드 및 합성 브라우저 QA이며 실제 공급자 가격/토큰 근거 채택이나 실제 품질평가는 포함하지 않는다.

## 1. 현재 구현과 남은 차이

검토 근거는 [최종 서비스 기획 v3](벤처패스_최종서비스기획안_v3.md)의 자료·운영 원칙 및 품질 검증 기준, [실행 증빙 설계](품질평가_실행증빙_연결설계.md), [후보 버전 등록 설계](품질후보_버전등록_연결설계.md), [평가 기록 규격](AI_품질평가_기록규격.md), [앱 운영 안내](../web/README.md)와 현재 구현이다. 앞선 설계의 구현 전 설명은 아래 현황으로 구분한다.

| 영역 | 이미 있는 기반 | 실제 실행 전에 필요한 최소 보완 |
|---|---|---|
| 입력 고정 | 후보 등록본의 전체 원문, 후보·자료·모델 입력 digest, 등록 버전 | 승인 당시 생성 요청 본문·프롬프트·요청 schema 보존, 검토 입력 파생 규칙 고정 |
| 실행 관측 | 엔진의 생성·검토 최대 2회, 전송 직전·응답 수신·출력 검증 훅 | 실제 요청 본문을 영속 보관하고 토큰·비용 예약 성공 후 전송하는 승인 검사 |
| 영속 기록 | 시작 nonce/CAS, 실행·이벤트·영수증 불변 기록, 과거 revision 조회·다운로드 | 실제 실행 전용 계약과 비용 예약·정산 원장. 모의 기록의 actual 승격 금지 |
| 실패 처리 | 응답 없는 전송을 미확인으로 보존, 자동 재전송 금지, 미확정 동일 후보 재실행 차단 | 미확인 비용 예약 유지, 명시적인 후속 조사·정산 기록과 미사용분 해제 기준 |
| 비용 | 모의 과금 0, 실제 가격·통화·예산·입력 토큰 추정은 null | 출처가 있는 요율, 검증 가능한 입력 토큰 상한, 요청별 최대 비용과 실행 총액 예약 |
| 화면/API | 별도 품질 개발 도구, 후보 선택·모의 준비·명시 실행·조회 복구 | 실제 전송 내용·목적지·모델·최대 비용의 구체적 승인 화면과 별도 actual 시작 경로 |
| 백업 | 품질 DB v1/v2/v3 및 현재 8개 테이블의 검사·복원 | actual 기록·입력 원문·비용 원장을 포함하는 새 백업 버전. 기존 다운로드 바이트 유지 |

`studio-engine.ts`에는 `generateObservedPlan(..., { mode: "actual-ai" })` 분기가 있으나 품질 실행 서비스·저장소·화면은 mock 계약만 받는다. 엔진 분기의 존재를 제품의 실제 실행 준비 완료로 표시하지 않는다. 기존 회사 원고 작성 승인과 후보 등록 확인도 이번 평가 실행 승인을 대신하지 않는다.

현재 관측 훅의 `requestDigest`는 실제 SDK 요청 JSON 전체를 고정한다. 그러나 영속 이벤트에는 요청 메타데이터와 digest만 있고 정확한 전송 본문은 없다. 후보 원문을 보관했다는 사실만으로 나중에 변경된 프롬프트·schema·입력 조립 코드까지 재현할 수 있는 것은 아니다.

## 2. 공급자 조사와 가격 근거

다음 항목을 실제 실행 직전에 공급자의 공식 자료로 확인한다. 이 문서에서는 제공자·모델·가격을 새로 채택하지 않는다. 현재 엔진의 OpenAI 목적지 고정을 변경하려면 별도 구현·승인 범위를 만든다.

| 확인할 항목 | 보관할 근거와 차단 조건 |
|---|---|
| 정확한 모델 식별자·요청 API | 지원되는 고정 모델/버전, 구조화 출력·토큰 제한·응답 메타데이터 지원. 별칭의 변경 가능성을 검토하고 설정 모델과 응답 모델을 따로 기록 |
| 입력·출력 요율 | 공식 URL, 확인 시각, 적용 시점, 통화, 가격 단위, 모델·API 조건과 근거 발췌 또는 스냅샷 digest. 어느 하나 불명확하면 준비 미완료 |
| 캐시·추론·부가 과금 | 캐시 할인 적용 조건, 추론 토큰의 포함 관계, 추가 요청·도구·저장 과금 여부. 확정되지 않은 할인이나 무료분을 예약액에서 빼지 않음 |
| 토큰 계산 | 선택 모델의 토크나이저와 버전, 메시지·system·schema 등 전체 요청의 계산 범위, 서버 부가분 처리, 최대 입력/출력 및 문맥 한도 |
| 보관·처리 조건 | `store:false`의 실제 범위, 보관·삭제 조건과 적용 정책. 모든 외부 보관이 사라진다는 표현 금지 |
| 오류·청구 확인 | 실패·중단·usage 누락 때의 과금 가능성, 응답 조회 지원과 별도 비용, 청구 대조 방법. 조사 전에는 조회 API 자동 호출도 추가하지 않음 |

가격 증빙은 승인 준비안과 함께 불변 버전으로 고정한다. 가격 유효성 확인 주기·만료 정책은 운영자가 정하고 코드에서 검사한다. 임의의 유효기간이나 환율을 만들지 않는다. 최초 구현은 공급자의 한 통화로 비용 상한을 표시하고, 환산이 필요하면 환율 출처·시점·오차 범위를 추가로 고정한다.

## 3. 승인할 입력과 요청 상한

승인 준비안에는 후보 `setId/version/versionDigest/candidateId/modelInputDigest`, 목적, 제공자·고정 목적지, 설정 모델, 엔진 계약, 프롬프트·schema 원문 및 digest, 단계별 최대 입력/출력 토큰과 최대 호출 2회, 재시도 0회, 자동 수정 없음, 가격 근거, 예약 총액·통화를 포함한다. 실제 전송할 생성 요청 전체를 열람·내려받을 수 있게 한다. 자격정보·작성자 메모·challengeTags·사람 정답표는 넣지 않는다.

원본 입력은 `candidateRegistryModelInput()`의 허용 목록을 재사용한다. 저장된 후보의 `profile/sources/candidate`만 읽고 현재 회사 DB나 이후 수정한 후보로 바꾸지 않는다. 실행 준비의 저장 시점과 명시 승인 시점을 구분하며, 승인된 준비안 digest가 달라지면 이전 승인으로 시작하지 않는다.

검토 요청은 생성 결과가 생겨야 완성된다. 존재하지 않는 검토 본문을 미리 승인받았다고 기록하지 않는다. 최초 승인 범위에 다음 파생 규칙을 구체적으로 포함한다.

1. 동일한 고정 후보 입력과 검토 프롬프트·schema에 이번 실행의 검증된 최초 생성 원고만 결합한다.
2. 생성 원고와 해당 검증 이벤트 digest를 검토 요청에 연결한다. 다른 실행 원고·수정본·추가 자료는 허용하지 않는다.
3. 검토 요청의 전체 본문·digest를 전송 직전에 보관하고, 승인한 입력 토큰 상한·예약액 안인지 다시 검사한다.
4. 생성 결과가 상한을 초과하면 검토 호출을 하지 않는다. 임의 요약·절삭·모델 변경으로 승인 범위를 맞추지 않고 구체적인 새 준비안을 제시한다.

현재 `maxInputChars: 240000`은 문자 수 방어이고 입력 토큰 상한이 아니다. `inputChars`는 system/user 내용 길이이므로 요청 schema 및 공급자 측 추가 계산까지 포괄하는 비용 근거로 사용하지 않는다. 생성은 정확한 전체 요청의 토큰 수와 검증된 부가 상한을 계산한다. 검토는 아직 알 수 없는 생성 원고까지 포함하는 보수적인 최대 입력 상한을 먼저 예약하고, 실제 요청이 만들어지면 다시 계산한다. 토크나이저나 전체 계산 범위의 상한을 입증할 수 없으면 실제 실행을 막는다.

`max_output_tokens`가 청구되는 출력·추론 사용량에 어떤 상한을 주는지는 공급자 자료로 확인한다. 문자 수를 임의 비율로 나누거나 usage 누락을 0으로 대체하지 않는다. 입력+출력의 문맥 한도도 따로 검사한다.

## 4. 비용 예약과 중단 처리

가격 계산은 부동소수점 누적 오차가 없는 금액 표현과 올림 규칙을 사용한다. 단위·정밀도·올림 규칙도 가격 계약에 포함한다. 요청별 최대액은 검증된 입력 상한, 출력 상한, 적용 요율과 허용된 추가 과금의 합이다. 최악 조건의 2회 비용과 이미 미확인인 예약액을 합쳐 사용자가 승인한 총액을 넘지 않아야 한다.

시작 트랜잭션은 승인 준비안·nonce·CAS·미확정 실행을 대조한 뒤 실행 영수증과 총액 예약을 함께 기록한다. 각 요청 전에는 해당 요청 본문, 단계·순번, 요청 digest와 비용 할당을 같은 트랜잭션으로 기록한 다음 전송한다. 예약 또는 원문 기록 실패 시 공급자 호출은 0회다. 기존 `beforeRequest`가 여러 번 불리는 것을 추가 전송이나 추가 비용 예약으로 세지 않는다.

| 관측 상태 | 비용 처리와 다음 행동 |
|---|---|
| 전송 전 검사 실패 | 외부 전송이 없음을 증명할 수 있는 범위만 미사용 예약 해제 기록. 원래 승인·예약 이력은 보존 |
| 전송 직전 기록 뒤 중단 | 실제 수신 여부 미확인. 해당 요청 예약 유지, 자동 재전송·자동 해제 금지 |
| 응답 수신, usage 없음/불일치 | 출력 성공 여부와 무관하게 사용량·비용 미확정. 예약 유지 및 근거 확인 필요 |
| 유효한 usage 수신 | 고정 가격으로 계산한 사용량 기반 금액을 별도 기록. 공급자 청구 확정으로 표시하지 않음 |
| 출력 검증 실패 | 이미 받은 응답·usage·예약은 유지. 다음 호출 중단, 실패를 무료 처리하거나 모의 결과로 대체하지 않음 |
| 실행 종료 | 아직 전송하지 않은 단계의 미사용 예약만 해제 가능. 보낸 요청의 불명확한 사용량은 남김 |

공급자 청구 근거를 실제로 확인한 경우에만 별도 대조 기록을 추가한다. usage 정산·예약 해제·청구 확인을 하나의 `paid/completed` 값으로 합치지 않는다. 복원·재시작은 저장된 기록 조회만 재개한다. 늦은 응답을 받는 후속 기능은 원래 실행·단계·requestDigest와 정확히 연결하며 신규 전송을 포함하지 않는다.

## 5. 최소 구현 묶음과 파일 연결

기존 모의 계약을 느슨하게 바꾸지 않는다. 아래 새 파일명은 제안이며 이번 문서 작성에서 제품 코드는 변경하지 않는다.

| 순서 | 최소 변경 | 재사용 및 변경 위치 | 완료 조건 |
|---|---|---|---|
| A. 실행하지 않는 실제 승인 준비 | 가격 증빙·토큰 계산·금액 계산의 순수 타입/helper, 승인할 생성 원문과 검토 파생 계약, 부족 조건 표시 | 신규 `src/lib/studio-plan-quality-actual-types.ts`, `studio-plan-quality-actual-preparation.ts`. 후보 registry 및 `getPlanExecutionContract()` 재사용. 엔진의 요청 본문 조립을 키/IO 없는 순수 함수로 추출 | 합성 가격·토큰 어댑터로 준비/차단 검증. 실제 가격은 미설정이면 차단. 준비 조회만으로 키 읽기·AI 호출·실행 승인 없음 |
| B. 실제 기록·예약 원장 | 실제 승인·원문·요청·응답·비용 예약/정산의 append-only 보관, nonce/CAS, 조회·고정 다운로드 | `studio-plan-quality-store.ts`의 경로·용량·트랜잭션 재사용. actual 전용 타입과 테이블/레코드 종류 사용. `scripts/local-data-quality.mjs`에 새 백업 버전 | 모의 기존 8테이블·JSON 불변, actual과 mock의 ID/nonce 충돌 거절, 실제 공급자 없이 중단·동시 실행·복원 검증 |
| C. 승인 범위 안의 실제 실행 연결 | 정확한 요청 원문·토큰·예약 검사 후 기존 관측 엔진 호출, 2회 이외 호출 금지. 별도 시작 경로와 승인 화면 | `studio-engine-execution-types.ts` 및 `studio-engine.ts`에 원문을 영속 검사하는 전송 전 훅 추가. `studio-plan-quality-execution-runner.ts`의 전이 패턴 재사용하되 actual runner/service 분리. 기존 `quality-execution-panel.tsx`와 UI helper에 별도 준비/승인 표시 | 로컬 가짜 공급자로 승인 누락·변경·한도·응답 유실 시험 통과 후에만 구체적 실제 1건 실행 승인을 요청 |

현재 `onDispatch`는 본문 없이 요청 메타데이터만 받는다. actual 원문 고정을 위해 `onRequestPrepared({ request, body })` 같은 별도 await 훅 또는 동등한 명시 계약이 필요하다. 이 훅은 모의 transport에만 있는 본문 접근을 actual에도 안전하게 제공하고, 키나 SDK client를 포함하지 않아야 한다. 원문 기록·비용 할당과 전송 직전 기록의 순서를 명확히 정하고, 중간 실패를 재전송 허가로 해석하지 않는다.

실제 실행의 상태·비용 이벤트는 현재 mock의 최대 7개 이벤트 계약에 억지로 넣지 않는다. 새 계약의 테이블 수·이벤트 한도·본문 한도·총 용량 및 백업 manifest 버전을 구현 전에 함께 확정한다. 원문 보존으로 필요한 용량은 계산하되 현재 256MiB 통합 한도를 임의로 늘리지 않는다. 후보 등록/기존 50개 평가/mock/actual의 모든 nonce 충돌 방향을 검사한다.

일반 사용자 메뉴 3개는 유지한다. 품질 개발 도구에서만 ‘로컬 모의 실행’과 ‘실제 전송 준비’를 구분한다. 준비안이 미완성이면 정확한 누락 항목을 표시한다. 미확인 요청의 GET 조회와 명시적 동일 nonce 확인은 재사용하지만, 시작 기록이 있는 actual 실행을 다시 호출하지 않는다. 모의 원고·사람이 입력한 평가 JSON·서버가 관측한 실제 응답은 별도 출처로 표시한다.

## 6. 필요한 합성 회귀

- 가격 근거·통화·단위·모델·적용 시점이 없거나 상한 계산이 불가능하면 호출 0회. 캐시 할인·usage 0·임의 환율을 만들어 준비 완료로 표시하지 않음.
- system/user/schema 전체와 다국어·이스케이프가 있는 요청을 계산하고, 모델·프롬프트·schema·토큰 상한·요율 중 하나만 바뀌어도 이전 승인 거절.
- 원래 승인 본문을 보존하고 코드 업데이트·후보 새 버전 이후에도 과거 JSON 바이트 동일. 변경된 현재 계약으로 과거 승인 실행 금지.
- 생성 최대액+검토 최대액을 정확히 예약. 두 프로세스 동시 시작과 한도 1단위 경계에서 초과 전송 0회. 같은 nonce 재조회는 추가 비용·전송 0회.
- 원문/예약 기록 실패 시 전송 0회, dispatch 뒤 단절 시 해당 예약 유지, 응답 영속화 실패 시 두 번째 호출 0회.
- 검토 입력에 동일 실행의 검증 원고만 연결. 다른 원고·정답표·메모·상한 초과 입력은 차단하고 승인 없이 축약하지 않음.
- 정상 usage/누락 usage/일관성 없는 usage/응답 모델 차이를 구분. 구조 검증 실패와 청구 가능성을 별도 보존.
- mock 기록의 mode·provider·가격만 actual로 바꾼 위조 거절. 백업 복원이 mock을 actual이나 미확인을 실패 확정으로 바꾸지 않음.
- 실제 시작 POST 응답 유실 뒤 다른 실행의 영수증으로 승인·pending을 해제하지 않음. 동일 nonce·준비안 digest·execution ID·예약 연결이 맞아야 복구.
- 과거 v1/v2/v3 품질 백업, 기존 50개 평가, 등록 후보 12개, 회사 DB가 보존됨. 새 actual 백업은 불변 원문·비용 원장과 단계 연결까지 검사.

이 시험은 합성 자료·가짜 요율·가짜 토크나이저/공급자 어댑터로만 수행한다. 시험용 값은 운영 가격이나 실제 모델 사용량의 근거가 아니며, 운영 준비안에 자동 채워 넣지 않는다.

## 7. 실제 실행 전에 한 번 받을 구체적 승인

A/B와 C의 모의 검증은 독립 개발로 진행할 수 있다. 실제 전송 직전에는 선택한 후보 한 개와 등록 버전, 정확한 입력/프롬프트/schema, 검토 입력 파생 범위, 제공자·목적지·모델, 보관 조건, 최대 2회·토큰 한도·재시도 0회, 확인한 가격 근거·통화·최대 예약액, 이미 미확정인 예약·실행을 한 검토안으로 보여 준다. 승인 범위가 변하지 않는 동일 요청을 단계마다 다시 묻지 않는다.

키·회사 자료가 존재한다는 이유로 승인됐다고 추정하지 않는다. 실제 1건 관측 검증 후에도 12건 전체 또는 외부 고객 자료 처리로 범위를 자동 확대하지 않는다. 외부 고객 자료에는 v3의 회원·권한·회사 격리·보관·삭제·지원 운영 준비가 별도로 필요하다.

## 8. 품질 검증 상태는 별개로 유지

추가 후보 12개는 AI가 작성한 합성 후보다. `humanAnswerKey: null`, `independentHoldoutConfirmed: false`, `performanceEvaluation: not-performed` 상태를 유지한다. 모의 또는 실제 생성이 끝나도 사람 정답표·독립 검토·기관 승인·원고 품질 합격으로 바꾸지 않는다.

v3의 독립 고정 세트 최소 50건, 담당자의 사실·쟁점 정답표, 두 사람의 독립 평가와 불일치 조정은 아직 별도 준비 대상이다. 기존 개발 회귀 50개와 추가 후보 12개를 ‘독립 62개’로 합산하지 않는다. 이번 묶음의 종료 기준은 실제 승인 준비와 비용·입력·복구 경계가 검증된 상태이며, 실제 품질 평가 완료와 구분한다.
