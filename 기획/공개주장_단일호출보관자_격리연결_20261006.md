## 2. 단일 슬롯과 명시 시작

보관자를 만들거나 attachView하는 것만으로 invocation/Request/타이머를 만들지 않는다. prepare는 현재 token/closed/critical/용량을 검사하고 creating entry를 예약한 뒤 원래 입력을 읽는다. 기존 factory가 만든 원래 호출을 먼저 보관하고 completion을 관측한 뒤 handle을 반환한다. 호출자가 원래 snapshot·선택·frame을 제공하고 명시 start하는 경우에만 기존 포트가 최대1회 실행된다.

회사/화면 전체에서 슬롯1개이며 회사별 Map·대기 queue는 없다. 이전 요청/응답 pending, cleanupFailed 또는 request unavailable이면 추가 생성 전에 BUSY다. 이전 호출이 정상 완료된 경우에도 fresh inspect().canForget을 읽고 같은 entry를 확인한 뒤 명시 교체한다. 이전 표시를 먼저 해제하므로 새 입력 검증 실패가 이전 exact를 다시 표시하지 않는다.

## 3. 표시·완료·폐기

display는 현재 view/handle/entry와 기존 ticket/frame을 모두 통과해야 한다. 기존 ticket은 원래 snapshot 참조/회사/revision·선택·열림/편집/차단 상태와 정확한 결과 신원을 계속 확인한다. 보관자가 결과를 자체 복제/저장하지 않으며 외부 display 사본의 변경은 내부 결과를 바꾸지 않는다.

화면 교체/분리·cancel/close는 먼저 표시를 폐기하고 자기 원래 호출만 취소한다. 옛 화면 token의 cleanup이나 옛 handle의 release/cancel이 새 entry를 지우지 않는다. closed는 영구 admission 거절이며 reopen/reset은 없다. 닫힌 뒤에도 pending/실패/불명이 남으면 호출자가 보관자 자체를 계속 보관해야 한다.

원래 completion 관측과 fresh canForget:true를 함께 확인해야 I/O 참조를 해제한다. 현재 화면에 연결된 깨끗한 완료 결과는 명시 교체/해제 또는 화면 분리까지 유지한다. 분리/closed entry는 정상 completion 뒤 같은 entry의 정리 성공이 관측되면 해제한다. 새 타이머/polling·자동 재조회·재시도는 없다.

원래 start/read/cancel이 늦으면 빠른 delivery 실패 후에도 슬롯은 남는다. completion 종료가 cleanupFailed:false를 뜻하지 않으며 영수증 불명은 완료를 추정하지 않는다. 원래30초 기한이 끝나도 completion/canForget이 확인되지 않으면 폐기하지 않는다. 준비만 한 호출도 기존 receiver의 기한을 따르며 자동 start하지 않는다.

critical 구간에서 추가 prepare/start/release/inspect가 원래 호출을 덮지 못하게 막는다. attach/detach/close의 취소 의도는 즉시 표시 상태에 반영하고 원래 객체를 확보한 뒤 정리한다. 생성 중 닫힘도 원래 호출을 보관한 다음 취소하며 전송0이다. 완료 callback/inspect/abort의 재진입과 옛 entry 대조를 분리한다.

용량1은 보관자 소유 호출 개수다. snapshot·Promise·외부 사본까지 포함한 JS heap4MiB 보장이 아니다. 호출자가 보관자 참조를 잃거나 브라우저/프로세스가 종료되면 지속성을 보장하지 않는다. 실제 React StrictMode/remount 설치·상위 구독/표시 통지는 아직 없다.
