# 신청회차·제출본·결과·차기 신청 이력 분리 설계

작성일·구현 확인일: 2026-09-25. 상태: **최소 범위 구현 및 기능별 검증 완료**. 전체 앱 최종 회귀·배포 빌드 결과는 별도 검증 기록을 따른다.

이 문서는 [서비스 기획](./혁신성장유형_서비스기획_v1.md) 1.1·8·10·12절과 [제품 완성 로드맵](./제품완성_개발로드맵.md) 10번을 구체화한다. 실제 기업자료·DB·계정·기관 화면을 조회하지 않고 제품 코드만 검토했다. 기관 접수나 제출 성공을 새로 확인한 문서가 아니다.

## 1. 첫 구현의 완료 범위

하나의 기업 작업공간 안에서 신청회차를 명시적으로 등록하고, 제출했다고 기록한 원고 버전·선택 원본·당시 검토 상태를 고정한다. 기존 기관 요청·답변·통보의 정확한 버전을 회차에 연결하고 결과·확인서 및 다음 신청회차를 구분한다. 오기입 정정과 회차 재귀속도 과거 기록을 남긴다.

첫 구현에는 공식 제출 버튼 실행, 기관 상태 자동 판정, 신청번호 추출, 과거 자료의 자동 제출 처리, 재확인 기한 자동 계산을 포함하지 않는다. 회사의 기존 자료·원고·업무·기관 기록·공식 입력 이력은 이동하거나 삭제하지 않는다.

사용자 흐름은 다음과 같다.

1. 회차 미지정 기존 이력을 그대로 확인한다.
2. 신규 또는 재확인 회차를 만든다. 과거 신청을 나중에 등록하는 것도 허용한다.
3. 원고 버전과 제출했다고 기록할 원본을 직접 선택한다. 당시 초안·검토 여부도 함께 보관한다.
4. 요청·접수 통보·결과·확인서의 정확한 기록 버전을 해당 회차에 연결한다.
5. 잘못 연결한 경우 정정 사유를 남겨 재귀속한다. 과거 귀속·제출본은 보존한다.
6. 다음 신청은 새 회차를 만들고 이전 회차를 연결한다. 과거 제출본을 새 제출로 복제하지 않는다.

## 3. 저장 구조와 하위 호환

다음 두 배열을 `StudioCase`에 추가했다. 별도 SQL 테이블 이동 없이 기존 회사 JSON과 공통 트랜잭션을 사용한다.

```ts
applications: ApplicationCycle[]; // 누락 시 []
applicationEvents: ApplicationEvent[]; // 누락 시 []
```

기존 배열은 자동 분할하지 않는다. 회차가 없거나 귀속 저널이 없는 기관 체인은 **회차 미지정**으로 표시한다. 현재 회사 단계가 `submitted`, `confirmed`여도 회차·제출 사건·확인서 기록을 자동 생성하지 않는다. 기존 업무 메모나 원고 제목으로 회차·제출일을 추정하지 않는다.

회차 선택은 우선 화면 조회 범위다. 전역 `activeApplicationId`를 추가하여 기존 작성·기관 입력을 암묵적으로 귀속시키지 않는다. 새 기록을 회차에 넣는 요청에는 대상 회차 ID가 반드시 포함되어야 한다.

### 3.1 신청회차

`ApplicationCycle`의 최초 값은 불변이며 다음 필드를 가진다.

| 필드                             | 의미                                                       |
| -------------------------------- | ---------------------------------------------------------- |
| `id`                             | 서버가 발급한 로컬 UUID. 기관 신청번호가 아님              |
| `clientRequestId`, `inputDigest` | 회사 내 단회 요청 식별과 정규 입력 해시                    |
| `recordedAt`, `origin: 'manual'` | 서버 보관 시각과 담당자 기록 출처                          |
| `title`                          | 사용자가 붙인 회차 명칭                                    |
| `kind: 'new' \| 'renewal'`       | 담당자가 확인한 신규·재확인 구분                           |
| `plannedOn`                      | 신청 예정일 또는 미확인 빈 문자열                          |
| `criteriaNote`                   | 적용 기준·기준일에 대한 담당자 메모. 공식 적합 판정이 아님 |
| `previousApplicationId`          | 같은 회사의 이전 회차 ID 또는 `null`                       |
| `companyAtCreation`              | 생성 당시 기업명·사업자번호 표시값. 현재 회사정보와 분리   |

명칭·예정일·구분·이전 회차 연결을 고치려면 `cycle-correction` 사건을 추가한다. 최신 메타 사건 ID를 `previousVersionId`로 요구하여 분기 정정을 차단한다. 자기 참조·다른 회사·없어진 ID·회차 연결 순환을 거부한다. 재확인이라고 해서 이전 회차를 만들어내지는 않는다. 앱 밖의 과거 신청만 있는 경우 이전 회차 미연결과 설명을 허용한다.

기관 신청 식별정보는 초기 범위에서 기존 접수 통보의 수기 번호를 정확한 기록 버전과 함께 보여주는 방식으로 충분하다. 도입하더라도 로컬 UUID와 이름을 분리하고 담당자 기록으로 표시해야 하며, URL이나 임의 텍스트에서 자동 추출하지 않는다.

### 3.2 공통 사건

모든 사건은 `id`, `applicationId`, `clientRequestId`, `inputDigest`, `recordedAt`, `origin: 'manual'`을 가진다. 메모·발생일·부모 버전은 사건 종류별 strict schema로 정의한다. `applicationId`는 원칙적으로 같은 회사의 회차 ID이며, 귀속 해제인 `agency-link-correction`에서만 `null`을 허용한다. 그 경우에도 이전 귀속은 별도 `fromApplicationId`와 부모 링크 ID로 남긴다. 제출 발생일 `occurredOn`은 보관 시각과 별도다. 입력에서 서버 ID·해시·보관 시각·검증 플래그를 받지 않는다.

사건 종류는 strict discriminated union으로 제한한다.

- `cycle-correction`: 회차 정보 정정.
- `submission-recorded`, `submission-correction`: 제출했다고 기록한 내용 및 정정.
- `agency-link`, `agency-link-correction`: 기관 체인의 회차 귀속과 정정.

회차별 별도 `stage-recorded`는 이번 최소 구현에 포함하지 않았다. 기존 회사 단계와 변경 이력은 유지하며 회차에 자동 동기화하지 않는다.

결과와 확인서는 `agency-link`의 고정 통보 버전에서 표시한다. 별도 결과 문자열을 중복 저장하고 이를 기관 판정으로 승격하는 경로는 만들지 않는다. 일반 단계 변경이나 결과 연결을 원인으로 다음 회차를 자동 생성하지 않는다.

## 4. 제출 당시 버전 고정

`submission-recorded`는 실제 외부 호출이 아니라 담당자의 과거 행위 기록이다. 입력에는 회차 ID, 원고 ID, 선택 원본 ID 목록, 제출했다고 기록할 날짜, 담당자 이름·메모, 선택적 기관 접수 기록 ID가 들어간다. 날짜가 미확인이면 제출 사건 대신 일반 메모/준비 상태에 머문다.

서버가 고정할 최소 스냅샷은 다음과 같다.

| 구분      | 고정할 값                                                                                                   |
| --------- | ----------------------------------------------------------------------------------------------------------- |
| 회사      | 기록 당시 회사 ID·revision·기업명·사업자번호 표시값                                                         |
| 원고      | `planId`, `version`, `generatedAt`, `mode`, `candidateId`, `sourceRevision`, `contentSha256`                |
| 당시 검토 | 당시 `confirmedAt`, `review`, 항목별 `needsConfirmation`, 최신 버전 여부, 근거 현재성, 미확인 사유          |
| 인용      | 해당 원고에 실제 있는 source ID·당시 자료명·인용문·locator와 당시 대조 상태. 다른 자료 본문은 저장하지 않음 |
| 선택 원본 | source ID·당시 이름·원본 파일명·MIME·크기·SHA256·자료 수정 시각                                             |
| 담당자    | 명시적으로 선택한 업무 ID·요청 버전과 당시 `owners` 이름. 이름은 권한·검토 완료 증거가 아님                 |
| 제출 기록 | `claim: 'reported-submitted'`, 담당자 발생일·기록자 표시명·메모                                             |
| 접수 근거 | 선택한 동일 회사 접수 통보의 정확한 기록 ID와 버전 또는 미연결                                              |

현재 원고가 초안이거나 과거 버전이어도 과거 제출 사실에 관한 담당자 기록 자체를 막아서는 안 된다. 대신 당시 선택의 초안·오래된 근거·미확인 상태를 명확히 고정하고 **내부 검토 완료**로 바꾸지 않는다. `confirmedAt`이 존재해도 기관 제출·수용 증명은 아니다.

원고 본문은 기존 `plans`의 불변 ID를 참조한다. 향후 원고 삭제·덮어쓰기 기능이 생기면 제출 사건에서 참조한 버전은 차단하거나 별도 보존해야 한다. 원고의 표시용 검토 상태는 현재 `plan.review/confirmedAt`를 다시 읽지 않고 제출 사건의 당시 스냅샷을 사용한다.

선택 원본은 기존 파일을 유지하고 해당 source 삭제를 차단한다. 같은 source ID의 실제 바이트가 과거 고정 SHA256과 달라졌다면 새 제출 연결과 역사 원본 다운로드를 거부하며, 다른 원본은 새 source로 등록하도록 안내한다. 과거 해시를 현재 파일 값으로 갱신하지 않는다. 앱 밖에서 파일이 훼손·삭제된 경우 복구된 척하지 않고 역사 원본 확인 실패로 표시한다.

제출 정정은 최초 사건을 덮어쓰지 않는다. 최초 제출 ID와 최신 정정 ID를 지정해 새 사건을 추가하고, 변경된 원고·원본은 다시 안전하게 읽어 별도 스냅샷을 만든다. 과거 기록과 이전 원본 보호는 계속 유지한다.

## 5. 기관 체인의 회차 귀속 저널

### 5.1 체인 식별

- 요청·요청 정정·답변은 서버가 기존 기록을 조회하여 도출한 최초 `requestRecordId` 하나가 체인 키다.
- 통보·통보 정정은 최초 `noticeRecordId` 하나가 체인 키다.
- 호출자가 임의 체인 루트나 다른 종류의 ID를 제출해도 서버가 계산한 루트와 일치해야 한다.

**한 체인의 현재 귀속은 하나의 회차 또는 미지정만 허용한다.** 요청 원문은 A회차, 그 답변은 B회차처럼 분할하지 않는다. 요청 버전별 업무도 동일 체인의 현재 귀속을 따라 조회하되, 제출 당시 고정한 업무·담당자 스냅샷은 변경하지 않는다.

### 5.2 최초 연결과 버전 고정

`link-application-agency` 요청은 정확한 기관 기록 버전인 `recordId`와 대상 회차를 받는다. 서버는 회사 소유, 실제 체인 관계, 선택 버전 존재를 검증하고 `chainRootId`, `chainKind`, `recordVersionId`를 계산해 `agency-link` 사건에 저장한다. 호출자가 체인 루트를 주입할 수 없다. 루트에 이미 귀속 저널이 있으면 새로운 최초 연결을 만들 수 없다. 같은 요청 nonce의 재생만 기존 결과를 반환한다.

회차 화면에서 근거로 표시하는 내용은 선택한 `recordVersionId`다. 이후 기관 기록이 정정되면 **후속 정정 있음**을 표시하고 과거 내용·기한·결과를 자동 변경하지 않는다. 새 버전을 채택하는 것도 최신 링크 사건을 참조하는 명시적 정정이다. 새 답변이나 정정은 체인에 속하지만 접수·수용 완료를 의미하지 않는다.

### 5.3 재귀속 정정

`agency-link-correction`은 `previousLinkEventId`, 서버가 대조할 현재 귀속 `fromApplicationId`, 새 대상 `toApplicationId` 또는 `null`, 정확한 채택 버전, 정정 사유를 요구한다. 저장 사건의 `applicationId`는 검증한 `toApplicationId`로 서버가 정한다. 이전에 해제된 체인을 다시 연결할 때는 `fromApplicationId: null`과 최신 해제 사건 ID를 요구한다. 과거/현재 회차별 이력 조회는 새 대상뿐 아니라 이전 귀속도 함께 조회한다.

1. 최신 링크 사건 ID가 정확히 일치해야 한다. 오래된 링크를 바탕으로 갈라지는 정정을 거부한다.
2. 같은 회사 내에서만 이동 또는 귀속 해제가 가능하다. 루트 종류와 체인 ID는 바꿀 수 없다.
3. 기존 링크는 남기고 새 사건을 추가한다. 현재 귀속만 최신 사건으로 계산한다.
4. 이전 회차는 ‘다른 회차로 재귀속됨’으로 표시한다. 오래된 링크를 현재 귀속처럼 중복 표시하지 않는다.
5. 과거 제출 사건에서 직접 고정한 접수/결과 근거는 소급 수정하지 않는다. 그 연결이 잘못됐으면 제출 사건도 별도로 정정한다.
6. 재귀속 정정은 기관 기록 원문·답변 버전·업무의 기한·완료 상태·담당자를 변경하지 않는다.

이 구조는 오기입을 고칠 수 있게 하면서 동일 요청 체인이 여러 신청회차의 현재 결과인 것처럼 나타나는 것을 막는다.

## 6. 사실 확인 수준과 회사 변경 영향

표시는 다음 수준을 구분한다.

| 표시                  | 의미                                    |
| --------------------- | --------------------------------------- |
| 회차 등록             | 로컬 구분을 만들었음                    |
| 제출했다고 기록       | 담당자가 날짜·버전·원본을 신고함        |
| 접수 통보 연결        | 담당자가 보관한 접수 문서 버전을 연결함 |
| 결과/확인서 기록 연결 | 담당자가 보관한 해당 통보 버전을 연결함 |
| 기관 접수 자동 확인   | 첫 구현에서 지원하지 않음               |

일반 요청으로 `verified`, `officiallySubmitted`, `accepted` 등을 받지 않는다. 향후 공식 관측 검증이 구현된다면 검증 출처·시각·기관 식별정보를 가진 별도 서버 생성 사건으로 추가한다. 현재 `origin: 'manual'` 기관 기록을 그 사건으로 변환하지 않는다.

회사 프로필·원본 본문·아이템·원고 변경은 기존 분석·검토 무효화 정책을 유지한다. 회차 생성 당시 값, 제출 당시 검토 상태, 당시 원본 해시는 바꾸지 않는다. 현재 회사 정보와 다르면 역사 값과 현재 값을 구분하여 표시한다. 회차 이름·기한·귀속을 고친 것만으로 분석·진단 근거를 무효화하지 않는다.

공식 입력 `completed`는 DOM 입력/첨부 확인에 한정한다. 연결한다면 회사별 workflow envelope에서 실제 존재하는 정확한 실행 ID·manifest fingerprint·상태·시각·touched/completed 목록만 서버가 사본으로 저장한다. 원문 입력값·쿠키·URL query·계정 암호문은 포함하지 않는다. 화면 이력이 나중에 잘려도 사본은 남기되 제출 상태로 재해석하지 않는다. 실행기·단회 승인·복구 정책을 회차 등록 때문에 변경하지 않는다.

## 7. API·한도·저장 원자성

기존 `PATCH /api/studio/cases/{caseId}`를 재사용한다. 구현한 action은 `create-application`, `correct-application`, `record-application-submission`, `correct-application-submission`, `link-application-agency`, `correct-application-agency-link`의 6개다. 모든 새 요청은 strict schema, 회사 revision, UUID nonce를 요구하며 URL query를 허용하지 않는다. 회차별 단계 저장 action은 후속 범위다.

구현한 한도는 다음과 같다. `studio-application-types.ts`의 상수와 서버의 공통 용량 검사를 사용한다.

| 항목                            | 한도                                               |
| ------------------------------- | -------------------------------------------------- |
| 회사별 회차                     | 30개                                               |
| 회사별 회차 사건                | 합계 200개, 자동 trim 금지                         |
| 제목/기록자/일반 메모/기준 메모 | 200/100/2,000/2,000자                              |
| 일반 메모 총량                  | 회차·사건 합계 200,000자                           |
| 제출 사건 원본                  | 10개, 각 12MiB·합계 24MiB                          |
| 제출 당시 업무 연결             | 20개, 역할별 이름 기존 100자 유지                  |
| 제출 당시 인용                  | 200개, 원래 quote 1,500자·locator 150자 유지       |
| 생성된 사건 스냅샷              | 사건당 JSON UTF-8 2MiB, 회차 이력 전체 8MiB        |
| 새 요청 본문                    | 64KiB; 서버 생성 스냅샷은 클라이언트가 보내지 않음 |

수기 날짜는 유효한 `YYYY-MM-DD` 또는 명시적으로 허용한 빈 문자열만 받는다. 제출 발생일은 필수다. 확인서 유효기간이나 후속 예정일을 현재 날짜·고정 연수로 채우지 않는다. 기관 기록의 기존 날짜 검증을 재사용한다.

저장 순서는 공통 회사 입력 잠금 → 트랜잭션 → 동일 nonce 재생 확인 → 회사 CAS → 부모/체인/버전 소유 검사 → 필요한 원본 safe read → 서버 스냅샷·digest 생성 → 원본 최종 SHA·메타 재검사 → 전체 한도 검증 → 단일 commit이다. 같은 회사·nonce·정규 입력이면 이전 사건을 그대로 반환하고 revision을 증가시키지 않는다. 다른 payload면 충돌이다. 회차와 사건 간 nonce 네임스페이스도 동일 회사에서 하나로 검사한다.

재생 응답은 ‘이미 기록된 당시 내용’의 조회다. 과거 SHA와 현재 원본이 여전히 일치한다는 새 검증으로 표시하지 않는다. 현재 바이트 대조는 별도 다운로드/검사에서 수행한다. 클라이언트 입력 해시에는 action·대상 회차·부모 버전·정규 payload를 포함하되 재시도 revision 자체는 제외하는 안을 사용한다.

한도 초과·원본 변경·연결 충돌·SQL 실패는 사건, 회차, source 보호 상태를 함께 rollback한다. 원본 파일을 새 위치로 이동하는 파일시스템 트랜잭션은 첫 구현에 넣지 않는다. 명시적인 기업 전체 삭제의 기존 동작은 별도 정책이며 회차만 삭제하는 API는 제공하지 않는다.

## 8. 데이터 이관과 되돌리기

1. 새 필드는 누락 시 빈 배열로 읽는다. 기존 DB를 열 때 전체 회사에 쓰기를 발생시키지 않는다.
2. read projection은 기존 원고·기관 기록·회사 단계를 그대로 노출하고 미귀속 안내만 추가한다.
3. 첫 회차 기록을 저장할 때 해당 회사 행 하나만 CAS로 갱신한다. 기존 데이터와 새 필드는 같은 트랜잭션에 포함한다.
4. 기존 기관 요청 nonce/digest 계산은 바꾸지 않는다. 회차 링크는 별도 action과 digest다.
5. 기존 자료를 자동 `submitted`로 이관하거나 회사별 최초 회차를 자동 생성하지 않는다.
6. 기능 중단 시 새 쓰기 버튼을 끄고 이력 읽기를 유지한다. 새 필드를 모르는 옛 앱으로 같은 DB를 편집하면 파서가 새 필드를 버릴 수 있으므로, 단순 바이너리 다운그레이드를 데이터 보존 rollback으로 취급하지 않는다.
7. 실제 이전이 필요하면 검증 백업과 새 경로 복원 절차를 사용하고 현재 DB를 자동 덮어쓰지 않는다. 이 문서 작성·구현 시험에서 실제 회사 데이터 이관은 실행하지 않는다.

## 9. 독립 검증 계획

합성 SQLite Store/API와 합성 원본만 사용한다. 제품 구현자와 별도의 리뷰/통합검사 담당자를 둔다.

- legacy JSON 읽기와 재시작에서 기본 배열이 비어 있고 기존 row·원고·기관 nonce가 바뀌지 않음.
- 회사별 같은 입력·nonce 재생, 응답 유실 재시도, 같은 nonce 다른 내용, 오래된 CAS, 공통 회사 입력 잠금.
- 다른 회사의 회차·원고·source·기관 루트·정정 버전·실행 ID를 거부하고 원본도 열지 않음.
- 요청/답변 및 통보 정정 체인의 루트 계산, 종류 혼동·분기·중복 귀속·자기/순환 이전 회차 연결 거부.
- 재귀속 정정 후 현재 귀속은 하나이고 이전 회차의 과거 사건 및 제출 스냅샷은 유지됨.
- 기관 정정 후 고정 버전은 그대로이며 후속 정정 안내만 생김. 기한·결과·업무 완료를 자동 변경하지 않음.
- 제출 후 profile/source/선택 아이템/원고 편집·재분석·확인 해제가 발생해도 당시 메타와 원고 해시가 유지됨.
- 오래된 원고·미확인 초안도 역사 기록은 가능하지만 초안 표시가 유지되고 내부 검토 완료가 생성되지 않음.
- 원본 링크·하드링크·경로 교체·같은 크기 변조·다중 파일 읽기 중 앞 파일 변경·삭제 보호·역사 해시 보존.
- 모든 한도와 잘못된 서버 메타 주입을 거부하며 SQL trigger 실패를 이용해 원자적 rollback 확인.
- 공식 실행 completed/파일 보유/수동 결과/회차 단계만으로 기관 접수·제출·확인 성공을 만들지 않음.
- UI 회사·revision 바인딩, 요청 중 회차 변경, 미저장 편집 보존, 실패 후 같은 nonce 재시도, 오래된 응답 폐기.
- 외부 AI·브라우저 입력·알림 호출 0회, 원문·키·실경로 로그 0회.
- 새 경로 백업·복원에서 두 배열과 체인·고정 해시가 유지됨.

## 10. 구현 순서와 범위 종료 기준

1차는 순수 타입/검증 → 공통 저장 트랜잭션 → 회차·귀속·제출 기록 UI → 독립 API/DB/UI 회귀 순서다. 새 작성·공식 실행의 암묵적 회차 전환은 하지 않는다. 회차 생성, 정확한 버전 고정, 체인 단위 귀속·정정, 결과 표시와 차기 회차 연결을 한 기업의 합성 데이터로 끝까지 확인하면 이 최소 범위를 완료로 기록한다.

고정 제출 사건을 지정한 ZIP 출력, 현재 실행 관측 사본 연결, 다중 사용자 권한, 공식 접수 검증은 후속 범위로 분리한다. 파일 바이트의 외부 훼손 복구와 기관 기록의 진위 판정은 이력 분리 기능의 성공만으로 보증하지 않는다.

독립 검토에서 기관 기록 저장 경로가 신청/소명에서 이미 고정한 원본 SHA를 우회할 수 있는 문제가 발견됐다. 기관·소명·신청 기록 사이에서 같은 source ID의 SHA256·크기·원본명·MIME가 다르면 저장을 거부하도록 보완했다. 소명과 신청 사이의 같은 원고 ID·버전·본문 SHA 불일치도 거부한다. 과거 해시는 덮어쓰지 않는다.

검사는 임시 SQLite와 합성 원본만 사용했다. 이 기능 구현·회귀 과정에서 실제 기업 자료·DB·기관 계정·Edge를 조회하거나 입력하지 않았다. 외부 AI와 공식 실행 호출은 시험에서 0회임을 확인했다. 배포 환경 전체 검사와 실사용 여부는 이 표만으로 추정하지 않는다.

### 남은 제약

- 제출 사건은 담당자의 수기 신고이며 `officialVerification: 'unverified'`를 유지한다. 회사 `stage`, 기관 접수·수용·확인 성공을 자동 변경하지 않는다.
- 과거 원본의 전용 다운로드 및 제출 사건 지정 ZIP은 미구현이다. 현재 원본 다운로드를 과거 시점 원본의 검증된 다운로드로 표시하지 않는다.
- 제출한 원고 전체 본문은 중복 저장하지 않고 기존 원고 ID·버전·본문 해시를 참조한다. 그 버전을 삭제하거나 덮어쓰는 후속 기능은 별도 보존 정책 없이는 허용하면 안 된다.
- 선택 원본 삭제는 과거 정정분까지 보호한다. 회사 전체 삭제는 기존 별도 동작이며, 장기 보관·공유 서비스의 보존기간 정책은 아직 없다.
- 회차별 별도 진행 단계, 공식 실행 관측 사본, 자동 접수 확인, 자동 재확인 기한 계산은 추가하지 않았다.
- 기존 회차 미지정 기록은 그대로 남는다. 실제 회사의 과거 이력을 추정해 회차에 일괄 배정하지 않는다.
