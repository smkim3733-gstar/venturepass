# 품질평가 운영 승인·실행 연결 후속 설계

작성일: 2026-09-27

상태: **다음 구현을 위한 설계**. 현재 운영 근거는 읽기 전용 제안이며 운영 채택·예산 설정·예약·전송 승인을 기록하지 않았다. 이 문서는 사용자 승인 요청, 실제 API 실행, 개발 전체 완료를 뜻하지 않는다. 키·환경설정·고객 DB·외부 AI를 조회하지 않고 현재 코드와 기존 공식 근거 검토 문서만 대조했다.

## 1. 다음 작업의 범위

등록된 합성 후보 한 건에 한정하여, 사용자가 실제 목적지·모델·자료·비용·보관 조건을 검토한 뒤 별도로 승인할 수 있는 운영 계약을 준비한다. 회사 실자료 분석이나 벤처인 접수 권한으로 확대하지 않는다. 합성 후보의 실제 AI 결과도 독립 정답표·사람 평가·최종 벤처확인 승인을 대신하지 않는다.

현재의 `proposal-only` 조회를 운영 승인으로 바꾸는 플래그를 추가하지 않는다. **운영 근거와 누적 예산 채택 → 정확한 후보 한 건 예약 → 해당 run의 전송 승인**을 각각 불변 기록으로 연결한다. 화면은 간단하게 유지하되 어느 동작이 예산만 설정하고 어느 동작이 외부 전송을 허용하는지 분명히 표시한다.

## 2. 현재 코드에서 재사용할 것과 부족한 것

아래 경로는 `web/` 기준이다.

| 경로·기능 | 현재 재사용할 내용 | 다음 구현에서 필요한 내용 |
|---|---|---|
| `src/lib/studio-plan-quality-provider-configuration.ts` | 서버 고정 공식 근거 제안, 출처·설정 digest, 만료 검증, 모델·보관·usage 정책 | 제안의 실제 운영 채택 기록과 그 기록에 결합된 정책 버전 |
| `provider-review-types.ts`, `provider-review-service.ts` | 정확한 등록 버전·후보의 읽기 전용 `proposal-only` 응답. 예산·준비안·manifest는 null, 계정 미확인, 실행 false | 운영 정책을 채택한 이후의 별도 엄격한 조회 분기. 기존 missing v1·proposal v2 응답은 유지 |
| `studio-plan-quality-provider-core.ts`의 `createProviderRequestReview()` | 예산·키·전송 없이 정확한 생성 본문 및 검토 템플릿 조립 | 같은 결과를 새 운영 정책과 새 reservation 준비안에 결합 |
| `studio-plan-quality-provider-reservation.ts` | 전체 문맥 입력 C와 출력 O의 조건부 금융 예약, BigInt·항목별 올림 | 기존 근거 계산을 운영 채택·계정 권한·토큰 적합성으로 잘못 승격하지 않는 연결 |
| `studio-plan-quality-provider-store.ts` | nonce/CAS, 불변 원문, 예약, 승인·dispatch·응답·검증·종결 기록, 비용 미확인 보존 | 현재 `enabled()`는 synthetic context의 `synthetic-test`만 허용. production 쓰기를 허용하기 전 운영 정책·계정·전송 능력의 엄격한 검증 필요 |
| 같은 store의 `budgetConfigure()` | 통화·정수 단위·누적 한도 설정과 재전송 멱등성 | 현 `ProviderPolicy`는 configuration/source/retention/usage 채택 digest를 갖지 않는다. 기존 configure만으로 운영 채택을 기록했다고 할 수 없음 |
| `studio-plan-quality-provider-runner.ts` | 승인 최초 commit 소유자만 진행, generation/review 원문 일치, 응답·usage 선보관, 실패·늦은 응답 처리 | 현재 `runQualityProviderSimulation()` 및 주입 transport는 합성 전용. 별도 서버 고정 production adapter 필요 |
| `studio-provider-observation.ts`, `scripts/local-data-quality-provider-usage.mjs` | 검증 전 응답 캡처, 실제 model/tier/usage 해석, 검토 요청 파생, 원고 검증 | production 응답도 같은 순서를 사용하되 합성 transport의 출처를 변경하지 않음 |
| `studio-plan-quality-ledger-database.ts`, `scripts/local-data-quality-*.mjs` | 기존 13테이블, 전역 nonce·용량, v1/v2 분리, v6 writer gate, 과거 prefix와 백업 | 새 운영 정책 grammar를 위한 명시 버전·엄격한 판독·원자 migration. 새 테이블은 기본안에 없음 |

위의 존재는 실제 AI 호출이 검증되었다는 뜻이 아니다. 현재 기본 store와 HTTP 경로에는 운영 실행 권한이 없다.

## 3. 사용자에게 제시할 정확한 한 건의 검토 범위

승인 화면은 다음 값이 모두 확정된 뒤 만든다. 아직 특정 등록 버전·후보 ID를 선택한 운영 승인서는 없으므로 이 문서에 임의 ID나 SHA를 채우지 않는다.

| 항목 | 승인서에 고정할 값 |
|---|---|
| 대상 | 서버에 보관된 합성 후보 한 건. registry version·versionDigest·candidateId·setId·label |
| 입력 | 후보 modelInputDigest, sourceDigest, candidateDigest, manifestDigest와 실제 전송할 프로필·자료 본문·후보 내용. 고객 폴더나 파일 원본은 범위에 넣지 않음 |
| 생성 본문 | UTF-8 원문 크기·SHA-256, canonical requestDigest, 요청 계약 digest, model. raw byte SHA와 canonical digest를 별도로 표시 |
| 검토 본문 | 고정 system·instruction·schema·입력 context·templateDigest 및 `this-run-validated-generation-only` 파생 규칙. 아직 없는 검토 본문의 SHA를 미리 만든 값처럼 표시하지 않음 |
| 모델·목적지 | 현재 제안 `gpt-5.4-2026-03-05`, `https://api.openai.com/v1/responses`, Standard/default, Global. 서버에서 고정하고 클라이언트의 대체 모델·base URL을 받지 않음 |
| 동작 | 생성 1회와 같은 실행의 최초 검증 원고에 대한 별도 검토 1회. 최대 2회, 자동 재시도·자동 수정 0회 |
| 요청 조건 | 텍스트만, 도구 없음, `store:false`, `truncation:disabled`, `background:false`, `stream:false`, previous response/conversation/compaction 없음, 요청별 출력 16,000 tokens |
| 비용 | 요청별 금융 예약 USD 5.61, 합계 USD 11.22라는 조건부 계산. 아래 누적 예산 제안 및 미확인 비용 처리와 함께 표시 |
| 보관 | 공급자 보관 안내의 전체 문구·retentionDigest·출처·내부 재확인 기한, 로컬 원문·usage·영수증 보관 범위 |
| 권한·시간 | 운영 정책 digest, 실제 계정 확인 상태, 현재 budget revision/head, run/preparation/manifest digest, 승인 시각·만료 시각·nonce |

검토 요청은 생성 결과에 따라 달라진다. 사용자는 그 결과 전체를 임의로 확장하는 권한이 아니라, 같은 실행에서 영속 보관한 최초 검증 원고를 고정 템플릿의 지정 슬롯에 넣는 범위만 승인한다. 검토 직전에 실제 파생 원문·SHA를 기록하고 승인된 규칙과 대조한다. 임의 사용자 원고·다른 run의 원고·수정본을 대체하면 새 검토안이 필요하다.

## 4. USD 11.22 계산과 USD 15 누적 예산 제안

수치는 [운영 모델 공식 근거 검토](품질평가_운영모델_공식근거_검토.md)와 현재 서버 제안에 근거한다. 여기서는 공식 가격을 새로 조회하거나 운영 설정으로 채택하지 않았다.

- 문맥 C: 1,050,000 tokens. 앱 출력 예약 O: 16,000 tokens.
- 확인한 장문 구간 최고 일반 입력 요율: USD 5.00/1M. 최고 출력 요율: USD 22.50/1M.
- 단위: USD의 백만분의 1, `unitScale:6`.
- 요청별 입력: `ceil(1,050,000 × 5,000,000 / 1,000,000) = 5,250,000 units`.
- 요청별 출력: `ceil(16,000 × 22,500,000 / 1,000,000) = 360,000 units`.
- 요청별 5,610,000 units = USD 5.61. 생성·검토 합계 11,220,000 units = **USD 11.22**.
- 초기 누적 한도 제안: `capUnits:"15000000"`, **USD 15**. 아직 미채택·미설정이다.

인정 비용과 미정산 예약이 모두 0일 때만 첫 예약 뒤 가용액이 USD 3.78이다. 모든 실행의 누적 인정 비용과 미정산 예약을 합산하며, 재시작·새 nonce·새 날짜로 한도를 초기화하지 않는다. 자동 충전·한도 증액·예약 초과 시 자동 재실행은 없다.

C 전체를 입력으로 잡고 O를 별도 더하는 방식은 의도적인 과대예약이다. 실제 토큰 실측·문맥 적합성·평균 견적·공급자의 모든 실패 청구 상한 보장이 아니다. 캐시 할인은 예약을 줄이는 이유로 쓰지 않는다. 장문 캐시 읽기 USD 0.50/1M은 공식 입력 배율을 적용한 산술 해석이며 독립 가격 행을 직접 확인한 값으로 표시하지 않는다.

현재 근거의 `validUntil`은 내부 재확인 기한이다. 만료되면 새 근거 검토·새 configuration digest로 제안을 다시 만든다. 기존 기록의 날짜만 연장하거나 과거 승인 digest를 새 근거에 재사용하지 않는다.

## 5. 운영 채택·예약·전송 승인을 분리하는 최소 기록 설계

### 5.1 운영 근거 채택과 누적 예산

기존 13테이블 중 예산 이벤트와 요청 영수증 저장소를 재사용한다. 제안 이름은 `configure-operating-policy` 이벤트와 대응 영수증이다. 정확한 이름은 구현 때 엄격한 schema와 함께 확정하되, 기존 `configure` 행에 필드를 덧붙이거나 그 의미를 변경하지 않는다.

새 이벤트는 production 전용 명시 discriminator(예: `operatingContractVersion:1`)와 다음 불변 내용을 갖는다.

- `configurationDigest` 및 채택한 설정 전체 원문: 모델, 조건, 공식 근거 7개와 각 recordDigest, 요율·문맥·usage 정책, 보관 안내.
- 통화·정수 단위·누적 한도 USD 15, 기존 예산 head에 대한 CAS, 정책 적용 범위와 유효 기한.
- 사용자가 확인한 정확한 제안 digest, 명시 동의 항목, `provenance:"explicit-user"`, 승인 시각·nonce·입력 digest.
- 운영 정책 event digest. 이후 production 준비안·예약·전송 승인은 이 digest를 참조한다.

운영 근거 채택과 최초 누적 예산 설정은 하나의 원자 transaction으로 처리할 수 있다. 둘 중 하나만 저장된 상태를 성공으로 표시하지 않는다. 기존 미채택 제안은 그대로 조회 가능하다. 최초 묶음에서는 정책 교체·증액을 지원하지 않고, 수정 필요 시 새 검토 설계를 먼저 만든다. 운영 정책 채택 자체는 외부 전송 허가가 아니다.

### 5.2 후보 한 건의 비용 예약

새 production 준비안은 운영 정책 event digest, 정확한 registry/candidate와 생성 원문, 현재 budget revision/head·인정 비용·미정산 예약을 고정한다. `acknowledgedReservationOnly:true`는 유지한다. 승인자가 예약만 허용했다면 전송 횟수는 0이어야 한다.

run은 새 운영 계약 discriminator를 갖는 엄격한 분기로 추가한다. 기존 v2 reservation run과 그 digest를 재작성하지 않는다. policy→preparation→run→reserve event→receipt를 완전히 대조하며 단순히 environment 문자열만 production으로 바꾼 행을 거절한다. 기존 scope별 CAS·전역 run count·모든 nonce 양방향 충돌 검사·동일 후보 미정산 차단을 재사용한다.

### 5.3 해당 run의 전송 승인

예약 후 run/preparation과 고정 usage 정책에서 manifest를 만든다. 새 운영 계약에서는 manifest가 운영 정책 digest와 정확한 계정 설정 식별자까지 참조하도록 버전 분기한다. 기존 `transmission-approved` 이벤트를 통해 해당 manifest에 대한 별도 사용자 의사를 기록하며, 기존 예약 승인이나 제안 조회를 전송 승인으로 간주하지 않는다.

승인 transaction의 최초 commit 호출자만 runner를 시작할 수 있다. nonce 재조회·replay·복원된 영수증은 새 전송 권한을 주지 않는다. 승인·계약·가격·보관·현재 예산이 달라지면 전송을 시작하지 않는다. 승인과 dispatch 사이의 만료도 전송 직전에 재검사한다.

UI는 정책 채택, 예약, 전송의 세 가지 효과를 설명하는 짧은 단계로 구성한다. 명시 의사와 요청 본문을 구분해 기록하면 한 화면에서 검토할 수 있지만, 모든 항목을 켠 포괄 승인 하나로 자동 후속 실행을 허용하지 않는다.

## 6. 서버 고정 실제 transport와 계정 권한

현재 simulation runner는 유지한다. 별도 server-only production adapter를 만들고 테스트 transport를 production 경로의 인자로 받지 않는다. 임의 `send`, base URL, model, service tier, project 식별자 등을 브라우저에서 넘겨 실제 전송에 사용할 수 없어야 한다.

운영 adapter는 승인된 서버 설정에서만 자격정보를 얻는다. 키는 요청·오류·로그·원장·백업·브라우저 응답에 넣지 않는다. 이 후속 설계와 합성 구현 시험 중에는 실제 키·환경설정에 접근하지 않는다. 실제 운영 연결 시의 자격정보 설정과 계정 확인은 별도 필요한 사실로 남긴다.

계정의 모델 접근·결제·처리 지역·보관 설정을 모르면 `accountAccess:"not-checked"` 및 실행 불가를 유지한다. 키가 존재하거나 공개 모델 문서에 모델이 있다는 이유로 접근 가능으로 표시하지 않는다. 계정 확인 절차가 마련되더라도 한 API의 성공을 실제 요청 수락·요금·ZDR 전체 보장으로 확대하지 않는다. 확인 결과에는 범위·방법·시각·계정 설정 식별자를 남기고, 계정이 바뀌면 기존 전송 승인을 재사용하지 않는다.

서버 고정 요청 조건과 source/model/usage policy를 전송 전에 다시 대조한다. SDK 자동 재시도는 0, 목적지는 공식 Global API, 출력은 승인 상한, `store:false`다. 요청 중간에서 모델 별칭·fallback·처리 등급을 바꾸지 않는다. 오류 응답 원문에 자격정보나 임의 헤더가 섞여도 외부로 노출하지 않는 제한된 오류 코드만 반환한다.

## 7. 전송과 비용 기록 순서

기존 순서를 유지한다.

1. 운영 정책·계정·예산·정확한 승인 범위를 검증한다.
2. phase별 요청 원문을 영속 보관한다. 생성은 예약 당시 원문, 검토는 같은 run의 저장된 최초 검증 원고에서 파생한다.
3. `dispatch-intent`를 CAS로 기록한다. 이 최초 commit의 일회성 소유권을 가진 caller만 transport를 한 번 호출한다.
4. 응답을 받으면 허용된 raw JSON과 실제 model/tier/usage를 먼저 영속 보관한다. 구조·도메인 검증보다 앞선다.
5. 확인 가능한 비용은 전액 인정한다. phase 예약 R보다 사용량 비용 U가 클 때 `min(R,U)`만 held에서 소비하고 U 전액과 초과·deficit를 기록한다. 다음 dispatch를 차단한다.
6. 사용량·모델·tier가 불명확하면 held를 유지한다. 0원이나 완료로 바꾸지 않는다. 전송하지 않은 phase만 근거에 따라 해제한다.
7. 원고 구조·근거 검증을 기록한 뒤에만 다음 phase를 준비한다. 응답 저장 실패나 검증 저장 실패 뒤 후속 호출은 없다.

dispatch 기록 직후 프로세스가 종료되면 전송 여부를 확신할 수 없다. 영수증 재생으로 재호출하지 않고 미확인 상태와 예약을 보존한다. 늦은 응답은 원래 dispatch·원문에 결합해 보관·정산할 수 있지만, 기존 중단을 철회하거나 검토를 재개하지 않는다.

`actualAiCalls` 또는 유사 지표는 확인한 관측만 표시한다. dispatch intent만으로 실제 요청 수신·청구·성공을 확정하지 않는다. 합성 transport의 성공은 production 관측으로 승격하지 않는다.

## 8. 공급자 보관과 로컬 보관

현재 제안의 보관 안내를 승인서에 그대로 결합한다. `store:false`는 응답 재조회용 저장을 끄는 조건이며 모든 입력·응답의 즉시 삭제나 ZDR 승인이 아니다. 기존 검토 문서가 설명한 악용 방지 로그의 통상 최대 30일·법률/안전상 예외, 지원 모델의 암호화된 확장 캐시 최대 24시간 가능성을 함께 드러낸다. 계정별 특별 보관 설정은 미확인 상태에서 추정하지 않는다.

로컬에는 승인 범위, 정확한 요청/응답 원문, 사용량, 영수증, SHA를 보관한다. 실제 계정 식별자는 필요한 비밀 아닌 범위만 기록하고 자격정보를 저장하지 않는다. 로컬 원문은 실행 revision의 prefix에 속한 것만 조회·다운로드하며, 과거 r0 다운로드에 이후 응답이 끼어들지 않아야 한다. 기존 32MiB run 예약, 원문 합계 20MiB, 전역 용량·슬롯 한도 안에서 보관한다. 공급자 보관과 로컬 백업의 보관은 별도로 설명한다.

## 9. v1·v2 합성 기록과 백업의 보존

현재 구조에 선언된 production 환경과 `candidate-quality-provider-v2-live` scope를 사용하되, 과거 synthetic scope·run·영수증을 이동하거나 복제해 운영 기록으로 만들지 않는다. legacy v1, v2 synthetic, 새 operating production은 출처·권한·예산·검증기를 분리한다.

- 기존 v1 JSON·A 준비 조회 bytes, v2 reservation r0/cancel r1의 archive format 2, v2 합성 전송의 format 3 bytes와 digest를 보존한다.
- 운영 정책/새 run/manifest를 기존 엄격한 schema의 선택적 자유 필드로 넣지 않는다. 버전이 지정된 새 분기와 새 archive 포맷을 정의하고 현재·과거 검증기를 명확히 나눈다.
- 추가 테이블 없이 기존 budget/run/event/receipt/artifact 테이블을 우선 재사용한다. 운영 정책의 저장 크기도 기존 총용량·슬롯 계산에 포함한다.
- 새 기록 grammar를 기존 v6 reader가 안전하게 해석할 수 없다면, 다음 writer gate/backup 버전(안: v7)을 원자 migration으로 추가한다. v6를 조용히 완화하거나 옛 writer를 허용하지 않는다.
- backup inspector는 각 행을 정확히 하나의 버전·환경·run에 귀속시키고 운영 정책 참조·nonce·SHA·예산·원문을 대조한다. unknown/고아/혼합 불일치 행을 필터로 숨기지 않는다.
- 과거 조회·복원은 저장 당시 불변 근거로 검증한다. 현재 가격·현재 엔진·현재 시각 때문에 옛 정상 export를 재작성하거나 접근 불가로 만들지 않는다. 신규 예약·전송은 현재 근거를 검증한다.
- 복원된 승인/dispatch 영수증은 실행을 자동 재개하지 않는다. 계정 자격정보나 현재 process의 전송 소유권을 백업에 포함하지 않는다.

SHA와 내부 연결 검사는 손상·부분 변조를 잡기 위한 것이다. 모든 행과 해시를 다시 만들고 최신 버전 표식까지 없앤 악의적 재구성을 외부 신뢰 anchor 없이 판별할 수 있다고 주장하지 않는다.

## 10. 코드 연결 순서와 시험

### 독립적으로 개발할 수 있는 부분

1. 별도 운영 정책 DTO·순수 schema/reducer와 해당 public facade 분기를 만든다. 제안서 전체 원문·digest·USD 15 cap·명시 동의를 append-only로 결합한다. 공통 CLI 검증기를 source of truth로 사용한다.
2. provider store에 운영 정책 채택과 새 production 준비안/예약의 내부 계약을 연결한다. 기본 production mutation gate는 계속 닫고 격리 합성 DB에서만 검증한다.
3. 기존 review service/UI에 채택 전 제안과 이후 정책·예약·전송 검토안의 구분을 연결한다. 기존 missing/proposal 응답을 바꾸지 않는다. 실패·늦은 조회·다른 후보·다른 revision의 응답을 채택하지 않는다.
4. 서버 고정 production adapter와 별도 runner 진입점을 구현하고, 통제된 SDK 대역을 통해 순서를 시험한다. 제품이 임의 transport를 주입받는 범용 production API가 되지 않도록 한다.
5. 새 grammar의 writer gate·백업·복원·다운로드 불변 회귀를 완료한다. 실제 전송 endpoint의 공개·활성화는 그 이후의 별도 조건으로 남긴다.

### 반드시 확인할 합성 회귀

- 모델·입력 SHA·정책/manifest digest·계정 설정 식별자 중 하나가 달라지면 예약/전송 거절. 기존 예약-only 승인의 자동 승격 거절.
- 누적 USD 15에 기존 recognized/held를 포함한 동시 예약 CAS. 동일 nonce 두 프로세스의 전송 합계는 승인된 phase별 최대 1회.
- 승인 및 dispatch 최초 commit의 replay/조회/프로세스 재시작으로 transport 0회. 응답 유실은 GET 조회로 복구하고 자동 재POST·재전송 없음.
- 원문·응답·영수증 저장 실패, 잘못된 output, usage 누락, 다른 tier/모델, 초과 사용량 전액, 늦은 응답 뒤 검토 0회.
- 실제 SDK 호출을 대체한 시험은 명시 합성 관측이다. 테스트가 production 계약 형식을 검증해도 운영 기록의 실제 실행 증빙·실제 비용·품질 통과를 생성하지 않음.
- fixture 전용 격리 DB, 키/환경설정/고객 DB/외부 네트워크 접근 0. 테스트에서 금지된 provider 호출·자격정보 로더를 호출하면 즉시 실패.
- 구 v1/v2와 새 운영 계약이 함께 있는 백업 round trip, 과거 prefix JSON/원문 바이트 고정, unknown held 보존, 구 reader의 새 기록 거절.

운영 권한을 문자열로 위조하는 test-only bypass를 HTTP 경로나 기본 store에 노출하지 않는다. 실제 SDK 응답 성공·청구서 대조는 합성 시험으로 완료 처리할 수 없다.

## 11. 정확한 사용자 검토안 전에 남은 사실

| 필요한 내용 | 현재 상태 | 처리 기준 |
|---|---|---|
| 실제 운영 모델·공식 근거·usage·보관 채택 | 제안만 있음 | 공식 근거 유효성을 재확인하고 새 proposal digest를 사용 |
| 정확한 후보 한 건 | 등록된 합성 후보 목록은 있으나 운영 승인 대상 미확정 | 사용자가 확인한 version/candidate와 본문 SHA를 확정 |
| USD 15 누적 한도와 단위 | 제안, 예산 미설정 | 기존 비용·예약 포함한 예산 검토 및 별도 명시 채택 |
| 실제 계정·프로젝트의 이용/결제/처리/보관 조건 | 미확인 | 키 존재로 대신하지 않고 확인 방법·범위와 결과를 구분 |
| 운영 credential 연결 | 이번 작업에서 접근하지 않음 | 승인된 서버 설정 방식과 비밀 노출 없는 준비 절차 필요 |
| 전송 승인 | 없음 | 예약 뒤 정확한 run/manifest와 보관·비용을 한 건씩 검토 |
| 실제 AI 결과의 품질 | 미측정 | 실제 결과 기록 후에도 사람 평가·독립 기준 검증 별도 |

이번 문서는 위 사실을 채웠다고 표시하지 않는다. 독립 개발과 합성 회귀를 먼저 끝내고, 실제 정책 채택·유료 전송이 필요한 지점에서 완성된 정확한 검토안을 제시한다. 그 전까지 현재 읽기 전용 화면의 실행 false와 production 쓰기 폐쇄를 유지한다.

## 12. 이 묶음의 완료 기준

다음 구현의 완료 기준은 운영 채택·예약·전송 권한이 구분된 엄격한 계약, 키 없는 합성 회귀, 과거 바이트·백업 보존, 그리고 남은 계정·예산·한 건 승인 내용을 명시한 검토안이다. 실제 사용자의 운영 승인이나 유료 실행이 없으면 해당 상태는 미완료로 남는다. 이 기반 구현을 벤처패스 전체 개발 완료, 사업계획서 품질 합격, 공식 벤처확인 신청·승인 완료로 표현하지 않는다.
