예약 명령은 목적·버전/nonce·회사/revision·기존 요청 command/identity·검토안 digest·원장/예산 head·동의 문구/보관 범위와 만료를 대조한다. 예약은 선택 본문의 로컬 보관과 금액 hold만 포함하고 전송은 별도 승인 필요 상태다. 사용자가 보낸 가격/최대금액을 그대로 쓰지 않는다. 같은 nonce의 정확한 원래 명령은 현재 회사/근거 만료·키/설정 검사보다 먼저 원래 결과만 반환하고 owner를 만들지 않는다.

취소는 원래 binding/run/예약과 기대 native·예산 head에 묶인 작은 strict 명령으로 정했다. 취소 명령의 모든 필드는 보관된 원래 binding·cancel event·금액 event·native 영수증에서 다시 구성해 전체 digest를 대조할 수 있어 별도 취소 승인 원장이 필요 없다. 취소 전 회사 변경/자료 삭제·가격 만료를 취소 차단 사유로 삼지 않는다. 단, dispatch/unknown/capture가 있거나 예약 상태를 확정할 수 없으면 해제하지 않는다. 취소 event·release·원래 영수증과 final-result/종료 event·내부 영수증을 같은 거래에서 보관하도록 정했다. 내부 종료 영수증은 별도 비용/승인 소유자가 아니다.

## 2. 서버 검토안과 근거

검토안 kind는 public-comparison-reservation-review이며 source는 supplied-reservation-review다. 순수 함수는 이미 읽은 회사 snapshot·현재 전체 원장 사본·명시 시각과 서버 호출자가 고정한 근거만 받는다. 파일/DB/환경/현재 시각을 내부에서 읽거나 네트워크로 근거를 채우지 않는다. 날짜/URL/provenance 문자열이 맞는 것과 그 원문을 실제 사람이 검토한 것은 다르다.

필수 필드:

- reviewVersion1/purpose compare-public-claim, inspectedAt/expiresAt/reviewDigest.
- DBinstance·원래 cutoverDigest/coverageDigest·기존 scope/environment 및 현재 전체 archiveDigest.
- 회사 ID/revision, 원래4I2 command/identity, contextSha256·rawBody SHA/UTF-8 byte/UTF-16 문자, 모델/요청 버전.
- 현재 budget revision/head/currency/unitScale/cap/recognized/held·전역 run 개수와 실제/예약 용량. 다른 DB 잔액을 포함하지 않는다.
- financialBasis와 그 digest, retentionNotice의 버전/본문/digest, consentNotice의 버전/본문/digest.
- 요청 본문·문맥은 기존 artifact에만 보관할 계획이다. 검토안에는 선택된 source ID/원래 claim·항목·발췌와 수동 메타데이터를 담은 context의 정확한 hash를 결합하며 다른 항목/profile·제외 원문은 추가하지 않는다.
- requestedTier:null, maxCalls1, automaticRetryLimit0, maxOutputTokens16000. contextFitVerified/priceAuthenticityVerified/humanConsentVerified/providerExecutionObserved/dispatchAllowed는 false, owner는 null.

retentionNotice는 로컬 보관 대상(context/request, 이후 response/validated/final-result), 회사 삭제나 원고 변경 이후에도 원장 증거로 남는 범위, 공급자에 이후 전송될 범위와 공급자 보관 근거를 구분한다. store:false를 공급자 무보관/즉시 삭제 보장으로 설명하지 않는다. 보관 근거 누락 때 예약 준비를 완료로 표시하지 않는다. 서버가 고정한 근거가 바뀌면 새 reviewDigest가 필요하다.

유효기간은 계약상 최대10분이며 inspectedAt+10분과 모든 해당 근거의 validUntil 중 빠른 시각이다. 이는 앱의 보수적 승인 기한이며 공급자 가격 불변 보장이 아니다. approvedAt은 inspectedAt 이상이고 서버 now 이하, now는 expiresAt 미만이어야 한다. 미리보기의 화면 표시 자체는 동의가 아니다.

### 단일 요청의 금액 근거

financialBasisVersion1/kind public-comparison-reservation-basis. 원래 request identity/digest와 모델, 공급자/정확한 destination·API·store:false, 한 번의 호출/무재시도/출력16000, currency/unitScale, 근거의 모델/조건/검토시각·원문/발췌 hash·유효기한을 결합한다. 조건은 요청에 실제 있는 것과 생략된 것을 별도로 기록한다.

service_tier, truncation, background, stream 생략을 명시한 omissionCoverage가 필요하다. 각 생략 조건의 가능한 처리/청구 범위가 상한 근거에 포함됐다는 설명과 원문 참조가 있어야 한다. 단순히 null을 default로 바꾸거나 생략 필드를 본문에 삽입하면 같은 요청이 아니다. 공식 근거가 이 조건을 덮지 못하면 blocked-financial-basis이며, 나중에 명시 옵션이 필요해지면 새 요청 버전·새 미리보기/동의를 만든다. 현 단계는 그런 근거가 실제 존재한다고 주장하지 않는다.

C는 검토된 모델 context의 보수적 입력 예약 토큰 수, O는16000이다. 입력의 단기/장기·uncached/cache-read/cache-write 적용 가능 all-in 요율과 reasoning을 포함한 출력 요율 각각의 최대치를 선택한다. 생략된 tier 등의 복수 가능한 경우가 있으면 해당 경우 전체를 덮는 유한한 상한이 필요하다. 적용 불가 요율에는 이유가 필요하며 미지정을0으로 채우지 않는다. 가산 청구를 replacement 요율로 오해하거나 추가 비용을 생략하지 않는다.

한 회 최대예약금액 = ceil(C × 최대입력요율.units / perTokens) + ceil(O × 최대출력요율.units / perTokens). 각 rate별 올림은 BigInt, 출력은 기존 금액 문자열 범위에 들어야 한다. 원래2단계 total을2로 나누거나 비교를 generation 한 단계로 cast하지 않는다. 양수 예약만 지원하며 실제 무료/0요금은 첫 예약 계약에서 미지원이다. 누락 usage=0과 실제0은 계속 다르다.

C+O는 금액상 보수적 예약일 뿐 실제 요청이 모델에 들어간다는 증거가 아니다. rawBody 길이를 토큰으로 변환하거나 미래 SDK header/입력 재직렬화를 측정했다고 표시하지 않는다. currency/unitScale은 기존 scope와 정확히 같아야 하고 FX 변환/새 cap/예산 초기화가 없다. supplied 근거의 산술/조건 일치만 확인하며 실제 비용 정산·usage 정책은 별도 후속이다. synthetic 근거는 synthetic scope에서만 구조적으로 허용하고 production으로 승격하지 않는다. official-reviewed 문자열도 진위 인증이 아니다.

## 3. 최초 예약 명령과 binding3

reserve-public-claim-comparison commandVersion1, purpose compare-public-claim, clientRequestId UUID, 회사ID/revision, 기존 strict request command/identity, approvedReviewDigest, expectedArchiveDigest, expectedBudgetHead, expectedGlobalRunCount가 필수다. 요청 endpoint/키/임의 system/schema/가격/amount를 클라이언트 명령에 넣지 않는다.

approval은 noticeVersion/noticeDigest/retentionNoticeDigest, approvedAt/expiresAt, 다음 명시 확인을 담는다: 공개 주장 비교 목적, 정확한 선택 문맥/발췌·수동 메타데이터 로컬 보관, 현재 scope의 표시된 예약 금액/잔액, 금액 상한이 토큰 적합성이나 사실 확인은 아님, 자동 재시도 없음. transmission은 separate-approval-required로 고정한다. approval bool을 서버가 생략 시 true로 채우지 않는다. 새로운 전달 채널/사람 인증이 구현되기 전 순수 계약 결과는 supplied 동의 주장에 그친다.

명령 전체는 UTF-8 8KiB, strict 필드/버전만 허용한다. review/binding은 원문을 자르지 않으며 binding 전체64KiB를 넘으면 거절한다. 이64KiB는 기존 body/context/artifact 한도와 별도다.

새 binding은 kind public-comparison-reservation-binding, recordVersion3/purpose, 전체 command와 commandDigest, 전체 approvedReview와 reviewDigest, runId/runDigest/manifestDigest, 원래 reserved event/예산 event digest와 native receipt nonce/inputDigest, recordedAt, dispatchAllowed:false를 보관한다. recordDigest는 자신을 제외한 전체 정규화 body의 digest다. SQL body/body_hash는 정확한 저장 문자열을 별도로 대조한다.

순환 hash를 만들지 않는다. 검토안/명령 → 기존 manifest1(run 내 요청/문맥·scope/head/예약금액·만료) → runDigest → 예산 reserve → reserved event/native 영수증 → binding 순서로 구성한다. manifest가 review를 직접 가리키지 않아도 binding에서 모든 값을 동등 대조하고 원래 runDigest/영수증과 결합한다. manifest bool만 검사하는 기존 native reader는 여전히 구조 읽기이며 신규 예약 writer의 승인 검사를 대신하지 않는다.

prepared-not-committed 행 계획: run1, context/request artifact2, reserve-comparison budget event1, reserved native event1, native receipt1, binding1. 모두 기존 같은 quality 원장 표다. receipt 하나가 nonce를 소유하며 금액 검사용 receipt는 메모리 투영이다. 과거 policy/approval/native 실행은 새 목적 동의가 아니다.

## 4. nonce 우선·현재 상태·용량

새 계획 전 전체 prefix/coverage/native/binding을 감사한다. 원래 nonce가 존재하면 회사/현재 근거/키/시각·새 runID 생성보다 먼저 저장된 commandDigest와 전체 strict command를 대조한다. 일치할 때 원래 결과/행만 반환하고 prepared 신규 행0·owner:null이다. 다른 명령·다른 목적이거나 binding 없는 점유 nonce면 conflict다. 현재 회사가 없어졌거나 근거가 만료됐다고 같은 명령의 원래 영수증 조회를 막지 않는다.

새 nonce일 때만 최신 회사 snapshot을4I1/2로 재대조하고 approvedReview/서버 고정 근거·시각·scope/head/용량을 검사한다. 늦은 응답, 같은 revision의 본문/hash 변경도 거절한다. 서버 planner 입력에 fresh runID를 제공하되 기존 모든 ID/nonce와 충돌하면 거절한다. 새 nonce로 중복 예약을 피하지 못하도록 미정산 hold/전체run 한도도 검사한다.

회사 DB 잠금 구현은 후속 writer에서 quality→studio 순서의 짧은 BEGIN IMMEDIATE와 SELECT guard를 사용한다. 선택 회사 revision을 예약 때문에 +1로 보정하지 않는다. 회사 자료는 쓰지 않는다. 순수 planner에 공급된 snapshot 검사가 실제 잠금이나 파일 신원 확인이라는 뜻은 아니다. 키/SDK·전송 owner는 첫 예약에 필요 없다.

전체20run/640event/140artifact/1000budget/1000receipt/256MiB, 진행 중 비교당32MiB와 남은32event/16budget/64receipt/7artifact 예약은 그대로다. binding의 실제 bytes와 원문 encoding 증가분은32MiB 외에 추가한다. binding 개수는 기존 전체run 한도를 넘기지 않는다. 예산 hold/저장 예약은 다르며 금액 해제만으로 저장 예약을 풀지 않는다.

## 5. 전송 전 취소와 종료

cancel-public-claim-comparison commandVersion1/purpose, clientRequestId, runId, expectedBindingDigest, reservationDigest, expectedRunHead(revision/headDigest), expectedBudgetHead만 받는다. 설명 문자열·임의 승인시각·가격·현재회사 자료를 받지 않는다. 고정 reason은 not-dispatched다. 금액도 입력받지 않고 원래 예약에서 읽는다.

이 작은 명령은 원래 binding, cancelled event의 previousDigest/revision/runId, release budget event의 previousDigest/revision/reservationDigest, native receipt nonce에서 정확히 재구성한다. 원래 full command digest를 대조하는 wrapper가 필요하다. 기존 금액 inputDigest만 보고 사용자 명령이 같다고 판단하지 않는다. 별도 cancel binding 행/nonce 원장을 추가하지 않는다.

회사 변경/삭제·근거/동의 만료 이후에도 원래 기록이 정확하고 아직 전송되지 않았으면 취소할 수 있다. 이미 dispatch-recorded/unknown/capture가 있거나 hold/원문이 손상됐으면 release 금지다. 단순 timeout/재시작을 미전송 증거로 사용하지 않는다. 같은 취소 nonce는 회사/가격 없이 원래 완료 결과를 반환하고, 다른 명령은 거절한다.

새 취소의 한 거래 계획:
1. cancelled event1과 기존 reserve 전액을 해제하는 release-comparison budget event1, 원래 취소 nonce의 native receipt1.
2. 기존4I8의 cancelled:true·costSettled:true·권한false인 정확한 final-result artifact1.
3. finalized event1과 해당 이벤트의 내부 native receipt1. 내부 nonce는 새 취소를 계획할 때만 서버가 만들고 전체 nonce에 대조한다. 외부 취소 nonce와 달라야 한다. 별도 승인/금액 소유자가 아니며 금액 투영은 없다.

내부 종료 nonce는 사용자 명령에 포함하지 않고 원래 취소 바로 뒤 동일 run/시각의 finalized 이벤트와 영수증에서 감사한다. 재호출은 보관된 원래 값을 재사용하고 새 내부 nonce를 만들지 않는다. 순수 계획 입력에서 공급한 내부 nonce도 아직 거래 증거는 아니다. 부분 취소만 있는 archive를 동일 writer가 완료했다고 표시하지 않는다. 사후 전체 감사와 COMMIT 관측 이후에만 취소/종료 완료를 반환한다. final-result까지 검증된 후에만 미사용32MiB/슬롯 예약을 해제한다.

## 6. 향후 SQLv11의 좁은 저장 계약

현재 제품 SQLv10은 계속 모든 INSERT가 닫혀 있다. 이 문서만으로 gate나 생성자를 바꾸지 않는다. 향후 v11은 다음 조건의 명시 migration으로만 연다.

- 감사된 v10이며 native 비교 suffix는0개여야 한다. v10 supplied native가 있으면 원래 읽기는 유지하고 전환은 거절한다. 기존 기록에 동의를 사후 부착하거나 삭제/필터링해 비우지 않는다.
- 원래 v9 prefix/coverage/가격·완료 실행·nonce·cap은 byte 불변이다. coverage의 target10은 과거 전환 증거로 남으며11로 고쳐 쓰지 않는다.
- v11 reader는 frozen prefix binding1/2와 신규 native run에 속한 binding3을 분리해 각각 원래 bytes로 감사한다. native run마다 binding3이 정확히 하나 있어야 한다. 예산/이벤트의 중간 항목을 필터링/재번호화하지 않는다.
- DDL 변경은 명시 버전의 gate뿐이다. 기존 table와 coverage immutable 행은 유지한다. v11에 구형 v9/v10 inspector/writer를 연결하면 거절한다.
- 허용 INSERT는 quality_actual_runs/events/artifacts/requests/budget_events와 quality_provider_reservation_bindings의 계획 행뿐이다. 일반 평가/정책/전송 binding/coverage 신규행과 UPDATE/DELETE는 계속 닫는다.
- connection-local writer capability는 private transaction 안의 정확한 operation reserve|cancel, 예상 SQL 키/원문 hash/횟수 집합에 한정한다. 단순 quality-v11 문자열/JSON bool만으로 허용하지 않는다. 콜백의 재진입/await·일반 SQL 접근을 허용하지 않고 종료/실패 때 capability를 폐기한다.
- gate는 제품의 실수/구형 쓰기를 막는 경계이지 DB 소유자가 임의 함수/DDL/전체해시를 바꾸는 상황을 인증하는 보안 장치가 아니다.
- BEGIN IMMEDIATE→전체 감사/nonce lookup→순수 계획→정확한 행 insert→전체 사후 감사/수량·용량→COMMIT. 실패는 원래 상태로 rollback, COMMIT 성공 후 반환 유실은 원래 nonce 조회로 복구한다. rollback 불명/연결 오류는 조회 필요이며 성공/미전송으로 추정하지 않는다.

최초 예약/취소 writer에는 dispatch 행/전송 승인·SDK 연결이 없다. 이후 전송 활성화에는 회사 guard·복원 증인·정확한 목적별 전송 동의·현행 공식 근거/모델 적합성·실제 wire 대조·응답 영속 복구가 따로 필요하다. backup/restore 지원과 저장소 외부 합성 시험 경로도 출시 조건에 남는다.

## 7. 다음4I11 구현 완료 조건

다음4I11은 이번 명세의 비교 예약/취소 명령·보관/금액 검토안·recordVersion3 예약 binding과 순수 행 계획을 한 단위로 구현한다. 기존4I1/2 현재 요청 대조,4I7 예산,4I8 native 감사와 원래 nonce 우선 계약을 재사용한다. 공급된 근거의 날짜/모델/생략 옵션 범위·한 번의 최대 금액을 대조하되 실제 가격 진위·사람 동의/전송 권한은 false다. 실제 SQLv11 migration/writer·route/UI·SDK/키·운영 DB는 열지 않는다. 합성 예약→취소/종료, stale/nonce/근거/용량 실패와 원래 bytes 보존을 검증한다. 예상3~6시간(잠정), 필수 결정0개, 전체 완료시간 미정, 자동후속 ACTIVE.

입력/결과는 supplied 자료만으로 재현 가능해야 하며 source는 supplied-reservation-plan, status는 prepared-not-committed 또는 replay/refused, owner:null이다. approvalVerified/humanConsentVerified/priceAuthenticityVerified/transactionCommitVerified/budgetWrite/databaseWrite/dispatchAllowed는 모두 false다.

필요한 합성 사례:

- 비어 있지 않은 과거 비용/coverage에서 같은 scope/head로 예약1회→취소/종료, 원래 source/request/과거 rows 불변.
- 반환 사본/추가 필드/getter·toJSON/초과 및 hash/본문·수동 메타데이터 변조 거절.
- 모델/요청/목적·통화/단위/생략 조건/근거 날짜/notice/digest·양수금액 상한 대조, null tier와 fixture provenance를 production 가격으로 승격하지 않음.
- 새 예약의 회사/revision/내용 변화·stale head/만료 거절, 반대로 원래 nonce replay와 취소는 현재 회사/가격 없이 동작.
- 전체 nonce 충돌·같은 nonce 다른 명령·binding 없는 native·과거candidate 동의 거절. 내부 종료 nonce 충돌과 부분 취소의 거짓 완료 거절.
- dispatch/unknown 이후 취소 거절·초과/held 때 새 예약 거절,32MiB/실제 binding bytes·전체 slots 대조.
- 원래 budget/native validators와 연동한 준비 행 전체 감사, 취소 명령 round-trip 재구성/full digest 일치, 실제 DB/SDK/config/fetch 금지.
- 산술 공통 추출이 필요하면 기존2단계 golden/회귀와 호출부 결과·필드순서 불변 확인. 기존 callback/승인/파서 전체를 복제하지 않는다.

대상 파일을 직접 지정하고 알려진 백업 시험은 이름까지 제외한다. 변경에 필요한 회귀→lint→typecheck→격리 build:local의 종료코드를 순서대로 확인한다. 이번4I10은 문서만 바뀌므로 이 검사를 재실행하지 않았다.

## 8. 남은 운영 조건

실제 공식 근거/모델 지원·가격/보관 검토, 사용자 실제 예약/전송 동의, SQLv11 격리 writer/migration/동시성·실패/복구, v10/v11 백업·복원, 회사 guard와 복원 증인·dispatch/capture/가격 정산, 실제 AI 의미 품질/사람 인수가 남는다. 이번 명세는 이 조건의 완료나 새 유료 호출 승인이 아니다.

과거 백업27개 DESTINATION_REPOSITORY를 우회하거나 다시 실행하지 않는다. 지정 루트/보호 편집기3개·미추적4개/운영DB와 완료 실행을 유지한다. 후속 독립 구현이 가능하므로 사용자 결정0개·ACTIVE다.
