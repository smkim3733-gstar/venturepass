## 전송 검토안과 전체 명령

전송 검토안 kind public-comparison-transmission-review/reviewVersion1은 기존 reservation state에 transmissionBindings 배열을 더한 supplied 입력을 전체 감사해 만든다. 배열이 빠졌다고 빈 배열을 자동 삽입하거나 기존 v11 digest에 새 필드를 소급 추가하지 않는다. 기존 reservation archiveDigest는 그대로 계산하고, 새 wrapper의 transmissionArchiveDigest는 그 digest와 정확한 transmission bindings를 별도로 결합한다. 과거 validator를 복제하지 않는다.

검토안 필수 항목은 원래 runId/runDigest·예약 bindingDigest/예약 event·manifestDigest, request command/identity·contextSha256, 같은 DBinstance/environment/scope·coverage/cutover 및 현재 native head/예산 head·cap/recognized/held/가용액/전체 용량, inspectedAt/expiresAt, 원래 financialBasis/retention digest, 아래 전송 문구·지원 근거와 reviewDigest다. 자료 본문은 기존 context/request artifact에 있고 검토안/새 binding에 중복 저장하지 않는다.

## 승인과 dispatch의 단일 행 계획

기존 예약 r1에서만 새 approve-dispatch를 계획한다. 원래 reservation이 온전하고 hold가 전액 남아 있어야 하며 다른 미정산/초과·부분 기록/승인 binding이 있으면 거절한다. 현재 회사는 기존4I2로 원래 request/identity와 재대조한다. 실제 DB 연결 때는4I14 회사 capability/SELECT 잠금 아래 수행한다.

행은 dispatch-recorded event1 + native receipt1 + quality_provider_transmission_bindings의 비교 binding1, 총3행이다. 금액 event0, request/context 재보관0, 새로운 승인 event0이다. event의 reservation/request/manifestDigest는 원래 값을 쓰고 nativeInputDigest는 동결 함수를 사용한다.

binding kind public-comparison-transmission-binding/recordVersion3에는 전체 strict command/commandDigest, approvedReview/reviewDigest, runId/runDigest, reservationBindingDigest/reservationDigest·manifestDigest/requestIdentityDigest, dispatchEventDigest/dispatchRevision·nativeInputDigest, recordedAt, dispatchAllowed:false, recordDigest를 둔다. SQL run_id/nonce·body_hash 및 원래 receipt의 nonce/run/revision/operationDigest/recordedAt도 일치해야 한다. commandDigest→native event/receipt→binding 순서이며 event 안에 아직 만들어지지 않은 bindingDigest를 넣지 않는다.

이 합성/저장 검토안은 승인 기록과 dispatch 의도를 같은 거래에 남기는 계약이다. 실제 fetch가 실행됐다는 증거는 아니다. 별도 “승인만 저장했다가 나중에 재사용” 경로는 첫 계약에 없다. 따라서 dispatch가 기록된 뒤에는 실제 start 이전 실패라도 기존 취소 명령으로 hold를 해제하지 않는다.

전체 legacy/native/reservation/transmission 감사와 같은 nonce의 전체 명령 대조가 현재 회사·시각/근거·키·새 ID보다 먼저다. 같으면 원래 binding/행만 조회하고 신규 행0·owner:null, 다르면 conflict다. binding 없는 dispatch나 generation/review 승인으로 비교를 승인하지 않는다.

과거 검토안은 그 dispatch 직전의 실제 native prefix와 대조한다. 같은 run의 r1과 그 앞에서 완전히 종료한 run/당시 binding을 사용하며 뒤의 run을 없던 것으로 바꾸어 현재 실행 권한을 만들지 않는다. 각 prefix의 원래 revision/hash·전체 금액 chain은 그대로다. 서로 다른 목적의 중간 이벤트를 제거하거나 새 head로 재해시하지 않는다. 이후 변경된 회사 없이 원래 archive 검토안을 재현할 수 있어야 한다.

## unknown 및 최초 response 보관

mark-public-comparison-unknown commandVersion1은 nonce/run/원래 transmissionBindingDigest·dispatchEventDigest, expectedRunHead, reason 중 하나(not-started-unconfirmed/transport-unknown/restart-unknown)를 받는다. event/receipt2행, budget0이다. 같은 run의 unknown은 최대1회다. 실제 현재 owner가 start를 못 했다는 사실과 냉시작에서 전송0을 증명하는 것은 다르다. 어느 경우에도 새 owner/retry/release를 만들지 않는다.

persist-public-comparison-capture commandVersion1은 nonce/run/원래 transmissionBindingDigest·dispatchEventDigest, expectedRunHead, responseArtifactSha256·sizeBytes를 받는다. 최초 복사한 capture는 별도 내부 입력이며 행은 comparison-response artifact1 + response-captured event1 + receipt1, 총3행이다. 명령 자체에 임의 현재 가격·회사 snapshot을 넣지 않는다. runtime 연결 뒤에는 원래 owner가 유지한 opaque capture만 허용하며 공개 HTTP의 supplied JSON은 이 capability가 아니다.

두 명령은 저장된 unique immutable transmission binding, run, event의 previousDigest/revision/원래 payload, receipt nonce, response artifact bytes에서 전체 strict command를 재구성한다. 외부 명령의 digest와 전체 값이 같아야 한다. native receipt.inputDigest는 event payload 기반이므로 이를 사용자 전체 명령 digest로 대체하거나 그 값 하나만 비교하지 않는다. witness intent의 commandDigest도 같은 재구성값이어야 한다.

response 보관은 회사 삭제/변경·승인/가격 만료와 무관하게 원래 dispatch·증인·capture를 대조한다. unknown 뒤 late capture를 허용하고 같은 원문 재조회는 idempotent다. 기존 캡처가 있는 상태에서 다른 nonce/다른 원문으로 덮어쓰거나 두 번째 캡처를 보관하지 않는다. capture 보관 이후 domain 비교/사용량 평가/금액 정산/종료는 별도이며 현재 계약에서 자동 연쇄 실행하지 않는다.

captureProviderResponse가 허용한 필드만 동기 복사하고 JSON.stringify(capture)의 UTF-8 bytes/SHA를 보관한다. 모델 별칭·불완전/refusal·usage 누락이라도 캡처 가능한 envelope는 원래대로 보관한다. 비교 decoder 실패와 비용은 별개다. 정규화된 허용 필드 사본이지 전체 HTTP 원문/headers·SDK 객체를 보관했다고 주장하지 않는다. 기존4MiB response/2MiB validated/4MiB final/20MiB artifact합계와 요청24만자·32MiB run예약은 유지한다.

최초 capture를 동기 확보할 수 없거나 상한을 넘으면 부분 원문을 자르거나 가짜 response를 만들지 않고 unknown/hold를 유지한다. HTTP 수신량 한도는 별도 transport 검증 대상이며 현재4MiB artifact 제한이 stream 전체 수신량 제한을 증명하지 않는다. dispatch 후 현재 회사 변경으로 비교를 적용할 수 없어도 과거 response/비용 근거는 보존한다.

## 후속 SQL12·witness2 연결 범위

SQL11의 existing reader/writer 및 purpose coverage를 소급 바꾸지 않는다. SQL12는 명시 migration·정확한 DDL/gate 검사로 구분하며 기존 생성자의 자동 승격은 없다. 원래 table/nonce/BLOB·coverage target10과 모든 과거 body bytes는 유지한다. 허용 INSERT는 기존 actual5종+reservation binding+transmission binding의 정확한 계획 행뿐이며 immutable UPDATE/DELETE 금지와 전체 사후 감사는 유지한다.

첫 전환은 감사된 SQL11이고 비교 run이 reserved 또는 cancelled+finalized 상태이며 비교 dispatch가0이어야 한다. 남은 witness intent/불명/활성 실행이 있으면 전환을 거절한다. reserved run을 기존 승인으로 전송 가능하게 바꾸지 않으며 해당 요청의 유효기간/새 전송 동의는 따로 검사한다. 비어 있지 않은 legacy 비용·완료 run과 native 예약/취소 bytes를 보존한다. 금액 hold가 남은 정상 미전송 예약의 존재 자체로 강제 취소하지 않는다.

witness2는 같은 두 사본·기존 lease에서 v1 마지막 record digest/원래 checkpoint를 가리키는 명시 전환 suffix다. 전체 v1 원문과 순서를 동결하고 v2 독립 decoder를 사용한다. v1 reader가 새 suffix를 실행 가능한 v1로 오인해서는 안 된다. 전환은 정확한 before/after SQL schema digest·기존 raw row 보존을 두 사본 intent에 결합한 뒤 DDL COMMIT, 사후 전체 감사와 transition ack를 기록한다. SQL12 행/DDL만 있고 ack가 없을 때 정확한 전환 intent와 현재 schema 전체가 맞으면 파일 ack만 복구한다. DB가 SQL11인데 intent만 남은 경우 자동 전환 재실행/intent삭제/새 경로 enrollment는 하지 않는다.

기존 binding/anchor와 root/quality/studio/control 신원은 바꾸지 않는다. scope/head·원래 coverage를 새로 만들지 않는다. 증인에는 승인/가격·회사/응답 원문을 넣지 않고 명령·영수증/행집합·checkpoint digest만 둔다. v2의 operation은 reserve7행/cancel6행/approve-dispatch3행/mark-unknown2행/persist-capture3행을 strict 분기한다. 아직 구현하지 않은 비교·사용량·정산·종료 operation은 미지원으로 거절한다.

witness record32KiB/최대128개/사본4MiB를 유지한다. reserve/cancel만 있던v1과 달리 최대 run20개를 모두 전송할 수 있다고 가정하지 않는다. 신규 reserve/전환과 dispatch 전에 기존 사용량+미완료 run의 남은 최악 경로를 계산한다. 한 run은 reserve→dispatch→선택적unknown→capture→comparison→usage-assessed→settled→finalized의 최대8개 거래, intent/ack 최대16개로 보수 예약한다. 이미 있는 단계는 빼되 동일 거래로 저장할 미래 단계 수를 미리 줄이지 않는다. future operation 미지원은 슬롯 예약으로 실행 권한을 얻지 않는다. 취소/종료를 대조한 뒤만 불필요한 예약을 해제한다. v1의 완료 취소 run은 사용 기록만 남기며 회전/삭제·제한 확대를 하지 않는다. 이 제한 때문에 전체20run보다 먼저 새 예약이 막힐 수 있다. 모든 향후 계획의 실제 encoded witness bytes와 전환2개 기록도 포함한다.

ack는 해당 거래의 COMMIT 관측/정확한 원래 DBreceipt와 사후 raw 전체에 근거하며 실행 permit은 아니다. intent만 있고 DB행 없음, ack 뒤 오래된DB, 한 사본·부분 파일·남은 lease는 신규 쓰기/전송 차단이다. 원래 nonce의 가능한 구조 조회와 신규 쓰기 가능성을 구분한다.

## 후속 실제 dispatcher 수명 — 이번 및 다음 순수 단계에서는 미구현

새 COMMIT을 실제 관측한 private server invocation만 dispatch 후보 owner를 가지며 외부 JSON/DB읽기/replay/명시 reconcile은 이를 재생성하지 않는다. witness ack 완료 전에는 SDK를 시작하지 않는다. COMMIT 뒤 ack/회사 잠금 해제가 실패하면 owner를 외부에 반환하지 않고 원래 원문/증거 조회만 가능하다. later reconcile가 성공해도 새 전송은0이다.

그 invocation이 같은 witness lease를 유지한 채 SDK 준비 후 실제 fetch hook에서 quality BEGIN IMMEDIATE→studio BEGIN IMMEDIATE를 다시 얻는다. 같은 DB파일/coverage/raw/head·원래 binding/dispatch/잔여hold·cap·만료/서버구성·회사4I2 및 정확한 frozen rawBody를 검사한다. 감사가 오래 걸렸다면 start 바로 전에 시각/취소를 다시 검사한다. 서버가 이미 소유한 좁은 guard를 사용하며 외부 transaction·일반 callback·caller getter/임의 network를 production입력으로 받지 않는다.

한 번의 fetch를 잠금 아래 동기로 호출한다. 첫 호출 전에 attempt를 소모하고 sync throw도 전송 불명으로 보수 처리한다. 즉시 rejection handler와 원래 응답 promise를 붙인 뒤 studio→quality 잠금을 끝내고 잠금 밖에서 await한다. 품질 DB/회사 DB 두 COMMIT·file+DB+HTTP 원자성은 없다. start 이후 잠금 해제/COMMIT 오류로 응답 promise를 버리거나 not-sent로 되돌리지 않는다.

원래 runtime/store/lease는 in-flight 요청과 아직 DB COMMIT이 확인되지 않은 최초 capture가 남아 있는 동안 교체/폐기하지 않는다. 키/현재 경로 설정 변경은 새 send를 막지만 원래 열린 신원의 capture-only 복구를 자동 폐기하지 않는다. 실제 파일 교체·복원 marker·증인 불일치가 생기면 새 DB에 복사/저장하지 않고 원래 메모리 capture와 복구 필요 상태를 보존한다. process crash로 메모리를 잃은 capture는 복구 가능하다고 보장하지 않으며 응답 재요청/새nonce 재전송을 하지 않는다.
