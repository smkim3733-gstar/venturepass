## 2. 한도의 의미와 고정값

아래는 다음 격리 구현의 내부 고정 기본값이다. 사용자 실행 명령·price/consent 입력으로 바꿀 수 없다. 기존 가격/hold·보관 원장·요청 bytes는 바꾸지 않는다.

| 대상 | 다음 계약 | 기존 한도와 관계 |
|---|---|---|
| 정상 HTTP status의 앱 노출 body | 4*1024*1024 bytes 이하, 정확히 경계는 수집 가능 | canonical4MiB와 숫자는 같아도 별도 검사. 공백/해독/필드 제거/캡처 wrapper 때문에 한 검사 성공이 다른 성공을 뜻하지 않음 |
| 비정상 HTTP status의 앱 노출 body | 64*1024 bytes 이하 | 오류 body는 canonical 응답·usage/비용 근거로 승격하지 않음 |
| 준비·헤더·body 대기 | SDK형 호출 준비 직전 단조시계에서120000ms 한 번. 새 헤더/청크로 갱신하지 않음 | 기존 request timeoutMs120000/maxRetries0 유지. 회사/정책의 전송 전 유효기한 검사와 별개 |
| canonical 응답 | 기존 captureProviderResponse의4MiB·중첩100·허용 필드 | 새 parser/산술 없음. 원문 잘라 성공시키지 않음 |
| 원장 공간 | 진행 run32MiB·전체256MiB 및 증인128기록/4MiB | body 임시 메모리 한도나 시간 초과 시 자동 해제할 공간이 아님 |

여기서 body bytes는 **fetch가 Response.body reader에 노출한 바이트**다. 전송 구현이 압축을 풀어 노출하면 그 결과를 센다. Content-Length나 네트워크 압축 크기·TLS/HTTP 헤더를 총수신량으로 증명하지 않는다. 실제 Node transport의 압축/버퍼링 동작은 후속 운영 연결 검증이 필요하다.

청크 개수만큼 배열/객체를 무제한 보관하지 않는다. 최대 크기가 고정된 byte buffer에 경계 확인 후 필요한 바이트만 복사하고 upstream의 큰 backing buffer를 계속 참조하지 않는다. 첫 초과 청크는 추가 복사·SDK 전달 없이 거절한다. upstream이 한 번에 할당한 거대 청크, 내부 socket 버퍼·문자열·JSON/SDK 객체와 Response 구성 사본까지 포함한 프로세스 heap4MiB를 보장하지 않는다. 입력량을 유한하게 줄이는 계약이며 별도 process memory 격리는 이번 범위가 아니다.

## 3. 단일 body 수집과 SDK Response

다음 구현은 **한 reader로 제한 수집을 완료한 다음 SDK에 bounded Response를 주는 방식**이다. SDK에 원래 무제한 스트림을 먼저 전달하거나 clone/tee한 두 경로를 병행하지 않는다. reader는 JSON을 파싱하지 않고 byte 사본만 만든다. decode는 기존 SDK 형태 parser에 한 번 맡기며 실제 SDK 실행은 금지한다.

1. 동일 private owner의 최종 guard 안에서 원래 network를 동기 시작한다. 즉시 실패 handler와 원래 promise 추적을 설치한 뒤 SQL/회사 읽기 잠금을 끝낸다. body read와 모든 await는 잠금 밖이다.
2. 도착한 실제 Response 인스턴스·status/redirect·body 사용/잠금 상태를 확인한다. status0·redirected·이미 사용/잠긴 body·지원 밖 반환은 거절하고 가능한 원래 body 취소 책임을 남긴다. native Response getter/헤더는 그 순간 snapshot으로 고정한다.
3. 정상/오류 status에 맞는 고정 상한을 정한다. Content-Length가 있으면 음수/소수/모호한 목록/정수 범위 초과를 거절하고 명백한 상한 초과는 조기 거절할 수 있다. 이 값이 작거나 없다고 cap 검사를 생략하지 않는다. 압축 길이와 노출 body 길이가 같다고 가정하지 않는다.
4. body는 getReader() 한 번, read는 한 번에 하나만 대기한다. 각 read 전/후 deadline과 signal·terminal 상태를 대조하고 value의 byteLength를 더하기 전에 남은 용량과 비교한다. byte 청크가 아닌 값은 거절한다. EOF가 아닌 빈 청크도 단조시계 검사를 우회하지 않는다.
5. EOF와 reader 종료/해제 확인 전에는 SDK Response를 만들지 않는다. 오류·초과·중단 뒤 prefix나 빈 성공 Response로 바꾸지 않는다. null body/204 등 bodyless 응답은 새 JSON을 만들지 않고 해당 status와 비어 있는 body의 SDK 반환 의미를 유지한다. 실제 capture 가능 여부는 기존 callback 검사에 맡긴다.
6. SDK용 Response는 수집된 **동일 byte 순서**와 원래 status/statusText·content-type·x-request-id 등 필요한 원래 헤더 사본으로 만든다. 버퍼가 이미 fetch 노출 body이므로 content-encoding/원래 content-length는 제거하고 실제 버퍼 길이에 맞춘 content-length만 사용한다. 이는 내부 buffered view이며 원래 Response 객체/URL/압축 wire와 동일하다고 표시하지 않는다. 예상치 못한 content-type을 application/json으로 강제하거나 JSON을 재직렬화하지 않는다.
7. SDK형 HTTP 오류는 여전히 오류로 전달한다. 4xx/5xx body가 성공 응답처럼 생겨도 capture/사용량 판정 입력으로 바꾸지 않는다. 상태·작은 reason enum만 공개하고 원문·헤더·SDK message/cause는 반환/로그/증인에 넣지 않는다.
8. read/cancel 종료 전 buffer/reader 참조를 버려 완료로 표시하지 않는다. EOF 뒤 필요 없는 자체 참조는 해제하되 SDK 내부 사본의 즉각적인 GC까지 증명한다고 주장하지 않는다.

현재4I24는 원래 Response 객체를 그대로 반환한다. 다음 bounded adapter만 원래 body를 한 번 소비한 buffered view로 넘기며, legacy 합성 start와 요청/원장 bytes는 그대로다. 이 내부 변경의 status/content-type/request-id·HTTP 오류 의미는 합성 호환 시험을 해야 하며 실제 설치 SDK의 end-to-end 호환 검증은 여전히 별도다.

## 4. 중단 신호와 수명 연결

원래 SDK wire signal을 start 뒤 다른 signal로 덮어쓰는 방식은 택하지 않는다. 같은 private sdk 호출에서 AbortController를 만들고 SDK형 create의 **별도 request 옵션 {signal} 하나**로 전달하도록 포트를 좁게 확장한다. 비교 body/requestv1에 signal/service_tier/stream을 추가하지 않는다. SDK 모양 fixture는 이 caller signal과 fetch wire signal의 연결을 흉내 내며, 미래 실제 SDK는 자신의 controller/composed signal을 만든다. 최종 snapshotProviderSdkWire가 확인한 wire signal은 network에 그대로 전달한다.

controller·timer·bounded reader와 I/O 추적은 private 호출에만 속한다. HTTP/명령 입력, 공개 commitObserved/settled boolean·JSON/spread token으로 생성하거나 교체할 수 없다. 새 driver/network 준비 전 원래 nonce 조회, fresh COMMIT/ack만 owner 생성은 유지한다. replay에는 controller/timer/factory 준비도0이다.

deadline은 한 번만 정하고 준비·최종 시작·각 read 전후에 확인한다. timer는 중단 요청과 제한된 실패 관측을 만든다. 시간/PID/retire는 DB hold/lease 종료의 증거가 아니다. 소유자가 신호를 보내도 transport가 무시할 수 있으므로 원래 fetch·pending read·cancel promise를 따로 보존한다. 준비가 끝없이 늦어져도 deadline 후 새 fetch는 거절된다.

최종 guard 전에 signal이 취소됐으면 시작0이다. 시작 뒤에는 응답이 불명이며 unknown/hold를 유지한다. 이미 시작한 원래 network가 timeout 뒤 늦게 Response를 주면 SDK/캡처를 새로 시작하지 않고 해당 body를 취소·종료 처리한다. deadline 경계와 EOF의 경합은 한 private terminal 결정으로 처리하고 두 번째 전달/두 번째 cancel을 만들지 않는다.

SDK가 bounded Response를 이미 받은 뒤 원래 살아 있는 SDK promise의 첫 JSON을 늦게 전달하면 **먼저 기존 동기 capture로 보관**한다. 그 직전에 가격/회사/시간을 재검사해 받은 원문을 버리지 않는다. SDK 내부 race로 callback에 전달되지 않은 JSON은 unknown이며 asResponse/clone/새 parser/재전송으로 되살리지 않는다.

동기 JSON.parse·SDK 변환이 event loop를 점유하는 동안 timer로 강제 선점할 수 없다.120초는 대기/중단 요청의 단조 deadline이며 CPU·전체 함수 wall time의 강제 상한이 아니다. byte cap으로 해독 입력을 유한하게 하고 callback에서 원래 응답을 보존한다. 정해진 시간 뒤 작업이 반드시 끝났다고 표시하지 않는다.

## 5. 원래 I/O 종료의 정확한 조건

4I24의 networkSettled는 포트가 반환한 promise의 관측이다. 다음에는 아래를 같은 엔진의 private 종료 조건에 추가한다. 별도 실행 owner/SQL writer/증인 상태 기계를 만들지 않는다.

- 원래 network promise: 실제 resolve/reject를 관측했다. deadline/race winner만으로 true가 되지 않는다.
- 원래 body pump: EOF 또는 실패를 관측했고 대기 read가 끝났다. releaseLock 호출만으로 완료를 추정하지 않는다.
- 취소 책임: 필요한 cancel을 한 번 요청하고 promise의 반환·거절을 관측했다. pending cancel/거절·release 실패는 cleanupRequired로 보존한다.
- SDK 전달 promise와 SDK 해독/driver: 각각 종료 관측. 이미 해독이 실패해도 원래 I/O가 살아 있으면 소유를 유지한다.
- 첫 canonical capture: 기존 동일 nonce/bytes의 영속 확인·정확한 ack와 pending 해소, SQL/회사 읽기 종료와 lease 종료까지 기존 조건을 통과해야 한다.

I/O 관련 promise는 만들어지는 즉시 거절 handler를 붙이고 private 관측에 등록한다. 늦은 fetch 결과에서 새 body/cancel 책임이 생길 수 있는 동안 잠깐 outstanding=0이 됐다고 finish하지 않는다. 등록이 닫혔고 모든 원래 책임이 종료됐다는 내부 조건으로만 정리한다. 공개 registerPromise나 arbitrary callback/settled flag를 복구 권한으로 받지 않는다.

SDK/호출자에 빠른 timeout 거절을 주는 promise와 원래 I/O의 종료 promise를 분리한다. 기존 execute/inspect/recover/retire는 같은 engine을 사용하며 원래 I/O가 끝나지 않으면 실행 await도 남을 수 있다. inspect는 recovery-required/draining을 유지한다. 운영 UI timeout/종료 버튼을 새로 만들지 않는다.

cancel 실패가 나면 이를 삼켜 성공으로 바꾸지 않는다. 원래 I/O가 끝났다는 추가 관측이 없으면 cleanup 책임을 유지한다. 이번 단계에서 일반적인 취소 재시도/자동 lease 해제 정책은 만들지 않는다. capture가 있어도 cleanup 미확정이면 owner/capture/lease를 보존한다. 모든 I/O가 끝나도 capture가 없으면 기존 계약대로 recovery-required·DB hold/미종료 run을 유지한다.

capture가 확정돼 메모리 수명이 정상 종료되더라도 비용/저장 hold 해제는 기존 result3행/close8행의 전체 감사가 따로 판단한다. usage missing·불명 응답은0원 근거가 아니며 식별 가능한 초과 비용은 기존 같은 scope 규칙으로 보존한다.
