설치 타입에서 background/service_tier/store/stream/truncation은 선택 필드다. 이것은 선택 모델의 실제 지원·요금/보관 의미를 입증하지 않는다. requestedTier:null은 앱의 생략 표현이며 SDK body에 service_tier:null을 넣는 값이 아니다.

기존 providerTransportSdkOptions의 baseURL/120000/maxRetries0/logLevel:off와 adminAPIKey/webhookSecret/organization/project:null, redirect:error를 유지한다. 실제 key는 미래 명시 서버 구성의 private 값이어야 하며 함수를 통한 credential/provider 및 caller baseURL/headers/query/fetchOptions/옵션 재정의는 받지 않는다. OPENAI_CUSTOM_HEADERS의 임의 값은 header allowlist에 있는 이름만 써도 영향을 줄 수 있으므로 미래 구성은 값 노출 없이 비어 있음 여부를 검사하고 존재하면 새 시작을 닫는다. 환경을 자동 삭제/덮어쓰지 않는다.

SDK가 성공/HTTP 오류 본문을 읽는 단계에는 앱 canonical4MiB 한도가 적용되지 않는다. 성공 body의 response.text/JSON.parse와 일반 Bearer HTTP 오류 body의 response.text는 이번 읽은 경로에서4MiB 제한이 없다. 기존4MiB는 **canonical 보관량**이지 HTTP 수신/해독 메모리 상한이 아니다. 실제 adapter 활성화 전 응답 스트림/오류 본문의 바이트·시간 제한을 별도 검토·검증해야 한다. 이를 해결하려고 native decoder를 복제하거나 한도 넘는 JSON을 잘라 캡처 성공으로 만들지 않는다. 이번/다음 합성 검증은 실제 SDK의 이 제한을 해결했다는 증거가 아니다.

## 3. 목적별 adapter의 입력·출력 계약

아래 내부 역할은 같은 비교 owner 수명에 연결한다. 모든 public 반환은 owner:null이며 SDK client/key/fetch callback/owner permit/원문은 노출하지 않는다.

| 역할 | 입력 | 반환·금지 |
|---|---|---|
| preparePublicComparisonTransportBoundary (기존) | 원래 request command·comparison-context·identity, bounded data-only | 무권한 rawBody/목적지/timeout/생략 조건. 현재 회사·키·SDK 접근 없음 |
| 내부 prepareComparisonSdkInvocation (설계) | 감사된 원래 boundary와 원래 inspector에서 복원한 body, 같은 호출의 private owner 포트, 내부 고정 메커니즘 | 해당 실행에 묶인 비직렬화 호출 수명만 보관. 사용자 SDK factory/임의 callback/현재 body/새 model 입력 없음 |
| 내부 startComparisonNetwork (설계) | SDK가 최종 작성한 url/init, 내부에 고정된 network start | wire 대조와 quality→studio guard 후 Promise<Response>를 같은 SDK에 반환. Response를 canonical capture에 넘기지 않음 |
| 내부 captureComparisonSdkCompletion (설계) | 같은 SDK 호출에 즉시 설치한 첫 성공 handler의 JSON | captureProviderResponse를 동기 실행해 기존 private retained에 보관. 공개 supplied JSON이나 다른 호출 응답 입력 없음 |
| 실패 handler (설계) | 같은 원래 SDK promise의 실패 | 제한된 reason/status만 투영, 기존 unknown 보관. 오류 message/body/headers/cause/credentials 보관·반환 없음 |
| execute/recover/inspect/retire (기존) | 기존 strict 명령2/current와 원래 runId/dispatchCommandDigest | 같은 SQL13 writer·nonce 조회·원래 capture 복구/폐기. SDK client/응답/nonce를 새로 공급해 복구하는 API 없음 |

SDK의 ResponseCreateParamsNonStreaming과 비교 body의 구조를 타입/strict 입력으로 직접 대조할 수는 있지만 ProviderObservationPrepared나 generation/review/default로 cast하지 않는다. body는 inspector에서 만들어진 정확한 값과 순서를 보존하고 identity.rawBodySha256/requestUtf8Bytes와 맞아야 한다. model을 별칭으로 자동 대체하거나 서비스 옵션을 채우려면 새 요청 계약/미리보기·새 동의가 필요하다.

현재4I22의 startFake는 Promise<unknown>에서 곧바로 retainResponse를 호출하고 Promise<void>를 돌려준다. 이 포트에 실제 fetch를 꽂으면 Response를 JSON으로 잘못 캡처하며 SDK에 Response를 반환할 수도 없다. 타입 cast나 SDK 전체 promise를 fetch hook에서 기다리는 방식으로 해결하지 않는다. 후자는 SDK가 기다리는 fetch가 SDK 해독 완료를 다시 기다리는 순환 대기를 만든다.

다음 구현은 **기존 수명 엔진 내부에서 두 완료 경계를 구분**한다. 저장·lease·owner·guard·reconcile 상태 기계를 새 파일에 복제하지 않는다. 합성 fixture의 기존 start는 내부 두 포트에 순서대로 연결하는 얇은 호환 경로로 유지할 수 있다. 실제 SDK/생산 driver는 다음 합성 포트와 별도의 비공개 생성 신원이 필요하며 synthetic token을 재분류하지 않는다.

## 4. 한 호출의 시작·캡처·정리 순서

1. 전체 원장/원래 nonce·전체 명령을 먼저 감사한다. replay는 새 current/회사/시계/설정/가격/ID·SDK 준비보다 먼저 반환한다. 과거 행/ack 복구/재시작에서 owner를 재생성하지 않는다.
2. 새 명령만 기존 같은 lease의 private write를 사용한다. 새 dispatch COMMIT·회사 SELECT 종료·전체 재읽기·정확한 두 ack와 거래 종료를 직접 관측한 호출만 일회용 owner를 갖는다. 공개 commitObserved 반환값을 권한으로 입력하지 않는다.
3. 원래 body/boundary·생략 옵션을 복원한다. 미래 실제 runtime의 구성 확인과 SDK 생성은 이 호출 안에서만 수행한다. 같은 key/DB/설정이 폐기되면 새 시작이 닫힌다. 독립 SDK 모듈/constructor/route import가 전송을 시작하지 않는다.
4. create(body)에 성공/실패 handler를 즉시 붙인다. SDK는 잠금 밖에서 비동기 준비할 수 있다. custom fetch가 실제로 들어오면 첫 진입을 소비하고 wire snapshot을 만든다.
5. 기존 quality→studio guard를 그대로 재사용한다. 자기 dispatch 이후 checkpoint/binding4·원래 금액 head/hold·요청/회사/파일/lease·고정 정책/기한·검사 전후 시계와 signal, runtime 폐기를 대조한다. 옛 pre-dispatch review head를 현재 head와 단순 동일 비교하지 않는다.
6. 마지막 검사 뒤 같은 동기 구간에서 고정 network를 호출하고 rejection handler를 붙여 원래 promise를 보유한다. SDK fetch hook에는 **동일한 Response 결과를 주는 promise**를 돌려준다. studio/quality 읽기 잠금을 정리하고 모든 await는 밖에서 진행한다.
7. SQL 읽기 종료가 시작 뒤 실패해도 이미 획득한 network promise와 SDK 해독 promise를 보존한다. 정상 Response를 SDK에 전달할 수 있는 경로를 유지하며 cleanupRequired만 별도로 남긴다. 실제 시작 뒤 실패를 not-sent나0원으로 표시하지 않는다.
8. raw Response가 도착했다는 사실만으로 capturePersisted/SDK완료를 만들지 않는다. SDK가 JSON을 성공 handler에 처음 전달한 즉시 await·DB·사용량/비교 의견·공개 투영보다 먼저 captureProviderResponse를 호출한다. 첫 canonical 사본은 기존 retained에만 보관하고 두 번째 completion으로 바꾸지 않는다.
9. 같은 private writer의 unknown2행/capture3행을 사용한다. 시작 후 현재 회사 삭제·가격/동의 만료·key 변경은 원래 응답 보관을 막지 않는다. 새 원문을 등록하거나 재전송해 보완하지 않는다. result3행/close8행은 기존 원래 캡처/고정 정책 기반의 별도 단계다.
10. network와 SDK 해독/driver 완료를 모두 관측하고 exact capture 영속 확인·pending 없음·SQL 읽기 종료·증인/lease 종료가 확인될 때만 owner/메모리를 정리한다. usage unknown은 DB hold·미종료 run을 그대로 남긴다.

응답 거절·timeout 뒤에도 **같은 살아 있는 원래 해독 promise가 실제 전달한** 늦은 첫 JSON은 보관할 수 있다. SDK 내부 Promise.race가 timeout으로 끝난 뒤 앱 handler에 전달하지 않은 JSON을 얻었다고 주장하지 않는다. raw Response를 두 번째 parser/asResponse/clone으로 재해독하거나 API 재조회해 capture를 조작하지 않는다. 전달받지 못한 경우 unknown/recovery-required이며 hold를 유지한다.

서비스 수명은 active/capture뿐 아니라 응답 없는 원래 lease·미해결 읽기/정리 책임까지 계산해야 한다. 종료 버튼·PID·경과시간·module reload가 lease나 hold를 자동 해제하거나 새 runtime을 덮어쓰게 하지 않는다. 메모리 소실 후 DB dispatch를 새 owner로 복원하지 않으며 디스크 증인/행은 현재의 미확인 상태를 유지한다.
