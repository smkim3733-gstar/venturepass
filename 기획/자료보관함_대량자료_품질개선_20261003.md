# 첨부 자료 보관함과 50~200개 자료 처리 제안

2026-10-03. 사용자는 회사별 PDF·워드 등을 50~200개 예상하며, 첨부 파일이 눈에 보이고 자료의 품질이 사업계획서 작성에 제대로 반영되기를 요청했다.

## 이번에 구현한 화면

- 파일을 선택하면 파일명·형식 아이콘·크기·전송/저장 상태가 카드로 나타난다. 파일 아이콘은 형식 표시이며 PDF 첫 페이지의 실제 이미지가 아니다.
- 서버가 보관한 자료를 별도 카드 목록으로 보여 준다. 본문 일부, 본문 확인 필요 여부, 등록 시각을 볼 수 있다. 파일명 또는 ‘본문 확인·고치기’를 누르면 기존 본문 확인 화면이 열리고, 원본은 내려받을 수 있다.
- 파일명·본문 검색, 본문 유무 필터, 최근 등록순, 12개씩 더 보기를 제공한다. 검색과 필터는 화면 목록만 바꾸며 AI 전송 동의나 사용할 자료를 변경하지 않는다.
- 선택한 파일의 전송 대기/저장 중/성공/실패/불확실/미전송과 실제 저장 목록을 구분한다. 본문 추출 성공은 내용의 사실 확인 완료가 아니다.
- 기존 원본 보관·업로드 중단·불확실 응답 조회·전송 동의·운영 예산은 변경하지 않는다. 이번 개선은 자료 확인 화면이며 200개 자료의 저장·복구·AI 처리 완료를 뜻하지 않는다.

## 현재 구조에서 확인한 한계

아래는 분석 시작 시점의 마지막 완료 커밋 c219ea3 기준이다. 검증 도중 별도 작업으로 들어온 100개 확장 변경은 이번 카드 기능의 완료 범위에 포함하지 않는다.

| 확인 항목 | 기존 구현 | 50~200개에서 필요한 보완 |
| --- | --- | --- |
| 간단 업로드 | 회사당 40개, 파일당 12MB | 보관 용량·총 본문량·대기열·백업 한도를 함께 설계 |
| 문서 읽기 | 추출 본문 10만 자, PDF 120페이지 제한 | 긴 문서 분리/페이지별 상태와 실패 위치 표시 |
| 별도 자료 접수 기능 | 회당 10개·24MB, 접수 항목 100개, 보관 본문 50만 자 제한 | 기존 접수·원본 해시·검토·채택 기능 재사용, 200개 상태 복구 검증 |
| AI 준비 | 읽힌 자료의 본문 전체를 합쳐 요청, 직렬화 입력 24만 자 상한 | 계획서 항목별로 관련 근거를 선택하고 입력량을 미리 표시 |
| 화면 데이터 | 회사 응답에 자료와 본문을 함께 포함 | 목록 정보와 본문 상세 조회 분리, 서버 검색·페이지 조회 |

24만 자는 JavaScript 문자열 길이 검사이며 실제 모델 토큰 수나 비용 측정값이 아니다. 문서 200개가 모두 짧은 경우와 장문의 PDF 20개는 부담이 다르므로, 파일 수만으로 적합성을 판단하면 안 된다. 카드 12개 표시는 화면 요소만 줄인다. 현재 API가 본문 전체를 내려주는 비용까지 해결하지는 않는다.

코드 근거: `web/src/lib/studio-schema.ts`, `studio-extract.ts`, `studio-source-intake-types.ts`, `studio-engine-request-preparation.ts`, `studio-guided-preparation-state.ts`. 비AI 작성 경로의 `studio-engine.ts/collectReferences`는 분류·단어 기준 발췌이며 의미 검색 구현으로 취급하지 않는다.

## 권장 처리 흐름

**원본 보관 → 읽은 내용 확인 → 분류·날짜·버전 정리 → 항목별 근거 선택 → AI 작성 → 출처 대조**

| 문제 | 제안하는 동작 | 사용자가 확인할 표시 |
| --- | --- | --- |
| 파일이 많아 무엇을 올렸는지 모름 | 자료 보관함과 파일별 처리 상태를 유지 | 저장 수, 처리 대기, 읽기 실패, 원본 열기 |
| 전원 종료·전송 중단 | 원본 저장과 본문 읽기를 분리한 지속 대기열, 재시작 시 원래 요청 조회 | 어디까지 보관됐는지, 남은 처리, 확인이 필요한 파일 |
| 같은 파일·다른 버전 혼재 | 내용 해시로 동일 파일 표시, 같은 이름의 다른 내용은 별도 버전 보존 | 중복 후보, 작성일/적용 기간, 사용 버전 |
| 스캔·표·숫자를 잘못 읽음 | 페이지/표 위치와 원문을 함께 보존, 단위·기간·중요 수치 대조 | 본문 확인 필요, 숫자 대조 필요, 페이지 위치 |
| 구자료와 현재 자료가 충돌 | 사실별 출처·날짜를 나란히 표시, 담당자가 채택 근거 선택 | 서로 다른 매출·인력·인증기간 등의 충돌 |
| 장문을 한꺼번에 보내 핵심이 묻힘 | 계획서 항목별 관련 근거 검색 및 직접 고정 | 사용 근거, 빠진 자료, 검색되지 않은 자료 |
| 요약 과정에서 과장됨 | 원문 인용과 한계·반대 근거를 함께 전달 | 계획/메모/실적 구분, 근거 문장과 원본 위치 |

문서 분류 후보는 회사 기본, 재무, 기술·특허, 연구개발·시험, 계약·매출, 시장, 인력, 상담 메모 등이다. 자동 분류는 제안으로 표시하고 수정 가능하게 한다. 문서의 이름이나 형식만으로 사실의 신뢰도를 확정하지 않는다. 예를 들어 자금 계획 메모를 현재 보유 현금으로 바꾸거나, 내부 시험 결과를 공인 성능 인증으로 표현하지 않도록 원래 범위를 유지해야 한다.

내용이 같은 자료도 자동 삭제하지 않는다. 같은 파일명이 다른 내용일 수도 있고, 서로 다른 파일의 일부 문장만 중복일 수도 있다. 표시와 선택을 제공하고 원본·버전·과거 원고의 인용은 보존한다.

## AI 품질에 연결하는 방식

‘많이 올리면 품질이 좋아진다’보다 **필요한 근거가 빠지지 않고, 최신성과 출처를 확인할 수 있는가**를 기준으로 삼는다. 기술성·사업성·시장·조직·자금 등 항목마다 사용 가능한 근거와 부족한 내용을 표로 보여 주는 방식이 적합하다.

첫 단계는 현재 PC 안에서 문서 분류·날짜·키워드와 본문 검색을 결합한다. 관련 근거를 충분히 찾지 못하는 사례가 확인되면 의미 검색을 추가한다. 처음부터 외부 벡터 저장소나 유료 문서 처리 서비스를 도입할 필요는 없다. 검색이 정답을 보장하지 않으므로 담당자가 근거를 고정하거나 제외할 수 있어야 한다.

문서를 나누어 찾을 때 회사명·기간·제목·표 단위처럼 문맥을 함께 보존하는 접근은 [Anthropic의 Contextual Retrieval 설명](https://www.anthropic.com/engineering/contextual-retrieval)을 참고했다. 키워드와 의미 검색을 조합하고 실제 업무 자료에서 평가하는 방향은 [Microsoft의 RAG 검색 설계 안내](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-information-retrieval)와 부합한다. 이 자료들의 성능 수치를 VenturePass의 개선율로 적용하지 않는다.

AI에 보낼 때는 선택된 파일 버전·해시·원문 구간·출처 위치를 고정한 목록을 만들고, 실제 입력량과 예상 비용을 확인한다. 원본 200개를 보관한 사실을 200개 전체 전송 동의로 취급하지 않는다. 검색 결과만으로 기존 승인 범위를 조용히 바꾸지 않으며, 새로운 입력 선택 방식에는 별도 실행 계약과 검증이 필요하다. 완료된 운영 평가의 요청·승인·원장·원문은 유지한다.

## 후속 개발 순서와 완료 기준

1. **200개 보관·중단 복구**: 기존 자료 접수 구조를 재사용한다. 한도와 목록/본문 조회를 분리하고 원본 우선 저장, 지속 대기열, 중복 표시, 재시작 복구를 연결한다. 50/100/200개 합성 자료에서 일부 실패·응답 유실·재시작·원본 다운로드·백업 복원을 확인한다.
2. **자료 정리와 읽기 품질**: 분류·날짜·버전·원본 위치·표 단위·본문 미확인 항목을 정리하고 사람이 교정할 수 있도록 연결한다. 스캔, 암호/손상 문서, 날짜가 다른 재무 자료, 같은 이름의 다른 파일을 구분한다.
3. **항목별 근거 선택과 작성 검증**: 근거표·검색·직접 고정·선택 범위 동의를 연결한다. 중복·구버전·충돌·부정 근거를 심은 합성 자료에서 누락, 잘못된 인용, 수치 단위 오류를 측정한다. 실제 고객 자료나 새 유료 모델 평가는 별도 승인된 범위에서 진행한다.

이번 카드·검색 개선은 완료 대상이고 위 세 묶음은 제안 단계다. 200개를 보관할 수 있는 것, 200개를 정확히 읽는 것, 그중 필요한 근거로 좋은 원고를 만드는 것은 각각 별도 완료 기준이다. 합성 시험이나 AI의 지적 0건을 사람 내용 확인이나 기관 제출 승인으로 대신하지 않는다.
