## 3. 보관 위치·용량·최소 필드

다음 factory의 가칭은 createComparisonReviewRetainer다. React/handler/service의 runtime import 없이 기존 createComparisonReviewInvocation만 사용한다. 호출자가 보관자를 먼저 만들고 보관하며, 생성 자체에는 invocation/Request/타이머가 없다. 루트 Providers 등 실제 부모에 설치하는 것은 다음 격리 구현의 범위가 아니다.

보관 범위는 동일 호출자 수명 전체다. 회사별 Map·화면별 별도 슬롯을 만들지 않는다. 회사가 바뀌어도 미종료 이전 호출은 같은 슬롯을 차지한다. 보관자 재생성으로 포화를 우회하지 않는다. 실제 운영 연결 전에 이 단일 수명을 책임질 상위 보관자와 원래 service/선택 취득 경로가 별도로 필요하다.

최소 내부 상태는 closed 여부, 현재 화면 token, 증가하는 호출 sequence, empty/creating/retained 슬롯, 원래 호출 객체·ticket·불투명 handle 및 양쪽 completion 관측 참조다. 표시를 해제했는지와 보관자 자신의 관측 실패도 보관한다. query/DTO/본문을 별도 cache/history에 복제하지 않고 원래 객체에 위임한다. 원래 회사/run/dispatch/mode·선택/section/snapshot 대조는 기존 invocation/ticket의 고정 값을 사용한다.

화면 token과 호출 handle은 같은 보관자에서 만든 객체 참조로만 비교한다. 외부 제공 문자열/회사번호/sequence만으로 기존 슬롯을 선택하지 않는다. sequence는 호출 생성마다 증가하며 회사/화면 변경으로 재설정하지 않는다. 안전 정수 한계면 새 호출을 거절하고 기존 객체는 보존한다. 이 값들은 화면 순서용이며 인증/DB owner/원래 실행 권한이 아니다.

용량1은 보관하는 호출 개수다. DTO4MiB/성공 wire4MiB+8KiB는 그대로지만 snapshot·Promise·문자열·외부 사본을 포함한 JS heap의 총4MiB 보장은 아니다. 영수증 불명/정리 실패는 무기한 슬롯을 차지할 수 있다. 이를 숨기거나 자동으로 다른 보관자를 만들지 않는다.

| close | 보관자 수명 종료 요청 | 현재 token/표시를 해제하고 자기 호출을 cancel한다. 재연결/새 생성은 영구 거절한다. pending/실패가 남으면 보관자 자체를 계속 보관한다. service.retire가 아니다. |

startRequest는 기존의 신뢰한 동기 주입 포트다. service/원래 선택의 운영 취득 경로는 여전히 없으며 null 주입은 기존 명시 미지원이다. global fetch 기본값, 요청당 DB/store/session/owner/registry, 최신 run·preview/쓰기 receipt 추정으로 보충하지 않는다.

동시에 두 prepare를 처리하지 않도록 첫 동기 검사부터 creating 슬롯을 예약한다. 입력 getter/관측/주입 포트에서 재진입하더라도 추가 생성 전에 거절하며 queue를 만들지 않는다. 객체 생성 중 화면이 교체되거나 close되면 반환된 원래 호출을 먼저 보관하고 cancel하며 start하지 않는다. 생성 전 검증 실패로 객체가 없음을 아는 경우만 예약을 풀 수 있다. 객체가 만들어진 뒤 관측 등록/처리 실패를 빈 슬롯으로 바꾸지 않는다.

새 명시 prepare는 이전 호출을 fresh canForget으로 정상 해제할 수 있을 때만 교체할 수 있다. 이전 표시를 먼저 무효화한다. 이후 새 입력이 실패해도 이전 exact를 복구해 보여 주지 않는다. capacity 거절은 새 invocation/receiver/타이머/Request를 생성하지 않는 것으로 검증한다.

## 5. 완료 관측과 폐기 조건

빠른 delivery와 requestCompletion/responseCompletion/aggregate completion을 원래 invocation에 그대로 맡긴다. 보관자는 동일 호출의 completion을 관측하되 완료 시점에 inspect를 다시 읽는다. completion Promise가 끝났다는 이유만으로 canForget:true나 정리 성공을 추정하지 않는다. 관측 오류는 고정 실패로 남기며 원문/stack을 노출하지 않는다.

현재 연결된 화면이 정상 결과/오류를 표시 중이면 깨끗한 완료 뒤에도 명시 교체·해제·화면 분리 전까지 슬롯을 보관한다. 이미 화면을 분리했거나 보관자가 closed인 entry는 원래 completion 관측 후 canForget:true일 때만 참조를 해제할 수 있다. 별도 주기 polling·유예 타이머·강제 폐기는 없다. 이미 완료된 호출의 화면 분리/close도 같은 조건을 즉시 검사한다.

모든 해제는 실제 entry/handle 동일성을 관측 전후 대조한다. inspect나 완료 callback에서 재진입하더라도 옛 callback이 새 슬롯을 지우거나 현재 token을 바꾸지 않는다. 임계 구간에서 추가 admission/release는 거절하거나 무해한 동일 결과로 끝내며, 취소/close 요청은 잃지 않는다. 불명/실패를 덮는 reset은 두지 않는다.

준비만 하고 start하지 않은 호출도 기존 receiver의 생성부터30초 기한을 갖는다. 시간 초과 자체는 강제 폐기 증거가 아니다. 원래 completion과 canForget이 확인되고 표시가 분리된 경우에만 위 조건으로 해제한다. start되지 않은 호출·사전 취소도 같은 기존 수명으로 처리한다.

화면 효과의 옛 cleanup, 회사/revision·탭·편집 상태 변경은 표시 수명만 바꾼다. actual React 설치 이후에는 StrictMode setup/cleanup이나 root 교체에서도 단일 보관 수명을 유지하는 검증이 필요하다. 이번/다음 격리 구현은 실제 React remount 검증·reload 복구가 아니다. 강한 참조를 잃거나 페이지/프로세스가 종료되면 메모리 보관의 지속성을 보장하지 않는다.

## 7. 서버·권한·격리 경계

호출 canForget은 양쪽 I/O의 보관 해제 조건일 뿐이다. 같은 service의 SQL/회사 guard/lease·pending ack·불명 명령·cleanupRequired와 별개다. 보관자는 service.retire/session close/recover/ack/INSERT·정산/hold 해제를 받거나 호출하지 않는다. 새 명시 읽기가 허용돼도 서버에서 READ_BLOCKED가 반환될 수 있고, 원래 명시 복구가 계속 필요하다.
