# 품질평가 v2 전송 승인 후속 설계

구현 갱신: 2026-09-27. 이 설계의 순수 계약·내부 저장소·v2 관측 어댑터·합성 runner·v6 백업을 구현하고 관련42파일1,014개 및 lint·독립tsc·격리 빌드를 검증했다. 기존 예약 원형과 r0/취소 r1 바이트를 유지한다. 1절의 ‘현재’는 설계 작성 당시 예약 전용 상태를 설명한다. 실제 운영 모델/근거·전송 API는 계속 미설정/차단이며, 다음 읽기 전용 검토 화면은 [v2 검토안 UI 연결 설계](./품질평가_v2_검토안_UI_연결설계.md)를 따른다. 합성 검증은 실제 AI 의미 품질이나 청구서 대조가 아니다.

기준: 2026-09-27. 기존 v2의 예약·승인·원문 보관 구현 뒤에 연결할 설계다. 이 문서 작성으로 운영 모델, 가격, 예산 또는 전송이 승인되지 않는다. 실제 공급자 쓰기 API는 계속 닫는다. 현재 모델 채택·운영 가격 설정·계정 접근권한 확인은 미완료이며, 이 작업에서 키·고객 DB·외부 AI에 접근하지 않았다.

## 1. 보존할 현재 계약

현재 `studio-plan-quality-provider-core.ts`와 `scripts/local-data-quality-provider.mjs`는 `schemaVersion:2` 준비안, 예약 전용 승인, 생성 요청 원문, 시작 영수증, 전송 전 취소만 지원한다. `acknowledgedReservationOnly:true`, 준비안의 `permissions.dispatchAllowed:false`, 실행 시작 행의 `observedTransport:'none'`·`actualAiCalls:0`를 기록한다. 현재 event는 revision 1의 `cancelled-before-dispatch`뿐이다.

이 필드·행·digest·원문을 수정하거나, 기존 예약 승인을 실제 전송 동의로 해석하지 않는다. 취소한 예약은 되살리지 않는다. v1 합성 원장과 이전 모의 실행 이력도 재해석하지 않는다. 기존 r0 및 취소 r1 다운로드는 후속 구현 전후 바이트가 같아야 한다.

운영과 합성 예산은 기존 고정 scope를 유지한다. `candidate-quality-provider-v2-synthetic`에서 생성한 승인이나 실행은 `candidate-quality-provider-v2-live`로 이전할 수 없다. 테스트 어댑터의 성공이 운영 전송·청구·AI 품질 증거가 되는 것도 아니다.

## 2. 최소 영속 확장: 기존 예약에 별도 전송 승인 추가

새 테이블을 만들지 않고 현재 13개 테이블을 재사용한다. `quality_actual_runs`의 v2 시작 행은 불변으로 두고, `quality_actual_events`에 새 `transmission-approved` 이벤트를 추가한다. 이 이벤트가 없는 예약은 전송할 수 없다.

첫 전송 승인은 현재 run revision 0에서만 가능하다. 취소·이전 전송 승인·전송 시도가 있는 run에는 추가하지 않는다. 만료·입력·모델·요율·요청 계약이 달라졌다면 기존 예약을 취소하고 새 준비안을 만든다. 승인 범위를 바꾸는 덮어쓰기나 과거 승인 시각 수정은 허용하지 않는다.

새 이벤트는 `schemaVersion:2`에 명시적 `executionContractVersion:1`을 갖는 별도 strict union으로 정의한다. 기존 취소 이벤트의 schema와 의미는 바꾸지 않는다. 새 전송 이벤트들은 전송 승인 event digest를 참조한다. 과거 취소만 있는 prefix는 기존 예약 전용 validator로, 전송 승인 이후 prefix는 새 실행 validator로 검사한다. 알 수 없는 이벤트를 무시하거나 이전 계약으로 fallback하지 않는다.

전송 승인의 제안 payload는 다음과 같다.

```ts
{
  kind: 'transmission-approved',
  executionContractVersion: 1,
  reservationRunDigest,
  approvedPreparationDigest,
  approvalManifestDigest,
  executionContractDigest,
  provenance: 'explicit-user' | 'synthetic-test',
  approvedAt,
  expiresAt,
  acknowledgedExternalTransmission: true,
  acknowledgedGenerationAndDerivedReview: true,
  acknowledgedRetentionNoticeDigest,
  acknowledgedFinancialReservationNotTokenFit: true,
  acknowledgedUnknownCostHoldAndNoRetry: true
}
```

`approvalManifest`는 정확한 등록 버전·후보 ID·model input SHA, 모델 ID, 목적지, 생성 요청 바이트 SHA, 검토 템플릿 digest와 파생 규칙, 호출 2회·수정/재시도 0회, 예약 근거와 금액, 예산 scope·정책·누적 한도, 보관 안내 digest를 포함한다. 저장된 준비안에서 서버가 구성하며 클라이언트가 별도 원문·scope를 추가하지 못한다. 거대한 본문을 receipt에 반복하지 않고 준비안과 생성 BLOB의 digest를 결합한다.

승인 시각과 expiry는 새로운 명시 동의의 기록이다. 기존 예약 승인 시각을 복사해 넣지 않는다. 새 승인은 원래 준비안과 문맥·가격·보관 근거의 재확인 기한 안에서만 유효하다. 공개 가격의 내부 `validUntil`을 공급자의 가격 보장일로 설명하지 않는다.

예약을 시작할 때 저장한 `actualAiCalls:0`와 `observedTransport:'none'`는 그 시작 기록의 사실로 보존한다. 전송 승인 이후의 현재 관측은 새로운 snapshot의 별도 집계 필드에서 보여 준다. 전송 의도 event만으로 실제 호출 횟수를 확정할 수 없으므로 `dispatchIntentCount`, `responseCount`, `unobservedDispatchCount`를 구분한다. 승인·dispatch 후 프로세스가 종료된 상태를 실제 공급자 전송 성공으로 표시하지 않는다.

## 3. 기록 형식과 과거 다운로드

기존 r0와 취소 r1 archive는 기존 `archiveFormatVersion:2` 직렬화기를 그대로 사용한다. 전송 승인 이후의 새 archive envelope에만 새로운 형식 버전을 부여한다. 내부 시작 행은 계속 원래 v2 body를 포함한다. 예전 run에 새 이벤트가 생겨도 과거 revision의 snapshot·budget prefix·receipt prefix·BLOB 목록은 당시 영수증에 고정한다.

검사·백업에는 명시적 다음 writer 계약이 필요하다. 현재 v5의 13개 테이블·39개 trigger 구조를 유지하고 gate literal만 다음 버전으로 원자 교체하는 안을 우선한다. 기존 immutable trigger를 제거하거나 기존 body를 변환하지 않는다. 이전 앱이 새 실행 event를 이해하지 못한 채 쓰지 못하도록 정확한 gate/validator 버전을 함께 올린다. v1~v5 백업 읽기·복원도 보존한다.

전역 nonce, run 20개, 공유 256MiB 및 event·receipt 예산은 모든 버전·scope에 대해 합산한다. 금액·head·revision은 scope별로 유지한다. v1의 기존 run 순번과 v2의 scope 순번·global CAS 의미를 바꾸지 않는다. 모의·실제·예약·전송 행의 소유권은 정확히 한 곳으로 분류한다.

## 4. 실행 승인과 전송 권한은 다르다

제안 내부 진입점은 `approveAndRunProviderExecution(store, request, fixedAdapters)`다. request는 run ID, 현재 run revision, 새 client nonce, 서버가 만든 한 건 승인안의 digest와 명시 동의만 가진다. production adapter는 서버의 고정 설정에서 선택하며 HTTP body가 provider URL·transport·키·scope를 지정할 수 없다.

runner 자신이 승인 트랜잭션을 호출하고 이번 호출의 `newlyCommitted:true` 결과를 받은 경우에만 생성 준비를 시작한다. 조회·과거 receipt·재시작 또는 같은 nonce의 replay에는 transport 호출이 없다. 클라이언트가 전달한 `newlyCommitted` 값은 권한으로 사용하지 않는다.

각 phase는 별도로 원문 고정과 dispatch-intent를 기록한다. dispatcher가 직접 받은 최초 commit 반환값만 같은 함수 호출의 한 번 전송을 허용한다. 이 권한은 반환 DTO·조회 API·DB snapshot에 재사용 가능한 토큰으로 보관하지 않는다. commit 뒤 실제 전송 전에 종료되더라도 다른 프로세스가 대신 보내지 않는다.

동일 nonce·동일 입력은 정확한 과거 receipt를 반환하고 전송하지 않는다. 동일 nonce·다른 입력은 거절한다. `not-observed` 조회는 미처리 확정이 아니며 자동 재전송을 허용하지 않는다. UI의 명시적 동일 요청 재확인도 서버 멱등성 검사를 거치며, 이미 승인·dispatch가 commit된 경우 새로운 전송을 만들지 않는다.

## 5. 전송 event와 단계 순서

다음 event를 기존 테이블에 append한다. 각각 run revision, 이전 event digest, 해당 작업이 확정한 budget revision, nonce receipt를 결합한다.

| 순서 | event | 필수 결합 |
| --- | --- | --- |
| 1 | `transmission-approved` | 예약 run·준비안·한 건 승인안·실행 계약 |
| 2 | `request-prepared` / generation | 시작 때 저장한 생성 BLOB과 동일한 bytes·SHA |
| 3 | `dispatch-intent` / generation | 직전 prepared event·승인·예산 head |
| 4 | `response-received` / generation | 원래 dispatch·SDK JSON BLOB·metadata·usage 상태 |
| 5 | `domain-validated` / generation | 저장된 응답·최초 검증 원고 BLOB |
| 6 | `request-prepared` / review | 같은 run의 generation 검증 event·원고 SHA·고정 template |
| 7 | `dispatch-intent` / review | 검토 prepared event·승인·현재 예산 head |
| 8 | `response-received` / review | 원래 검토 dispatch·SDK JSON·metadata·usage 상태 |
| 9 | `domain-validated` / review | 저장된 검토 응답·검토 의견 BLOB |
| 10 | `execution-stopped` | 결과 또는 차단 원인·최종 BLOB·해제한 미사용 예약 |

phase별 dispatch는 최대 한 번, 전체는 최대 두 번이다. 검토는 생성 응답 보관·비용 구분·도메인 검증이 모두 완료된 경우에만 준비한다. generation 검증 실패나 usage 미확인은 두 번째 호출을 허용하지 않는다. 수정 생성·재검토·token counting·계정 조회·추가 후보 호출은 이 승인에 없다.

승인 후 아직 dispatch가 없는 취소는 새로운 `execution-stopped/before-dispatch`로 남기고 미사용 예약을 해제한다. 기존 `cancelled-before-dispatch` revision 1 형태는 전송 승인 전의 기존 경로에만 유지한다. dispatch 뒤에는 전체 취소·전체 환불처럼 표시하지 않는다.

## 6. C1 엔진에서 재사용할 것과 분리할 것

현재 `generateObservedPlan()`은 `getPlanExecutionContract()`의 v1 digest와 builder를 엄격히 대조한다. v2 body에 있는 `service_tier`, `truncation`, `background`, `stream`을 v1 경로에 몰래 덧붙이거나, 기존 실제/모의 요청 digest를 바꾸면 안 된다.

별도 v2 관측 진입점을 두고 원고 생성·근거 검증·독립 검토의 공통 도메인 함수를 재사용한다. v2의 실행 계약은 준비안의 request contract에 더해 response capture schema·usage 정규화·도메인 validator 버전을 명시적으로 고정한다. 현재 엔진을 바꾸면 아직 전송하지 않은 새 phase는 중단한다. 이미 전송한 응답의 원문·사용량 보관은 당시 dispatch 계약으로 계속 가능해야 한다.

generation에서는 시작 때 보관한 `generation-request` BLOB의 JSON bytes를 그대로 사용한다. 객체 재직렬화 결과가 달라지면 승인 범위가 바뀐 것으로 거절한다. parsed body 비교만으로 raw SHA 검사를 대체하지 않는다.

review에서는 같은 run의 최초 `domain-validated/generation` 원고만 읽는다. 현재 회사 원고, AI 검토 후 수정한 최종 원고, 다른 run의 원고는 사용할 수 없다. 기존 `buildPlanReviewRequest`의 입력 구성 규칙을 재사용한 뒤 고정 v2 옵션을 적용하고, derivedFrom에 generation event·artifact·output digest를 기록한다. 생성 전에 검토 body가 완성됐다고 표시하지 않는다. 승인 대상은 정확한 고정 template와 이 제한된 파생 규칙이다.

훅 순서는 C1의 `onRequestPrepared → onDispatch → transport → onResponseCaptured → domain validation → onValidated`를 유지한다. 각 영속 훅은 await해야 한다. response hook의 성공을 output 검증 성공으로 간주하지 않는다. v2 runner에서는 captured hook만 durable response를 기록하고 metadata-only hook은 중복 기록하지 않는다.

## 7. v2 공급자 응답 원문과 사용량

현재 `captureObservedResponse()`는 `id`, `_request_id`, `model`, `status`, `usage`, `output`만 보존한다. `service_tier`는 버리고, 정산용 metadata는 input/output/total tokens, cached input, reasoning output까지만 정규화한다. 따라서 현재 C1 metadata를 실제 tier·캐시 쓰기 정산 증거로 그대로 사용할 수 없다.

v2 전용 capture schema는 해당 SDK 응답의 `service_tier`를 보관하고, `usage`의 JSON 세부를 손실 없이 보존한다. 키·HTTP 인증 헤더·SDK client·원시 오류 객체는 보관하지 않는다. 이는 허용된 SDK 응답 JSON이지 HTTP wire 전체 또는 청구서 원문이 아니다. 전달물은 현재 방식처럼 동기 복제·동결 후 훅으로 넘긴다. v1 capture 결과와 과거 BLOB은 바꾸지 않는다.

정산 metadata에는 최소 configured model, response model, requested tier, response tier, response status, input/output/total tokens, cached input·reasoning output 및 요율 구분에 실제 필요한 cache write 세부의 관측 여부를 둔다. cache write 필드명·중복 집계 관계는 모델 채택 시 공식 응답 계약으로 확정한다. 아직 확인하지 않은 공급자 필드 이름이나 `cached_tokens`만으로 cache write 수를 만들어 넣지 않는다.

누락은 0이 아니다. 입력·출력 합계와 캐시·추론 토큰의 포함 관계를 검증하며, 추론 토큰을 output에 또 더하지 않는다. 요청 `service_tier:default`만으로 응답 tier까지 관측했다고 기록하지 않는다. exact response model 또는 사전 승인한 명시적 매핑을 벗어나면 같은 이름처럼 보여도 요율을 추측하지 않는다. 최초 운영 시험은 날짜 고정 모델 등 모호하지 않은 식별 정책이 확정되어야 한다.

raw response BLOB과 metadata/usage 상태는 원고 JSON 파싱·근거 검증 전에 한 트랜잭션으로 보관한다. 원문 보관 실패 뒤에는 다음 호출이 없다. capture 한도 초과·형식 이상으로 raw 응답을 보관하지 못한 경우에도 허위 0원/성공을 기록하지 않고 미확인 예약을 유지한다.

## 8. 비용 정산과 미확인 예약

현재 reserve/release 두 단계용 예산 reducer는 전송 승인 경로에 한해 새 usage/phase release 이벤트를 이해하도록 확장한다. 기존 configure·reserve-run·release-run 이벤트의 body·해시·계산 의미는 바꾸지 않는다. 새 정산 이벤트는 run·phase·reservation·dispatch·response artifact·당시 가격 근거 digest를 모두 결합한다.

API usage와 승인한 요율로 계산한 비용은 `usage-based-cost`로 구분한다. 공급자 최종 청구서와 대조한 확정 청구액이라는 표현을 쓰지 않는다. 실제 토큰 구분·tier·모델·요율 조건이 완전한 경우에만 사용량 기반 비용을 기록한다. 캐시/문맥 요율 적용 조건은 요율표와 함께 명시적으로 고정한다. 단순히 가장 비싼 예약 요율을 실제 관측 비용으로 기록하지 않는다.

미확인 항목이 비용에 영향을 줄 수 있으면 해당 phase 예약을 그대로 유지하고 검토 전송을 막는다. 가격 채택 때 모든 가능한 구분의 요율이 같다는 근거로 분류가 불필요함을 정의할 수 있지만, 실행 중 편의상 같다고 가정하지 않는다. 저장된 usage가 없는 오류·연결 단절·타임아웃을 무료라고 처리하지 않는다. 수신 status가 incomplete 또는 output 검증 실패여도 관측 비용은 원고 성공과 별도로 보관한다.

phase 예약 R, 관측 비용 U일 때 예약 소비는 `min(R,U)`로 제한하되 recognized usage에는 U 전액을 기록한다. U가 R보다 크면 초과액과 deficit을 남기고 해당 scope의 신규 dispatch를 차단한다. 잔량보다 큰 U를 기록 자체에서 거절하거나 R까지만 비용으로 저장해서는 안 된다. 다른 run의 held 금액을 임의 소비하지 않는다.

미사용 잔액은 관측 비용이 완전히 정리된 phase 또는 전송하지 않았음이 확정된 phase만 명시 해제한다. 문맥/출력 상한 초과·가격 범위 이탈은 비용 초과와 별도 위반 상태로 남기며 다음 전송을 막는다. 공급자 오류의 청구 상한 보장은 미확인 상태를 유지한다. 사후 청구 대조·누락 usage 수정은 별도 승인과 근거가 필요한 다음 범위이며 이번 경로에서 자동 생성하지 않는다.

## 9. 불확실 결과, 늦은 응답과 보관 한도

dispatch commit 뒤 response가 없으면 `result-unobserved`이며 예약을 유지한다. 재오픈·조회·새 nonce로 같은 후보를 다시 보내지 않는다. 동일 후보의 미해결 실행은 scope 안에서 새 예약/전송을 막는다. 이전 실행의 취소나 정산 기록이 새 실행보다 뒤에 추가되어도 과거의 선행 미해결 조건을 숨길 수 없어야 한다.

전송 중 다른 작업이 중단 기록을 추가했더라도 원래 dispatch와 prefix가 정확하면 늦게 도착한 원문·usage는 보관한다. 중단은 철회하지 않고 domain validation·review를 자동 재개하지 않는다. 현재 모델 설정·엔진·근거 유효기간이 바뀌었다는 이유로 이미 받은 응답의 비용 기록을 버리지 않는다. 다음 전송을 막는 검사와 수신 증거를 보존하는 검사를 분리한다.

기록 실패 후 실패 event 저장까지 실패하면 마지막 확정 상태만 반환한다. 오류 원문·비밀을 로그에 노출하지 않는다. 메모리의 응답이나 원고를 영속 완료로 표시하지 않는다.

시작 때 예약한 32MiB와 event/budget/receipt 슬롯 안에서 수행해야 한다. 7개 원문을 각각 무조건 8MiB까지 허용하면 합계가 32MiB를 넘을 수 있다. 전송 계약에서 request/response/validated/final의 합산 상한과 terminal event 여유를 먼저 확정한다. 이미 보관한 시작 행의 예약 크기를 올리지 않는다. 허용 총량을 넘는 응답은 다음 호출 없이 미확인 상태로 남긴다. 공급자가 반드시 로컬 capture 크기 안에서 응답한다는 보장은 만들지 않는다.

## 10. 정확한 한 건 승인안과 구현 순서

운영 승인안은 등록한 합성 후보 한 개에만 한정한다. 후보명·등록 버전·input SHA, 선택 모델, 공식 목적지, 생성 본문 펼침, 검토 파생 범위, 두 번 호출과 재시도 없음, 예약액·통화·단위·누적 한도, 보관 안내와 미확인 비용 유지 조건을 한 화면에서 검토할 수 있게 한다. 고객 회사 자료와 후보 12건 전체는 포함하지 않는다.

다음 구현도 먼저 합성 공급자만 연결한다. 명시 production mutation은 계약·백업·원문·경합 회귀가 통과하고, 모델·가격·계정·보관·운영 예산을 검토한 정확한 한 건의 사용자 승인 뒤에만 별도로 연다. 이 문서에는 채택 모델이나 운영 금액을 정하지 않는다.

최소 구현 묶음은 다음 순서다.

1. 새 전송 승인/event/usage schema와 frozen archive validator, 다음 writer gate 및 백업 분기.
2. v2 요청/응답 관측 어댑터와 도메인 파이프라인 재사용. 기존 v1 요청·digest·모의 경로 회귀.
3. 기존 provider store에 승인·prepared·dispatch·response·validated·finish 메서드와 최초 commit 결과 연결. 제품 운영 쓰기는 계속 닫기.
4. 합성 runner·고정 JSON/원문 조회·한 건 검토 UI 연결. 응답 유실 조회 복구와 비종결 상태 표시.
5. 공식 근거·운영 조건·사용자 승인이 갖춰진 한 건만 검토. 실제 호출의 성공이나 내부 품질 평가가 벤처확인 승인 보증을 뜻하지 않음을 유지.

## 11. 필수 회귀

- 예약 전용 승인만으로 dispatch 0회. 잘못된 한 건 승인 digest·만료·원문·모델·요율·scope 변경 시 0회.
- 취소한 예약 승인 거부. 합성 출처의 운영 승격 거부. 같은 nonce의 두 프로세스에서 단계별 transport 최대 1회.
- 승인 또는 dispatch 직후 프로세스 종료·응답 유실·재시작은 재전송 0회. replay가 raw transport 권한을 반환하지 않음.
- generation BLOB 바이트 대조, 같은 run 최초 검증 원고만 review 파생, 다른 회사/최종 수정본/다른 run 원고 거부.
- 응답 보관 선행, 잘못된 원고에도 usage 기록, service tier/cache/모델·합계 누락은 held 유지 및 review 0회.
- 예약 초과 비용 전액 기록, deficit·상한 위반 신규 dispatch 차단. 미확인 비용을 0으로 정산하지 않음.
- 늦은 응답·실행 중 엔진 변경에서 raw/usage 보존, 다음 호출 0회. response/validation/final 기록 실패 뒤 마지막 확정 상태 유지.
- 기존 v1 및 v2 r0/취소 r1 archive bytes 불변, 과거 snapshot은 자신의 budget·receipt prefix만 포함.
- v1/v2/새 execution prefix 혼합 백업·재오픈, 변조·고아·중복 nonce·잘못된 scope 차단. 실제 고객 DB·키·네트워크 접근 0인 합성 검증.
