## 4B2b 조합과 실행 명령

- `studio-operational-validation-preparation.ts`는 core 스키마로 명령/검토 전체를 파싱하고 DB 쓰기 전 journal에 보존한다. 원래 nonce 조회와 영수증 대조, 등록 버전·고정 후보·정책 head·전체 run·production 예산 감사를 수행한다. 기존 core의 등록→정책 채택→예약→별도 전송 승인 writer를 그대로 사용한다. SQLite 직접 쓰기나 시험용 저장소 옵션은 없다.
- 고정 후보는 서버 번들의 `validation-candidate-mfg-new-seal-inspection`이며 등록 버전 1 및 최초 단일 run에 묶는다. 정책/예약/전송 명령의 nonce와 검토 내용은 재시작 후에도 교체하지 않는다. DB 저장 직후 응답이 유실되면 조회로 확인하고 같은 기록을 확정한다. 확인 영수증이 있는데 DB에 기록이 없으면 새 요청으로 채우지 않는다.
- `studio-operational-validation-session.ts`는 같은 모듈 그래프에서 production server를 설치한다. 실행 직전 외부/내부 일회용 실행 명령을 보존하고, 완료/복구 후 run revision·snapshot·budget head·인식 비용·미정산을 기록한다. 과거 승인 시점 DB를 같은 파일에 복원해도 기록된 완료 상태와 불일치하면 거절한다. 실행 명령이 이미 있으면 단순 `run`으로 재전송하지 않는다.
- 생성 응답 보존 실패는 같은 owner에서 `recover`로 복구한다. 생성 검증 완료 r5·검토 미시작·실행 확인 기록이 있는 경우에만 별도의 일회용 `continue-review`로 원래 run의 누락된 첫 검토를 진행한다. 생성이나 불확실한 검토를 재시도하는 명령이 아니다. 검토 capture 복구도 새 전송 없이 처리한다.
- `scripts/operational-typescript-loader.mjs`는 Node의 실제 `react-server` 조건으로 서버 모듈을 불러온다. 시계/fetch/server-only 대체와 과거 fixture/test helper를 사용하지 않는다. 기본 상태 확인은 이 로더나 production owner를 설치하지 않는다.
- `scripts/operational-validation-run.mjs`는 기존 `.env.local`의 키만 전용 프로세스에 로드하고 자료 경로를 위 고정 검증 경로로 지정한다. 입력 명령은 직렬 처리한다. 진행 중/미보존 응답이 있으면 EOF·종료 요청에도 owner와 이벤트 루프를 유지한다. 응답을 보존한 정상 종료만 lease를 해제한다. stdout에는 안전한 상태·집계·고정 오류 코드만 내보낸다.

앱 폴더에서 전용 pnpm을 사용한다. 아래 실제 실행은 승인 범위의 유료 전송을 시작하므로 사전 원장/이력 조사와 공식 근거 기한 확인 후 실행한다. 고정 외부 경로 권한 실패를 새 경로로 우회하지 않는다.

```powershell
& '..\..\.venturepass-tools\pnpm.cmd' validation:status
& '..\..\.venturepass-tools\pnpm.cmd' validation:run
```

실제 `validation:run`은 stdin을 유지하는 터미널 세션에서 시작한다. `owner-retained`라면 그 프로세스를 종료하지 않고 `status`, `recover`, 조건 충족 시 `continue-review`, 보존 완료 후 `close`를 입력한다. 생성 응답을 안전하게 복구·확정한 뒤 프로세스가 종료된 r5 상태는 `validation:continue-review`로 같은 승인 run의 첫 검토만 재개할 수 있다. 그 밖의 실패는 기록을 조사하며 명령/DB/잠금을 삭제해 다시 실행하지 않는다.

검증: 조합 8개는 원래 승인 재개, 실제 core COMMIT 후 응답 유실, 생성·검토 각 1회/정산, 과거 DB 복원 차단, 생성·검토 capture 복구, 불확실 전송의 미정산 유지, 예상 밖 정책 head, SDK 요청 중 종료/동시 lease 거절을 검사했다. 모의 응답 두 건의 380 micro-USD는 구성요소별 올림으로 계산한 시험 값이며 실제 비용이 아니다. 파일 18개와 별도 Node 로더 3개도 통과했다. Windows의 반복 DB 감사 시험에 120초 제한을 적용했으며 앱의 시계·만료 검사·검증 항목은 완화하지 않았다.

다음은 고정 위치의 기존 이력/원장/미정산/보관 응답과 공식 근거 기한을 다시 확인하고 승인된 실제 생성·별도 검토·정산·의미 품질을 확인하는 것이다. 현재 기록은 합성 파일 및 core 조합 검증이며 실제 공급자 수락/품질 검증 완료가 아니다.

## 확인된 출발점

- 기존 자료 경로, 현재 앱, 상위 도구 폴더에서 품질평가 DB를 찾지 못했다. 기존 자료 경로에는 회사 DB 및 WAL/SHM만 있다. 컴퓨터의 모든 임의 경로를 조사했다는 뜻은 아니다.
- 전용 검증 경로는 아직 없으며 상위 VenturePass 디렉터리는 있다. 이 경로를 한 번 고정하고 이후 실행마다 다른 디렉터리를 만들지 않는다.
- `.env.local`에는 키 설정이 있고 현재 쉘의 키·자료 경로 환경변수는 비어 있다. 키 값은 출력하지 않았다. 기존 환경파일을 수정하지 않고 전용 프로세스에서만 로드한다.
- 기존 `PlanQualityStore`의 일반 생성자는 고객 DB를 열지 않지만 품질 DB/스키마를 만들 수 있다. 따라서 파일 존재 여부 조사에 저장소 생성자를 사용하면 안 된다.
- `installProviderProductionServer()`는 명시적 서버 구성 함수이며 같은 모듈 그래프에 있는 실행 서비스의 소유자를 설치한다. 기본 Next 서버나 라우트는 이를 자동 호출하지 않는다.
- 기존 approved runner는 생성이 검증되면 원래 승인 범위의 파생 검토까지 연결한다. 이를 생성용/검토용 새 실행 두 개로 나누지 않는다. capture-only 복구는 새 검토를 시작하지 않으며 r5 이후 진행은 같은 원래 승인으로 명시적으로 재개한다.

## 최소 실행 구성

1. 기존 서버와 별개인 로컬 Node 명령 실행기를 둔다. 기본 동작은 상태 확인이며 유료 실행은 별도 명시적 명령이다. 새 공개 HTTP 경로나 제품 화면을 추가하지 않는다.
2. 모델·공급자 URL·예산·후보·경로는 브라우저나 임의 CLI 입력으로 받지 않는다. 이 검증의 로컬 승인 설정에 고정하고 공식 configuration getter 및 서버 등록 합성 자료와 대조한다. 확인된 등록 버전·후보·원문 digest와 원래 run을 보존한다.
3. 기존 key 파일의 설정은 전용 프로세스에만 로드한다. 데이터 환경변수는 이 검증의 고정 위치로 명시한다. 비밀을 명령줄 인자·stdout·로그·승인 설정·요청 기록에 넣지 않는다.
4. TypeScript 모듈 실행 지원이 필요하면 운영용 로더를 별도로 둔다. 과거 test worker/fixture, fake clock, `synthetic-test` store 옵션, 모의 fetch를 운영 실행 경로에서 재사용하지 않는다. Node의 `react-server` 조건 등 실제 서버 모듈 로딩을 우선하며 시험 전용 우회와 구분한다.
5. 기존 정책 채택 → 예약 → 별도 전송 승인 저장소 메서드와 기존 production server/execute/recover를 그대로 연결한다. 직접 SQL INSERT, 예산 configure 우회, 테스트 helper로 만든 운영 승인은 사용하지 않는다.

## 한도·요청 보존

- 최초 초기화는 이 승인에 묶인 로컬 기록을 먼저 확인한다. 승인 설정과 초기화 이력은 검증 DB의 삭제/분실을 감지할 수 있도록 보존한다. 초기화 이력은 있는데 DB가 없거나 다른 경로라면 자동으로 빈 원장을 생성하지 않는다.
- 기록 없는 새 검증의 최초 초기화와 기록 유실은 구분한다. 중단된 초기화, 다른 프로세스의 동시 초기화, 일부 파일만 존재하는 상태에서 새 한도를 만들지 않는다. 단계가 불확실하면 쓰기·전송을 차단하고 기존 파일을 보존한다.
- 실제 비용 원장은 기존 production USD/6자리/15000000 한도를 사용한다. 재개 시 금액·원장 head·전체 run·미정산 hold를 감사한다. 이미 기록된 정책과 예산은 원래 nonce로 조회·대조하며 새 초기 예산 nonce를 발급하지 않는다. 이 검증의 보존 명령과 일치하지 않는 선행 정책/예산을 발견하면 새 예산을 채택하지 않고 중단한다.
- 등록·정책·예약·승인 명령은 원래 nonce와 전체 요청/검토를 쓰기 전에 보존한다. 응답 유실 시 기존 lookup/replay로 복구한다. 새 UUID나 새 후보·run으로 원래 요청을 대체하지 않는다. 파일 기록과 DB 저장 사이의 장애를 검증한다.
- 한 번 고정한 후보/승인 run을 다음 프로세스에서도 사용한다. 수신이 불확실한 r3/r7은 새 전송으로 해결하지 않는다. 금액이 알려지지 않은 요청은 비용 0이나 자유 예산으로 표시하지 않는다.

## 서버 수명과 결과
